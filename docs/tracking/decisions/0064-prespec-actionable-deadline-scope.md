# 사전규격 검토할 항목의 기본 시야를 마감 구간으로 나눈다

- 상태: 채택 (2026-09-21 사용자 결정)
- 일자: 2026-09-21
- 관련 결정: `docs/business-rules.md` "누적 목록의 업무 보기 (2026-09-16)"·`docs/contracts.md` `PreSpecList`·`docs/0915_ui-redesign/spec.md` "사전규격 누적 탐색 변경 (2026-09-16)"의 마감 관련 문장 개정(제외 금지는 유지, 기본 시야만 한정), 사전규격 검토 제외·복원 PoC(2026-09-21 배포)
- 근거 요청: 사용자 질문 2026-09-21 — "모든 회차를 누적해서 보고 있을 때, 마감이 지난 사전규격 공고를 실무자에게 보여줄 필요가 있을까?"

## 맥락

사전규격 목록의 기본 보기 `검토할 항목`(`workspace=actionable`)은 누적 전체를 대상으로 하고, 사람이 손대지
않으면 줄지 않는다. 2026-09-21 운영 DB 실측은 검토할 항목 99건 중 44건(44%)이 이미 의견등록 마감을 지났고,
그 44건은 전부 마감 후 0~6일이며 42건이 추적 `미선택`이었다. 수집 이력이 2주도 안 된 시점의 비율이라
분기 단위로는 수백 건이 된다. 줄이는 수단은 같은 날 배포한 수동 검토 제외 하나뿐이다.

그렇다고 마감 경과를 숨김 근거로 삼을 수는 없다. 사전규격의 `deadline_at`은 의견등록 마감(`opninRgstClseDt`)
이고, 지나면 끝나는 것은 규격에 의견을 낼 기회뿐이다. 참여 판단·제안 준비·입찰공고 추적은 마감 직후가
핵심 구간이다. 실측의 44건은 "끝난 일"이 아니라 "아직 아무도 결정하지 않은 일"이었다.

검토한 대안:

- **마감 경과를 검토할 항목에서 자동 제외한다.** 미처리 건이 사람 결정 없이 사라진다. 2026-09-16 결정이
  막으려던 바로 그것이다. 채택하지 않았다.
- **마감 후 N일 유예 뒤 자동 만료시킨다.** 목록이 스스로 줄지만 여전히 결정 없는 건이 조용히 내려간다.
  기준 N을 정할 근거도 없다. 채택하지 않았다.
- **입찰공고 전환을 종료 신호로 쓴다.** 마감 경과 사전규격 626건 중 공고까지 연결된 건이 18건(3%)뿐이라
  신호가 되지 못한다. 채택하지 않았다.
- **현행 유지하고 행 표식만 개선한다.** 쌓이는 문제를 전혀 건드리지 못한다. 채택하지 않았다.
- **기존 `deadline_status`를 다중값으로 확장한다.** 아래 결정 3의 이유로 채택하지 않았다.
- **검토할 항목에서 구간 전환과 고급 `마감 상태` 필터를 함께 노출한다.** 같은 축을 다루는 컨트롤 둘이
  모순 조합(`구간=마감 전` + `상태=마감 경과` → 0건)을 만든다. 채택하지 않았다.

## 결정

1. **마감 경과를 업무 대상에서 제외하지 않고 소멸시키지도 않는다.** 2026-09-16 결정의 이 부분은 그대로다.
   바뀌는 것은 기본 시야뿐이다.
2. **검토할 항목의 기본 구간은 `마감 전 + 마감 미확인`이고, `마감 경과` 구간은 건수와 함께 항상 보이며
   1클릭으로 전환한다.** 검토할 항목 탭의 건수는 현재 구간 기준이다. 최근 수집·추적 중·전체 이력의 건수와
   내용은 구간에 영향받지 않는다. **마감 미확인(`deadline_at`이 null)은 항상 기본 구간에 남으며 마감 경과로
   접지 않는다** — `unknown`·`null`은 검증 대기 상태로 보존한다.
3. **질의 인자는 새 `deadline_scope=current|passed|all`(기본 `all`)이고 기존 `deadline_status`는 그대로 둔다.**
   `deadline_status`는 모든 집계에 걸리는 전역 SQL 필터인데 새 구간은 actionable 술어의 일부여야 한다.
   하나로 합치면 같은 인자가 workspace에 따라 적용 범위를 바꾸는 숨은 규칙이 생기고, 단일 `Literal`을
   다중값으로 바꾸는 것은 이미 등록된 계약의 타입 변경이다. `current`와 `passed`는 서로소이고 합집합이
   전체라서 아래 집계의 분할 항등식을 보장한다.
4. **구간은 `workspace_matches()`의 actionable 분기 한 곳에만 둔다.** `items`·`total`·`overview_status_counts`·
   `workspace_counts`가 모두 그 함수에서 파생되므로 "actionable에만 적용"이라는 규칙이 한 군데에 산다.
   검토 제외 숨김 가드가 구간 술어보다 **먼저** 온다 — 제외 건이 구간 분할의 분모에 들어가면 탭 건수와
   집계가 어긋난다.
5. **응답에 `deadline_scope_counts{current,passed}`를 더한다.** 구간 적용 **전** actionable 집합을 두 구간으로
   나눈 건수이며, 활성 workspace·활성 구간과 무관하게 항상 같은 값이고 항상 존재한다. 다른 모든 필터는
   반영한다. 화면이 건수를 다시 세지 않게 하려는 것이다.
6. **화면은 `current`·`passed` 두 값만 쓰고 기본값은 URL에 싣지 않는다.** 깨끗한 `/pre-specs`가 곧
   `검토할 항목 + 마감 전·미확인`이다. 다른 보기로 이동하면 구간을 지운다. 구간은 의미 필터이므로 선택
   지문에 넣어 전환 시 선택을 비운다. 검토할 항목에서는 고급 `마감 상태` 필터를 숨긴다.
7. **구간 전환은 새 줄을 만들지 않고 조회 도구 줄의 네 번째 칸에 둔다.** 필터 영역은 보기 탭 줄과 조회
   도구 줄 두 줄을 유지한다. 자리는 `상세 필터 토글 → 검색 → 수집 회차 → 추가 조회 조건` 중 마지막
   칸이며(목록 조회 도구·검색 UX 통일이 정한 순서), 전체 이력 전용인 `검토 포함 여부`와 검토할 항목 전용인
   마감 구간은 서로 배타적이므로 **같은 칸을 나눠 쓴다** — 두 컨트롤이 동시에 보이는 보기는 없다.

   **2026-09-21 개정([ADR-0066](0066-practitioner-ops-information-boundary.md), ADR-0066 구현 시 적용)**:
   위 순서에서 `수집 회차` 칸이 빠져 `상세 필터 토글 → 검색 → 추가 조회 조건` 세 칸이 된다. 수집 회차
   선택은 공용 컴포넌트 `SourceRunFilter`로 통일해 `상세 필터`(`WorkspaceFilterAdvanced`) 안으로 옮긴다
   ([ADR-0062](0062-explore-workspace-structure-unification.md)의 `수집 회차 선택` 행 개정). 이 결정의 나머지는
   그대로다 — 필터 영역은 두 줄을 유지하고, 마감 구간은 조회 도구 줄의 마지막 칸에서 `검토 포함 여부`와
   같은 칸을 계속 나눠 쓴다. 회차가 걸렸다는 사실은 상세 필터 토글의 `activeCount`와 필터 둘째 줄의 회차
   줄이 알린다.

## 결과

- migration 없음. 요청 시각 기준으로 `Notice.deadline_at`에서 파생하는 조건일 뿐 새 컬럼·상태·감사 기록이
  없다. Alembic head는 `0030_prespec_review_exclusion` 그대로다.
- 마감 정렬 규칙(`마감 전 가까운 순 → 마감 경과 최근순 → 미확인`)은 바뀌지 않는다. 기본 구간에서는 경과
  버킷이 비고, 경과 구간에서는 경과 버킷만 남는다.
- 시간 비교는 SQL이 수행하고 시계는 요청당 1회 고정한 `_now_utc()` 하나를 쓴다. 파이썬에서 naive/aware
  datetime을 비교하지 않는다.
- 검토 제외와 구간은 독립적으로 AND 된다. "검토 제외 + 마감 경과"인 건은 어느 구간에서도 보이지 않고
  `deadline_scope_counts` 어느 칸에도 세지 않는다.
- 남은 것: 이 구간은 `마감 전·미확인 / 마감 경과` 2분할이지 D-n 임박 창이 아니다. 대시보드 "사전규격
  의견등록 마감 임박" 건수는 계속 `null`(확인 불가)로 남는다 — `docs/tracking/findings.md`.
