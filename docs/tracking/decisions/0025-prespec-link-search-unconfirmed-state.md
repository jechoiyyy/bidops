# 사전규격 후보 연결은 전략을 표시하고 못 찾은 건은 미확인으로 남긴다

- 상태: 채택
- 일자: 2026-08-28

## 맥락

발주계획에서 사전규격으로 가는 공식 키는 없다. 사업명 부분일치 검색이 유일한 대체 경로다
(`docs/validation-runs/20260828-lifecycle-linkage-survey.md`).

측정으로 확인한 것:

- 정답쌍 87건에 전략 사다리(`full` → `breaking_split` → `normalized` → `longest_fragment` →
  `prefix12`)를 적용하면 재현율은 **87.4%**(76/87)다.
- `breaking_split`과 `normalized`는 **오탐이 0**이다. `longest_fragment`와 `prefix12`는
  각각 1건씩 "결과는 나왔는데 정답이 아닌" 경우를 만든다.
- 적중 18건 중 결과가 1건뿐인 것은 9건이고 나머지는 후보가 여럿이다.
- 못 찾은 11건(12.6%)은 사전규격 쪽 이름이 실제로 다르다. 이름 검색으로 더 회수할 방법이 보이지 않는다.
- 검색을 깨뜨리는 문자는 다섯이다: `·`U+00B7, `&`U+0026, `‘`U+2018, `’`U+2019, `•`U+2022.

**운영 시점에는 "사전규격 미공개"와 "공개됐지만 이름으로 못 찾음"을 구분할 수 없다.**
실험에서 구분할 수 있었던 것은 나중에 입찰공고가 `bfSpecRgstNo`를 실어 정답을 알려줬기 때문이다.
검색하는 그 순간에는 두 경우가 같은 모습이다.

## 결정

**1. 네 전략을 모두 쓰고, 후보마다 어느 전략으로 걸렸는지 데이터에 남긴다.**

후보 목록은 전략의 정밀도 순서(`breaking_split`·`normalized` 먼저)로 정렬한다.
오탐이 있는 전략을 배제하지 않는다. 후보 연결은 어차피 사람이 확인하므로
후보 하나를 더 보는 비용보다 사업을 놓치는 비용이 크다.

**2. 사전규격 연결 상태를 네 가지로 둔다.**

| 상태 | 의미 | 함께 남기는 값 |
|---|---|---|
| `확정` | 입찰공고의 `bfSpecRgstNo`로 공식 확정 | 근거가 된 입찰공고번호 |
| `후보 확인 대기` | 이름 검색 후보가 있고 사람이 아직 확인하지 않음 | 후보 수, 각 후보의 전략, 발주기관 일치 여부 |
| `사람 확인 완료` | 사람이 후보를 연결하거나 기각함 | 판정자, 시각, 이유 |
| `검색 미확인` | 이름 검색으로 찾지 못함 | 마지막 검색 시각, 시도한 전략 |

**3. `검색 미확인`을 "사전규격 없음"으로 표시하지 않는다.**

이 상태는 사전규격이 없다는 뜻이 아니라 확인되지 않았다는 뜻이다.
화면 문구, API 응답 필드, 집계 어디에서도 부재로 바꾸지 않는다.
`검색 미확인`은 사람이 직접 찾아볼 대상이므로 재검색과 수동 검색 경로를 함께 제공한다.

**4. 검색 미확인을 두 상태로 쪼개지 않는다.**

"미공개"와 "이름 불일치"를 구분해 표시하지 않는다. 검색 시점에 구분할 근거가 없으므로
쪼개면 화면에 근거 없는 구분을 만드는 것이다.

## 대안

**오탐 0인 두 전략만 사용**은 후보의 신뢰도가 높지만 기각했다. 재현율이 낮아져 `검색 미확인`이
늘어나고, 그중 상당수가 실제로는 찾을 수 있었던 건이 된다. 조기 탐색이 제품의 목적이므로
회수하지 못한 사업의 비용이 후보 하나를 더 검토하는 비용보다 크다.

**오탐 가능성이 있는 후보를 기본 접어두기**도 검토했으나 채택하지 않았다. 정렬과 전략 표시로
같은 목적을 달성하면서 화면 상태를 늘리지 않는다.

**"사전규격 없음"으로 표시**는 기각했다. 측정상 최소 12.6%가 실제로는 존재하는데 못 찾은 것이다.
없다고 단정하면 `AGENTS.md`의 "확인되지 않은 사실을 추정하지 않는다"에 어긋난다.

**미공개와 이름 불일치를 나눠 표시**는 기각했다. 검색 시점에 두 경우를 가를 관측이 없다.

## 결과

- 사업기회 저장 구조에 사전규격 연결 상태, 후보 목록, 후보별 전략, 마지막 검색 시각,
  사람 판정을 담아야 한다. D-2(누적 구조)의 입력이다.
- 후보 생성기는 파손 문자 다섯에서 쪼개는 전략을 반드시 포함해야 한다. 무해가 실증된 문자
  (괄호·쉼표·하이픈·마침표·낫표·겹낫표·물결·빗금·밑줄·`・`·`‧`·`․`)에서는 쪼개지 않는다.
  질의가 짧아질수록 후보가 늘어 사람 확인 부담만 커진다.
- **정확도가 저절로 측정된다.** 나중에 입찰공고가 `bfSpecRgstNo`를 실어 오면 그 사전규격을
  이름 검색이 찾았었는지 대조할 수 있다. 실험에서 정답쌍을 만든 방법과 같다.
  운영에서 재현율이 유지되는지, 어떤 이름에서 놓치는지가 별도 장치 없이 쌓인다.
  이는 `docs/business-rules.md:62`가 요구하는 누락률 측정과 같은 성격이다.
- 재검색 주기는 이 결정에 포함되지 않는다. D-3에서 정한다.
- 87.4%와 12.6%는 3일 표본에서 만든 정답쌍 87건 기준이다. 운영 관측으로 갱신한다.

## 개정 (2026-09-17)

[사업 추적 연결·조치 고도화](../../0917_opportunity-tracking/intent.md)에서 이 ADR의 네 전략
사다리와 후보 정렬 규칙을 그대로 재사용하며 세 가지를 더한다.

- 판정 대상이 **기관 조건**을 얻는다. SW사업대상=Y 사전규격이 적재되는 시점에는 이름 사다리
  일치에 더해 발주계획 기관명과 사전규격 발주·수요기관이 공백 정규화 기준으로 같아야 자동
  후보를 만든다. 기관 불일치는 자동 후보에서 빠지고 사람이 찾아보기로만 확인한다 — 이름만으로는
  기관이 다른 사업을 잘못 묶을 위험이 이름 검색 자체의 오탐보다 크다고 판단했다.
- 검색 대상이 **보관 회차의 수집 색인**으로 넓어진다. 담당자가 `사전규격 찾아보기`·
  `입찰공고 찾아보기`를 누르면 그 순간 수집된 전체 레코드(선별 적재 여부와 무관)를 이름 사다리로
  검색하므로, 선별 적재에서 제외된 레코드도 나중에 찾을 수 있다.
- `검색 미확인` 대기 행이 어느 종류를 찾다 실패했는지 구분하는 `search_target_kind`
  (`pre_spec`\|`bid_notice`)를 더한다. 이 ADR이 정한 "미확인은 부재가 아니다" 원칙은 그대로다.

전략 사다리 함수 자체(`experiments/lifecycle-linkage-survey/scripts/name_normalize.py`)는
`app/lifecycle/services/name_matching.py`로 그대로 옮겼으며 판정 로직은 바꾸지 않았다. 상세는
[spec.md §4](../../0917_opportunity-tracking/spec.md#4-후보-대조와-찾아보기)가 정본이다.
