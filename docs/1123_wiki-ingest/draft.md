# 회사 위키 넣기(ingest) 기능 — 계획 초안

2026-11-23 작성. 초안이며 승인된 계획이 아니다. 기능 등록(`docs/work/groups/RL/features/`, `scripts/feature_status.py`)은 하지 않았다.
근거 시험: [업무별 근거 지도와 위키 탐색](../validation-runs/20261123-llm-wiki-evidence-map/README.md), [에이전트 위임 시험](../validation-runs/20261123-engine-agent-delegation/README.md).

## 무엇을 만드나

회사가 수행한 사업의 제안요청서 파일을 관리 화면에 올리면, 백엔드가 그 문서의 요구사항을 회사 위키의 "업무별 근거 지도"에 반영한다. 반영된 뒤에는 새 공고 분석이 그 사업을 근거로 쓸 수 있다.

지금은 이 일을 사람이 평가 도구와 원본 저장소 명령으로 한다. 사업 23건을 넣는 데 건당 모델 실행 1회, 1분 16초~2분 43초가 걸렸다.

## 흐름

```
[화면] 수행 사업 선택 + 제안요청서 업로드
   ↓
[백엔드] 파일 검사·저장 → 문서 변환(블록) → 요구사항 표 추출        … 기존 첨부·변환 경로 재사용
   ↓
[분류] 모델이 요구사항을 업무 단위로 분류 → 분류 파일(mapping)        … 새로 만드는 부분
   ↓
[검토] 사람이 분류 요약과 새 단위 제안을 확인하고 승인
   ↓
[반영] wiki_tools ingest-apply → 곁 파일 갱신, 페이지 다시 그리기, 변경 일지, 형식 검사
   ↓
[위키] 실적 페이지(요구사항 전체 목록) + 업무별 근거 지도 갱신
```

## 이미 있는 것

| 부분 | 상태 |
|---|---|
| 파일 검사(ClamAV)·저장(MinIO)·HWP 변환 | 사전규격 첨부 경로에 구현돼 있음 |
| 요구사항 표 추출 | 엔진 패키지의 결정적 파서. 표 형식에 따라 0건이 나올 수 있음 |
| 분류 프롬프트 생성·답 검사·재질문 프롬프트 | `bid_deep_engine.wiki_tools ingest-prompt`, `ingest-validate` (테스트 있음, 모델 호출 없음) |
| 분류 파일 반영·다시 그리기·변경 일지·형식 검사 | `bid_deep_engine.wiki_tools ingest-apply` (테스트 있음, 모델 호출 없음) |
| 실적 페이지의 요구사항 전체 목록 생성 | 원본 저장소 `scripts/expand_portfolio_requirements.py` (BidOps로 옮겨야 함) |
| 내용 점검, 되돌려 쓰기 | `wiki_tools check`, `feedback-apply` |

## 새로 만들 것

1. **수행 사업 등록과 업로드 화면·API.** 실적 번호(예: `P2026-03`), 사업명, 기간, 역할과 파일. 실적 목록 YAML에 없는 사업이면 항목을 먼저 만든다.
2. **넣기 실행(run) 모델.** 상태: 접수 → 변환 → 추출 → 분류 → 검토 대기 → 반영 → 완료 / 실패. 입력 파일 해시, 분류 파일 해시, 위키 묶음 digest(반영 전·후)를 남긴다. 기존 판정 큐(FIFO, 동시 실행 1)를 쓴다.
3. **분류 호출.** 프롬프트 한 번으로 한다(2026-11-23 결정, 아래 "분류 방식 결정"). `wiki_tools ingest-prompt`가 프롬프트를 만들고, 백엔드가 모델에 보내고, `ingest-validate`가 답을 검사한다. 틀리면 문제 목록을 붙인 두 번째 프롬프트로 한 번만 다시 묻고, 그래도 틀리면 실패로 닫아 사람에게 넘긴다.
4. **검토 화면.** 분류 요약(요구사항 수, 단위별 건수, 미분류), 새 단위 제안, 기존 단위와 이름이 비슷한 제안을 보여 주고 승인·수정·반려를 받는다.
5. **위키 쓰기 경로.** 지금 운영 web은 위키를 읽기 전용으로 마운트한다. 쓰는 주체(전용 worker)와 쓰기 전 백업, 실패 시 되돌리기를 정해야 한다.

## 지켜야 할 것

- **모델 전송:** RL 범위의 승인 모델은 codex-exec `gpt-6-luna`/high이고 정책 단위 사전 승인 + 건별 감사다(ADR-0073). 시험은 `gpt-6.2-sol`/medium으로 했다. 제품에 넣으려면 승인 모델로 다시 재거나 정책을 새로 승인받는다. 보내는 내용은 공개 문서(RFP 요구사항)와 분류표이며 회사 프로필은 필요 없다.
- **원본 불변:** 올린 파일, 추출 결과, 분류 파일은 덮어쓰지 않는다. 같은 사업을 다시 넣으면 새 실행으로 남기고 위키의 연결만 바꾼다.
- **사람 승인:** 위키는 판정의 근거가 되므로 자동 반영하지 않는다. 새 단위 추가와 반영은 사람이 승인한다.
- **금액·비공개 값:** 실적 페이지에는 금액을 쓰지 않는다(생성 스크립트가 가린다).
- **감사:** 누가 언제 어떤 파일로 넣었는지, 반영 전·후 위키 digest를 감사 이벤트로 남긴다.

## 정할 것

1. **정본의 버전 이력.** 정본은 BidOps `wiki/`로 정했다(2026-11-23). Git 밖 폴더라 이력이 없고 지금은 백업과 원본 저장소 커밋으로 남긴다. 백엔드가 쓰게 되면 객체 저장소(MinIO)에 버전을 남길지 정해야 한다.
2. **요구사항 표를 못 읽는 문서.** 0건이 나오면 반려할지, 모델에게 문서에서 요구사항을 뽑게 할지.
3. **새 단위의 중복 정리.** 지금은 제목이 같을 때만 잡는다. 비슷한 단위를 모델이 찾아 제안하게 할지.
4. **분류표의 갱신 주기.** 사업이 쌓이면 분류표 자체를 다시 정리해야 한다. 누가 언제 하는지.
5. **수주하지 않은 사업의 RFP.** 수주 실적만 넣는지, 참여했지만 떨어진 사업도 넣되 근거로는 쓰지 않는지.

## 분류 방식 결정 (2026-11-23)

**프롬프트 한 번 + 코드 검사 + 한 번의 재질문**으로 한다. 근거는 [시험 기록](../validation-runs/20261123-llm-wiki-evidence-map/README.md)의 "넣기 분류 방식" 절이다.

- 승인 모델(`gpt-6-luna`/high)로 사업 5건(요구사항 33~83건)을 한 번씩 보냈다. 5건 모두 요구사항을 빠짐없이 순서대로 분류했다. 3건은 그대로 통과했고 2건은 단위 id 하나씩이 틀렸다(이름은 맞고 주제 접두어가 틀림). 문제 목록을 붙여 한 번 다시 묻자 2건 모두 통과했다.
- 에이전트 방식보다 입력이 5~12배 적고(4만 2천~5만 1천 토큰 대 27만~60만) 시간도 짧다(64~114초 대 76~143초).
- 분류 내용은 에이전트 방식과 겹침 정도 평균 0.71로, 서로 다른 모델 사이(0.73)와 같은 수준이다.
- 실행 격리가 필요 없고, 보내는 내용(지시문·분류표·요구사항)이 고정되므로 기존 전송 승인·감사 체계에 그대로 맞는다.

## 순서 제안

1. 위키 쓰기 경로와 버전 이력을 정한다(위 1번).
2. 넣기 실행 모델과 API, 검토 화면을 만든다.
3. 분류 호출을 붙이고 감독 시운전을 한 번 한다.
