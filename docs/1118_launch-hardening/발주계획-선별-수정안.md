# 발주계획 선별(C-2) 수정안

작성 2026-11-18. [설계 고도화안](설계고도화안.md) D 묶음의 후속이다.
이 문서는 계획이며 구현 사실·품질 합격·운영 활성화의 근거가 아니다. 아래 수치는 기존 실행 결과로 다시 계산한 값이고 새 정책으로 모델을 돌려 얻은 값이 아니다.

## 1. 결론

- 모델 판정 범위를 BM25 상위 300건에서 **상위 150건**으로 줄인다(새 정책 `c2-order-plan-screening-v6`).
- 목록을 **필수 검토(`관련`) → 훑어보기(`불확실`, BM25 순위순) → 모델 미판정(BM25 순위순)** 세 단으로 정리한다.
- 선별 정책·결과 계약의 의미(상태 값, 검토 후보 정의, 게이트 채점 규칙)는 바꾸지 않는다. 바뀌는 것은 절단 값과 화면의 순서·이름이다.
- 권장안 4개 중 두 가지를 코드와 데이터를 확인한 뒤 조정했다(§5). 점수 하한은 뺀다. "수집 직후 BM25 목록"은 값싼 부분만 지금 하고 나머지는 2단계로 둔다.

## 2. 근거

### 사람 정답 표본 (gold adjudicated v3, 8월 4일치 625건, 관련 54건·그중 높음 25건)

v5 게이트 2차 pass의 결과 행에서 다시 계산했다.

| 방식 | recall | precision | 하루 최대 후보 | 높음 누락 |
|---|---:|---:|---:|---:|
| 현재 v5 (상위 300 + 모델) | 100% | 39.7% | 73 | 0 |
| **상위 150 + 모델 (수정안)** | 96.3% | 45.6% | 59 | 0 |
| 상위 100 + 모델 | 92.6% | 49.5% | 50 | 0 |
| BM25만 상위 75 | 92.6% | 28.7% | 75 | 0 |
| 모델 `관련`만 | 85.2% | 97.9% | 23 | 1 |

- 상위 150 밖으로 나가는 gold 관련 건은 2건(230위·259위)이고 둘 다 우선순위 `낮음`이다.
- 수정안은 현재 게이트 임계(recall ≥ 90·precision ≥ 35·중요 누락 ≤ 3·하루 검토량 ≤ 80)를 계산상 모두 넘는다. 임계값은 바꾸지 않는다.
- `불확실` 89건 중 gold 관련은 8건(9%)이다. `관련` 47건은 46건이 gold 관련이다.

### 운영 14일 (평일 규모 14일, 하루 평균 500건, 모델 판정 4,200건)

| BM25 순위 | 모델 `관련` 비율 | `관련` 누적 |
|---|---:|---:|
| 1~50 | 59.4% | 60.8% |
| 51~100 | 29.1% | 90.6% |
| 101~150 | 6.9% | 97.7% |
| 151~200 | 1.9% | 99.6% |
| 201~300 | 0.2% (1,400건 중 3건) | 100% |

- 151~300위 판정(모델 시간의 절반)이 찾는 `관련`은 전체의 2.3%다.
- 하루 평균 `관련` 49건(최대 64), `불확실` 46건이다. 지금 화면의 "사람 검토" 97건 중 절반이 적중률 9%대의 `불확실`이다.
- 201~300위의 `관련` 비율이 0.2%이므로 300위 밖의 누락도 드물 것으로 본다. 사람 채점이 아니라 모델 판정 기준의 간접 근거다.

## 3. 변경 내용

### A. 정책 v6 — 모델 범위 상위 150건

| 항목 | v5 | v6 |
|---|---|---|
| `stage1.top_k` | 300 | 150 |
| 모집단이 top_k 이하인 날 | 전부 판정 | 그대로(전부 판정) |
| BM25 방식·토큰화·가중치, 프롬프트, 모델, generation config, 회사 역량, 배치 25건·재시도 2회 | — | 변경 없음 |
| 감사 표본 | 탈락분에서 실행당 10건, 근접 순위 창 25 | 값은 그대로. 창이 301~325위에서 151~175위로 옮겨 간다 |

- 지금은 300이 순위 스크립트·병합 스크립트·워커·JSON 스키마에 상수로 박혀 있다. 이를 **정책 파일의 `top_k`를 읽는 방식**으로 바꾸고 허용 값을 `{150, 300}`으로 제한한다. v5 파일과 v5 실행 기록은 그대로 유효하다.
- 새 파일: `order-plan-screening-policy.v6.json`, `order-plan-screening-phase0-binding.v6.json`. compose 마운트와 `app/core/config.py` 기본 경로를 함께 올린다. v5 파일은 지우지 않는다.
- 결과 행·실행 행의 스키마와 DB는 바꾸지 않는다. **migration 없음.**
- 예상 효과: 평일 판정 300건 → 150건(12배치 → 6배치), 실행 시간 약 20분 → 약 10분(건수 기준 추정).

### B. 목록과 화면

| 화면 | 지금 | 수정 |
|---|---|---|
| 발주계획 탭 | `관련`·`불확실`·`전체`·`1차 선별 제외`·`선별 실패` | `관련`(필수 검토)·`불확실`(훑어보기)·`모델 미판정`·`전체`. `모델 미판정`은 순위 밖(`filtered_out`)과 판정 실패를 합쳐 BM25 순위순으로 보인다 |
| `불확실` 정렬 | 발주 예정월순 | 지난 건을 뒤로 보낸 뒤 **수집일 최신 → BM25 순위순** |
| `모델 미판정` 정렬 | 서버 순서 | 수집일 최신 → BM25 순위순, 행에 순위와 가까운 회사 역량 표시 |
| 대시보드·정책 화면의 일일 수집 줄 | `사람 검토 107건 (관련 48 · 불확실 59)` | `필수 검토 48건(관련) · 훑어보기 59건(불확실) · 모델 미판정 N건` |
| 용어 | `1차 선별 제외`, `선별 실패` | `모델 미판정(순위 밖)`, `모델 미판정(판정 실패)` |

- `관련` 탭의 정렬(발주 예정월이 가까운 순)과 사이드바 배지(`관련` 건수)는 그대로다.
- 모델이 통째로 응답하지 않은 날은 지금도 결과 행에 BM25 순위가 남는다(`부분 성공`, 판정 실패 건). 수정 뒤에는 그 건들이 `모델 미판정`에 **BM25 순위순으로** 보이므로 그날도 훑어볼 목록이 생긴다.
- 정렬·필터는 지금처럼 화면이 받은 목록에 적용한다(서버 응답은 이미 `stage1_rank`·`stage1_score`·`nearest_capability`를 준다). 서버 API·응답 스키마 변경 없음.
- `human_review_count`(관련 + 불확실 + 실패)의 계약상 정의, 게이트의 검토 후보 규칙은 바꾸지 않는다. 화면 문구만 필수와 훑어보기를 나눈다.

### C. 문서

- ADR 신규(0075): Top300 → Top150, 근거와 한계. ADR-0037을 대체하지 않고 값만 갱신한다.
- `docs/contracts/c2.md`·`docs/business-rules.md`의 "Top 300" 문장, `docs/operations/daily.md`의 실행 시간, `docs/tracking/status.md`.

## 4. 하지 않는 것

- BM25 방식 자체(토큰화, IDF 기준, 회사 역량 문장) 변경. 순위가 바뀌므로 별도 측정이 필요하다.
- 게이트 임계값·감사 표본 값(PoC 결정 D-b·D-c) 변경.
- 프롬프트·모델 변경, LLM wiki 본문 주입.
- gold 확장(v4). 실제 규모(하루 430~630건)에서의 사람 채점은 여전히 없다.

## 5. 권장안에서 조정한 것

| 권장안 | 조정 | 이유 |
|---|---|---|
| ④ 소량일 점수 하한 | **제외** | 소량일 7일을 합쳐 줄어드는 판정이 약 130건(주말 하루 1~2분)이다. 하루 20~40건 표본에서는 IDF가 불안정해 점수 7.0인 실제 `관련` 1건이 하한(8)에 걸렸다. 정책 매개변수를 하나 더 두는 값을 못 한다 |
| ① 수집 직후 BM25 목록(워커 없이) | **1단계에서는 모델 장애 시 목록만, 나머지는 2단계** | 결과 테이블이 append-only라 판정 전 순위를 같은 테이블에 먼저 넣을 수 없다. 워커 없이 목록을 내려면 web이 실행 생성 때 순위를 계산하고, 순위 파일을 읽는 새 API와 "판정 전" 화면 상태가 필요하다. 모델 장애는 B로 해결되고, 워커가 꺼지는 경우는 재시작 정책(`unless-stopped`, 결정 대기)으로 대부분 사라진다 |

2단계(선택): web이 실행 생성 직후 같은 순위 스크립트를 subprocess로 돌려 `screening-ranking.json`을 남기고(워커는 있으면 재사용한다), `GET …/executions/{id}/ranking`으로 판정 전 목록을 보여 준다. migration은 없다. 재시작 정책 결정 뒤에 필요 여부를 다시 본다.

## 6. 진행 순서와 승인 경계

| 단계 | 내용 | 승인 |
|---|---|---|
| 1 | 작업 브랜치에서 A·B·C 구현, 격리 테스트(순위·병합 스크립트, 워커, 서비스, 감사 표본, 화면 spec). 리더가 영향 범위 검사를 다시 돌린다 | 불필요(운영 영향 없음) |
| 2 | main 병합, 이미지 빌드, web·analysis-worker 교체(백업·롤백 태그 포함). v5가 active인 채로 배포한다 — 코드가 v5·v6 둘 다 받아야 한다 | **필요** |
| 3 | v6 정책·binding 적재(`c2_policy load`) → 후보 지정 → 게이트 행 생성(임계 동일, gold v3) | **필요** |
| 4 | 게이트 측정 2 pass × 4회차 = **모델 실행 8건**(pass당 14배치, 약 12분) → 제품 밖 채점 → evaluation 제출 | **필요**(모델 호출, 제출은 사람 이름으로) |
| 5 | 통과 시 v6 활성화(v5는 자동 retire) → 일일 스위치를 v6에 다시 ON | **필요** |
| 6 | 다음 날 일일 실행을 v6 첫 실행으로 확인(실행 시간, 후보 수, 감사 표본) | — |

- 중단 조건: 4단계에서 두 pass 중 하나라도 임계 미달이면 5단계를 하지 않는다. v5가 active로 남고 일일 실행은 그대로다.
- 되돌리기: 활성화 전에는 후보 지정만 풀면 된다. 활성화 뒤에는 retire된 v5를 되살리지 않으므로, 같은 내용의 새 버전을 발행해 다시 게이트를 지나야 한다. 이미지·코드는 태그로 되돌린다.
- 이미 판정된 11-04~11-17 결과(v5)는 그대로 둔다. 다시 판정하지 않는다.

## 8. 남는 한계

- gold는 8월 평일 2일·관련 54건이다. 수정안의 recall 96.3%는 그 표본의 계산값이다.
- 운영 규모(평일 평균 500건)의 근거는 모델 판정을 기준으로 삼았다. 151위 밖에 사람이 `관련`으로 볼 건이 얼마나 있는지는 감사 표본(실행당 10건)으로만 계속 본다.
- 운영에서 `관련` + `불확실`은 상위 150으로 줄여도 하루 평균 82건이다(gold 규모의 59건과 다르다). 필수 검토를 `관련`으로 본다는 전제에서만 80건 아래다.
