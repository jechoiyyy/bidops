# 실사용 전 설계 고도화안

작성일: 2026-11-18. 실사용 전 최종 고도화의 범위·순서·승인 경계를 정한다.
이 문서는 계획이며 구현 사실·품질 합격·운영 활성화의 근거가 아니다. 진행 상태는 맨 아래 "진행 기록"에만 적는다.

## 1. 결론

1. 실사용을 막는 것은 화면 완성도가 아니라 **운영이 2026-10-14 이후 멈춰 있다**는 점과 **회사 적합 판정이 차단 조건을 구조적으로 내지 못한다**는 점이다.
2. 순서는 **발주계획 단계 수정 → cron 등록 → 판정 품질 → 흐름 정리**이고, **UI 밀도·4px 이행**은 운영과 독립이라 병행한다.
3. 발주계획 단계에 LLM wiki 본문을 넣지 않는다. 같은 wiki에서 **결정적으로 뽑은 보조 신호**(유형·발주처 실적·입찰 규칙)만 쓴다(§5).

운영 화면 20개 경로를 읽기 전용으로 캡처·측정했고 cron·컨테이너·대조기 코드를 직접 확인했다. 그 밖의 수치는 저장소 기록 인용이다.

## 3. 목표 흐름

```text
수집(cron) ─ 발주계획 C-2 선별 ─ 사람: 추적 시작
                                   │
              사전규격 수집 ─ 문서 준비 ─ 개요(선별) ─ RL 카드 판정(정본) ─ 사람: 판정 확인
                                   │                                        │
                       입찰공고 연결 ─ 조건 확인·delta ─ 사람: Go/No-Go ─ 제안서 초안
                                   │
                              일일 브리핑(Slack·화면)
```

- 사업기회 레코드 하나가 전 단계의 중심이다. 각 단계 화면은 레코드로 가는 링크와 레코드에서 돌아오는 링크를 갖는다.
- 추적 시작, 판정 확인, Go/No-Go는 사람이 결정한다. 자동화는 분석의 시작까지만 연다.
- 꺼진 기능은 화면에서 "이 환경에서 꺼짐"으로 미리 밝힌다.

## 4. 작업 묶음

### A. 발주계획 단계 수정 → cron 등록

목표: 무인 일일 실행이 조용히 멈추거나 조용히 건너뛰지 않게 한 뒤 cron을 건다.

| ID | 수정 | 근거 | 구현 요지 | 검증 |
|---|---|---|---|---|
| A-1 | `대기` 실행 회수 | findings W-5: 워커가 없으면 `대기`가 영구히 남고 일일 스크립트는 exit 0으로 건너뜀 | `대기` 최대 체류 시간을 넘긴 실행을 `중단됨`+사유로 닫는다. 회수는 워커 claim과 실행 생성 요청에서 돈다(조회는 상태를 바꾸지 않는다). 자동 재시작은 만들지 않는다 | 단위+PostgreSQL 변형. 옛 코드에서 실패 확인 |
| A-2 | 적재 경고 등급별 차단 | findings W-2: `info` 한 줄로 C-2가 영구 409 | `info`는 통과시키고 통과시킨 경고를 실행 metadata에 남긴다. `warning`·`error`는 지금처럼 `source_run_incomplete` | 단위+PostgreSQL 변형, 계약 문서 |
| A-3 | 누락일 감지 | findings W-3·4: 창이 1일이라 빠진 날은 유실, 기록도 없음 | 일일 스크립트가 최근 N일의 회차 연속성을 검사해 누락일을 출력하고 비0으로 끝난다. `--catch-up-days N`(기본 0)을 주면 그 범위만 오래된 날부터 메운다 | 스크립트 테스트(가짜 web은 실제 계약 기준) |
| A-4 | 상태 서비스 재시작 정책 | findings 2026-11-18: postgres 등 `restart: no`, host 재시작 뒤 3주 정지 | prod overlay에서 postgres·minio·clamav·document-worker에 `unless-stopped` | `docker compose config` 렌더 확인(적용은 §7) |
| A-5 | 운영 가시성 | 스위치 ON인데 5주째 실행 없음이 화면에 안 보임 | 대시보드·정책 화면에 "마지막 일일 실행일·경과일·누락일·막힌 실행"을 표시. "다음 일일 스크립트가 실행합니다" 문구는 마지막 실행 사실로 바꾼다 | 화면 검사 2폭 |
| A-6 | 검토량 분리 | 10월 실운영 평일 4일 중 3일이 임계 80건 초과(84·102·93) | 발주계획 목록에서 `관련`과 `불확실`을 분리해 보여 주고 기본 보기를 `관련`으로 둔다. 모델 판정·정책은 바꾸지 않는다 | 화면 검사 |
| A-7 | 메뉴 이름 | 사이드바 "연차 예고"가 발주계획 화면 | "발주계획"으로 바꾸고 화면 제목과 맞춘다 (C 묶음과 함께) | 화면 검사 |

cron 등록 전 관문(순서 고정, §7의 승인 대상):

1. A-1~A-4 병합·이미지 빌드·전체 백업·롤백 태그·재배포
2. analysis-worker 기동, 로컬 Ollama·LiteLLM 응답 확인
3. cron과 같은 깨끗한 환경에서 `--dry-run` 1회와 실제 web 조회
4. 감독 시운전 1회(전일 1일치, 실제 C-2 호출)
5. 구현에 관여하지 않은 컨텍스트의 독립 검증에서 차단 0
6. `flock`(두 트랙 공용 lock)+`timeout`을 붙인 cron 설치

정책을 바꾸는 개선(BM25 Top300 절단 손실 재측정, 감사 표본의 gold v4 편입)은 cron이 돈 뒤 실규모 날짜로 측정하고 새 policy 버전·게이트·승인을 받는다. 이번 묶음에서 다루지 않는다.

### B. UI 밀도·4px 이행

목표: 모든 화면이 같은 간격·글자·컨트롤 척도를 쓰고, 렌더된 여백이 4px 격자에 놓인다.

원인: `shell-relaxed.css`의 `--bo-ui-scale: 0.9`가 간격 토큰을 3.6px 단위로 만든다. 사전규격 상세만 ×1.0으로 되돌려 한 앱에 밀도가 둘이다.

**목표 척도**

| 항목 | 값 |
|---|---|
| 간격 | 4 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48 (예외: 테두리 1, 광학 보정 2) |
| 글자 | 12 캡션 · 14 본문 · 16 화면 제목·목록 제목 · 20 상세 제목 |
| 굵기 | 400 · 500 · 600 |
| 컨트롤 높이 | 28 · 32 · 36 |
| 반경 | 4 컨트롤·칩 · 8 패널·카드 · 9999 알약 |
| 캔버스 여백 | 상 16 · 좌우 24 · 하 24 (전 화면 동일) |
| 표 | 머리 8×12, 조밀한 목록 셀 8×12, 설정형 표 셀 12×12 |
| 패널 | 패딩 16, 머리 최소 44 |

**순서**

| ID | 작업 | 요지 |
|---|---|---|
| B-1 | 죽은 CSS 삭제 | TSX·e2e 어디서도 참조하지 않는 규칙과 import 없는 파일을 지운다. 추정 약 6,400줄. 삭제 전후 빌드·화면 검사로 회귀 없음을 확인한다 |
| B-2 | 축척 제거 | `--bo-ui-scale`과 compact 토큰 덮어쓰기를 지우고 루트 글꼴을 14px로 둔다. 사전규격 상세의 ×1.0 복원 블록도 지운다 |
| B-3 | raw px 치환 | 5→4, 7·9→8, 11·13→12, 17→16, 19·21→20. 6·10·14·18은 용도별(gap은 내림, padding은 올림). 치수를 `calc(spacing × K)`로 만든 곳은 값을 고정한다 |
| B-4 | 공통 틀 통일 | 캔버스 여백, 화면 제목 크기·위치, 버튼 크기, 패널 패딩을 위 척도로 맞춘다. 화면 루트에서 `.astryx-*`를 재정의하는 규칙을 공통 한 곳으로 모은다 |
| B-5 | 부품 통합(후속) | 판정 기준·실행 상태의 중복 부품 7종, 표 4종, 상태 표시 6종을 공용으로 수렴 |

**인수 기준**

- 화면별 렌더 측정에서 4px 격자 밖 여백 비율 5% 이하(예외 1·2px와 Astryx 내부 값 제외).
- 글자 크기 종류가 척도 값뿐이다.
- 1280×800과 1440×900에서 가로 넘침·겹침 없음. 조밀한 목록의 보이는 행 수 감소는 화면당 2행 이내.
- 대비 검사·빌드 통과, 픽셀 기준선과 `design-shell.spec.ts` 기대값 갱신.

## 5. 발주계획 단계와 LLM wiki

**결론: wiki 본문은 넣지 않고, wiki에서 결정적으로 뽑은 보조 신호만 쓴다.**

wiki의 실체: `bid-deep-agent`의 회사 지식 베이스(공고 유형 6, 역량 10, 입찰 규칙 4, 실적 38, 용어집). 엔진은 공고 본문으로 유형을 분류한 뒤 유형·역량 페이지 12,000자와 관련 실적 16,000자를 대조 프롬프트에 넣는다. 요구사항 문장과 회사 근거를 맞대는 용도다.

본문을 넣지 않는 이유:

- 발주계획은 제목·기관·예산·예정월뿐이다. 맞댈 요구사항이 없어 페이지를 넣어도 판정 근거가 늘지 않는다.
- C-2는 25건 배치당 입력 약 1,600 token이고 300건에 약 26분이다. 페이지를 넣으면 배치마다 입력이 수 배로 늘고 32k 창 여유가 준다.
- wiki 유형 페이지는 `confidence: estimate`다. 확인되지 않은 역량을 판정 근거로 올리면 강제 게이트에 어긋난다.
- C-2 입력을 바꾸면 새 policy 버전과 게이트 재측정이 필요하다.

대신 쓸 수 있는 것:

| wiki 요소 | 발주계획 단계 용도 | 방식 | 정책 영향 |
|---|---|---|---|
| 유형 `keywords`, 용어집 | 제목에 공고 유형 라벨(홈페이지 구축·운영 유지관리·AI 등)을 붙여 검토자가 묶어 본다 | 결정적 키워드 점수(엔진의 `classify_notice`와 같은 규칙) | 없음(표시만) |
| 실적의 발주처 | "이 기관 실적 있음", 연차 사업 신호 | 기관명 정규화 대조 | 없음(표시만) |
| 규칙(no-bid·예산 구간·지역) | 제외 분야·예산 구간 밖·지역 조건 주의 표시 | 결정적 규칙 | 없음(표시만). 자동 제외는 하지 않는다 |
| 유형 `keywords` | BM25 1단계 질의 어휘 보강 | 질의 사전 교체 | **있음** — 새 policy+게이트 |

- 앞의 세 가지는 모델 판정을 바꾸지 않는 **보조 신호**라 정책 변경 없이 붙일 수 있다. RL-05가 놓친 차단 유형 두 가지(지역·제외 분야)를 가장 이른 단계에서 표시하게 된다.
- 유형 라벨은 사전규격 단계에서 같은 유형의 wiki 페이지를 고르는 열쇠가 되어 단계 사이가 이어진다.
- 회사 지식의 정본은 하나여야 한다. BidOps의 RL-00 회사 근거(`confirmed`/`proposed`/`unknown`)를 정본으로 두고, wiki는 거기서 파생한 검토용 문서로 취급한다. 보조 신호는 `confirmed` 사실과 wiki의 어휘만 쓴다.
- 착수는 A 묶음과 cron 안정화 뒤다. 새 기능 문서로 등록한다.
