# 사전규격 단계 수정안

2026-11-19 작성. [설계고도화안](설계고도화안.md) §4 E(분석 경로 정리)와 사전규격 단계 가동의 수정안이다.
근거는 같은 날의 읽기 전용 조사(운영 GET, 코드, compose 파일)이며 핵심 조건식과 운영 수치는 리더가 직접 다시 확인했다.
계획 문서이며 품질·운영 활성화 근거가 아니다.

## 1. 결론

- 사전규격 화면에 검토할 건이 0건인 이유는 화면이 아니라 **문서 준비가 열리지 않아서**다. 문서 준비 자격은 C-1 등급 `우선 검토`이거나
  개요 플래그가 켜진 상태의 SW사업대상 건인데, 운영에는 C-1 등급이 한 건도 없고 개요 플래그가 꺼져 있다.
- 1단계로 **로컬 모델만 쓰는 흐름**을 연다: 첨부 취득 → 문서 준비 → 개요 → 사람이 개요를 읽고 추적 결정. 외부 모델 전송이 없다.
- 2단계로 **RL 카드 판정**을 추적 중인 건에 붙인다. 판정 품질이 인수 reject 상태이므로 대조 보강(D-1)과 재측정이 끝난 뒤에 켠다.
- 기존 심층 검토와 C-1 등급 표시는 화면에서 내린다. 그 자리(검토할 항목 조건, 다음 행동, 참여 조건 열)를 개요와 RL 판정이 채운다.

### 규모 추정

- 평일 SW사업대상 사전규격은 하루 41~81건, 평균 약 58건이다(11-02~11-18 게시일별).
- 게시에서 의견 마감까지 중앙값 5.3일. 전일 수집이라 실제 검토 여유는 약 4일이다(추정).
- 10-15 참조 실행(151건)의 비율을 적용하면 하루에 개요 run 약 41건, 그중 모델 호출까지 가는 것이 23~27건(평균 139초, 약 1시간),
  입력 초과로 호출 전에 끝나는 것이 약 14건이다(추정). 개요 내용의 정확성은 사람이 대조한 적이 없다(미측정).

## 3. 변경 내용

### A. 문서 준비와 개요 열기 (1단계)

| 항목 | 지금 | 수정 |
|---|---|---|
| 문서 준비 자격 | `우선 검토` 등급(운영 0건) | 개요 플래그를 켜 SW사업대상 사전규격을 연다. 등급 규칙은 그대로 둔다 |
| 자동 처리 범위 | 마감 필터 없음(밀린 603건도 대상) | **자동 취득·준비·개요는 의견 마감 전(또는 마감 미확인) 건과 사업기회가 추적 중인 건만.** 마감이 지난 건은 사람이 추적을 시작하면 그때 처리된다 |

### C. RL 카드 판정 연결 (2단계, 별도 승인)

- **"개요는 선별"의 뜻**: 사람이 개요를 읽고 추적을 정하는 근거다. RL 판정의 입력에는 넣지 않는다. RL-03 결정 D1(개요를 기다리거나
  부르지 않음)과 "RL 범위의 모델 호출은 Luna 하나" 규칙을 그대로 지킨다. 새 RL 정책 버전이 필요 없다.
- **판정 대상**: 추적 중인 사업의 사전규격. 사람이 사업기회 레코드에서 요청한다. 브리핑 추천에 따른 자동 시작은 그 뒤에 따로 정한다.
- **켜기 전 조건**: (1) D-1 대조 보강 → 같은 gold 재측정에서 차단 조건을 잡는 것 확인, (2) 운영 회사 근거 등록(회사 인터뷰 답 필요),
  (3) RL 정책 행 등록, Luna 실행기, 전송 승인과 일일 상한.
- **RL을 켤 때 같이 막을 것**: 같은 Luna 플래그로 기존 심층 검토 API도 열린다. active profile/policy id를 비워 두는 지금의 차단을
  명시적 차단으로 바꾼다.
- **"판정 확인" 상태**: 고도화안 §3의 "사람: 판정 확인"에 대응하는 구현이 없다(피드백 4종뿐). 2단계에서 상태와 화면을 정의한다.

## 4. 하지 않는 것

- C-1 공고 판정 재가동, 등급을 내는 개요 v8(LiteLLM용 파일이 없다).
- 개요 정책·프롬프트 변경, 입력 초과 구간 분할(D-5).
- RL 판정에 개요 결과를 입력으로 넣는 것(D1 유지).
- 기존 심층 검토·엔진의 백엔드 코드 삭제. 화면에서만 내린다.
- 사전규격에 대한 새 자동 선별 모델(발주계획의 C-2 같은 것).

## 6. 진행 순서와 승인 경계

| 단계 | 내용 | 승인 |
|---|---|---|
| 1 | 작업 브랜치에서 A(마감 전 제한, compose 수정)·B(조건식·화면)·D 구현과 격리 테스트. 리더가 영향 범위 검사를 다시 돌린다 | 불필요(운영 영향 없음) |
| 2 | main 병합, 백업·롤백 태그, 이미지 빌드, web·analysis-worker 교체, 첨부 worker 재생성(나라장터 첨부 host egress), 재시작 정책 | **필요** |
| 3 | 개요 플래그를 web·analysis-worker·첨부 worker에 같은 값으로 켠다. 마감 전 건의 첨부 취득·문서 준비·개요가 자동으로 시작된다(로컬 모델 호출) | **필요** |
| 4 | 첫날 감독: 취득·변환 성공률, 개요 완료·실패·입력 초과 건수, 처리 시간, C-2 일일 실행과의 슬롯 간섭, 화면의 `검토할 항목` | — |
| 5 | 2단계(RL 판정): D-1 재측정(Luna 전송), 회사 근거 등록, 전송 승인·일일 상한, RL 플래그 | **따로 승인** |

- 상한: 자동 처리는 의견 마감 전(또는 추적 중) 건만. 첫날 밀린 분 약 158건, 이후 평일 약 58건.
- 중단 조건: `binding_mismatch`, 첨부 변환 실패가 절반을 넘음, 모델 endpoint 연속 2회 실패, 로그·응답에 비밀값·회사자료 노출,
  C-2 일일 실행이 개요 때문에 시작하지 못함, migration이 필요해짐.
- 되돌리기: 개요 플래그를 끄고 첨부 worker를 내린다. 만들어진 묶음·개요 run은 지우지 않는다. 이미지·코드는 태그로 되돌린다.

| 마감 지난 건은 자동 취득·준비·개요에 들어가지 않고, 사람이 누르면 처리된다 | 자격·취득 큐 테스트(PostgreSQL 변형 포함) | 테스트 결과 |
| 새 `검토할 항목` 조건과 `확인 필요` 건수, 타일 건수 = 목록 기본 보기 | 목록·작업량 API 테스트, 화면 spec 2폭 | 테스트 결과, 캡처 |
| 기존 심층 검토·등급 표시가 화면에 없다 | 화면 spec(링크·버튼 부재), 운영 번들 문자열 확인 | 테스트 결과 |
| 첨부 worker가 등록한 개요 run이 `binding_mismatch` 없이 호출까지 간다 | 세 서비스의 정책 digest 대조, 첫날 감독 | 운영 기록 |
| 실제 흐름(수집 → 취득 → 변환 → 개요 → 목록) | 첫날 감독 1회 | validation-runs 기록 |

상시 첨부 worker에서 개요까지 이어지는 경로는 10-15에도 끝까지 증명된 적이 없다. 첫날 감독 전까지 "검증됨"으로 적지 않는다.

## 8. 남는 한계

- 개요 요약이 원문과 맞는지 사람이 대조한 적이 없다. 1단계의 개요는 읽기 보조이며 판정이 아니다.
- 하루 약 41건의 개요가 마감 전 약 4일 동안 쌓이면 `검토할 항목`이 150건 안팎이 될 수 있다(추정). 읽을 순서를 돕는 신호는
  추적 중 발주계획 연결뿐이다. 유형 라벨·발주처 실적 같은 보조 신호(고도화안 §5)가 다음 후보다.
- 입력 초과 약 24%는 사람이 범위를 확정해야 한다.
- Mac에서 변환이 `차단`으로 끝난 첨부를 되살리는 경로가 없다(findings, 미해결).
- RL 판정은 인수 reject 상태다. 2단계 전까지 사전규격 단계에는 회사 적합 판정이 없다.
