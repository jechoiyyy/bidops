## 보고서 내용의 충분성

요약·쟁점 제목·상태·원문 링크만으로 보고서를 완성하지 않는다. 본문을 읽으면 사업의 실제 과업·산출물, 회사의 관련 근거와 격차, 수행·평가·검수·계약·비용상 의미를 설명할 수 있어야 한다. 원문 링크는 내용을 검증하는 경로로 유지한다.

- 주요 항목은 **원문의 구체적 요구와 조건·예외 → 회사에 미치는 영향과 그 이유 → 확인된 회사자료·차이·미확인 → 필요한 확인·준비와 판단에 미치는 영향**을 기술한다. 영향은 사실·계산·해석·가정을 구분한다.
- 자격과 위험뿐 아니라 발주 목적, 포함·제외 과업, 데이터·연계, 산출물·교육·인계, 평가·제출물, 검수·대금·하자·권리·변경 조건을 다룬다. 관련 내용이 없거나 읽지 못했으면 그 한계를 표시하며 일반론으로 빈 부분을 채우지 않는다.
- 회사의 긍정 근거와 활용 가능한 경험도 실제 자료에서 설명한다. 유사 경험을 이번 규모·성능·가용성의 충족으로 승격하지 않는다.
- 조건 간 영향을 별도로 설명한다. 예를 들어 데이터 사용 제약과 검수 조건이 이관 방법·일정·원가에 함께 작용하면 관련 근거를 연결한다.
- 도입부의 판단은 같은 본문의 상세 사실·설명으로 이어진다. 조건별 근거와 미분석 범위를 본문에 표시하며 내부의 전체 범위 검증을 유지한다. 별도의 사용자용 대조 보고서는 이번 PoC에 추가하지 않는다. 중요 항목만 골라 보였다는 사실을 전수 분석으로 표현하지 않는다.
- 경제성 자료가 부족하면 비용 발생 요인·산정 입력·범위를 설명하고 계산 불가를 유지한다. 빈 표나 임의의 수익률로 대체하지 않는다.

### 시각적 편집 — 사용자 확정

- **편집된 문서형:** 핵심 문장, 절 제목, 상세 설명, 대조표, 근거 주석을 타이포그래피와 여백으로 구분한다. 각 절은 어떤 질문에 답하며 정보가 어떻게 이어지는지 짧게 안내한다. 전체 본문은 기본 펼침이며 다른 형식의 보고서를 만들지 않는다.
- **핵심에서 상세로:** 첫 절의 판단 조건을 먼저 강조하고 회사 근거·수행 조건·계약과 원가의 상세 절로 이동하게 한다. 핵심으로 선택한 문장도 원래 claim·근거 연결을 유지한다.
- **정보의 연결:** 조건 간 영향이 분석 결과에 존재하면 문서 조건→회사 영향→확인 사항→판단 갱신의 도식으로 읽을 수 있게 한다. 사실·해석·확인 제안의 역할을 문자로 표시하고 단계마다 근거를 제공한다. 없는 관계를 브라우저가 생성하지 않는다.
- **설명을 보존:** 강조와 도식은 상세 설명을 함께 읽도록 돕는다. 전체 본문·조건·예외·미확인은 유지한다. 색은 프로젝트 테마를 사용하며 우선순위·위험·준비 상태를 장식적인 수치나 색으로 만들어내지 않는다.

### 채택한 본문의 구성

| 순서 | 본문에서 설명할 내용 |
|---|---|
| 검토 기준 | 사업·문서·회사자료 기준, 의견 기한과 읽지 못한 범위 |
| 1. 먼저 알아야 할 판단 | 사업의 성격, 검토할 긍정 근거와 판단을 바꿀 조건 |
| 2. 사업 목적과 과업 | 발주 목적, 포함·제외 범위, 과업·산출물·완료 의무 |
| 3. 회사 근거와 부족한 자료 | 자격·실적·기술·인력의 대조와 확인 가능한 범위 |
| 4. 수행에 영향을 주는 조건 | 데이터·보안·성능·검수·일정과 조건 간 영향 |
| 5. 평가와 제안 준비 | 배점, 설명·증명할 내용, 확보한 자료와 준비할 자료 |
| 6. 계약과 경제성 | 책임·변경·권리·하자·대금과 비용 요인·산정 한계 |
| 7. 확인할 일 | 질문·내부 확인 자료와 그 결과가 바꾸는 판단 |
| 8. 판단 갱신 조건 | 확인 결과에 따른 재검토 조건과 별도의 사람 의견 |

본문 안의 도입·표·근거 표시는 하나의 보고서를 구성한다. 별도 요약본, 질문형 보고서, 조건 대조형 보고서·부록과 이들을 위한 생성·전환 기능은 PoC 범위에 추가하지 않는다. 원문의 사실·근거 연결, 전수 누락 검사, 사람 결정의 분리는 유지한다. 출력이 하나라는 선택은 모델 호출을 한 번으로 합치거나 검증 절차를 줄인다는 뜻이 아니다.

[report.md](report.md)는 채택한 구성의 가상 예시다. 절 수와 예시의 숫자를 현재 API·DB 계약으로 취급하지 않는다. 실제 입력에 관련 자료가 없으면 해당 절에 무엇을 설명할 수 없는지와 필요한 자료를 적는다. 설명 깊이를 웹 시안의 공간 제약으로 줄이지 않는다. 이후 분석·조회·화면 요구는 이 본문을 실제 제품에 연결하는 후속 범위다.

## 결과의 단위와 기준

보고서는 공고, 확정한 문서 묶음·문서 버전, 회사 프로필, 분석 정책, 실행 시도, 보고서 수정본, 검증 결과에 결합한다. 화면은 현재 공고 메타데이터와 보고서가 분석한 기준을 구분한다. 현재 문서나 회사자료를 읽어 과거 보고서의 의미를 다시 계산하지 않는다.

### 서로 구별할 정보

| 정보 | 의미 | 표시 원칙 |
|---|---|---|
| 실행 상태 | 대기·진행·완료·실패 등 작업 진행 | 완료를 자격 충족이나 사업성 확인으로 사용하지 않음 |
| 분석 범위 | 무엇을 읽고 판단했으며 무엇을 빠뜨렸는가 | 전체 범위와 누락·제외·판단 불가를 함께 표시 |
| 근거 검증 | 인용·숫자·ID·연결 관계 등의 검사 결과 | 사업 위험의 심각도와 별도 표시 |
| 사업 쟁점 | 확인한 조건·위험과 수행·계약에 미치는 영향 | 조건과 근거를 함께 제시. 근거가 있다는 이유로 위험을 없애지 않음 |
| 업무 확인 항목 | 판단 전에 확보할 회사자료나 확인할 사실 | 기술 실패와 구분하고 관련 쟁점에 연결 |
| 품질 표식 | 측정됨·미측정 참조·mock 참조·표식 없음 | 기존 의미 유지. 기술 검증 통과로 품질을 승격하지 않음 |
| 결과 기준 변화 | 보고서의 입력과 현재 확인 대상의 관계 | 문서 변경·새 묶음 준비·판단 불가를 구분 |

이 표의 한글 상태는 업무 의미 정의다. 기존 저장 enum을 번역 없이 교체하거나 새 enum이 이미 존재한다고 취급하지 않는다.

### 결과에 필요한 논리 구조

| 결과 묶음 | 필수 정보·제약 |
|---|---|
| 참여 조건 | 원문 조건·예외, 관련 회사 근거, 항목별 충족/불충족/확인 필요, 사유·원문 위치. 자료 미기재는 불충족이 아님 |
| 요구사항·과업·평가 | 원문 ID 또는 원문 위치에 묶인 내부 키, 요구 내용, 산출물·조건·배점 등 확인된 값, 분석 상태·근거. 내부 키를 원문 ID처럼 표시하지 않음 |
| 수행·계약 쟁점 | 영역, 쟁점, 발생 조건, 영향, 확인 근거, 근거 검증 상태, 관련 요구사항. 심각도 분류 기준은 결정 대기 |
| 경제성·수행 시나리오 | 확인된 예산·기간·수량, 계산식과 입력 출처, 가정과 미확인 비용. 내부 원가자료 없이 수익성을 확정하지 않음 |
| 다음 행동 | 확인할 질문/자료/행동, 이유, 연결된 쟁점·조건·근거. 담당자·기한은 원문 또는 사람 입력이 없으면 미지정 |
| 분석 제한·검증 결과 | 빠진 첨부·요구사항·영역, 실패 사유, 검사별 상태와 연결 대상, 품질 표식 |
| 검토 의견·이력 | 정확한 보고서·검증 기준, 작성자 이름·시각·사유, 수정·과거 의견 이력 |

`다음 행동`은 이 보고서에서 확인할 일을 안내한다. 별도 담당자 배정 시스템·알림·발주처 자동 연락은 만들지 않는다. 경쟁사·시장 정보가 입력에 없으면 경쟁 우위도 사실로 확정하지 않는다.

## 분석과 보고서 생성

### 입력 범위와 회사 근거

- 원문에서 결정적으로 식별할 수 있는 요구사항 목록과 문서·쪽·절·표/셀 위치를 먼저 고정한다. 번호가 없는 조항과 예외도 검토 범위에 포함한다.
- 각 호출에 포함한 요구사항, 관련 회사 fact, 조건·유효기간·예외, 근거를 함께 전달한다. 문서 조각과 프로필 조각을 같은 순번이라는 이유로 묶지 않는다.
- 회사자료의 확인된 사실과 추론·미확인을 구별한다. 추론된 역량이나 개요의 모델 의견을 확인된 회사 사실로 승격하여 자격 충족 근거로 쓰지 않는다.
- 자료가 없거나 검색·입력 예산 때문에 충분한 근거를 전달하지 못하면 이유를 남기고 회사 상태를 확인 필요로 둔다. 모든 문서×모든 회사자료의 교차 호출을 기본으로 만들지 않는다.
- 요구사항을 앞 단계 결과에서 가져오는지 원문에서 구성하는지, 영역별 호출을 쓰는지는 구조 결정에 따른다. 어느 경우에도 원문의 조건·예외와 연결이 유지되어야 한다.
- 종합 호출마다 참조하는 선행 claim과 근거가 그 호출 안에서 해석되어야 한다. 조각 사이의 공유 근거를 전체에서 한 번만 전달하고 끝내지 않는다.

### 누락과 종합

- 조각별 포함 ID·출력 ID를 검사하고 전체 문서의 기대 목록과 조각 합집합도 비교한다. 입력에서 누락한 요구사항을 검사 대상에서 제외하여 통과시키지 않는다.
- ID를 언급한 것과 해당 조건을 분석한 것을 구분한다. 8 claim은 현재 slice별 프롬프트 지시이며 8 요구사항 또는 문서 전체 상한으로 해석하지 않는다.
- 기대 목록을 만들지 못한 문서는 범위 확인 불가로 남긴다. 분모를 알 수 없는데 완전성 100%를 표시하지 않는다. 표·그림·추출 실패 부분도 한계로 표시한다.
- 화면 요약의 길이 제한과 전체 분석 결과의 출력 예산을 분리한다. 잘림·누락·한도 초과를 검증 완화나 자동 보완으로 성공 처리하지 않는다.
- 최종 종합이 참조한 전체 결과를 기록한다. 조각별 권고가 충돌하거나 핵심 근거가 부족하면 판단 제한을 표시한다. 기술·분석상 판단 불가와 업무상 보류 사유를 구별한다.

### 절별 조립과 검증

- 결과와 보고서 영역을 명시적으로 연결한다. 없는 영역에 전체 claim을 복사하지 않으며, 분류하지 못한 결과는 미분류 목록과 한계로 보존한다.
- 동일 영역의 모든 결과에 접근할 수 있게 한다. 요약을 접거나 개수를 제한하더라도 전체 건수·전체 보기와 근거 연결을 제공한다.
- 사실 주장에는 해당 원문 또는 회사 근거를 연결한다. `미분석`, 묶음 제외 등 서버 설명은 알려진 상태·원천 ID로 생성하고 무관한 claim을 빌리지 않는다. 일반 메모를 이용해 근거 없는 사실을 검증에서 제외하지 않는다.
- 빈 목록만으로 `위험 없음`을 선언하지 않는다. 미분석/범위 불명/검증 실패가 있으면 그 상태를 먼저 보인다. 분석 범위 내 식별 결과가 없더라도 회사의 전체 위험 부재를 보증하지 않는다.
- 검증 checks를 확정한 뒤 동일한 목록에서 통과·경고·실패 건수와 상태를 계산한다. 업무 확인 항목 수는 별도다. 실패 시 claim·근거 또는 누락한 원문 위치로 이동할 수 있게 하고, 위치를 알 수 없으면 그 이유를 알린다.

## 조회·재실행·기준 변화

실행 조회와 보고서 snapshot 조회를 구분한다. 최신 실행을 숨기지 않으면서 이전 완료 결과를 읽을 수 있게 하는 것이 목표다.

| 상황 | 화면과 조회 동작 |
|---|---|
| 분석 미시작, 보고서 없음 | `아직 분석하지 않음`. 조건·위험이 없다고 말하지 않음 |
| 첫 실행 대기/진행 | 진행 상태와 아직 결과가 없음을 표시 |
| 첫 실행 실패 | 실패의 업무상 영향과 가능한 후속 행동 표시 |
| 이전 완료 보고서가 있고 새 실행 대기/진행/실패 | 이전 결과를 기준 문서·시점과 함께 유지하고 최신 실행 상태를 별도 표시 |
| 새 묶음이 초안/실패이며 확정 원문 변화는 확인되지 않음 | 새 문서 준비 상태 표시. 묶음 ID 차이만으로 기존 분석의 무효를 확정하지 않음 |
| 분석 기준 이후 확정 원문 변화가 확인됨 | 이전 문서 기준임을 표시하고 변경된 기준으로 검토가 필요함을 안내 |
| 원문·묶음 관계를 판별할 수 없음 | 기준 확인 필요. 최신 결과로 자동 선택하거나 확정하지 않음 |
| 정책·프로필만 바뀌거나 같은 입력을 재시도함 | 문서 변경과 구별. 과거 결과의 입력 기준을 유지하고 자동 재분석하지 않음 |
| 보고서 조회 API가 실패함 | 조회 오류 표시. 이미 읽은 결과를 유지하면 최신 조회 실패 사실도 함께 표시 |

현재 보고서 수정본은 응답의 정확한 revision ID로 선택한다. 이력의 첫 행이나 단순 생성 시각으로 추정하지 않는다. GET은 기존 결과를 읽기만 하며 보고서 생성·보정·DB 변경을 수행하지 않는다.

의견은 저장 당시의 report revision과 validation에 귀속한다. 현재 보고서에 의견이 없더라도 과거 의견은 이력에서 보인다. 과거 revision에 새 의견을 허용하는 정책은 [결정 대기](decision.md)에 있으며, 현재 API의 허용 동작을 이 문서만으로 변경하지 않는다.

## 화면과 사용자 동작

### 정보 순서와 노출 범위

상단에는 사업명·기관·의견 마감, 보고서 기준, 최신 실행 상태를 보여준다. 그 아래에서 핵심 쟁점·참여 조건·업무 확인·다음 행동을 읽고 상세 분석과 원문으로 이동한다. 로딩 중인 상태를 완성된 요약처럼 보여주지 않는다.

| 기본 화면에 유지 | 접힌 기술정보/기존 운영 화면으로 이동 |
|---|---|
| 사업·기관·마감·문서명·쪽수·분석 기준 시점 | UUID, 객체·입력 hash, 내부 키, bbox 좌표 |
| 중요한 조건·영향·확인 필요·다음 행동 | 정책·모델 세부 버전, 실행 세부 이력, 원시 오류 코드 |
| 품질 미측정, 부분 범위, 검증 실패, 이전 문서 기준 안내 | 문제 진단에 필요한 기술 세부 정보 |

기술정보는 필요한 경우 전체 값을 확인할 수 있게 한다. 품질·범위 경고는 접기에 숨기지 않는다. 별도 운영 화면을 새로 만드는 것은 이 작업의 필수 범위가 아니다.

사전규격 상세와 심층검토는 같은 의미의 요약을 공유한다. 상세에서는 중요한 항목과 전체 보기 링크를 제공하며 `unknowns`만 위험 목록으로 취급하지 않는다. 근거 부족·업무 미확인·확인된 위험은 서로 다른 이름으로 보인다. v1에서 구분할 수 없는 의미는 확인 불가로 표시한다.

### 원문·편집·의견

- 근거 버튼은 읽을 수 있는 문서명·쪽/절로 구분하고, 클릭 즉시 인접 패널에서 해당 위치를 보여준다. 선택 상태와 키보드 초점을 연결하고 닫으면 원래 문장으로 복귀한다. UUID만 읽고 찾아가게 하지 않는다.
- 원문 조회 실패는 패널 안에서 알리며 임의의 다른 문서·쪽으로 대체하지 않는다. 분석한 불변 문서 버전의 근거를 사용한다.
- 읽기와 편집을 구별하고 수정 대상 행/쟁점·근거·사유를 명시한다. 근거는 선택 UI로 연결한다. 새 revision 저장, 사실 수정 근거 검사, 감사와 동시성 충돌 처리를 유지한다.
- 편집 초안은 시작 시 revision에 고정한다. 재조회나 다른 사용자의 저장으로 dirty 초안을 초기화하지 않는다. 서버 버전이 바뀌면 비교/갱신 안내를 제공하며 실패 후에도 입력을 보존한다.
- 의견 값은 `추진|조건부 추진|보류|검토 종료`를 유지하되 초기에는 선택하지 않은 상태로 둔다. 서버에는 사용자가 명시적으로 고른 유효 값만 제출한다. 이 값들은 최종 입찰 Go/No-Go가 아니다.
- 의견 확인창에는 보고서·검증 기준과 값·사유를 고정한다. 확인 중 기준이 바뀌어도 다른 보고서로 조용히 바꿔 저장하지 않는다. 검증 실패 확인 의무, 담당자 이름·사유·멱등성을 보존한다.
- 담당자 이름은 수정·의견·재실행 동작에 필요한 감사 입력으로 배치한다. 읽기 진입을 막거나 이름을 인증·권한으로 표현하지 않는다.
- 의견 저장 후 연결된 사업기회의 추적 결정 화면으로 이동할 수 있게 한다. 후보 관계는 확정 관계로 취급하지 않으며, 추적 상태를 자동으로 바꾸지 않는다.

### 레이아웃과 접근성

1280×800·1440×900을 검증한다. 모바일·태블릿 전용 화면은 추가하지 않는다. 직접 진입·새로고침·SPA 이동에서 공통 스타일과 정보 순서가 같아야 한다. 상세 데이터는 행 중심으로 표현하고 13개 절을 전부 길게 펼치는 것은 필수로 삼지 않는다.

기존 Astryx와 프로젝트 `bidops` 테마·공용 컴포넌트를 사용한다. 구체적인 배치·접힘·원문 패널은 [기존 사용자 시안 절차](../0921_practitioner-screens/intent.md)에 따라 fixture 시안을 확인한 뒤 구현한다. 키보드로 쟁점 선택·근거 열기·닫기·의견 작성을 수행할 수 있어야 한다.

## 호환성과 인수

새 의미·블록·검증 규칙은 새 report/stage 계약으로 발행한다. 기존 v1 payload·hash·사람 의견을 덮어쓰거나 새 규칙으로 조용히 재해석하지 않는다. 이전 결과는 원 계약으로 읽고, 새 분석은 새 불변 정책·입력·실행으로 생성한다. v1/v2 reader, API, 타입, mock, validator를 함께 준비한다.

기존 JSONB·이력으로 정확한 관계를 표현할 수 있는지 확인한 뒤 DB migration 필요성을 판단한다. 버전 식별자를 바꾼다는 이유만으로 새 DB 테이블을 만들지 않는다. 새 필드가 필요하면 ERD·Alembic·복구 절차를 함께 갱신한다.

인수는 [plan.md의 검증 묶음](plan.md)을 따른다. 최소한 **서로 다른 영역의 복수 결과 → 생성·검증·저장 → API → 두 화면의 요약·근거 확인**이 하나의 대표 통합 사례에서 이어져야 한다. 입력 분할·근거 공유·재실행·문서 기준 변화·동시 편집도 포함한다.

실제 모델 품질과 실무 효과는 사람 정답 및 사용 관찰로 검증한다. 합성 테스트는 결함 수정의 근거이며 운영 정확도 측정을 대신하지 않는다. 구현·시안·모델 평가·운영 반영의 완료 여부를 각각 기록한다.

## 이번 PoC의 구현 계약

정본 wire 상세는 [contracts.md의 v2 항목](../contracts.md#심층검토-설명형-보고서-v2-2026-09-22-선택형-poc)이며 기존 v1과 구별한다.

1. 입력: 동결 문서를 동일한 원문 조각으로 나누어 단계 1·2에 전달한다. 실제 문서 요구사항 ID의 inventory 합집합과 조각 합집합을 대조한다. 회사 자료는 문자열·한국어 이음절 관련도에 따른 결정적 선택이며 사실과 근거를 통째로 넣는다. 선택·미선택·예산 제외 범위를 invocation metadata에 남긴다. 이 방식의 의미 회수율은 미측정이다.
2. 종합: 각 묶음에 해당 주장들의 공유 근거를 다시 포함한다. 부분 종합은 전체 권고를 만들지 않으며 마지막 전체 종합만 권고 하나를 만든다. 모든 입력 주장 ID를 연결해야 한다. 전체 종합이 입력 예산을 넘으면 실패하며 일부 결과를 전체 판단으로 발행하지 않는다.
3. 저장: 역할·절·연결·핵심 표시를 stage JSON에 보존하고 DB claim projection을 대조한 뒤 report v2를 만든다. 모든 문장은 정확히 한 번 본문에 나타난다. 없는 절은 `not_analyzed`; 자료 부족은 역량 미달이나 위험 없음이 아니다. 검증 건수는 실제 checks에서 산출한다.
4. 읽기: 핵심 강조·상세 문단·판단 이유·양방향 관계 링크·목차·글자 확대·집중 읽기·옆 원문 패널을 제공한다. 연결은 모델이 명시한 관계의 정방향/역방향 조회이며 화면이 새 인과관계를 만들지 않는다. 세부 내용을 표로 축약하거나 별도 보고서를 생성하지 않는다.
5. 수정과 의견: 문장 단위 수정은 claim과 문단을 함께 변경한다. 근거는 선택 목록으로 지정하고 사유·base revision을 유지한다. 새 수정본 도착 시 초안을 보존하고 이전 base의 저장을 차단한다. 의견은 빈 선택에서 시작하며 확인창을 열 때 담당자·의견·보고서·검증 ID를 동결한다.
6. 실행과 조회: 실행 상태와 보고서 조회는 기존 두 API를 함께 사용한다. 새 envelope를 추가하지 않았다. 재시도 중/실패에도 이전 보고서를 읽으며 현재 실행 완료 전 수정·의견 저장은 막는다. 회사 프로필·정책·새 문서의 현재성 자동 판별은 이번 PoC에서 추가하지 않는다.
7. 검증 강도: 의미를 바꾸지 않는 인용 표기 차이는 같은 원문 위치의 연속 문자열로 연결한다. 같은 원화 금액의 단위 환산은 허용한다. 축약 연도의 확장은 문장 옆 `year_notation` 확인 사항이며 세기를 자동 확정하지 않는다. 숫자·조건·출처 변경은 차단한다. 모델 원본과 실패 이력은 보존한다.
8. 처리상 제약: 한 원문 조각의 회사 대조 입력도 여러 묶음으로 나눠 모든 선행 주장을 전달한다. 모델의 로컬 UUID는 호출별 namespace에 결속한다. 업무 내용은 바꾸지 않으며 전체 종합의 입력 상한은 유지한다.
9. 원문 대조 선택: 웹의 새 분석/재실행 설정에서 인용 일치·숫자 대조를 on/off한다. 기본 on이며 실제 선택은 attempt 감사 기록으로 고정한다. off 보고서는 ‘원문 대조 미실시’ 표시와 모델 인용/실제 페이지 구분을 유지한다. 원문 hash·출처/접근 범위·JSON/참조·계산식·누락 검사는 항상 수행한다. 상세 REST·과거 이력 처리는 위 정본 계약을 따른다.

남은 평가: 실제 고정 표본의 의미 누락·예외 손실·잘못된 숫자/해석·관련 회사 근거 회수율, 호출량/지연, 실무자 판단 충분성. 55개 요구사항 규모와 다양한 묶음 변경 사례의 인수는 아직 증명하지 않았다. 문장 수/ID 연결/인용 검증만으로 의미적 전수 분석을 보증하지 않는다.
