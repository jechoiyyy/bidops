# 사전규격 심층검토 고도화 — 의도

- 작성: 2026-09-22. 상태: **사용자 확정 방향의 PoC 운영 적용·실제 Qwen 참조 검증**. 최신 결과는 [실제 검증 기록](../validation-runs/20260922-narrative-review/live-validation.md)을 따른다.
- 문서: [의도](intent.md) · [명세](spec.md) · [결정 기록](decision.md) · [수정 계획](plan.md).
- 대상 사용자: 사전규격 제안요청서를 읽고 사업의 추적 여부와 확인할 일을 정하는 기획·사업개발 실무자.
- 현재 작업: 2026-09-22 사용자 선택에 따라 **A안의 설명형 본문 하나를 PoC 제품에 연결**한다. 새 정책·stage/report v2·읽기 화면을 구현했다. [보고서 본문](report.md)을 기준으로 편집된 문서형의 읽기 시안을 만들었다. 핵심과 상세의 위계, 문서 조건→회사 영향→확인→판단의 연결을 시각적으로 표현한다. 별도 요약본·질문형 보고서·조건 대조형 보고서는 PoC 범위에 추가하지 않는다.

## What — 무엇을 바꾸는가

심층검토를 **원문과 회사자료에 근거하여 참여 조건·수행 위험·미확인 사항·다음 행동을 파악하는 작업 공간**으로 개선한다. 분석이 결과를 만드는 방식과 실무자가 그 결과를 읽고 확인하는 화면을 함께 바꾼다.

보고서 본문은 문서에 무엇이 적혀 있는지, 그것이 회사에 어떻게 작용하는지, 실무자가 무엇을 알고 준비해야 하는지를 설명한다. 핵심 쟁점의 제목·상태만으로 본문을 대신하지 않는다. 과업·산출물·평가·검수·계약·비용과 조건 간 영향, 회사의 긍정 근거와 부족한 근거를 함께 다룬다.

읽는 순서도 설계한다. 핵심 문장을 먼저 발견하고 상세 설명과 근거로 이어지게 하며, 서로 관련된 조건은 연결 관계를 드러낸다. 타이포그래피·간격·강조·대조표·관계 도식은 설명을 이해하기 위한 수단이다. 충분한 본문을 유지하면서 판단에 필요한 부분을 찾기 쉽게 만드는 것이 시각적 편집의 목적이다.

보고서를 열면 다음 질문에 답할 수 있어야 한다.

| 실무자의 질문 | 서비스가 제공해야 할 정보 |
|---|---|
| 어떤 사업이며 무엇을 언제까지 검토해야 하는가? | 사업명, 기관, 의견 마감, 과업과 분석 기준 문서 |
| 참여 조건은 무엇이고 우리 회사가 충족하는가? | 원문 조건, 확인된 회사 근거, 충족 여부와 미확인 이유 |
| 수행하거나 계약할 때 무엇이 문제가 될 수 있는가? | 중요한 기술·일정·보안·계약·경제성 쟁점과 영향 |
| 판단하기 전에 무엇을 더 확인해야 하는가? | 질문, 필요한 자료, 내부 확인 사항과 연결된 쟁점 |
| 이 설명을 얼마나 믿어도 되는가? | 원문 위치, 분석한 범위, 빠진 항목, 검증 실패, 결과 기준 시점 |
| 검토 뒤 무엇을 남겨야 하는가? | 해당 보고서에 대한 사람 의견과 사업 추적 결정으로 이어지는 동선 |

**가상 예시:** 제안요청서에 “특정 인증 필수”라고 적혀 있지만 회사자료에는 인증 정보가 없다면, `필수 조건 확인 · 회사 보유 여부 확인 필요`로 보여준다. 원문을 바로 열고 `인증 보유 자료 확인`을 다음 행동으로 제시한다. 자료가 없다는 이유로 참여 불가를 확정하지 않는다.

## Why — 왜 필요한가

현재 구현에는 분석 결과의 의미와 화면의 표현이 어긋나는 경로가 있다. 앞선 점검과 Fable high 독립 검토를 대조했으며, 근거와 보정 사항은 [수정 계획의 검토 기록](plan.md)에 있다.

| 확인한 문제 | 실무자가 겪을 수 있는 일 |
|---|---|
| 근거가 충분한 위험 문장이 있어도 위험 요약은 `차단 위험 없음`이 될 수 있음 | 중요한 조건을 문제없는 것으로 받아들임 |
| 한 영역에 결과가 없으면 다른 영역의 문장을 채우고, 여러 문장 중 첫 문장만 표시함 | 자격·경제성 내용을 잘못 이해하거나 뒤의 쟁점을 놓침 |
| 문서 조각과 회사자료를 순번으로 묶고, 종합 조각 사이에서 근거가 빠짐 | 회사에 자료가 있어도 해당 분석에서는 확인하지 못함 |
| 검증 경고 건수와 실제 검사 목록이 다름 | 결과의 확인 수준을 잘못 파악함 |
| 내부 식별자·실행 정보가 앞에 나오고 원문 확인은 멀리 떨어져 있음 | 판단에 필요한 정보를 찾느라 화면을 오가게 됨 |
| 재실행 때 이전 보고서 조회가 막히고 수정본·초안 처리가 불완전함 | 이전 판단 근거를 찾지 못하거나 작업 내용을 잃을 수 있음 |

이 문제들은 **보고서가 만들어졌다는 사실만으로 판단에 쓸 수 있는 결과가 만들어졌다고 볼 수 없는 이유**다. 화면의 순서와 문구를 개선하면서, 잘못된 결과를 만드는 조립·입력·검증 규칙도 수정해야 한다.

위 문제의 존재는 코드·합성 입력·mock 화면으로 확인한 범위다. 운영에서 얼마나 자주 발생하는지, 실제 모델의 정확도가 어느 정도인지는 아직 측정하지 않았다.

## How — 어떻게 개선하는가

현재는 아래 구현에 앞서 선택한 A안의 본문을 정리한다. 문서 사실→회사 영향→회사 근거·미확인→확인·준비의 설명을 하나의 보고서 안에서 이어 간다. 본문 안의 소제목·표·근거 표시는 유지하고 같은 내용을 다른 형식의 보고서로 다시 생성하지 않는다. [가상 입력](report-source.md)은 본문의 근거를 확인하기 위한 작성·검증 자료다.

1. **읽기와 작업의 신뢰성부터 보완한다.** 직접 진입 배치, 원문 열기, 현재 수정본 표시, 편집 초안 보존, 실패 안내를 고친다.
2. **보고서의 의미를 바로잡는다.** 사업 위험, 근거 검증, 업무상 미확인, 분석하지 못한 범위를 구분한다. 무관한 내용을 채우거나 일부 결과를 생략하지 않는다.
3. **분석에 필요한 자료를 함께 전달한다.** 요구사항별 회사 근거와 조건·예외를 연결하고, 각 분석 조각과 전체 문서의 누락을 확인한다.
4. **실무 순서에 맞춰 화면을 구성한다.** 사업 정보와 중요한 쟁점·다음 행동을 먼저 보여주고, 세부 조건과 원문을 이어서 확인하게 한다. 운영용 정보는 접힌 기술정보나 기존 운영 화면으로 옮긴다.
5. **정확성과 사용성을 함께 평가한다.** 사람 정답과 비교해 중요한 누락·왜곡을 확인하고, 실무자가 조건과 근거를 찾는 시간·정답률도 측정한다.

## 성공의 기준

- 원문에서 확인한 조건·숫자·예외와 회사자료의 사실을 결과와 연결할 수 있다.
- 자료 없음·분석 누락·검증 실패가 `문제없음`으로 바뀌지 않는다.
- 참여 조건·중요 쟁점·다음 행동을 두 화면에서 일관되게 읽고 원문을 즉시 확인할 수 있다.
- 이전 보고서와 사람 의견을 보존하며 어느 문서·수정본 기준인지 알 수 있다.
- 사람이 중요한 내용을 더 정확히 파악하는지 확인한다. 화면이 짧아졌거나 읽는 시간이 줄었다는 사실만으로 성공을 판단하지 않는다.

구체적인 동작과 인수 조건은 [spec.md](spec.md), 검사 실행 범위는 [plan.md](plan.md)에 둔다. 실제 모델 품질의 수치 기준과 위험 우선순위는 [decision.md](decision.md)의 결정 대기 항목이다.

## 이번 작업의 경계

현재 PoC의 우선 산출물은 A안의 설명형 본문 하나다. 가상 자료의 기준 예시 정리와 실제 분석 기능의 구현·품질 검증은 구분한다. 아래는 후속 제품 고도화의 대상이며 본문 형식 선택을 운영 실행 승인으로 해석하지 않는다.

사전규격 상세의 심층 결과 요약, 심층검토 보고서·근거·편집·의견 화면, 그 결과를 생성하고 조회하는 경로가 대상이다. [0921 실무 화면 고도화](../0921_practitioner-screens/intent.md)의 공용 컴포넌트와 기술정보 정리를 재사용한다.

회사자료와 공고 사실은 추정하지 않는다. 사람의 심층검토 의견, 사업 추적 선택, 최종 입찰 Go/No-Go를 서로 대신하지 않는다. 개요의 등급·자동 심층 시작 게이트·참여 준비 상태를 이 작업의 결과로 자동 변경하지 않는다.

모델 교체·역할별 분석 도입·개요 회사핏 통합·예비판단 v8 활성화는 별도 결정이다. 자동 입찰, 발주처 연락, 알림, SSO, 모바일 대응, 입찰 변경 비교 worker는 이번 범위에 포함하지 않는다.

## 구현된 What / Why / How

- **What:** Qwen의 문서 분석·회사 근거 대조·종합 결과를 여덟 절의 설명형 보고서로 만든다. 핵심 문장은 먼저 강조하고, 상세 설명과 판단 이유를 보존하며 연결 문장과 옆쪽 원문 패널로 이동한다.
- **Why:** 제목이나 간단한 위험 목록만으로는 “문서에 어떤 조건이 있으며 우리에게 왜 중요하고 무엇을 확인해야 하는가”를 판단하기 어렵다. 보고서 조립 과정의 문장 생략·무관한 절 복제·공유 근거 누락도 바로잡아야 한다.
- **How:** 명시적인 문장 역할·절·근거·관계를 받는 새 불변 정책과 계약을 사용한다. 입력 조각별 확인 상태와 실제 문서 요구사항 ID를 대조하고 전체 종합 뒤 모든 문장을 저장한다. 읽기 화면과 사람의 수정·의견을 구분하며 이전 결과를 덮어쓰지 않는다.

운영 적용과 실제 Qwen 호출을 진행했다. 합성 자료의 연결 검증과 실제 보고서의 의미 품질은 구별한다. 관련 회사 자료 선택의 회수율과 담당자 사용성은 별도 평가가 필요하다.

- **What:** 과도한 문자열 일치 검사를 완화하고 판단에 영향을 주는 차이는 유지한다.
- **Why:** 원문에 없는 공백 한 칸과 축약 연도 표기만으로 보고서 전체가 중단되는 실제 사례를 확인했다. 실무자가 확인할 수 있는 불확실성은 문장 옆에 보여 주는 편이 목적에 맞는다.
- **How:** 같은 위치의 연속된 원문으로 표기 차이를 연결하고 같은 금액의 단위를 환산한다. 축약 연도는 확인 사항으로 남긴다. 다른 값·조건·출처는 계속 차단한다. 긴 후속 입력은 누락 없이 나누어 처리한다.

추가 확정한 on/off는 PoC에서 검증의 효과와 모델 원출력을 비교하기 위한 실행별 선택이다.
웹의 분석 설정에서 원문 인용·숫자 대조를 끌 수 있다. 끈 보고서에는 대조 미실시를 명확히
표시하고 원문을 직접 확인하게 하며, 문서 접근 범위와 데이터 형식 검사는 유지한다.
