### Fable 제안에서 변경한 부분

- **v1 유지 + 새 `note` enum + 작성일로 세대 판별은 채택하지 않는다.** 닫힌 JSON Schema·Pydantic·TypeScript 소비자에는 호환되지 않으며 의미 변경도 있다. 새 계약 식별자를 쓰고 생성 규칙을 불변 정책/manifest에 명시한다. 임의 `note`로 사실 검증을 우회하지 않는다.
- **회사 fact의 축약 색인만 모델에 주고 사후에 근거를 붙이는 안은 기본안으로 채택하지 않는다.** fact 존재와 실제 조건 충족은 다르다. 필요한 범위·기간·예외와 원문 근거를 같은 호출에 제공하고, 찾지 못하거나 예산에 넣지 못하면 `unknown`으로 남긴다. 색인은 검색 보조로만 검토한다.
- **`report.bundle_id != latestBundle.id`만으로 낡음 확정은 하지 않는다.** 최신 묶음이 미확정·실패·같은 원문인 경우를 구분해야 한다. 문서 기준이 다름은 표시하되, 확정 원문 변화와 판단 불가를 서버 규칙으로 구분한다.
- **검증 기대 집합을 slice로 좁히는 것만으로 전수 검증을 대체하지 않는다.** slice별 검사와 묶음 전체 inventory 합집합 검사를 모두 유지한다. 출력 부족을 경고 하향이나 자동 ID 채우기로 숨기지 않는다.

### 대조 중 추가로 확인한 사항

- `DeepReviewPage.tsx:363`은 `history[0]`을 표시하지만 서버 `reports.py:976`은 이력을 오름차순으로 준다. 현재 수정본 ID로 해당 이력을 찾아야 한다.
- 같은 화면 `190–195`의 effect는 새 report 응답마다 편집 초안을 초기화한다. 다른 사용자의 수정 등으로 재조회 응답이 바뀌면 미저장 내용이 사라질 수 있다. 초안의 기준 revision을 고정하고 갱신 충돌을 알린다.
- `deep_reviews.py:1039–1064`는 종합 조각 전체에서 공유 근거를 한 번만 넣는다. 8,000자 claim 두 개가 같은 근거를 참조하는 합성 입력에서 조각 2개가 생겼고 두 번째 입력의 근거 행은 비었다. 각 호출 안에서 참조 근거가 모두 해석되게 해야 한다. 기존 테스트는 같은 조각 안의 중복 제거만 증명한다.
- 종합은 조각마다 권고를 만들고 병합한다. 서로 다른 권고가 나올 때 `보류`로 닫히는 안전 경계는 유지하되, 전체 쟁점을 본 최종 종합인지와 업무상 보류인지 구별해야 한다. 실제 오판율은 확인하지 않았다.

## 목표 결과와 화면

아래 표는 후속 화면에 필요한 정보의 색인이다. 현재 PoC는 [A안 본문](report.md) 하나에 요구 내용·회사 영향·근거·미확인·대응을 충분히 설명하는 것을 우선한다. 별도 요약 보고서를 만들거나 본문을 쟁점 제목·상태로 제한하는 지침이 아니다.

실행 상태·분석 범위·근거 검증·사업 위험·모델 품질·결과 현재성은 서로 대신하지 않는다. `완료`는 분석 실행의 종료이고, `검증 통과`만으로 회사 자격이나 사업성을 보증하지 않는다.

A안 본문의 읽기 순서는 **검토 기준 → 판단 도입 → 사업 목적·과업 → 회사 대조 → 수행 조건 → 평가 → 계약·경제성 → 확인할 일 → 판단 갱신**으로 확정했다. 이 흐름과 설명 깊이를 보존하여 이후 화면 배치를 정한다. 본문 안의 표와 원문 연결을 유지하며 설명 문단을 짧은 상태로 대체하지 않는다.

UUID·hash·bbox·정책/모델 버전·원시 오류 코드는 접힌 기술정보 또는 기존 실행 상태 화면에서 본다. 사용자에게 필요한 문서명·쪽수·절·기준 시점·오류의 업무상 영향은 기본 화면에 남긴다. 담당자 이름은 의견·수정·재실행 때 받으며 인증으로 표현하지 않는다.

### 결정적 보고서 조립과 조회 계약 수정

## 계약 이행과 기존 결과 보존

1. 새 생산자 전에 v1/v2를 구분하는 reader·API·프런트 타입·mock·회귀 사례를 함께 준비한다. 기존 API의 의미를 몰래 바꾸지 않고 새 조회 envelope/경로와 구 소비자 처리 방식을 `docs/contracts.md`에 고정한다.
2. 기존 report payload·hash·원문·사람 의견은 수정하지 않는다. v1은 v1로 읽고 부족한 의미는 확인 불가로 남긴다. 새 분석은 새 정책/실행/보고서에 귀속하고 기존 실행을 재시도해 새 정책으로 바꾸지 않는다.
3. 새 renderer·validator·prompt의 버전을 불변 입력에 명시한다. `created_at`으로 생성 규칙을 추정하지 않는다. 과거 보고서의 사람 수정은 원 계약을 유지하는 별도 revision으로 처리하고 새 의미가 필요하면 명시적 새 분석 경로를 쓴다.
4. DB migration은 JSON 계약 버전 증가만으로 필수라고 단정하지 않는다. 현재 JSONB·이력·감사 자료로 attempt↔report 및 근거 버전을 정확히 연결할 수 있는지 먼저 확인한다. 불가능한 연결을 추정하지 않으며 새 영속 필드가 필요하면 Alembic·정본 ERD·복구 절차까지 포함한다.
5. 배포는 새 reader → 새 producer의 호환 순서와 롤백 후 v2 읽기 가능성을 확인한다. 운영 migration·실제 심층 모델 호출·정책 활성화·재배포는 각각 직전 사람 확인을 받는다. 이번 CLI 코드 검토 승인은 이 운영 승인들을 대신하지 않는다.

## 남은 결정과 범위 경계

남은 선택·권장안·필요한 근거와 결정 시점은 [decision.md의 결정 대기](decision.md)에 둔다. 분석 구조·회사 근거 선택, 위험 우선순위, 과거 보고서 의견, 시안, 품질 채택 기준, 조회 API·영속 필드가 해당한다. 문서 작성 요청을 제품 설계 전체나 운영 실행의 승인으로 기록하지 않는다.

역할별 모델 분석(ADR-0051), 개요 회사핏의 심층 통합(ADR-0057 결정 4), v8 예비판단 운영 활성화(ADR-0065), 입찰 delta worker, 알림·SSO·모바일은 이번 수정 계획에 자동 편입하지 않는다. 이 계획에서 심층 내부의 회사자료 연결을 고치는 것과 개요 단계의 회사핏 게이트를 옮기는 것은 별개다.

현재까지 완료한 일: Fable high 검토 수신, 소스 대조, 종합 공유 근거의 합성 입력 재현, 수정 계획·미해결 기록 작성, 텍스트 형식 비교 후 사용자가 선택한 A안의 단일 본문 기준 정리, 해당 본문을 직접 표시하는 웹 시안 작성, 현재 Qwen 결과의 제품 사용 경로와 추가 수정 범위 확인. 가상 입력과 설명의 일치·본문 구성·문서 링크·공백을 확인했다.

웹 시안은 독립 브라우저의 1280×800·1440×900에서 검사했다. 두 폭 모두 본문 8개 절·표 5개와 문장·제목·표 셀 133개 단위의 보존, 목차 이동, 문서·회사 근거 선택, 닫기·Escape 후 초점 복귀, 패널 가시성, 집중·글자 확대, Markdown 내려받기 원본 일치가 통과했다. 가로 넘침·누락된 테마 토큰·브라우저 오류·HTML 로딩 외 외부 요청은 없었다. 결과 화면은 [시안 폴더](prototype/README.md)에 저장했다. 이 검사는 가상 본문을 읽는 시안의 동작을 확인한 것이며 실제 API 연결·Qwen 분석 품질을 증명하지 않는다.

제품 코드·운영 설정·정책·배포는 변경하지 않았으며 실제 모델 호출도 수행하지 않았다. Qwen 점검은 소스와 정책 파일 기준이고, 운영 DB의 개별 결과·활성 정책을 조회한 것으로 기록하지 않는다.

시각적 편집 갱신: 핵심 판단 조건을 첫 절에서 먼저 강조하고, 절별 정보 흐름·소제목·표의 읽기 안내를 추가했다. 보안 조건→수행 영향→확인 사항→판단 갱신의 도식과 단계별 원문 연결을 구현했다. 1280×800·1440×900 모두 기존 133개 내용 단위, 8개 절·표 5개, 4단계 도식과 근거 열기·초점 복귀·읽기 확대·내려받기 검사가 통과했다. 화면을 다시 캡처해 확인했으며 가상 입력의 해석·미확정과 실제 분석 결과의 경계를 유지했다. 이 회차는 읽기 시안과 문서 변경이며 제품 테스트·실제 분석은 실행하지 않았다.
