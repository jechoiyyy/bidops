# 사전규격 심층검토 고도화 — 결정 기록

- 작성: 2026-09-22. 연결: [의도](intent.md) · [명세](spec.md) · [수정 계획](plan.md).
- 상태: **A안 본문 하나, Qwen 입력·출력·보고서 조립 개선 방향, 편집된 문서형의 시각적 구성을 사용자 확정(2026-09-22)**. 구현 진행과 운영 실행의 상태는 구분한다. 운영 모델 호출·정책 활성화·배포 승인은 포함하지 않는다.
- 새 구현 방식이 기존 정본을 바꿀 때는 해당 ADR·업무 규칙·계약을 함께 개정한다. 이 문서는 기존 ADR을 대체하지 않는다.

## 사용자 확정

### Qwen을 유지하면서 분석 경로와 보고서 조립을 함께 개선한다

- 선택: Qwen 결과 사용 경로와 수정 필요성을 설명한 뒤 사용자 지시 “이 방향으로 진행하면 될 것 같아”를 받았다. UI뿐 아니라 관련 회사자료 선택·분석 지시·출력 연결·검증·본문 조립을 함께 구현하는 방향이다.
- 범위: 기존 결과와 사람 의견을 보존하고 새 생성 의미를 버전으로 구분한다. 실제 모델 호출·운영 정책 교체·배포는 별도 운영 경계를 따른다.
- 현재 상태: 호출·저장·계약 구조의 구현 전 조사를 진행했다. 이어진 사용자의 시각적 편집 요청을 반영하여 읽기 시안을 갱신했다. 제품 코드 구현을 완료한 상태는 아니다.

### 편집된 문서형으로 핵심·상세의 위계와 정보의 연결을 표현한다

- 선택: 사용자 인터뷰 응답 “편집된 문서형, 핵심과 상세의 구분 + 정보의 연결”.
- 핵심·상세: 첫 절에서 판단을 바꾸는 조건을 먼저 강조하고 상세 설명을 이어 둔다. 절 제목·정보 흐름 안내·소제목·본문·표 설명의 글자 크기와 간격을 구분한다. 본문을 기본적으로 펼쳐 두며 원래 설명을 축약본으로 대체하지 않는다.
- 정보의 연결: 수행 조건의 대표 관계를 **문서 조건 → 회사에 미치는 영향 → 확인 사항 → 판단 갱신**의 네 단계로 표현한다. 각 단계의 근거를 열 수 있고 해석·미확정 조건을 명시한다. 확인되지 않은 위험 점수·비용·기간은 시각화를 위해 만들지 않는다.
- 시안 반영: [같은 본문을 읽는 화면](prototype/README.md)을 갱신했다. 8개 절·표 5개와 기존 문장·제목·표 셀 133개 단위는 모두 남는다. 보안 조건의 관계 도식은 가상 자료를 바탕으로 한 설명이며 실제 Qwen 산출물이 아니다.
- 제품 연결: 실제 보고서에서는 서버가 제공한 요구·영향·확인·판단 관계와 근거를 표시한다. 프런트에서 주장 역할이나 인과관계를 추정해 만들지 않는다. 다른 보고서 형식이나 별도 요약 보고서를 추가하는 결정이 아니다.

### A안의 설명형 본문 하나를 PoC 기준으로 삼는다

- 선택: 사용자 지시 “A안으로 진행하자. PoC단계라서 본문 하나만 먼저 완성해두는게 좋을 것 같아”에 따라 [설명형 본문](report.md)을 기준으로 삼는다. 별도 요약본·질문형·대조형 보고서나 혼합 형식은 추가하지 않는다.
- 이유: 원문 요구·회사 영향·근거·미확인·대응을 충분히 설명하면서 PoC에서 관리할 산출물을 하나로 집중한다. 앞선 웹 시안에서 드러난 내용 부족을 먼저 해결한다.
- 영향: 본문 안의 8개 절과 필요한 표·근거를 유지하고, 관련 조건의 상호 영향을 같은 본문에서 설명한다. 보고서 전체를 다른 형식으로 중복 생성하지 않는다. 기술적인 원문 연결·범위·숫자 검증을 생략하거나 한 번의 모델 호출을 강제하는 결정은 아니다.
- 산출물: `report.md`는 단일 본문 기준 예시, `report-source.md`는 작성·검증용 가상 입력이다. 후자는 별도의 실무 보고서가 아니다. 미채택 B·C 본문과 비교 문서는 정리하고 채택 근거를 이 결정에 남긴다.
- 경계: 형식 선택과 가상 본문 정리는 완료했다. 실제 문서의 보고서 생성·품질 검증과 웹 반영은 후속 작업이며 운영 모델 호출·배포 승인은 포함하지 않는다.

## 설계안 채택

### 결과 의미를 먼저 바로잡는다

- 선택: 사업 위험·근거 검증·업무 미확인·분석 범위·모델 품질·결과 기준 변화를 구별한다. 짧은 요약에서도 이 경계를 유지한다.
- 이유: 원문 근거가 충분한 위험도 현재 요약에서 빠질 수 있고, 시스템 사유가 업무 확인 항목에 섞인다.
- 영향: 보고서 조립·검증·두 화면의 요약을 함께 바꾼다. 출력 구조가 갖고 있지 않은 의미를 UI가 추정하여 만들지 않는다.

### 작은 신뢰성 수정과 새 분석 계약을 나눈다

- 선택: 직접 진입 배치·원문 동선·수정본 표시·초안 보호를 먼저 고친다. 영역 연결·위험 구조·검증 집계 등 의미 변경은 버전 있는 계약으로 진행한다.
- 이유: 당장 고칠 수 있는 읽기·작업 결함을 새 모델 실험 때문에 미루지 않으면서, 출력 의미는 생산자와 소비자가 함께 바꿔야 한다.
- 영향: 작은 UI 수정만 완료한 상태를 심층분석 품질 개선 완료로 보고하지 않는다. 구체적인 실행 순서는 plan이 소유한다.

### 과거 보고서를 보존하며 새 계약으로 이행한다

- 선택: 새 reader와 버전 구분을 먼저 준비한다. 새 의미는 새 report/stage 계약과 불변 생성 규칙에 기록하고 기존 보고서는 원 계약으로 읽는다.
- 이유: 기존 v1은 닫힌 schema다. enum·의미를 추가하면 구 소비자나 사람 수정 경로가 달라질 수 있다.
- 영향: v1/v2 reader·validator·API·타입·mock·이력을 함께 검증한다. 작성 시각으로 생성 규칙을 추정하지 않는다. DB migration은 필요한 관계·필드 검토 뒤 결정한다.

### 회사자료와 종합 근거를 해당 호출에서 확인할 수 있게 한다

- 선택: 요구사항과 관련 회사 fact·조건·예외·근거를 함께 전달한다. 종합 조각마다 참조하는 근거를 포함한다. 누락은 명시적으로 남긴다.
- 이유: 순번별 결합과 조각 전체의 근거 중복 제거는 실제 대조에 필요한 문맥을 빠뜨린다.
- 영향: 관련 자료 선택 기준·입력 예산·누락 이유를 기록하고 관련 근거를 얼마나 찾았는지도 평가한다. 세부 검색·분할 알고리즘은 결정 대기다.

### 이전 완료 결과와 최신 실행 상태를 함께 보여준다

- 선택: 이전 완료 보고서는 읽기 유지하고 재실행 진행/실패는 별도 표시한다. 문서 기준 변화는 원문 관계로 판단한다.
- 이유: 재실행 때문에 이전 판단 근거를 잃어서는 안 되며, 이전 성공만 보여 최신 실패를 숨겨서도 안 된다.
- 영향: 조회 계약을 분리·버전화한다. 과거 보고서를 현재 분석처럼 보이게 하지 않는다. 과거 revision에 새 의견을 쓰는 정책은 별도 결정한다.

### 실무 정보와 기술정보의 위치를 구분한다

- 선택: 사업 정보·조건·쟁점·다음 행동·원문을 먼저 배치한다. UUID·hash·모델/정책 세부 정보는 접힌 기술정보나 기존 운영 화면에 둔다.
- 이유: 기본 화면에서 실무 판단에 필요한 내용과 운영 진단 내용이 경쟁하고 있다.
- 영향: 품질 미측정·검증 실패·빠진 범위·이전 문서 기준은 기본 화면에 남긴다. 0921 공용 변경을 중복 구현하지 않는다.

### Qwen의 검증된 분석 결과를 재료로 쓰고 A안에 필요한 생성 경로를 수정한다

- 선택: [코드 경로 점검](qwen-analysis.md)에 따라 기존 Qwen의 사실·수치·근거를 활용하는 구조를 유지한다. A안의 회사 영향·이유·확인·판단 갱신 조건은 분석 입력·지시·출력 계약과 본문 조립에서 연결하며 프런트가 임의 생성하지 않는다.
- 이유: 현재 제품은 Qwen 결과를 사용하지만 영역별 첫 본문 선택·다른 영역의 결과 복제, 순번별 회사자료 결합, 조각별 근거 누락과 출력 제한이 충분한 설명을 방해할 수 있다.
- 영향: 모델 교체나 긴 자유 문장 한 번 생성부터 시작하지 않는다. 새 정책·계약·검증과 생성기를 함께 검토한다. 이번 웹 시안의 가상 본문은 실제 Qwen 출력이나 품질 검증의 근거가 아니다.

## 독립 검토 제안의 미채택·보정

| 검토한 대안 | 판단과 이유 | 대신 적용할 방향 |
|---|---|---|
| v1에 `note` enum을 추가하고 작성일로 생성 세대 구분 | 닫힌 계약의 호환 확장으로 볼 수 없음. 무근거 사실을 note로 우회할 위험도 있음 | 새 계약. 서버 상태 설명은 알려진 code·원천에서 생성 |
| 축약 회사 색인만 모델에 전달하고 나중에 근거 연결 | 근거의 존재가 실제 조건 충족 판단을 보증하지 않음 | 관련 조건·예외·근거를 같은 입력에 포함. 색인은 검색 보조로 검토 |
| 최신 묶음 ID가 다르면 낡은 결과로 확정 | 초안·실패·같은 원문인 경우까지 섞임 | 확정 원문 변화·준비 중·판단 불가 구별 |
| 조각별 기대 ID만 검사하거나 누락을 경고로 낮춤 | 전체 입력 누락이 숨겨질 수 있음 | 조각별 검사와 전체 inventory 대조 유지 |
| 모든 문서×모든 회사자료 호출 | 관련 없는 반복과 호출량 증가가 크며 근거 선택의 품질을 설명하지 못함 | 예산 내 관련 근거 연결과 누락 검사 |
| 모델 교체·역할별 분석부터 시작 | 결정적 조립·입력·표시 결함이 남아 모델 효과를 평가하기 어려움 | 현재 결함 수정 뒤 동일 입력·사람 정답으로 구조와 모델 평가 |

Fable의 지적을 모두 그대로 채택한 것은 아니다. 검토 결과의 원 분석 대조표와 코드 근거는 [plan.md](plan.md)에 보존되어 있다. 실제 모델 정확도나 운영 발생 빈도는 이번 코드 검토로 확인되지 않았다.

| 분석 호출 구조 | 기존 흐름 결함을 먼저 수정. 문서 단일/영역별 호출, 앞 단계 결과 활용 범위를 동등 입력으로 비교 | [기존 평가 계획](../0917_qwen-luna-deep-review/evaluation-plan.md)과 한 번만 결정. 새 실제 심층 호출 전 |
| 회사 근거 선택 방식 | 근거가 포함된 입력을 기본으로 하되 검색·영역 연결·분할 방식은 표본으로 선택 | 필요한 회사자료의 회수율·조건 보존·입력량. 새 정책 확정 전 |

| 과거 보고서에 새 의견 작성 | 기본 작업은 명시적으로 선택한 현재 보고서. 과거 의견은 열람 유지 | 기존 API의 역사 revision 의견 허용 목적 확인. 새 의견 계약 확정 전 |
| 실제 결과에 적용할 편집 규칙 | 편집된 문서형·핵심/상세 위계·조건 관계는 사용자 확정. 새 서버 결과에서 핵심과 관계를 표시할 필드 연결은 구현 때 확정 | 본문과 도식의 같은 claim·evidence 연결, 두 폭의 실제 결과 표시 검사 |
| 모델 품질·업무 효과 채택 기준 | 중요한 누락·왜곡을 차단하고 정확도·업무 시간·호출량을 함께 평가 | 사람 gold·대표 표본·수치 임계값·채택 주체. 참조 실행 전 |
| 조회 API와 영속 필드 | 버전 있는 조회 응답. 기존 JSONB·이력으로 관계를 정확히 읽을 수 있으면 재사용 | attempt↔report↔validation 관계와 구 소비자 조사. API/DB 구현 전 |

위 항목은 문서 작성의 중단 사유가 아니다. 기본안과 결정에 필요한 정보를 준비하고 해당 구현/실행 경계에서 확정한다. 기존 제약과 동일한 사항을 반복 승인받는 절차는 추가하지 않는다.

## 구현 시 확정한 선택 (2026-09-22)

- 기존 lean-v1은 그대로 두고 `analysis-policy-narrative-v2.json`을 명시적으로 등록·선택한다. v2 정책 전문을 immutable DB snapshot으로 보존한다. 자동 정책 전환·기존 결과 재생성은 하지 않는다.
- 새 역할·연결 필드는 stage/report의 JSON 정본에 저장한다. 공통 claim 행을 대조해 조립하므로 DB migration 없이 불변성과 버전 경계를 유지한다.
- 전체 보고서를 읽는 API와 최신 실행 API를 함께 사용한다. envelope를 새로 늘리는 대신 report 자체의 v2 discriminator와 기존 실행 상태를 분리해서 소비한다.
- 이번 PoC는 전체 문장·이유를 읽는 편집된 문서와 관계 링크를 구현한다. 표/도식으로 문장을 자동 축약하지 않는다. 기존 텍스트 예시의 표 다섯 개를 실제 자료와 무관하게 강제로 생성하지 않는다.
- 회사 근거 선택은 결정적 문자열 관련도 기반이다. 순번 결합을 없애되 의미 회수율이나 자격 판단의 정확성을 보장한다고 하지 않는다. 실표본 확인 후 필요하면 새 정책으로 검색 방식을 바꾼다.
- 전체 종합 입력 한도를 넘으면 실패한다. 무제한 prompt, 임의 생략, 마지막 부분 권고의 전체 승격은 허용하지 않는다. 큰 문서의 추가 계층 종합은 실측 후 별도 버전으로 결정한다.
- 코드·격리 검증과 운영 적용은 구별한다. 이후 사용자의 적용·품질 검증 요청으로 운영 배포와 참조 정책 선택·실제 Qwen 호출을 진행했다. [실제 검증 기록](../validation-runs/20260922-narrative-review/live-validation.md)에 결과를 남긴다.

## 실제 실행 후 검증 강도 조정 (2026-09-22)

사용자가 과도한 원문 일치 검사의 완화를 요청했다. 실제 실패 응답에서는 인용 8개 중
1개의 공백 차이와 축약 연도 확장 3건이 전체 결과를 차단했다. 모두 사실 왜곡으로
취급하는 것은 실무자가 내용을 읽고 판단하도록 돕는 목적에 맞지 않는다.

| 대상 | 결정 | 이유 |
|---|---|---|
| 공백·줄바꿈·따옴표·전각 ASCII | 고정 위치의 연속 원문에 유일하게 대응하면 원문 문자열로 연결 | 표시 차이로 전체 보고서를 막지 않음. 모델 응답 원본은 보존 |
| 원화 금액 단위 | 정확한 Decimal 환산값이 같으면 허용 | 84백만원과 84,000,000원은 같은 사실 |
| 축약 연도의 확장 | 해당 문장 옆 확인 사항으로 표시하고 생성 허용 | 세기를 자동 확정하지 않으면서 실무자가 판단 가능 |
| 다른 값·단위·부정 조건·출처/위치 | 기존 차단 유지 | 업무 판단을 바꾸거나 원문과 연결되지 않는 차이 |
| 한 원문 조각의 큰 후속 분석 | 입력 예산 내 여러 호출로 분할·누락 없이 합병 | 출력이 충실해졌다는 이유로 다음 단계가 실패하지 않도록 함 |
| 호출 사이 모델 로컬 UUID 중복 | 호출별 namespace에 결속, 내부 참조도 함께 변경 | 식별자 생성 문제와 업무 내용 검증을 분리 |

새 정책 파일이나 이전 snapshot을 덮어쓰지 않는다. 이번 변경은 입력 처리·결정적 검증·
표시 구현의 수정이다. 정책 지시나 생성 설정을 바꾸면 별도 불변 버전을 발행한다.
전체 종합의 입력 상한과 요구사항 누락 검사는 유지하며 큰 표본의 처리 가능성을
이번 작은 문서의 결과로 주장하지 않는다.

## 원문 대조 on/off 선택 (2026-09-22 사용자 확정)

사용자가 단일 문단 제한의 필요성을 재질문하고 검증 레이어 on/off를 요청했다.
선택 질문에 ‘권장대로’라고 답해 **원문 인용·숫자 대조만, 웹의 분석 설정에서 선택**을 확정했다.

- 단일 문단 제한은 필수가 아니다. page 위치의 인용은 고정 페이지의 원문 순서대로
  연속된 문단까지 허용한다. 페이지를 넘거나 중간 내용을 생략한 연결은 허용하지 않는다.
- 기본값은 켜짐이다. 새 분석/재실행에 선택을 전달하고 attempt 감사 기록으로 고정한다.
  조회·대기 중 설정 변경이나 환경 변경이 기존 실행/보고서의 의미를 바꾸지 않는다.
- 끄면 인용 일치·숫자의 근거 대조를 생략한다. 출처 접근 범위·원문 hash·JSON/참조·계산식
  재연산·입력 누락 검사는 유지한다. 모델 인용을 확인된 원문처럼 표시하지 않는다.
- 보고서에 ‘원문 대조 미실시’를 표시하고 실제 페이지와 대조할 수 있게 한다. 기존 검증
  상태는 계약 검사 결과이며 저장된 skip check로 원문 대조 상태를 별도 구분한다.
- 별도 전역 스위치나 migration 대신 실행별 입력·불변 감사·기존 validation checks를 사용한다.

실제 off 실행에서 회사 대조가 입력 안의 `considered_claim_ids`를 추가 반환하는 경우도
허용하도록 보완했다. 단순히 빈 배열이 아니라는 이유로 중단할 필요는 없다. 입력에 없는
주장, 회사 근거 ID를 주장 ID로 쓰는 참조 오류, 필요한 근거 연결 누락은 계속 거부한다.
스위치 적용과 실제 보고서의 내용 품질은 별도로 판정한다.
