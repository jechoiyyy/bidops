# A안 본문과 현재 Qwen 심층검토 경로의 관계

2026-09-22. 현재 코드와 저장소의 정책 파일을 읽어 확인했다. 운영 DB의 개별 분석 결과·활성 정책 행·모델 정확도는 이번에 조회하거나 측정하지 않았으며 실제 모델 호출도 하지 않았다.

**결론: 제품은 Qwen의 분석 결과를 실제 보고서 재료로 사용한다. 하지만 현재 결과를 화면에서 재배치하는 것만으로 A안의 충분한 설명을 보장할 수 없다. 보고서 조립과 함께 분석 입력·프롬프트·출력 계약·종합 방식을 수정해야 한다. Qwen 모델 자체를 교체해야 한다는 근거는 이번 확인에 없다.**

## 무엇을 사용하고 있는가

| 대상 | 입력과 결과 | 이번 확인의 의미 |
|---|---|---|
| 현재 제품의 심층검토 | 문서와 고정 회사자료 → 모델의 구조화된 주장·근거 → 검증·DB 저장 → 보고서 조립 → API → 화면 | Qwen 결과를 버리고 별도 수작업 보고서를 표시하는 구조가 아님 |
| 이번 A안 웹 시안 | 사람이 작성한 `report.md`와 가상 입력 `report-source.md`를 빌드 때 포함 | 실제 Qwen 결과를 연결한 화면이나 모델 품질 증거가 아님 |
| 목표 제품 | 검증된 분석 결과에서 A안의 설명형 본문 하나를 생성하고 원문·회사 근거를 연결 | 출력 형식 하나를 만드는 결정이며 모델 호출 한 번을 뜻하지 않음 |

저장소의 기본 분석 정책은 `qwen3.8-27B`다. 실제 작업은 시작 때 고정한 DB 정책의 `model_name`·프롬프트·회사 프로필을 사용하며, `deep_review` 용도의 공통 모델 클라이언트로 나간다. 따라서 기본 JSON 파일을 고치는 것만으로 이미 고정된 실행이나 운영 정책이 바뀌지는 않는다.

근거: [정책 파일](../../web/backend/app/deep_review/policies/analysis-policy-lean-v1.json), [정책 투영·모델 결합](../../web/backend/app/deep_review/services/deep_reviews.py) 255–265·438–466행 및 1423–1482행.

## 실제 처리 순서

1. **요구사항·평가 분석:** 확정 문서의 조각을 읽고 자격·요구사항·제출물·일정·배점을 추출한다.
2. **수행·위험·경제성 분석:** 문서 조각과 회사자료 일부를 함께 읽고 수행 방안·적합성·위험·금액을 분석한다.
3. **종합:** 앞 단계의 주장과 근거를 읽고 종합 결과·권고를 만든다.
4. **검증·저장:** 응답은 자유로운 완성 보고서가 아니라 `claims`, `evidence`, `unknowns`, `warnings` 등을 가진 JSON이다. 각 응답을 검증한 뒤 조각을 병합하고 주장과 근거를 저장한다.
5. **보고서 조립·표시:** 서버가 저장한 결과를 기존 13개 절의 보고서로 만든다. 프런트는 report API의 절·본문·표와 근거를 표시한다.

근거: [세 단계 실행](../../web/backend/app/deep_review/services/deep_reviews.py) 1484–1603행, [출력 계약](../../web/backend/app/deep_review/contracts/bidops.deep-review-stage.v1.json), [보고서 조립](../../web/backend/app/deep_review/services/reports.py) 468–498·660–740행, [report API](../../web/backend/app/deep_review/routers/reports.py) 223–226행, [화면 소비](../../web/frontend/src/pages/DeepReviewPage.tsx) 185–193·654–668행.

## 왜 화면 수정만으로 충분하지 않은가

| 확인한 코드 동작 | A안에 미치는 영향 | 수정할 부분 |
|---|---|---|
| 서버가 영역을 category 부분 문자열로 찾고, 없으면 `or claims`로 전체 주장을 사용함 | 결과가 없는 절에 무관한 내용이 들어가 설명의 의미가 달라질 수 있음 | 명시적 영역 연결. 결과가 없으면 이유·미분석 상태를 표시 |
| 여러 서술형 절의 본문에 `selected[0]["body"]`만 사용함 | Qwen이 여러 내용을 생성했어도 나머지 수행·위험·비용 설명이 본문에서 빠질 수 있음 | 관련된 모든 결과를 의미 순서대로 조립하고 문장별 근거 유지 |
| 2단계에서 문서 조각과 회사자료 조각을 같은 순번으로 결합함 | 회사에 관련 실적·자격 자료가 있어도 해당 요구를 분석하는 호출에는 없을 수 있음 | 요구별 관련 회사 근거·조건·기간·예외를 연결하고 부족한 자료를 명시 |
| 3단계의 근거를 여러 입력 조각 전체에서 한 번만 포함함 | 같은 근거를 쓰는 다음 조각에는 주장은 있으나 실제 인용 내용이 빠질 수 있음 | 각 호출이 참조하는 주장·근거를 그 호출 안에서 해석할 수 있게 구성 |
| 기본 지시는 조각당 주장·근거·미확인·경고를 각각 최대 8개로 생성하고 중요한 항목을 우선하도록 함 | 상세 조건·예외·영향 설명을 모두 담는 목표와 충돌할 수 있음 | 조각별 분석 범위와 출력 예산을 맞추고 전체 누락 검사 유지 |
| 기존 프롬프트는 분석 영역을 지시하지만 A안의 설명 관계를 명시적으로 요구하지 않음 | 사실·회사 영향·확인 사항이 각각 존재해도 서로 연결된 설명이 충분히 생긴다고 보장할 수 없음 | 사실·회사 근거·영향과 전제·확인할 일·판단 변경 조건의 연결을 요구 |
| 마지막 단계도 조각별로 호출되고 고정된 권고 값 한 개를 요구함 | 전체 조건 간 영향을 읽는 본문과 판단 갱신 조건이 자동으로 완성되는 구조가 아님 | 검증 결과 전체를 다루는 종합 범위와 본문 구성 규칙 정의 |

앞의 두 행은 **생성된 결과를 제대로 활용하지 못하는 문제**이고, 뒤의 행들은 **충분한 설명을 만들 입력·지시가 필요한 문제**다. UI에서 새 문장을 임의로 작성하여 둘을 메우지 않는다.

근거: [보고서 renderer](../../web/backend/app/deep_review/services/reports.py) 676–740행, [입력 분할](../../web/backend/app/deep_review/services/deep_reviews.py) 1001–1066행, [프롬프트 구성](../../web/backend/app/core/model_client.py) 406–473행. 조각당 8개는 프롬프트 지시이며 문서 전체 요구사항의 상한이나 JSON Schema의 `maxItems`가 아니다. `_policy_payload`는 현재 별도 `prompt_output_contract`를 전달하지 않으므로 이 기본 지시가 적용되는 경로다. 새 정책의 지시를 바꿀 때에는 정책 투영과 프롬프트 구성까지 함께 연결해야 한다.

## 기존 결과를 어디까지 재사용할 수 있는가

- 기존에 검증·저장된 사실, 수치, 자격·과업·평가·계약 조건, 회사 근거와 그 위치는 재사용할 수 있는 재료다. 과거 보고서·입력·사람 의견은 원래 버전으로 보존한다.
- 이미 적절한 영향·추론이 생성됐는데 조립 과정에서 빠졌다면 먼저 그 결과를 올바르게 보여주는 것으로 개선할 수 있다.
- 기존 결과에 영향의 전제, 관련 회사자료, 조건 간 관계가 없다면 UI만으로 이를 생성할 수 없다. 부족한 내용을 확인한 후 수정된 분석 경로가 필요하다.
- 실제 결과 표본을 대조하지 않았으므로 어느 정도를 재사용할 수 있는지의 비율이나 실제 누락 빈도는 아직 알 수 없다. 기존 v1을 새 A안의 품질 기준을 충족한 결과로 자동 승격하지 않는다.

## PoC에서 바꿀 범위와 유지할 범위

**유지:** 현재 Qwen 모델과 승인된 `deep_review` 전송 경계, 원문·회사자료의 버전 고정, 구조화 출력, 결정적 근거·수치 검증, 사람 의견·추적·최종 Go/No-Go 분리. 별도 B·C 보고서나 외부 모델 fallback은 추가하지 않는다.

**수정:** 관련 회사자료 선택·입력 분할, 분석 지시와 출력 예산, 영역·요구·근거·영향의 연결 계약, 종합 범위, A안 본문 조립·조회·표시. 호환성을 깨는 필드·의미는 새 계약·불변 정책으로 발행하고 기존 결과를 덮어쓰지 않는다.

본문을 자유로운 긴 Markdown 하나로 생성하도록 바꾸면 근거·미확인·검증 연결이 약해질 수 있다. PoC의 기본 방향은 **구조화된 분석 결과를 바탕으로 하나의 설명형 본문을 조립**하는 것이다. 자연스러운 해석·영향·다음 행동은 그 전 단계의 분석 결과에 존재해야 하며, renderer는 새로운 업무 사실을 만들어내지 않는다. 상세 stage/report 필드는 구현 전 버전 계약으로 확정한다.

## 구현 전 확인할 대표 사례

1. 같은 영역의 결과가 둘 이상인 기존/합성 입력에서 모두 본문에 나타나는지, 다른 영역에 잘못 복제되지 않는지 확인한다.
2. 요구와 회사자료의 순서를 바꿔도 같은 관련 근거가 제공되는지, 각 종합 조각의 참조 근거가 실제로 포함되는지 확인한다.
3. 분석 범위의 조건·예외를 추출했는지와 단순 ID 언급을 구분한다. 조각별 제한을 맞추려고 전체 누락 검사를 완화하지 않는다.
4. 실제 문서·회사자료와 A안 본문을 대조해 수행·평가·검수·계약·비용 설명이 근거에서 이어지는지 확인한다. 운영 결과 열람 범위와 새 모델 실행은 구분하며, 실제 호출은 기존 승인 경계를 따른다.

이번에 완료한 것은 코드 경로의 확인과 수정 범위 정리다. Qwen 호출부·정책·생성기·제품 화면의 변경이나 실제 분석 품질 검증을 수행한 것은 아니다. 작업 순서는 [plan.md](plan.md)를 따른다.
