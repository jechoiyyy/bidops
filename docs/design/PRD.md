|---|---|

| 대상 사용자 | 기획·사업개발 담당자(판정), 운영자(실행 감시) |

이 문서는 제품 요구사항을 다시 쓰지 않는다. 제품의 목적과 업무 규칙은 [`docs/PRD.md`](../PRD.md)와
[`docs/business-rules.md`](../business-rules.md)가 정본이며, 이 문서는 **그 업무를 화면에서
수행할 때의 요구사항**만 다룬다.

## 1. 판단 기준

BidOps는 조회 도구가 아니라 사람이 네 번 결정하는 파이프라인이다. 화면 요구사항은 이 네 결정을
기준으로 세운다.

| 결정 | 내용 | 규모와 주기 | 주 화면 |
|---|---|---|---|
| 결정 1 | 발주계획 후보 선별 | 3일 약 1,200건, 월·목 주 2회 | 발주계획 C-2 |
| 결정 2 | 심층 추적 승인 | 사전규격 단위 | 사전규격 상세 |
| 결정 3 | 공고 1차 판정과 담당자 리뷰 | 회차당 표본 약 120건 | 검토 대기열 |
| 결정 4 | 최종 입찰 Go/No-Go | 사업기회 단위, 되돌릴 수 없음 | 입찰 변경 비교 |

네 결정은 서로를 대신하지 않는다. 화면이 이 넷을 하나의 조작으로 합치는 설계는 요구사항 위반이다.

## 2. 정보구조 요구사항

### 2.1 1차 분류

사이드바 1차 분류는 **회차 검토**와 **누적 추적**이다. 담당자의 업무가 "이번 회차를 처리한다"와
"사업기회를 계속 따라간다"로 갈리기 때문이다. 기준과 운영은 그 아래 별도 묶음이다.

| 묶음 | 항목 | 비고 |
|---|---|---|
| 회차 검토 | 대시보드, 검토 대기열 | 회차 선택기가 항상 보인다 |
| 누적 추적 | 발주계획 C-2, 사전규격, 사업기회, 최종 Go/No-Go | 회차 선택기가 보이지 않는다 |
| 기준과 운영 | 판정 기준, 실행 상태 | 회차 선택기가 보이지 않는다 |

### 2.2 통합과 흡수

| 현재 | 이후 | 근거 |
|---|---|---|
| 회사 프로필 · 판정 정책 · 품질 게이트 · 검증 지표 | `판정 기준` 한 화면의 탭 | 편집 빈도가 낮고 서로를 참조하며 읽는 자료다 |
| 수집 실행 · 첨부 확보 · 상시 운영 · 산출물 감사 로그 | `실행 상태` 한 화면 | 대상 사용자가 담당자가 아니라 운영자다 |
| 마감 추적(`/deadlines`) | 검토 대기열의 저장된 뷰 | 정렬 하나가 메뉴 한 칸을 쓰고 있다 |
| 공고 판정 이력 · 담당자 리뷰 기록 | 검토 대기열의 탭 | 같은 데이터이고, 리뷰 기록은 미구현이다 |
| 입찰 변경 비교(메뉴 없음) | `최종 Go/No-Go` 최상위 항목 | 되돌릴 수 없는 결정이 가장 깊은 곳에 있다 |
| 심층 검토 보고서(메뉴 없음) | 사업기회 화면의 명시적 진입점 | 만든 뒤 다시 찾아갈 길이 필요하다 |

### 2.3 수용 기준

- 사이드바 항목은 모두 실제 화면으로 연결된다. 리다이렉트 항목과 미구현 안내 항목을 두지 않는다.
- 회차 선택기의 표시 여부가 1차 분류만 보고 예측 가능하다.
- 최종 Go/No-Go에 사이드바에서 한 번에 도달한다.

## 3. 판정 동선 요구사항

### 3.1 공통 규칙

판정이 필요한 모든 화면은 다음을 만족한다.

1. **목록과 상세가 같은 화면에 있다.** 한 건을 판정하기 위해 페이지를 옮기지 않는다.
2. **판정 입력이 상세 영역 안에 있다.** 저장 후 목록의 위치와 스크롤이 유지된다.
3. **다음 항목으로 이동하는 조작이 있다.** 저장과 이동을 한 흐름으로 처리한다.
4. **필터를 조합할 수 있고 조합을 저장할 수 있다.** 단일 선택 버튼으로 필터를 구성하지 않는다.
5. **결정 액션은 스크롤 위치와 무관하게 누를 수 있다.** 긴 상세 화면에서 헤더에 고정한다.

### 3.2 화면별 요구사항

**발주계획 C-2** — 결정 1

- 목록은 밀집 행이다. 한 행은 판정에 필요한 값만 담는다. 현재 카드가 담는 16개 필드 중 신호
  세부(BM25 rank·score·nearest capability, Qwen score·reason)는 상세 영역으로 옮긴다.
- 사람 피드백(relevance, priority, memo)을 목록 화면에서 저장한다.
- 운영 텔레메트리는 상세 영역의 별도 탭에 둔다. 판정 화면의 기본 표시에서 뺀다.
- 페이지 상단의 설명 블록은 접을 수 있다. 실행 상태는 한 줄로 요약하고 문제가 있을 때만 펼친다.
- `filtered_out`·`not_relevant`·`unknown`·`null`을 서로 바꾸어 표시하지 않는다.

**검토 대기열** — 결정 3

- 현행 구조를 유지한다. 이 화면이 판정 동선의 기준 구현이다.
- 필터 조합을 저장된 뷰로 남길 수 있게 한다(예: 우선 검토 + 첨부 미확보).
- 공고 판정 이력과 담당자 리뷰 기록을 탭으로 흡수한다.

**사전규격** — 결정 2

- 목록을 개요 검토 상태별 접이식 그룹으로 만든다. 그룹마다 건수를 표시한다.
- 사람 검토 필요·실패 그룹을 기본으로 펴고 완료 그룹은 접는다.
- 심층 추적 승인을 목록 화면에서 내릴 수 있게 한다.

**최종 Go/No-Go** — 결정 4

- 결정 대기 중인 사업기회 목록을 먼저 보여준다.
- 결정 액션을 헤더에 고정한다.
- 변경 항목(delta)을 반복 목록으로 보여주고 각 항목의 근거 위치를 연결한다.

**대시보드**

- 현행 구조를 유지한다.
- `지금 처리할 일` 스트립을 네 결정 전체로 확장한다. 회차 안의 세 항목뿐 아니라 C-2 검토일
  대기 건수, 사전규격 의견등록 마감, Go/No-Go 대기를 같은 자리에 올린다.

## 4. 표시 규칙

- `unknown`은 확인 대기, `null`은 값 없음이다. 둘을 빈칸이나 `0`으로 바꾸지 않는다.
- 적합성 등급 4값, 참여 준비 상태 4값, 개요 검토 상태 10값은 계약이 정의한 문자열 그대로 쓴다.
- 모델이 만든 수치와 요구사항은 원문 위치와 연결한다. 연결이 없으면 그 사실을 표시한다.
- 부분 산출물인 회차는 화면에서 그 사실을 알린다.
- 실패·미측정 상태를 성공이나 정상으로 보이게 하지 않는다.

## 5. 비기능 요구사항

| 항목 | 요구 |
|---|---|
| 색 모드 | 라이트 우선. 다크 모드는 이번 범위가 아니다 |
| 서체 | Pretendard 자체 호스팅 유지. 런타임에 외부 폰트 호스트를 부르지 않는다 |
| 외부 통신 | 화면 코드가 런타임에 외부로 나가는 경로를 만들지 않는다 |
| 접근성 | 키보드로 판정 동선을 끝까지 수행할 수 있다. 초점 표시가 보인다 |
| 반응형 | 노트북 폭에서 목록과 상세가 함께 보인다. 좁은 폭에서는 상세가 목록을 덮는다 |
| 회귀 | 화면 변경은 시각 기준선 갱신을 동반한다. 기준선 없는 변경을 병합하지 않는다 |

## 6. 범위 밖

- 다크 모드
- 로그인·역할 기반 권한(현재 사내망 접근 제한이 경계다)
- 알림
- 미구현 흐름의 신규 화면(준비·실패 재시작 화면 등)
- Astryx 전면 적용에 따른 프론트엔드 재작성
