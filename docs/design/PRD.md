데이터이며 운영 사실이나 확인된 회사 역량이 아니다.

## 1. 판단 기준

BidOps는 조회 도구가 아니라 사람이 네 번 결정하는 파이프라인이다. 화면 요구사항은 이 네 결정을
기준으로 세운다.

| 결정 | 내용 | 규모와 주기 | 주 화면 |
|---|---|---|---|
| 결정 1 | 발주계획의 추적 결정 | 3일 약 1,200건, 월·목 주 2회 | 발주계획 |
| 결정 2 | 심층 검토 실행 승인 | 사전규격 단위 | 사전규격 |
| 결정 3 | 공고 1차 판정의 예외 조치 | 회차 표본 약 120건 중 예외분 | 사업 추적 |
| 결정 4 | 최종 입찰 Go/No-Go | 사업기회 단위, 되돌릴 수 없음 | 최종 Go/No-Go |

네 결정은 서로를 대신하지 않는다. 화면이 이 넷을 하나의 조작으로 합치는 설계는 요구사항 위반이다.

결정 3은 사람이 회차 표본 120건을 전수 순회하는 작업이 아니다. 모델이 1차 판정을 만들고, 사람은
근거 없음·검증 실패·연결 불확실처럼 **예외로 표시된 건만** 사업 추적에서 처리한다. 표본 전체의
판정 결과는 읽기 전용 이력으로 남는다.

### 1.1 결정 1과 사람 판단 수정의 분리

발주계획 화면은 서로 다른 두 가지를 저장한다. 하나로 합치지 않는다.

| 조작 | 저장 대상 | 성격 |
|---|---|---|
| 추적 결정 | 사업기회의 추적 상태 | 결정 1 그 자체. 선택 즉시 append-only 이력을 남긴다 |
| 사람 판단 수정 | `relevance`·`priority`·메모 | 선택 사항. 별도 revision이며 모델 판단을 대신하지 않는다 |

일상 검토에서는 모델 판단을 그대로 쓰고 사람 판단 수정 영역은 접어 둔다. 사람 판단 수정은
적합성 등급, 참여 준비 상태, 추적 상태, 최종 Go/No-Go에 영향을 주지 않는다.

### 1.2 추적 상태의 표시 이름

화면 문구는 [`docs/business-rules.md`](../business-rules.md)가 정의한 상태 값에 1:1로 대응한다.
새 상태를 만들지 않는다.

| 업무 규칙 값 | 화면 표시 | 화면 조작 |
|---|---|---|
| `미선택` | `추적 결정 없음` | (없음 — 미선택은 종료가 아니다) |
| `계속 추적` | `추적 중` | `추적 시작` |
| `보류` | `보류` | `보류` |
| `종료` | `추적 종료` | `추적 종료` |

## 2. 정보구조 요구사항

### 2.1 1차 분류

사이드바 1차 분류는 **오늘의 업무**와 **탐색과 추적**이다. 오늘의 업무에는 회차를 보는 화면만
두고, 담당자가 사업기회를 계속 따라가는 화면은 모두 누적 축에 둔다. 기준과 운영은 그 아래 별도
묶음이다.

| 묶음 | 항목 | 회차 선택기 |
|---|---|---|
| 오늘의 업무 | 대시보드 | 보인다 |
| 탐색과 추적 | 발주계획, 사전규격, 사업 추적, 최종 Go/No-Go | 보이지 않는다 |
| 기준과 운영 | 판정 기준, 실행 상태 | 보이지 않는다 |

사이드바 항목은 16개에서 **7개**로 줄인다. 회차 축을 가진 화면은 대시보드와, 사업 추적 상세에서
여는 공고 판정 이력뿐이다. 공고 판정 이력은 사이드바 항목이 아니므로 사이드바만 보면 회차
선택기의 표시 여부가 예측된다.

### 2.2 통합과 흡수

| 현재 | 이후 | 근거 |
|---|---|---|
| 검토 대기열 | `사업 추적`으로 대체 | 한 사업기회가 회차마다 다른 행으로 나타나 같은 건을 여러 번 본다 |
| 사업기회 | `사업 추적`으로 이름과 구조 변경 | 목록의 기본 단위가 "다음 행동"이지 조회 대상이 아니다 |
| 마감 추적(`/deadlines`) | 사업 추적의 `조치 필요` 뷰 | 정렬 하나가 메뉴 한 칸을 쓰고 있다 |
| 공고 판정 이력 · 담당자 리뷰 기록 | 사업 추적 상세의 이력 탭 | 같은 사업기회의 이력이고, 리뷰 기록은 미구현이다 |
| 회사 프로필 · 판정 정책 · 품질 게이트 · 검증 지표 | `판정 기준` 한 화면의 탭 4개 | 편집 빈도가 낮고 서로를 참조하며 읽는 자료다 |
| 수집 실행 · 첨부 확보 · 상시 운영 · 산출물 감사 로그 | `실행 상태` 한 화면의 탭 4개 | 대상 사용자가 담당자가 아니라 운영자다 |
| 입찰 변경 비교(메뉴 없음) | `최종 Go/No-Go` 최상위 항목 | 되돌릴 수 없는 결정이 가장 깊은 곳에 있다 |
| 심층 검토 보고서(메뉴 없음) | 사업 추적 화면의 명시적 진입점 | 만든 뒤 다시 찾아갈 길이 필요하다 |

### 2.3 수용 기준

- 사이드바 항목은 모두 실제 화면으로 연결된다. 리다이렉트 항목과 미구현 안내 항목을 두지 않는다.
- 흡수된 화면의 옛 경로는 리다이렉트가 아니라 흡수한 뷰·탭의 정식 주소로 남는다. 현재
  `routes.tsx`에 등록된 경로(index 포함 26개) 중 어느 것도 404를 내지 않는다.
- 회차 선택기의 표시 여부가 1차 분류만 보고 예측 가능하다.
- 최종 Go/No-Go에 사이드바에서 한 번에 도달한다.
- 한 사업기회는 사업 추적 목록에서 한 행으로만 나타난다.

## 3. 판정 동선 요구사항

### 3.1 공통 규칙

판정이 필요한 모든 화면은 다음을 만족한다.

1. **목록과 상세가 같은 화면에 있다.** 한 건을 판정하기 위해 페이지를 옮기지 않는다.
2. **판정 입력이 상세 영역 안에 있다.** 저장 후 목록의 위치와 스크롤이 유지된다.
3. **다음 항목으로 이동하는 조작이 있다.** 저장과 이동을 한 흐름으로 처리한다.
4. **필터를 조합할 수 있고 조합을 저장할 수 있다.** 단일 선택 버튼으로 필터를 구성하지 않는다.
5. **결정 액션은 스크롤 위치와 무관하게 첫 화면에서 보인다.** 두 형태를 쓴다.
   - 목록·상세 분할 화면: 상세 pane 바닥에 고정한다. 목록 pane과 상세 pane은 각자 스크롤을 가둔다.
   - 단독 상세 화면: 헤더에 고정한다. 우측 레일은 이력과 연결만 담고 결정 액션을 두지 않는다.
6. **되돌릴 수 없는 입력 form은 헤더에 올리지 않는다.** 헤더에는 저장 버튼과 입력 위치로
   이동하는 조작만 두고, form은 본문에 둔다(최종 Go/No-Go).

### 3.2 화면별 요구사항

**발주계획** — 결정 1 · 시안 `Main`, `OrderPlanDetail`

- 상단은 `누적 데이터 · C-2 relevance 정책 · 회차 선택기 없음`을 한 줄로 밝히고, 실행 상태는
  배지 하나(성공·부분 성공·실패, 실행 ID 앞자리, 시각)로 요약한다. 상세는 `실행 상세`로 연다.
- 필터는 저장된 뷰 segmented(기본 보기 · 전체 · BM25 선정 제외 · 실패·거부), 모델 판단 selector,
  BM25 selector, 사람 판단 보정 selector, 제목·계획번호 검색, `현재 조합 저장`, `필터 초기화`로
  구성한다. 목록 머리글에 현재 조합의 의미(예: `BM25 선정 AND 모델 판단 관련`)와 건수를 쓴다.
- 기본 보기가 숨기는 것(BM25 선정 제외·비관련·실패)을 목록 바닥에 명시한다. 숨김을 부재로
  표시하지 않는다.
- 목록은 밀집 행이다. 한 행은 제목, BM25 선정·순위, 모델 판단, 사람 판단 유무, 기관·예산·계획
  시기만 담는다. 신호 세부(BM25 score·nearest capability, Qwen score·reason)는 상세의 `신호 세부`
  탭으로, 운영 텔레메트리는 `실행 기록` 탭으로 옮긴다.
- 상세 pane 바닥의 결정 액션은 `추적 시작` · `보류` · `추적 종료` · `이번 건 넘기기`이며, 선택
  즉시 이력을 기록하고 다음 발주계획으로 이동한다. 별도 저장 버튼을 두지 않는다.
- 추적 결정 영역은 미선택이 추적 종료가 아니라는 사실과, 추적 상태만 기록하며 모델 판단·적합성
  등급·참여 준비 상태를 바꾸지 않는다는 사실을 화면에 쓴다. 사유 selector와 담당자 감사 표식을
  함께 남긴다.
- 사람 판단 수정은 접힌 채로 두고, 열었을 때만 relevance·우선순위·메모를 새 revision으로
  기록한다. 상세 화면은 append-only 수정 이력을 revision 단위로 보여준다.
- `filtered_out`·`not_relevant`·`unknown`·`null`·`failed`·`rejected`를 서로 바꾸어 표시하지 않는다.

**사전규격** — 결정 2 · 시안 `PreSpecs`, `PreSpecDetail`

- 목록은 개요 검토 상태별 접이식 그룹이다. 상태 10값이 모두 그룹으로 나타나고 0건 그룹도
  숨기지 않는다. `사람 검토 필요`와 `실패`만 기본 펼침이고 나머지는 기본 접힘이다.
- 그룹 머리글에 건수를 표시하고, 행에는 제목·마감 D-n·상태 배지·기관·사전규격 번호를 둔다.
- 상세 pane에서 `심층 검토 실행`을 승인한다. 목록 아래에 별도 패널을 덧붙이지 않는다.
- 추적 상태가 발주계획에서 승계된 건은 승계 사실을 배지로 밝히고 추적 상태를 다시 묻지 않는다.
- 발주계획에 없던 **신규** 사전규격만 `추적 시작하고 심층 검토`를 한 번의 조작으로 제공한다.
  이때도 이력에는 추적 시작과 심층 검토 실행을 **별도 항목으로** 남긴다.
- `추적 종료`·`보류`는 사업 추적에서만 사람이 선택한다. 심층 검토가 정상 완료돼도 추적 상태를
  다시 묻지 않는다.
- 상세는 개요 검토 진행을 첨부 확보 → 문서 구조화 → 개요 입력 범위 확정 → 모델 실행 → 결과 검증
  단계로 보여주고, 이 결과가 적합성 등급·참여 준비 상태·심층 검토 실행 승인·최종 Go/No-Go를
  채우거나 대신하지 않는다는 사실을 같은 자리에 쓴다.
- 요구사항 항목은 근거 위치와 함께 보여주고, 근거 위치가 없는 항목은 그 자리에 남겨 강조한다.
  자동 보정하지 않는다.
- 첨부는 배포 가능·배포 불가를 구분하고, 배포 불가 사유(예: 압축 내부 확인 실패)를 함께 쓴다.

**사업 추적** — 결정 3 · 시안 `Opportunities`, `Queue`

- 목록의 기본 단위는 사업기회이며 한 사업기회는 한 행으로만 나타난다. 구역은 `조치 필요` ·
  `추적 중` · `보류` · `추적 종료` segmented로 나눈다.
- `조치 필요`는 이미 등록된 사업기회의 다음 행동이다. 미선택 원본을 이 목록에 넣지 않는다.
- 행 배지는 추적 상태와 다음 행동(예: `조치 필요 · 심층 검토 실행`, `조치 필요 · Go/No-Go`)을
  함께 보여준다.
- 상세 탭은 `연결 레코드` · `추적 이력` · `시스템 신호`다. 연결 레코드는 발주계획·사전규격·
  입찰공고·심층 검토를 각각의 화면으로 연결하고, 없는 것은 `아직 게시되지 않음`·`실행 승인 전`
  처럼 상태 문구로 남긴다. 빈칸으로 두지 않는다.
- 시스템 신호는 보조 정보다. 탭 집계나 사람의 추적 결정을 자동으로 만들지 않는다.
- 추적 상태 변경은 접힌 채로 두고, 열었을 때만 보류·추적 종료와 **필수 사유**, 담당자 감사
  표식을 새 revision으로 기록한다.
- 공고 판정 이력은 사업 추적 상세에서 여는 **읽기 전용** 화면이다. 회차 선택기를 갖고, 저장된
  뷰(전체 · 마감 임박 · 검증 예외 · 사람 리뷰 있음)와 등급·참여 준비 상태 필터를 제공하며,
  판정 근거·판정 이력·리뷰 기록을 탭으로 보여준다. 판정 근거의 각 항목은 원문 위치와 연결하고,
  연결이 없으면 `근거 위치 없음`을 그 자리에 남긴다.
- 현재 검토 대기열이 제공하는 리뷰 저장 경로를 **삭제하지 않는다.** 사업 추적의 예외 작업으로
  옮기며, 옮길 경로가 동작하기 전에는 공고 판정 이력을 읽기 전용으로 바꾸지 않는다.

**최종 Go/No-Go** — 결정 4 · 시안 `GoNoGo`, `BidDelta`

- 결정 대기 중인 사업기회 목록을 먼저 보여주고, 과거 기록을 덮어쓰지 않는 결정임을 밝힌다.
- 목록 행에는 등급·참여 준비 상태·변경 건수를 둔다. `변경 비교 결과 없음`도 값으로 표시한다.
- 변경 항목(delta)은 범주별 반복 목록으로 보여주고 각 항목의 근거 위치를 연결한다. 근거 위치가
  없는 항목은 `근거 없음`으로 표시하고 숨기지 않는다.
- 중요 변경·비중요 변경·`확인 필요 · 중요도 미확인`을 구분한다. 확인 필요를 변경 없음으로
  해석하지 않는다.
- 비교 기준(기준 사전규격과 대상 입찰공고, 문서 묶음 상태, 계산 시각과 요청 ID)을 상세에 남긴다.
- 헤더에는 `결정 저장` · `결정 입력으로 이동` · `비교 재계산`만 두고, 최종 결정 form은 본문에
  둔다. form은 Go·참여 / No-Go·불참 두 값과 담당자 claimed name(필수), 결정 이유(필수)를 받는다.
- 보류는 최종 결정 값이 아니다. 결정하지 않으면 기록을 만들지 않는다.
- 저장 조건(계산 완료 비교만 결정 가능, 확인 필요 잔여 건수, 이 결정이 등급·준비 상태·심층 검토
  실행 승인을 대신하지 않음)을 form 바로 위에 쓴다.
- 결정은 append-only로 기록하며, current 결정이 stale이 되면 재검토로 표시한다.

**심층 검토 보고서** — 시안 `DeepReview`

- 모델 종합 판단, 참여 준비 상태, 미확인 사항, 보고서 revision을 상단 카드 4개로 요약한다.
- 모델 제안이며 사람 확정 전이라는 사실을 헤더에 쓴다. 정상 완료된 심층 검토가 추적 상태를
  다시 묻지 않는다는 사실도 같은 자리에 쓴다.
- 결정 카드 요약은 항목·내용·근거·검증 결과 표로 두고 `검증됨`·`근거 없음`·`불일치`를 구분한다.
- Validation 실패는 숨기지 않고 실패 블록으로 남기며 `원문에서 확인`과 `새 attempt로 재시도`를
  제공한다. 자동 보정하지 않는다.
- 수정본은 기존 보고서를 덮어쓰지 않고 새 immutable revision으로 append-only 저장하며 담당자
  claimed name을 필수로 받는다.

**대시보드** — 시안 `Dashboard`

- 회차 선택기를 갖는 유일한 사이드바 항목이며 회차 데이터는 읽기 전용임을 밝힌다.
- `지금 결정할 일` 스트립은 네 결정 전체를 담고 각각 해당 화면으로 이동한다: 발주계획·추적 결정,
  사전규격·심층 검토 승인, 예외 조치·연결·실패(사업 추적), 최종 입찰 Go/No-Go.
- 회차 진행(수집 → 표본 선정 → 1차 판정 → 담당자 리뷰)과 적합성 등급 분포, 검증 상태를 보여준다.
- 검증 상태는 계산 불가·미확인·값 없음·0을 구분해 표시하고, 계산 불가를 0으로 바꾸지 않는다.
- 검증 실패 건수는 사람 검토로 보내며 자동 보정하지 않는다는 사실을 함께 쓴다.

**판정 기준** — 시안 `Criteria`

- 회사 프로필 · 판정 정책 · 품질 게이트 · 검증 지표를 탭 4개로 통합한다. 누적 기준이며 회차
  선택기가 없다.
- 회사 역량은 근거와 확인 상태(확인 완료 · 부분 확인 필요 · 확인 필요 · 해당 없음)를 함께
  보여준다. 확인되지 않은 역량·자격·실적을 추정하지 않는다.
- 이 화면이 정하지 않는 것(등급 4값, 참여 준비 상태 4값, 심층 검토 실행 승인, 최종 Go/No-Go)을
  화면에 명시하고, 기준 편집이 기존 판정을 소급해 바꾸지 않는다는 사실을 쓴다.
- 활성화 대기 정책은 차단 상태와 차단 사유를 보여준다. 품질 게이트 미충족은 해당 탭으로 연결한다.

**실행 상태** — 시안 `RunStatus`

- 실행 · 첨부 확보 · 상시 운영 · 산출물 감사 로그를 탭 4개로 통합한다. 운영자 화면이며 회차
  선택기가 없다.
- 실행 표는 여러 회차를 한 표에 담고 상태·실행 ID·source run·시작·소요·산출물을 보여준다.
- 선택한 실행의 운영 텔레메트리(`model_digest`, token 수, `duration_ms`, error code)를 이 화면에
  남긴다. 판정 화면의 기본 표시에서 뺐을 뿐 삭제하지 않았다는 사실을 함께 쓴다.
- 스케줄러와 상시 운영의 기본값은 비활성이며, 승인 조합 불일치 상태에서는 켤 수 없다. 앱
  startup이 migration·seed·정책 활성화·모델 호출을 수행하지 않는다는 사실을 같은 자리에 쓴다.

**상세 공통 골격** — 시안 `DetailSkeleton`

- 사전규격 상세 · 발주계획 상세 · 입찰 변경 비교 세 화면은 같은 골격을 쓴다: 요약 헤더 →
  헤더에 고정한 상태 배지와 결정 액션 → 본문 반복 목록 → 우측 이력·연결 레일.
- 우측 레일은 이력과 연결된 화면만 담는다. 결정 액션을 우측 레일에 두지 않는다.

## 4. 표시 규칙

- `unknown`은 확인 대기, `null`은 값 없음이다. 둘을 빈칸이나 `0`으로 바꾸지 않는다. `계산 불가`도
  별도 상태이며 `0`으로 표시하지 않는다.
- 적합성 등급 4값, 참여 준비 상태 4값, 개요 검토 상태 10값, 추적 상태 4값은 계약이 정의한
  문자열 그대로 쓴다. 화면 표시 이름은 §1.2의 대응만 허용한다.
- 등급은 심각도가 아니라 우선순위 순서다. 의미색(성공·위험)에 싣지 않고 accent 한 색의 농도
  4단으로 순서만 나타낸다. `판정 없음`은 다섯 번째 등급이 아니라 아직 판정하지 않음이므로 무채색
  으로 따로 둔다. 4단의 실제 값은 §4.1의 등급 ramp다. 농도만으로는 인접 단이 구분되지 않으므로
  등급 표시는 **항상 텍스트 라벨을 동반한다.** 색만으로 등급을 나타내는 표시를 만들지 않는다.
- 모델이 만든 수치와 요구사항은 원문 위치와 연결한다. 연결이 없으면 `근거 위치 없음`을 그 자리에
  표시하고 숨기지 않는다.
- 부분 산출물인 회차는 화면에서 그 사실을 알린다.
- 실패·미측정 상태를 성공이나 정상으로 보이게 하지 않는다. 실패는 사람 검토로 보내고 자동
  보정하지 않는다.
- 사람이 남기는 기록은 append-only다. 기존 revision을 덮어쓰지 않는다.

### 4.1 색 사용 규칙

색은 무드보드 [`moodborad.jpg`](moodborad.jpg)의 5색 anchor에서 나온다([ADR-0047](ADR.md)).
화면은 이 값을 직접 쓰지 않고 **테마 토큰만 읽는다.** `:root`나 화면 CSS에서 `--color-*`를
재정의하지 않는다.

| 무드보드 anchor | 역할 | 토큰 |
|---|---|---|
| `#D4CDCB` warm greige | 본문 canvas 계열과 구분선 | `--color-background-body`(`#F2F0EF`) · `--color-background-muted`(`#E7E4E2`) · `--color-border`(`#D4CDCB`) |
| `#8D8F8E` cool gray | 비텍스트 보조 요소 전용 | `--color-icon-*` 보조값 · disabled 표시 |
| `#5B687C` slate blue | accent와 등급 ramp의 기준색 | `--color-accent` · `--color-icon-accent` · `--color-text-accent` |
| `#161B2F` deep navy | 사이드바 surface | `--color-background-inverted` (Astryx core 토큰; 사이드바 본문은 `--color-nav-text` = `#D4CDCB`) |
| `#17181F` near-black ink | 본문 텍스트 | `--color-text-primary` |

카드·상세·팝오버 surface는 흰색이고 greige canvas 위에 뜬다. 보조 텍스트는 `#3C4452`
(slate + ink)이며 무드보드 anchor를 그대로 쓰지 않는다.

`--color-nav-text`는 Astryx 토큰 이름이 아니라(`TokenName`이 닫힌 union) 프로젝트 토큰이다.
셸 bridge 안에서 `--color-on-dark` 기반으로 유지하며, bridge는 새 색 값을 만들지 않으므로 위
규칙에 어긋나지 않는다.

**적합성 등급 ramp** — slate 농도 4단이며 의미색이 아니다. 토큰은
`web/frontend/src/themes/bidops/grade-ramp.css` 의 `--bo-grade-1`~`4`·`--bo-grade-none` 과
각각의 라벨 색 `--bo-on-grade-*` 다. 테마 정의가 아닌 프로젝트 토큰인 이유는
[ADR-0047](ADR.md) §3에 있다.

| 단계 | 배경 | 라벨 | 대비비 |
|---|---|---|---|
| 1단(최우선) | `#2F3A4C` | `#FFFFFF` | 11.47 |
| 2단 | `#5B687C` | `#FFFFFF` | 5.65 |
| 3단 | `#93A0B0` | `#17181F` | 6.65 |
| 4단 | `#D3D9E1` | `#17181F` | 12.45 |
| `판정 없음` | `#E5E5E5` | `#262626` | 12.01 |

화면은 이 ramp를 직접 읽지 않고 `Badge`의 등급 변형(`.badge-grade-1`~`4`)과 목록 행 레일
(`.rail-grade-*`)을 통해 쓴다. 그 두 곳이 `--bo-grade-*`를 읽는 유일한 자리이며, 등급 변형은
라벨이 비면 계약의 기본 라벨을 채워 색만으로 등급이 표시되지 않게 한다(단계 B).

**하지 않는 것.**

- 무드보드로 **의미색을 만들지 않는다.** 성공·부분 성공·실패·경고·`계산 불가`는 테마의
  categorical 팔레트에서 가져온다. 무드보드 톤에 맞추려고 실패·미측정의 색을 낮추지 않는다.
- 등급 ramp가 slate이므로 **상태 표시에 blue 계열을 쓰지 않는다.** 상태는 green(성공) ·
  yellow·orange(부분 성공·경고) · red(실패) · gray(미측정·`계산 불가`)만 쓴다.
- `#8D8F8E`를 **텍스트로 쓰지 않는다.** 흰 배경 3.25, greige canvas 위 2.87, greige anchor 위
  2.08로 AA에 미달한다. 흰 surface 위 비텍스트 요소(3.25)와 사이드바 위 보조 텍스트(5.24)로만
  쓰고, greige 계열 면 위에서는 쓰지 않는다.
- 대비비가 anchor를 이긴다. 텍스트는 4.5:1, 컴포넌트를 식별하는 비텍스트 요소는 3:1 이상이며,
  새 값이나 배지 조합을 추가할 때 대비 검사(`npm run test:contrast`)를 통과해야 한다. 카드
  테두리·구분선은 장식이므로 3:1 대상이 아니다.
- 색은 테마가 정하고 화면 CSS는 읽기만 한다. **예외는 이행용 token bridge 하나**로,
  `styles/shell-relaxed.css`가 legacy 이름을 테마 토큰에 잇기만 하며 새 색 값을 만들지 않는다
  ([ADR-0047](ADR.md) §1). Tailwind `@theme`은 `:root`로 방출돼 테마를 이기므로 디자인 시스템과
  이름이 겹치는 토큰을 거기에 두지 않는다([ADR-0047](ADR.md) §4-1).
