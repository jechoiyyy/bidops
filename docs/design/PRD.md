캔버스 `사전규격 상세 시안`의 첫 페이지(`A · 브리핑형 · 구현 목표판`)다.

**헤더 카드.** 칩 줄(`사전규격 · 신규/추적`, 의견등록 마감 긴급도, `SW사업대상`, 구분) →
공고명 20px → 기관·공식 사전규격번호·복사·원문 URL 메타 줄(14px) → PDF 기반 개요의 첫 문장과
PDF 쪽 링크를 담은 `사업 개요` 요약 띠 순서다. 오른쪽에는 `추적 결정 · {상태}` 칩과
`목록으로 돌아가기`만 둔다. **헤더에는 버튼도 입력도 두지 않는다.** 번호는 projection 또는
lifecycle의 동일 필드만 사용하며 내부 PK를 대신 표시하지 않는다. 원문은 API가 제공한 유효한
절대 HTTP(S) URL만 새 탭으로 열고, 없거나 유효하지 않으면 안내한다. 현재 사전규격 수집기는
상세 URL을 null로 둔다. 첨부 주소나 추정 URL로 대체하지 않는다.

**추적 결정 카드.** 헤더 바로 아래, `<header>` 밖의 카드 한 장에 선택 사유 드롭다운(기타는
직접 입력) · 담당자 이름 · `추적 시작`을 한 줄로 둔다. 폼이 자기 저장 버튼을 가지며 목록 화면의
공용 폼과 같은 동작이다. 카드 아래 캡션에 추적 시작이 무엇을 계속 확인한다는 뜻인지,
`보류`·`추적 종료`는 사업 추적에서 변경한다는 것, 입찰 참여 여부는 최종 Go/No-Go에서
결정한다는 것을 쓴다([ADR-0046](ADR.md) 결정 6은 그대로다). 승계했거나 이미 결정한 사업은
폼 대신 현재 상태와 해당 사업 추적 링크를 보여준다. 입력·담당자 기억·저장 오류 처리·이동
경고는 기존 공용 폼을 재사용한다.

**팩트 스트립 6칸.** 사업 예산 · 의견등록 마감 · 게시 · 구분(+SW사업대상) · 적합성 등급(등급
출처) · 첨부 원문 건수다. 구조화 필드만 쓰고 모델 문장을 파싱한 칸은 두지 않는다.

**본문 2열.** 왼쪽은 읽기 열, 오른쪽은 400px 판단 열이며 **오른쪽 열은 sticky가 아니다.**

- 왼쪽: `검토 요약`(v1 개요의 `사업 핵심`·검증 경고·대기/오류 상태) → `무엇을 만들어야 하나`
  (PDF 기반 v4 개요의 주요 과업(번호 마커)·사업 규모와 일정·핵심 조건·검토 포인트이며 항목마다
  `PDF n페이지 ↗` 근거 링크) → `지켜야 할 조건`(v1 조건이 있을 때만) → `첨부 문서·근거`
  (v1 근거 목록과 원문 블록 뷰어) → `문서 준비와 심층 검토 실행`(자동 준비 4단계 → 문서 준비
  패널 → 첨부 원문 취득 집계이며 **접지 않는다**) → 접힌 `처리 이력과 실행 정보`(고정 입력과
  식별 정보·해시·실행 이력·이전 개요 결과·검토 범위와 실행 정보). 개요·v4 실행·회사 핏·문서
  묶음 가운데 실패나 사람 확인 상태가 있으면 이력은 기본으로 열린다.
- 오른쪽: `현재 판단`(개요 권고와 품질 표식, 회사 핏 판정·품질 표식·요약, 현재 v4 개요 실행,
  고정 입력 상태, 접힌 품질·검증 정보, 추적 상태·자동 준비) → `확인이 필요한 것 N`(개요 검토
  미확인 항목은 이유·확인 방법을 항상 펼치고, PDF 개요 추가 확인 사항과 회사 핏 확인할 사항을
  잇는다. N은 세 목록 길이의 합이다) → `회사 업무 부합 여부`(판단 사유·근거·실행 정보는 기본
  접힘, 자동 심층 검토 안내, 이전 판정).

검증 실패 경고는 해당 결과 자리에 함께 표시한다. 개요 API에 확인 항목과 근거의 개별 연결이
없으므로 임의로 짝짓지 않고 근거 목록으로 이동한다. 본문 14px·보조 12px를 유지한다.

**없앤 것.** 헤더의 `검토 요약`·`첨부 문서`·`처리 이력` 이동 버튼, 오른쪽 sticky 결정 패널과
그 바닥의 저장 버튼, 헤더의 게시 시각이다. 게시 시각은 팩트 스트립의 한 칸으로 옮겼다.
등급 라벨과 현재 추적 상태 텍스트는 화면에 각각 한 번만 나온다.

**시안과 의도적으로 다른 것.** 시안 원안의 계약 방식·대금·하자·보고 팩트 칸은 모델 문장을
파싱해야 하므로 구현하지 않는다. `보류` 버튼을 두지 않는다. 과업에 굵은 제목을 붙이지 않고
서버 문장을 그대로 쓴다. 운영 정보는 지우지 않고 본문 하단으로 옮긴다.

이 배치는 라벨·상태 enum·REST 계약·저장 API·업무 규칙을 바꾸지 않는다. 회사 핏 `unknown`
라벨은 `판단 보류 · 정보 부족` 그대로다. 조회 실패를 판정 없음·미선택·묶음 없음으로 바꾸지
않고 목록 복귀 시 URL 필터를 보존한다.

시안 HTML의 CSS는 `.ps-record` 범위의 `.ps-*` 클래스로 1:1 이식한다. 색은 전부 `bidops` 테마
토큰이고, 반지름과 17px 글자는 앱 루트 글꼴이 14px이라 rem 토큰이 px 시안과 어긋나므로
spacing 토큰에서 파생한 `.ps-record` 범위 별칭으로 만든다. raw hex·`@media`·`--color-*`
재정의를 두지 않는다.

대체된 2026-09-08 시안과 그 검증용 HTML·TSX/CSS·캡처는 저장소 밖
`bidops-prespec-detail-ux-20260908`과 `bidops-prespec-detail-ux-implementation-20260908`
패키지에 남아 있으며 현재 구현 기준이 아니다.

## 1. 판단 기준

BidOps는 조회 도구가 아니라 사람이 네 번 결정하는 파이프라인이다. 화면 요구사항은 이 네 결정을
기준으로 세운다.

| 결정 | 내용 | 규모와 주기 | 주 화면 |
|---|---|---|---|
| 결정 1 | 발주계획의 추적 결정 | 3일 약 1,200건, 월·목 주 2회 | 발주계획 |
| 결정 2 | 심층 검토 실행 승인 | 사전규격 단위 | 사전규격 |
| 결정 3 | 공고 1차 판정의 예외 조치 | 회차 표본 약 120건 중 예외분 | 사업 추적 |
| 결정 4 | 최종 입찰 Go/No-Go | 사업기회 단위, 되돌릴 수 없음 | 최종 Go/No-Go |

네 결정은 서로를 대신하지 않는다. 화면이 이 넷을 하나의 조작으로 합치는 설계는 요구사항 위반이다.

결정 3은 사람이 회차 표본 120건을 전수 순회하는 작업이 아니다. 모델이 1차 판정을 만들고, 사람은
근거 없음·검증 실패·연결 불확실처럼 **예외로 표시된 건만** 사업 추적에서 처리한다. 표본 전체의
판정 결과는 읽기 전용 이력으로 남는다.

### 1.1 결정 1과 사람 판단 수정의 분리

발주계획 화면은 서로 다른 두 가지를 저장한다. 하나로 합치지 않는다.

| 조작 | 저장 대상 | 성격 |
|---|---|---|
| 추적 결정 | 사업기회의 추적 상태 | 결정 1 그 자체. 선택 즉시 append-only 이력을 남긴다 |
| 사람 판단 수정 | `relevance`·`priority`·메모 | 선택 사항. 별도 revision이며 모델 판단을 대신하지 않는다 |

일상 검토에서는 모델 판단을 그대로 쓰고 사람 판단 수정 영역은 접어 둔다. 사람 판단 수정은
적합성 등급, 참여 준비 상태, 추적 상태, 최종 Go/No-Go에 영향을 주지 않는다.

### 1.2 추적 상태의 표시 이름

화면 문구는 [`docs/business-rules.md`](../business-rules.md)가 정의한 상태 값에 1:1로 대응한다.
새 상태를 만들지 않는다.

| 업무 규칙 값 | 화면 표시 | 화면 조작 |
|---|---|---|
| `미선택` | `추적 결정 없음` | (없음 — 미선택은 종료가 아니다) |
| `계속 추적` | `추적 중` | `추적 시작` |
| `보류` | `보류` | `보류` |
| `종료` | `추적 종료` | `추적 종료` |

## 2. 정보구조 요구사항

### 2.1 1차 분류

사이드바 1차 분류는 **오늘의 업무**와 **탐색과 추적**이다. 오늘의 업무에는 회차를 보는 화면만
두고, 담당자가 사업기회를 계속 따라가는 화면은 모두 누적 축에 둔다. 기준과 운영은 그 아래 별도
묶음이다.

| 묶음 | 항목 | 회차 선택기 |
|---|---|---|
| 오늘의 업무 | 대시보드 | 보인다 |
| 탐색과 추적 | 발주계획 | 수집 회차 선택 (2026-09-07 사용자 요청) |
| 탐색과 추적 | 사전규격, 사업 추적, 최종 Go/No-Go | 보이지 않는다 |
| 기준과 운영 | 판정 기준, 실행 상태 | 보이지 않는다 |

사이드바 항목은 **7개**다. 대시보드·공고 판정 이력 외에 발주계획은
2026-09-07 사용자 요청에 따라 수집 회차 선택을 제공한다. 선별 전 데이터도 조회하기 위한
범위 선택이며 사업기회의 추적 상태와 사람 결정은 누적 정본을 유지한다.

### 2.2 통합과 흡수

| 현재 | 이후 | 근거 |
|---|---|---|
| 검토 대기열 | `사업 추적`으로 대체 | 한 사업기회가 회차마다 다른 행으로 나타나 같은 건을 여러 번 본다 |
| 사업기회 | `사업 추적`으로 이름과 구조 변경 | 목록의 기본 단위가 "다음 행동"이지 조회 대상이 아니다 |
| 마감 추적(`/deadlines`) | 사업 추적의 `조치 필요` 뷰 | 정렬 하나가 메뉴 한 칸을 쓰고 있다 |
| 공고 판정 이력 · 담당자 리뷰 기록 | 사업 추적 상세의 이력 탭 | 같은 사업기회의 이력이고, 리뷰 기록은 미구현이다 |
| 회사 프로필 · 판정 정책 · 품질 게이트 · 검증 지표 | `판정 기준` 한 화면의 탭 4개 | 편집 빈도가 낮고 서로를 참조하며 읽는 자료다 |
| 수집 실행 · 첨부 확보 · 상시 운영 · 산출물 감사 로그 | `실행 상태` 한 화면의 탭 4개 | 대상 사용자가 담당자가 아니라 운영자다 |
| 입찰 변경 비교(메뉴 없음) | `최종 Go/No-Go` 최상위 항목 | 되돌릴 수 없는 결정이 가장 깊은 곳에 있다 |
| 심층 검토 보고서(메뉴 없음) | 사업 추적 화면의 명시적 진입점 | 만든 뒤 다시 찾아갈 길이 필요하다 |

### 2.3 수용 기준

- 사이드바 항목은 모두 실제 화면으로 연결된다. 리다이렉트 항목과 미구현 안내 항목을 두지 않는다.
- 흡수된 화면의 옛 경로는 리다이렉트가 아니라 흡수한 뷰·탭의 정식 주소로 남는다. 현재
  `routes.tsx`에 등록된 경로(index 포함 26개) 중 어느 것도 404를 내지 않는다.
- 회차 선택기의 표시 여부가 1차 분류만 보고 예측 가능하다.
- 최종 Go/No-Go에 사이드바에서 한 번에 도달한다.
- 한 사업기회는 사업 추적 목록에서 한 행으로만 나타난다.

## 3. 판정 동선 요구사항

### 3.1 공통 규칙

판정이 필요한 모든 화면은 다음을 만족한다.

1. **목록과 상세가 같은 화면에 있다.** 한 건을 판정하기 위해 페이지를 옮기지 않는다.
2. **판정 입력이 상세 영역 안에 있다.** 저장 후 목록의 위치와 스크롤이 유지된다.
3. **다음 항목으로 이동하는 조작이 있다.** 저장과 이동을 한 흐름으로 처리한다.
4. **필터를 조합할 수 있고 조합을 저장할 수 있다.** 단일 선택 버튼으로 필터를 구성하지 않는다.
5. **결정 액션은 스크롤 위치와 무관하게 첫 화면에서 보인다.** 두 형태를 쓴다.
   - 목록·상세 분할 화면: 상세 pane 바닥에 고정한다. 목록 pane과 상세 pane은 각자 스크롤을 가둔다.
   - 단독 상세 화면: 기본은 헤더에 고정한다. 최종 Go/No-Go 변경 검토는 오른쪽 결정 form의
     바닥에 저장·확인 액션을 두고 왼쪽 근거 읽기 영역과 별도로 유지한다. 사전규격 개별 상세는
     2026-09-09 브리핑형에서 헤더 바로 아래 `<header>` 밖의 추적 결정 카드가 입력과 저장을
     함께 갖는다. 헤더에는 상태 칩만 두고 입력 form을 올리지 않으므로 규칙 6과 어긋나지 않는다.
6. **되돌릴 수 없는 입력 form은 헤더에 올리지 않는다.** 헤더에는 저장 버튼과 입력 위치로
   이동하는 조작만 두고, form은 본문에 둔다(최종 Go/No-Go).

### 3.2 화면별 요구사항

**발주계획** — 결정 1 · 시안 `Main`

- 상단은 `발주계획` 제목과 수집 회차 선택을 제공한다. 소개 문구는 두지 않는다.
  `source_run_id`를 URL과 동기화하고 회차 변경 시 필터·행 선택·페이지를 초기화한다.
  최신 수집 회차를 기본으로 조회하며 선별 전 회차는 전체 원본과 선별 전 안내를 보여준다.
  모델 판단 수정은 게시된 선별 결과가 있어야 저장하고 추적 결정과 구분한다. 실행 상태는
  배지 하나(성공·부분 성공·실패, 실행 ID 앞자리, 시각)로 요약한다. 상세는 `실행 상세`로 연다.
- 필터는 저장된 뷰 segmented(기본 보기 · 전체 · BM25 선정 제외 · 실패·거부), 모델 판단 selector,
  BM25 selector, 사람 판단 보정 selector, 제목·계획번호 검색, `현재 조합 저장`, `필터 초기화`로
  구성한다. 목록 머리글에 현재 조합의 의미(예: `BM25 선정 AND 모델 판단 관련`)와 건수를 쓴다.
- 검토 목록은 필터 선택 순서와 관계없이 모델 판단 `relevant → uncertain → not_relevant → 값 없음`
  순으로 묶는다. 같은 판단 안에서는 API 응답 순서를 유지하며, 페이지 분할 전에 전체 필터 결과를
  정렬한다. 방향키 이동과 다음 건 이동도 이 순서를 따른다.
- 기본 보기가 숨기는 것(BM25 선정 제외·비관련·실패)을 목록 바닥에 명시한다. 숨김을 부재로
  표시하지 않는다.
- 목록은 밀집 행이다. 제목과 기관의 기존 순서를 유지하고 기관 글자만 강조한다.
  한 행은 제목, BM25 선정·순위, 모델 판단, 사람 판단 유무, 기관·예산·계획
  시기만 담는다. 신호 세부(BM25 score·nearest capability, Qwen score·reason)는 상세의 `신호 세부`
  탭으로, 운영 텔레메트리는 `실행 기록` 탭으로 옮긴다.
- 상세 pane 바닥의 결정 액션은 `추적 시작` · `보류` · `추적 종료` · `이번 건 넘기기`이며, 선택
  즉시 이력을 기록하고 다음 발주계획으로 이동한다. 별도 저장 버튼을 두지 않는다.
- 추적 결정 영역은 미선택이 추적 종료가 아니라는 사실과, 추적 상태만 기록하며 모델 판단·적합성
  등급·참여 준비 상태를 바꾸지 않는다는 사실을 화면에 쓴다. 사유 selector와 담당자 감사 표식을
  함께 남긴다.
- 사람 판단 수정은 접힌 채로 두고, 열었을 때만 relevance·우선순위·메모를 새 revision으로
  기록한다. 목록의 사람 판단 대화상자에서 수정 이력을 확인한다.
- 별도 공고 상세페이지는 제공하지 않는다(2026-09-09 사용자 정정). 검토목록의 오른쪽 상세
  패널에서 확인하며, 다른 화면의 연결과 기존 상세주소도 해당 발주계획을 선택한 목록으로 이동한다.
- `filtered_out`·`not_relevant`·`unknown`·`null`·`failed`·`rejected`를 서로 바꾸어 표시하지 않는다.

**사전규격** — 결정 2 · 시안 `PreSpecs`, `PreSpecDetail`

- 목록은 한 목록이며 `전체`·`개요 완료`·`사람 확인`·`진행·대기`·`실패` 보기로 좁힌다.
  개요 미시작과 서버 상태 10값은 각 행에서 구분한다. 취소는 건수가 있거나 현재 선택한
  보기일 때 따로 표시하며 실패에 합치지 않는다.
- 행은 사업명 → 기관 → 예산·발견 구분 → 개요·추적 상태 순서이며 목록 열 이름도
  `사업명 / 발주기관`이다. 굵은 글자는 사업명 하나뿐이고 기관은 같은 크기의 보통
  굵기다. 의견 마감은 오른쪽 열에 D-day와 짧은 날짜를 둔다. 사전규격 번호·정확한 금액·일시·등급·자동 준비 사유는 선택 상세에서
  읽는다. 등급과 자동 준비의 모든 상태 이름은 보존하며 행마다 배지를 늘리지 않는다.
- 행과 사업명을 누르면 같은 화면의 오른쪽 상세를 선택한다. `개요 검토`·`첨부 문서`·`처리 이력`
  탭을 두고 단독 상세 진입은 하단의 `상세 검토 열기`가 맡는다.
- 상세 pane에서 `심층 검토 실행`을 승인한다. 목록 아래에 별도 패널을 덧붙이지 않는다.
- 추적 상태가 발주계획에서 승계된 건은 승계 사실을 배지로 밝히고 추적 상태를 다시 묻지 않는다.
- 발주계획에 없던 **신규** 사전규격만 `추적 시작하고 심층 검토`를 한 번의 조작으로 제공한다.
  이때도 이력에는 추적 시작과 심층 검토 실행을 **별도 항목으로** 남긴다.
- `추적 종료`·`보류`는 사업 추적에서만 사람이 선택한다. 심층 검토가 정상 완료돼도 추적 상태를
  다시 묻지 않는다.
- 상세는 개요 검토 진행을 첨부 확보 → 문서 구조화 → 개요 입력 범위 확정 → 모델 실행 → 결과 검증
  단계로 보여주고, 이 결과가 적합성 등급·참여 준비 상태·심층 검토 실행 승인·최종 Go/No-Go를
  채우거나 대신하지 않는다는 사실을 같은 자리에 쓴다.
- 요구사항 항목은 근거 위치와 함께 보여주고, 근거 위치가 없는 항목은 그 자리에 남겨 강조한다.
  자동 보정하지 않는다.
- 첨부는 배포 가능·배포 불가를 구분하고, 배포 불가 사유(예: 압축 내부 확인 실패)를 함께 쓴다.

**회사 핏 판정 사유 — 2026-09-08 구현, 참조 실행 전용**

v4 개요 이후 회사 핏 판정을 두는 전환 설계에 아래 표시를 포함한다. 현재 개요 권고나
적합성 등급을 회사 핏으로 재해석하지 않는다. 이 절은 화면 요구이며 새 판정의 저장·REST
계약이나 자동 심층 시작 정책이 이미 구현·활성화됐다는 뜻이 아니다.

- 사전규격 개별 상세는 판정을 오른쪽 `현재 판단` 카드에, 판단 사유·근거·실행 정보는 오른쪽
  `회사 업무 부합 여부` 카드(기본 접힘)에 둔다. 목록의 선택 상세에도 같은 판정과 핵심 사유를
  표시하며, 전체 사유는 개별 상세에서 읽을 수 있어야 한다.
- `부합하지 않음`일 때 핵심 사유를 기본으로 펼쳐 표시한다. 상세 사유는 공고의 실제
  수행 과업, 대조한 승인 회사 역량·사업 범위, 서로 맞지 않는 점, 그 판단의 근거로 구성한다.
  제목의 단어나 추정한 회사 역량만으로 사유를 만들지 않는다.
- 공고 근거는 해당 개요와 결속된 원문 위치로, 회사 근거는 해당 실행의 승인 프로필 버전과
  구조화 근거로 연결한다. PDF 페이지와 HWPX 절·문단·표 셀을 구분하며 존재하지 않는
  근거 링크를 만들지 않는다. 회사 프로필 전문·내부 파일 경로는 노출하지 않는다.
- 회사자료에 역량·자격·실적이 없다는 사실만으로 `부합하지 않음`을 표시하지 않는다.
  확인된 업무 불일치와 `정보 부족으로 판단 보류`를 구분하고, 보류에는 무엇을 확인해야
  판단할 수 있는지 표시한다. 아직 판정이 없는 상태, 실행 중, 실행 실패, 검증 실패도
  부합 여부와 별도로 표시한다.
- 회사 핏과 실제 심층 검토 처리 상태를 따로 보여준다. 참조 판정만 있는 경우 그 사유로
  실제 심층 검토를 생략했다고 표시하지 않는다. 자동 시작·생략·대기는 서버의 실제 처리
  결과와 사유를 읽으며, 부합 판정만으로 실행 완료를 추정하지 않는다.
- 판정 시각, 사용 개요·회사 프로필·모델·정책 버전, 품질·검증 상태를 확인할 수 있게 한다.
  판정 이후 입력이 바뀌면 과거 입력 기준임을 표시하고 새 입력의 현재 판정으로 쓰지 않는다.
- 모델 판정은 적합성 등급·참여 준비·사람 추적·최종 Go/No-Go를 덮어쓰지 않는다.
  저장된 사유가 없으면 화면에서 개요를 재요약해 채우지 않고 사유 미제공을 표시한다.

**사업 추적** — 결정 3 · 시안 `Opportunities`, `Queue`

- 목록의 기본 단위는 사업기회이며 한 사업기회는 한 행으로만 나타난다. 구역은 `조치 필요` ·
  `추적 중` · `보류` · `추적 종료` segmented로 나눈다.
- `조치 필요`는 이미 등록된 사업기회의 다음 행동이다. 미선택 원본을 이 목록에 넣지 않는다.
- 행은 사업명 → 기관 → 확정된 최근 단계·추적 상태 순서이며 오른쪽 열에 다음 확인 한 가지를
  둔다. 후보를 확정 단계로 올리거나 추적 상태를 최종 참여 결정으로 표시하지 않는다.
- 상세는 `사업 흐름`·`확인할 점`·`최근 결정` 탭으로 구성한다. 사업 흐름은 발주계획·사전규격·
  입찰공고의 공식 연결, 사람이 확인한 연결, 확인 대기 후보, 검색 미확인을 구분한다.
  확인된 연결만 해당 단계에 체크를 표시하며 분석 완료를 뜻하지 않는다. 연결 레코드와
  심층 검토는 실제 상세 경로로 연결하고, 조회로 확인하지 못한 것은 `연결 미확인`으로 남긴다.
- 시스템 신호는 보조 정보다. 탭 집계나 사람의 추적 결정을 자동으로 만들지 않는다.
- 추적 상태 변경은 하단 버튼으로 대화상자를 열어 계속 추적·보류·추적 종료와 **필수 사유**,
  담당자 감사 표식을 기록한다. 사유는 드롭다운과 `기타` 직접 입력이며 최근 결정은 실제
  API가 제공한 기록만 표시한다.
- 공고 판정 이력은 사업 추적 상세에서 여는 **읽기 전용** 화면이다. 회차 선택기를 갖고, 저장된
  뷰(전체 · 마감 임박 · 검증 예외 · 사람 리뷰 있음)와 등급·참여 준비 상태 필터를 제공하며,
  판정 근거·판정 이력·리뷰 기록을 탭으로 보여준다. 판정 근거의 각 항목은 원문 위치와 연결하고,
  연결이 없으면 `근거 위치 없음`을 그 자리에 남긴다.
- 현재 검토 대기열이 제공하는 리뷰 저장 경로를 **삭제하지 않는다.** 사업 추적의 예외 작업으로
  옮기며, 옮길 경로가 동작하기 전에는 공고 판정 이력을 읽기 전용으로 바꾸지 않는다.

**최종 Go/No-Go** — 결정 4 · 시안 `GoNoGo`, `BidDelta`

- `검토 대상`·`재검토`·`결정 기록`·`전체` 보기를 둔다. 검토 대상에는 미결정뿐 아니라 기존
  결정의 유효성 재확인이 필요한 건과 조회 실패·미확인도 포함한다. 과거 기록은 덮어쓰지 않는다.
- 목록 행은 사업명·기관·비교 상태·최근 결정을 보여준다. API에 없는 등급·참여 준비 상태를
  채우지 않는다. 변경 건수는 실제 비교 결과에서만 읽고 결과 없음·계산 대기·실제 0을 구분한다.
- 오른쪽은 변경 요약·비교 문서·결정 기록을 보여주며 하단 `변경 검토·결정 열기`에서 전체
  변경 검토 화면으로 이동한다. 목록 집계는 실제 조회 범위를 밝히고 서버 전체 집계로 부풀리지 않는다.
- 변경 항목(delta)은 범주별 반복 목록으로 보여주고 각 항목의 근거 위치를 연결한다. 근거 위치가
  없는 항목은 `근거 없음`으로 표시하고 숨기지 않는다.
- 중요 변경·비중요 변경·`확인 필요 · 중요도 미확인`을 구분한다. 확인 필요를 변경 없음으로
  해석하지 않는다.
- 비교 기준(기준 사전규격과 대상 입찰공고, 문서 묶음 상태, 계산 시각과 요청 ID)을 상세에 남긴다.
- 변경 검토는 왼쪽 원문·변경 근거 62%, 오른쪽 결정 form 38%다. form은 빈 선택에서 시작하는
  Go·참여 / No-Go·불참 두 값과 담당자 감사 표식(필수), 결정 이유(필수)를 받는다.
  form 하단에서 결정 내용을 확인한 뒤 저장한다. 비교 선택·정확한 문서 쌍 지정·재계산 경로는 유지한다.
- 보류는 최종 결정 값이 아니다. 결정하지 않으면 기록을 만들지 않는다.
- 저장 조건(계산 완료 비교만 결정 가능, 확인 필요 잔여 건수, 이 결정이 등급·준비 상태·심층 검토
  실행 승인을 대신하지 않음)을 form 바로 위에 쓴다.
- 결정은 append-only로 기록하며, current 결정이 stale이 되면 재검토로 표시한다.

**심층 검토 보고서** — 시안 `DeepReview`

- 모델 종합 판단, 참여 준비 상태, 미확인 사항, 보고서 revision을 상단 카드 4개로 요약한다.
- 모델 제안이며 사람 확정 전이라는 사실을 헤더에 쓴다. 정상 완료된 심층 검토가 추적 상태를
  다시 묻지 않는다는 사실도 같은 자리에 쓴다.
- 결정 카드 요약은 항목·내용·근거·검증 결과 표로 두고 `검증됨`·`근거 없음`·`불일치`를 구분한다.
- Validation 실패는 숨기지 않고 실패 블록으로 남기며 `원문에서 확인`과 `새 attempt로 재시도`를
  제공한다. 자동 보정하지 않는다.
- 수정본은 기존 보고서를 덮어쓰지 않고 새 immutable revision으로 append-only 저장하며 담당자
  claimed name을 필수로 받는다.

### 3.3 승인 ERP 시안의 고정 기준

- 대시보드 시안 원본은 저장소 밖 `design-previews/bidops-dashboard-erp-20260908/`의
  HTML·`source/`·상태별 캡처다. 대시보드는 §3의 67:33 네 패널 구조를 적용한다.

- 탐색과 추적 목록 4화면(발주계획·사전규격·사업 추적·최종 Go/No-Go)은 상단바가 제목(`h1`)과
  페이지 액션을 갖고 페이지는 제목 줄을 두지 않는다. 상세 화면은 목록으로 돌아갈 경로를 표시한다.
- 대시보드 외 여섯 화면은 목록 38% : 상세 62%다. 발주계획과 사전규격의 기본 목록 폭은 같은 앱 셸과
  viewport에서 오차 1px 이하다. 발주계획을 사용자가 리사이즈하기 전의 기본값은 비율이다.
- 발주계획의 사업명은 15px semibold이고 기관은 기존 제목 아래 위치에서 14px 보통 굵기다.
  사전규격의 기관·사업명은 16px이며 semibold는 사업명만 갖고,
  사업 추적과 최종 Go/No-Go의 사업명·기관은 15px다. 보조 목록 정보는 14px, 상세 사업명은 20px다.
  CSS는 대응하는 프로젝트 토큰과 Astryx 간격 토큰으로 이 크기를 표현한다.
- 판정 기준·실행 상태의 목록 제목은 15px semibold, 보조 정보와 본문은 14px, 캡션은 12px 이상,
  상세 제목은 20px다. 상단 4개 탭 → 짧은 요약 → 목록·상세 → 업무 경계 안내 순서를 유지한다.
  시안 확인용 40px 도구 모음은 제품에 포함하지 않는다.
- 공통 치수(사이드바 248px·상단바 76px·논리 캡션 12px)는 CSS 논리값으로 유지한다. 브라우저
  배율 100%에서 전역 UI 배율 90%를 적용하므로 실제 표시는 각각 약 223.2px·68.4px·10.8px이며,
  이는 캡션 토큰을 낮춘 것이 아닌 사용자 요청에 따른 시각 배율이다. 셸과 body의 최소 폭은
  `1280px / 0.9`로 보정해 실제 지원 최소 폭 1280px을 유지하고, 그보다 좁으면 가로 스크롤한다.
  사전규격 상세의 `page-canvas`는 시안 픽셀을 지키기 위해 루트 배율을 상쇄해 100%로 표시하며, 셸과 body portal은 90%를 유지한다.
- 상단 소개 문단을 두지 않는다. 긴 실행 설명과 보조 정보는 대화상자로 열고, 미확인·품질 표식·
  필터 적용 범위처럼 판단에 필요한 제한은 해당 값 옆에 짧게 남긴다.
- 목록과 상세 읽기 영역은 따로 스크롤하며 하단 액션은 계속 보인다. 기본 발주계획 상세는
  두 지원 폭에서 스크롤 없이 읽히고, 긴 내용은 본문만 스크롤한다.
- 선택 사유는 빈 드롭다운에서 시작한다. 예시 선택 시 그 문장이 사유이며 `기타`일 때만
  직접 입력한다. 실패 시 입력 보존, 이탈 확인, 성공 시 초기화와 마지막 항목 저장 안내를 지킨다.
- 시안은 구현 기준이다. HTML과 원본 TSX/CSS의 구조·토큰·정보 순서를 재사용해 실제 API를
  연결한다. 가상 제목·기관·금액·분석·결정을 제품에 하드코딩하지 않는다.
- 1280×800과 1440×900에서 동일한 정보 밀도의 시안·구현을 직접 대조한다. 기본 화면과 긴 제목,
  빈 목록, 로딩·실패, 드롭다운·직접 입력·결정 확인을 확인한다. 앱 공통 셸 차이는 따로 기록한다.

## 4. 표시 규칙

- `unknown`은 확인 대기, `null`은 값 없음이다. 둘을 빈칸이나 `0`으로 바꾸지 않는다. `계산 불가`도
  별도 상태이며 `0`으로 표시하지 않는다.
- 적합성 등급 4값, 참여 준비 상태 4값, 개요 검토 상태 10값, 추적 상태 4값은 계약이 정의한
  문자열 그대로 쓴다. 화면 표시 이름은 §1.2의 대응만 허용한다.
- 등급은 심각도가 아니라 우선순위 순서다. 의미색(성공·위험)에 싣지 않고 accent 한 색의 농도
  4단으로 순서만 나타낸다. `판정 없음`은 다섯 번째 등급이 아니라 아직 판정하지 않음이므로 무채색
  으로 따로 둔다. 4단의 실제 값은 §4.1의 등급 ramp다. 농도만으로는 인접 단이 구분되지 않으므로
  등급 표시는 **항상 텍스트 라벨을 동반한다.** 색만으로 등급을 나타내는 표시를 만들지 않는다.
- 모델이 만든 수치와 요구사항은 원문 위치와 연결한다. 연결이 없으면 `근거 위치 없음`을 그 자리에
  표시하고 숨기지 않는다.
- 부분 산출물인 회차는 화면에서 그 사실을 알린다.
- 실패·미측정 상태를 성공이나 정상으로 보이게 하지 않는다. 실패는 사람 검토로 보내고 자동
  보정하지 않는다.
- 사람이 남기는 기록은 append-only다. 기존 revision을 덮어쓰지 않는다.

### 4.1 색 사용 규칙

색은 무드보드 [`moodborad.jpg`](moodborad.jpg)의 5색 anchor에서 나온다([ADR-0048](ADR.md)).
화면은 이 값을 직접 쓰지 않고 **테마 토큰만 읽는다.** `:root`나 화면 CSS에서 `--color-*`를
재정의하지 않는다.

| 무드보드 anchor | 역할 | 토큰 |
|---|---|---|
| `#D4CDCB` warm greige | 본문 canvas 계열과 구분선 | `--color-background-body`(`#F2F0EF`) · `--color-background-muted`(`#E7E4E2`) · `--color-border`(`#D4CDCB`) |
| `#8D8F8E` cool gray | 비텍스트 보조 요소 전용 | `--color-icon-*` 보조값 · disabled 표시 |
| `#5B687C` slate blue | accent와 등급 ramp의 기준색 | `--color-accent` · `--color-icon-accent` · `--color-text-accent` |
| `#161B2F` deep navy | 사이드바 surface | `--color-background-inverted` (Astryx core 토큰; 사이드바 본문은 `--color-nav-text` = `#D4CDCB`) |
| `#17181F` near-black ink | 본문 텍스트 | `--color-text-primary` |

카드·상세·팝오버 surface는 흰색이고 greige canvas 위에 뜬다. 보조 텍스트는 `#3C4452`
(slate + ink)이며 무드보드 anchor를 그대로 쓰지 않는다.

`--color-nav-text`는 Astryx 토큰 이름이 아니라(`TokenName`이 닫힌 union) 프로젝트 토큰이다.
셸 bridge 안에서 `--color-on-dark` 기반으로 유지하며, bridge는 새 색 값을 만들지 않으므로 위
규칙에 어긋나지 않는다.

**적합성 등급 ramp** — slate 농도 4단이며 의미색이 아니다. 토큰은
`web/frontend/src/themes/bidops/grade-ramp.css` 의 `--bo-grade-1`~`4`·`--bo-grade-none` 과
각각의 라벨 색 `--bo-on-grade-*` 다. 테마 정의가 아닌 프로젝트 토큰인 이유는
[ADR-0048](ADR.md) §3에 있다.

| 단계 | 배경 | 라벨 | 대비비 |
|---|---|---|---|
| 1단(최우선) | `#2F3A4C` | `#FFFFFF` | 11.47 |
| 2단 | `#5B687C` | `#FFFFFF` | 5.65 |
| 3단 | `#93A0B0` | `#17181F` | 6.65 |
| 4단 | `#D3D9E1` | `#17181F` | 12.45 |
| `판정 없음` | `#E5E5E5` | `#262626` | 12.01 |

화면은 이 ramp를 직접 읽지 않고 `Badge`의 등급 변형(`.badge-grade-1`~`4`)과 목록 행 레일
(`.rail-grade-*`)을 통해 쓴다. 그 두 곳이 `--bo-grade-*`를 읽는 유일한 자리이며, 등급 변형은
라벨이 비면 계약의 기본 라벨을 채워 색만으로 등급이 표시되지 않게 한다(단계 B).

**하지 않는 것.**

- 무드보드로 **의미색을 만들지 않는다.** 성공·부분 성공·실패·경고·`계산 불가`는 테마의
  categorical 팔레트에서 가져온다. 무드보드 톤에 맞추려고 실패·미측정의 색을 낮추지 않는다.
- 등급 ramp가 slate이므로 **상태 표시에 blue 계열을 쓰지 않는다.** 상태는 green(성공) ·
  yellow·orange(부분 성공·경고) · red(실패) · gray(미측정·`계산 불가`)만 쓴다.
- `#8D8F8E`를 **텍스트로 쓰지 않는다.** 흰 배경 3.25, greige canvas 위 2.87, greige anchor 위
  2.08로 AA에 미달한다. 흰 surface 위 비텍스트 요소(3.25)와 사이드바 위 보조 텍스트(5.24)로만
  쓰고, greige 계열 면 위에서는 쓰지 않는다.
- 대비비가 anchor를 이긴다. 텍스트는 4.5:1, 컴포넌트를 식별하는 비텍스트 요소는 3:1 이상이며,
  새 값이나 배지 조합을 추가할 때 대비 검사(`npm run test:contrast`)를 통과해야 한다. 카드
  테두리·구분선은 장식이므로 3:1 대상이 아니다.
- 색은 테마가 정하고 화면 CSS는 읽기만 한다. **예외는 이행용 token bridge 하나**로,
  `styles/shell-relaxed.css`가 legacy 이름을 테마 토큰에 잇기만 하며 새 색 값을 만들지 않는다
  ([ADR-0048](ADR.md) §1). Tailwind `@theme`은 `:root`로 방출돼 테마를 이기므로 디자인 시스템과
  이름이 겹치는 토큰을 거기에 두지 않는다([ADR-0048](ADR.md) §4-1).

### 4.2 용어 표시 규칙

화면을 쓰는 사람은 기획·사업개발 담당자다. 계약과 구현에서 쓰는 개발 용어를 화면 문자열에
그대로 두지 않는다. 정본은 `web/frontend/src/lib/glossary.ts`의 `TERM`이며 아래 표와 같다.

| 계약·구현 용어 | 화면 표시 |
|---|---|
| `attempt` | 분석 회차 |
| `revision` | 수정본 |
| `bundle` | 문서 묶음 |
| `snapshot` | 고정 입력 (문맥에 따라 `저장 시점 사본`) |
| `digest` | 식별 해시 |
| `binding` | 모델 연결 |
| `locator` | 원문 위치 |
| `claimed name` | 담당자 이름 |
| `workspace` | 작업 화면 |
| `projection` | 요약 정보 |
| `append-only` | 추가만 기록(덮어쓰지 않음) |
| `manifest` | 목록 |
| `validation` | 검증 |
| `currentness` | 최신 여부 |
| `fence` | 저장 조건 |
| `evidence` | 근거 |

`attempt`를 `회차`로 옮긴 것은 수집 회차(run)와 다른 축이므로 항상 **`분석 회차`**로 적어
구분한다. 회차 선택기를 갖는 화면(대시보드·공고 판정 이력)에서는 `분석 회차`라는 말을 쓰지
않는다.

**옮기지 않는 것.**

- 서버 계약의 enum 토큰(`relevant`, `filtered_out`, `needs_human_review`, `passed`, `pending`,
  `completed`, `go`, `no_go` 등). 값 자체가 계약이므로 한국어 설명을 덧붙일 수는 있어도
  (`completed · 계산 완료`) 토큰을 지우지 않는다. §4의 등급·준비·개요·추적 4벌도 같다.
- 식별자와 해시 값 자체(문서 버전 ID, SHA-256, 요청 식별자). 사람이 눈으로 대조하는 값이다.
  옮기는 것은 그 값을 가리키는 **이름**뿐이다.
- 이미 라벨 맵을 가진 업무 상태(`BUNDLE_STATUS_LABELS`, `PRE_SPEC_*_LABEL`,
  `QUALITY_STATUS_LABEL`). 그 맵이 해당 도메인의 정본이다.

**문구 구조.** 화면 헤더와 섹션 도입문은 첫 문장이 *이 화면에서 할 수 있는 것*을, 둘째 문장이
*이 화면이 정하지 않는 것*을 말한다. 규칙상 남겨야 하는 문장(네 결정은 서로를 대신하지 않는다 ·
참조 실행·mock 표식 · `unknown` 보존 · 되돌릴 수 없음)은 지우지 않고 한 문장으로 압축한다.
버튼 이름은 상태 문장이 아니라 행동 하나이며, 눌림·펼침 상태는 `aria-pressed`·`aria-expanded`가
말한다.

**오류 문구.** 화면이 서버 message를 그대로 싣지 않는다. `web/frontend/src/lib/apiErrors.ts`의
`describeApiError`가 status와 안전한 오류 코드를 제목·설명·다음 행동으로 옮기고, 화면은 그
결과만 표시한다.

| 항목 | 요구 |
|---|---|
| 지원 기기 | 데스크톱과 노트북만이다. 모바일·태블릿 레이아웃을 만들지 않는다([ADR-0047](ADR.md)) |
| 지원 폭 | 최소 1280px, 설계 기준 1440px, 상한 1920px. 1280px 미만은 가로 스크롤을 허용하고 별도 레이아웃을 만들지 않는다 |

| 색 모드 | 라이트 우선. 다크 모드는 이번 범위가 아니다. 사이드바의 `#161B2F`는 라이트 모드 안의 어두운 surface이며 다크 모드가 아니다 |

| 서체 | Pretendard 자체 호스팅 유지. 런타임에 외부 폰트 호스트를 부르지 않는다 |
| 외부 통신 | 화면 코드가 런타임에 외부로 나가는 경로를 만들지 않는다 |
| 접근성 | 키보드로 판정 동선을 끝까지 수행할 수 있다. 초점 표시가 보인다 |
| 레이아웃 | 사이드바 248px, 상단바 76px, 목록 pane 38%, 상세 pane 62%(§3.3). 목록·상세 pane은 각자 스크롤을 가둔다 |
| 회귀 | 화면 변경은 시각 기준선 갱신을 동반한다. 기준선 없는 변경을 병합하지 않는다. 팔레트 적용은 v2 기준선을 새로 만들며 무채색 v1을 덮어쓰지 않는다 |
