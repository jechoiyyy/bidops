## ADR-0039: Astryx 디자인 시스템 채택과 승인 범위

| 항목 | 내용 |
|---|---|
| 상태 | 채택 — 결정 3은 [ADR-0048](#adr-0048-무드보드-기반-색-팔레트와-테마-소유권)이 개정 |
| 결정일 | 2026-09-02 |
| 범위 | `web/frontend`의 컴포넌트·테마 |
| 정본 | 이 문서, [`PLAN.md`](PLAN.md) 0단계 |

### 문맥

현재 프론트엔드는 React 19 · Tailwind 4 · radix-ui다. 밀집 표, 상태 배지, 진행률처럼 판정
화면의 핵심 요소를 화면마다 손으로 만들고 있어 같은 의미가 화면마다 다르게 보인다.

`@astryxdesign/core`를 후보로 검토했다. 확인한 사실은 다음과 같다.

- MIT, Meta 공식 npm 계정(`fb <opensource+npm@fb.com>`)이 관리자, `github.com/facebook/astryx` 실재
- 버전 0.5.2, 주간 다운로드 약 10.6만, 컴포넌트 163종
- 테마는 `astryx theme build`가 `@scope([data-astryx-theme="…"])`로 감싼 정적 CSS를 만든다
- 지침이 Tailwind 유틸리티 클래스 사용을 금지한다

네 가지 적용 방식(부분 적용 · 기본 테마 · neutral · stone)을 같은 화면으로 렌더해 비교했고
`neutral`을 선택했다.

`@astryxdesign/core`는 [`CLAUDE.md`](../../CLAUDE.md)가 열거한 승인된 외부 의존성에 없었다.

### 결정

1. `@astryxdesign/core@0.5.2`를 `web/frontend`의 dependency로 추가하고 **승인된 외부
   의존성으로 등록한다.** 버전은 고정하며 자동 갱신하지 않는다.
2. `@astryxdesign/cli`는 devDependency로만 둔다. 테마 빌드와 컴포넌트 조회 도구이며 런타임
   코드가 아니다.
3. 테마는 `neutral`을 쓴다. `astryx theme build` 산출물(CSS·JS)을 저장소에 커밋하고 런타임
   `defineTheme()`은 쓰지 않는다. 런타임 테마는 hydration 이후에 주입되어 첫 페인트와
   결정적 산출을 깨뜨린다.
   → **[ADR-0048](#adr-0048-무드보드-기반-색-팔레트와-테마-소유권)이 개정한다.** 테마는 무드보드
   anchor에서 파생한 프로젝트 소유 테마 `bidops`이고 stock `neutral`은 대조용으로만 남는다.
   빌드 산출물을 커밋하고 런타임 `defineTheme()`을 쓰지 않는다는 나머지는 그대로 유지한다.
4. 색 모드는 **라이트 우선**으로 고정한다. 다크 모드는 이번 범위가 아니다.
5. **서체는 현행 Pretendard 자체 호스팅을 유지한다.** neutral이 지정하는 Figtree와 Montserrat에는
   한글 글리프가 없어 한글 본문을 담당할 수 없다. 시안에서는 비교를 위해 웹폰트를 썼으나,
   운영은 내부망이 경계이므로 **런타임에 외부 폰트 호스트를 부르지 않는다.** neutral 테마의
   `--font-family-*` 토큰은 Pretendard를 앞에 둔 스택으로 덮어쓴다. 테마가 `bidops`로 바뀐 뒤에도
   같다(ADR-0048).
6. 외부 통신은 **빌드 타임 npm 레지스트리 접근에 한정**한다. 런타임에 Astryx가 외부로 나가는
   경로를 만들지 않는다.
7. `astryx theme add neutral`이 만드는 아이콘 레지스트리(`icons.tsx`)가 `lucide-react`를
   import하므로 `lucide-react@1.39.0`도 dependency로 고정해 함께 승인한다. 0단계에서는
   테마 CSS만 import하므로 번들에 들어가지 않고, 화면 이행이 아이콘을 쓸 때부터 사용된다.

### 대안

| 대안 | 기각 사유 |
|---|---|
| 현행 유지 | 같은 의미가 화면마다 다르게 보이는 문제를 해결하지 못한다 |
| Astryx 전면 재작성 | Tailwind와 공존하지 않아 프론트엔드 재작성이 된다. 회귀 위험이 이번 개선의 이득보다 크다 |
| 다른 디자인 시스템 | 밀집 표·상태 표현·상세 패널을 한 벌로 제공하는 후보를 이번 비교 범위에서 찾지 못했다 |

### 결과

- 화면 단위 이행이 가능해진다(ADR-0040).
- 이행 기간 동안 Tailwind와 Astryx가 저장소에 함께 존재한다.
- 0.x 버전이므로 breaking change를 감수한다. `astryx upgrade --apply`가 있으나 버전 갱신은
  별도 결정으로 다룬다.

## ADR-0040: 레이아웃 소유권과 화면 단위 이행

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-02 |
| 선행 결정 | ADR-0039 |
| 정본 | 이 문서, [`PLAN.md`](PLAN.md) |

### 문맥

Astryx 지침은 레이아웃을 컴포넌트로만 구성하고 `<div>`를 쓰지 말라고 요구한다. 그 규칙을
따르면 현행 화면 골격(사이드바 248px, 상단바 76px, 대시보드 `1.25fr : 0.95fr` /
`1.55fr : minmax(320px,1fr)`, 대기열 목록 pane `min(390px, 34%)`)을 Astryx의 페이지 템플릿으로
갈아엎어야 한다. 시안으로 확인한 결과, 골격을 유지한 채 컴포넌트만 바꿔도 화면은 성립한다.

### 결정

1. **레이아웃은 프로젝트가 소유한다.** 화면 골격과 그리드 비율은 현행 구현을 정본으로 삼고,
   Astryx의 페이지 템플릿으로 대체하지 않는다. Astryx의 "레이아웃도 컴포넌트로만" 규칙은
   이 저장소에 적용하지 않는다.
2. Astryx 페이지 템플릿은 **참조 자료로만** 쓴다. 필요한 상호작용 패턴(토큰 필터, 저장된 뷰,
   크기 조절 상세 패널, 접이식 그룹)만 골라 현행 골격 안으로 가져온다.
3. **화면 단위로 이행한다.** 테마 CSS가 `@scope`로 격리되므로 이행한 화면과 하지 않은 화면이
   한 앱 안에서 충돌 없이 공존한다.
4. Tailwind는 제거하지 않는다. 다만 **한 화면 안에서 두 체계를 섞지 않는다.** 이행을 마친
   화면은 Tailwind 유틸리티 클래스를 쓰지 않고, 색·간격은 Astryx 토큰만 읽는다.
5. 골격 CSS도 값을 새로 정하지 않고 Astryx 토큰(`--color-*`)을 읽는다.

### 결과

- 되돌리기 단위가 화면 하나다. 문제가 생기면 그 화면만 되돌린다.
- 이행 완료 화면과 미이행 화면의 모양이 한동안 다르다. 이는 의도한 상태다.
- 골격 CSS를 직접 유지해야 한다. 시안에서 세 화면 골격이 164줄이었다.

## ADR-0041: 정보구조와 판정 동선

| 항목 | 내용 |
|---|---|
| 상태 | 채택 — 결정 1·2·4는 [ADR-0046](#adr-0046-사업-추적-중심-정보구조와-추적-결정의-위치)가 개정 |
| 결정일 | 2026-09-02 |
| 선행 결정 | [`../business-rules.md`](../business-rules.md)의 판단 단계 정의 |
| 정본 | 이 문서, [`PRD.md`](PRD.md) |

### 문맥

`route-meta.ts`는 모든 화면을 `dataScope: "run"`(회차 종속, 9개)과 `"cumulative"`(누적, 10개)로
나눈다. 그러나 사이드바는 모니터링·판정·기준·운영으로 묶여 이 축이 드러나지 않고, 상단 회차
선택기가 화면마다 나타났다 사라진다.

사이드바 16항목 중 `/deadlines`와 `/audit`은 리다이렉트, `/reviews`는 미구현 안내,
`/judgments`는 선택 없는 상세 화면이다. 반대로 최종 Go/No-Go(`/opportunities/:id/bid-delta`)와
심층 검토 보고서(`/deep-reviews/:id`)는 사이드바에 항목이 없다.

판정 동선도 화면마다 다르다. 검토 대기열은 목록과 상세를 나란히 놓고 한 화면에서 판정하지만,
발주계획 C-2와 사전규격은 목록에서 상세 페이지로 이동해야만 판정을 저장할 수 있다.

### 결정

1. 사이드바 1차 분류를 **회차 검토 / 누적 추적**으로 바꾼다. 기준·운영은 그 아래 별도 묶음이다.
2. 메뉴 항목을 **16에서 8로** 줄인다. 리다이렉트 항목은 각 화면의 저장된 뷰로 흡수하고,
   기준 4개는 한 화면의 탭으로, 운영 3개와 감사 로그는 한 화면으로 묶는다.
3. **최종 Go/No-Go를 최상위 메뉴로 올린다.** 빈도는 낮아도 되돌릴 수 없는 결정이다.
4. **판정 입력은 목록과 같은 화면에 둔다.** 목록에서 상세 페이지로 이동해야만 판정할 수 있는
   구조를 없앤다. 저장 후 다음 항목으로 이동하는 조작을 모든 판정 화면에 둔다.
5. 다음은 **바꾸지 않는다.**
   - 적합성 등급, 참여 준비 상태, 심층 추적 승인, 최종 Go/No-Go는 각각 별도 조작으로 남긴다.
     화면 수를 줄이려고 한 컨트롤로 합치지 않는다.
   - `unknown`과 `null` 표기를 빈칸으로 바꾸지 않는다. 확인 대기와 값 없음은 다른 상태다.
   - 회차 종속 화면과 누적 화면을 한 목록으로 합치지 않는다.
   - 운영 텔레메트리(`model_digest`, token 수, `duration_ms`)를 삭제하지 않는다. 판정 화면에서
     분리하되 감사 목적으로 접근 가능한 자리에 남긴다.

### 결과

- 메뉴가 업무 축과 일치해 회차 선택기의 등장·소멸이 예측 가능해진다.
- 판정 화면 세 곳의 조작 방식이 하나로 통일된다.
- 리다이렉트로 존재하던 진입점 두 개가 사라지므로, 기존 링크와 북마크는 각 화면의 저장된 뷰로
  연결한다.

## ADR-0046: 사업 추적 중심 정보구조와 추적 결정의 위치

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-04 |
| 선행 결정 | [ADR-0041](#adr-0041-정보구조와-판정-동선) (결정 1·2·4를 개정) |
| 근거 | 화면 시안 14종 `mockups/_shots/` (2026-09-02 렌더), `routes.tsx`·`Sidebar.tsx` 코드 검토 |
| 정본 | 이 문서, [`PRD.md`](PRD.md) §2, §3 |

### 문맥

ADR-0041은 사이드바 1차 분류를 `회차 검토`(대시보드·검토 대기열)와 `누적 추적`으로 나누고 항목을
16에서 8로 줄였다. 그 구조를 화면 시안으로 그려 보고 두 가지가 드러났다.

첫째, `검토 대기열`은 회차 축이므로 같은 사업기회가 회차마다 다른 행으로 나타난다. 담당자가
한 사업기회를 따라가려면 회차를 옮겨 가며 같은 건을 다시 찾아야 한다. 회차 표본 약 120건을 사람이
전수 순회한다는 전제도 실제 업무와 맞지 않는다. 사람이 손을 대야 하는 것은 근거 없음·검증 실패·
연결 불확실 같은 예외분이다.

둘째, 추적 결정을 내리는 자리가 화면에 없었다. `업무 규칙`은 추적 상태(`미선택`·`계속 추적`·
`보류`·`종료`)를 사업기회의 상태로 정의하는데, 담당자가 그 결정을 처음 내리는 순간은 발주계획을
훑을 때다. ADR-0041은 발주계획 화면이 사람 피드백(relevance·priority·memo)만 저장한다고 보아
결정 1을 피드백 저장으로 좁혔고, 그 결과 결정 1이 화면 어디에도 없었다.

### 결정

1. 사이드바 1차 분류를 **`오늘의 업무` / `탐색과 추적`**으로 바꾸고 항목을 **16에서 7로** 줄인다.
   `오늘의 업무`에는 대시보드만 두고, 사업기회를 따라가는 화면은 모두 `탐색과 추적`에 둔다.
   `기준과 운영`은 그 아래 별도 묶음으로 유지한다.
2. **`검토 대기열`을 사이드바에서 없애고 `사업 추적`으로 대체한다.** `사업기회` 화면이 이름과
   구조를 바꿔 그 자리를 받는다. 목록의 기본 단위는 사업기회이고 한 사업기회는 한 행으로만
   나타난다. 구역은 `조치 필요`·`추적 중`·`보류`·`추적 종료`다.
3. **공고 1차 판정 화면은 읽기 전용 이력이 된다.** 사업 추적 상세에서 열리며 회차 선택기를 갖는다.
   사람의 수정은 사업 추적의 예외 작업 경로에서 수행한다. 다만 **그 경로가 동작하기 전에는 현재의
   리뷰 저장 기능을 읽기 전용으로 바꾸지 않는다.** 기능을 먼저 옮기고 나중에 잠근다.
4. **결정 1을 추적 결정으로 고정하고 발주계획 화면에 둔다.** `추적 시작`·`보류`·`추적 종료`·
   `이번 건 넘기기`가 상세 pane 바닥의 결정 액션이며, 선택 즉시 append-only 이력을 남기고 다음
   건으로 이동한다.
5. **사람 판단 수정을 추적 결정에서 분리한다.** relevance·우선순위·메모는 선택 사항이고 별도
   revision이며 기본 접힘이다. 추적 상태·적합성 등급·참여 준비 상태·최종 Go/No-Go에 영향을 주지
   않는다.
6. **추적 상태를 묻는 자리는 하나로 제한한다.** 발주계획에서 승계된 사전규격은 추적 상태를 다시
   묻지 않고, 심층 검토가 정상 완료돼도 다시 묻지 않는다. `보류`와 `추적 종료`는 사업 추적에서만
   사람이 선택한다. 발주계획에 없던 신규 사전규격만 `추적 시작하고 심층 검토`를 한 조작으로
   제공하되, 이력에는 두 항목을 따로 남긴다.
7. **회차 축을 두 화면으로 제한한다.** 회차 선택기는 대시보드와 공고 판정 이력에만 있다. 공고
   판정 이력은 사이드바 항목이 아니므로 사이드바만 보면 회차 선택기의 표시 여부가 예측된다.
8. 다음은 ADR-0041에서 **그대로 유지한다.**
   - 최종 Go/No-Go는 최상위 메뉴다.
   - 흡수된 화면의 옛 경로는 리다이렉트가 아니라 흡수한 뷰·탭의 정식 주소로 남기고 404를 내지
     않는다.
   - 적합성 등급, 참여 준비 상태, 심층 검토 실행 승인, 최종 Go/No-Go를 한 컨트롤로 합치지 않는다.
   - `unknown`과 `null`을 빈칸으로 바꾸지 않는다.
   - 운영 텔레메트리를 삭제하지 않고 실행 상태 화면에 남긴다.

### 대안

| 대안 | 기각 사유 |
|---|---|
| 검토 대기열을 그대로 두고 사업기회를 추가 | 같은 건이 회차 목록과 누적 목록에 두 번 나타나고, 어느 쪽이 정본인지 화면이 답하지 못한다 |
| 추적 결정을 사업기회 화면에만 두기 | 사업기회가 만들어지기 전 단계인 발주계획에서 결정 1을 내릴 자리가 없다 |
| 추적 결정과 사람 판단 수정을 한 폼으로 합치기 | 결정 1과 모델 판단 보정은 저장 대상도 되돌리는 방법도 다르다. 업무 규칙이 금지한 결정 혼합이다 |
| 공고 판정 이력을 즉시 읽기 전용으로 전환 | 현재 동작하는 리뷰 저장 경로가 대체 경로 없이 사라진다 |

### 결과

- 담당자가 한 사업기회를 한 행에서 끝까지 따라간다. 회차를 옮겨 다니며 같은 건을 다시 찾지 않는다.
- 결정 1이 화면에 존재하게 되고, 결정 1과 모델 판단 보정이 서로 다른 저장 경로를 갖는다.
- `검토 대기열`을 전제로 쓰인 문서·테스트·경로 설명은 `사업 추적`과 `공고 판정 이력`으로 나뉘어
  다시 쓰여야 한다. `route-meta.ts`의 `queue` 항목(`editScope: "리뷰 저장 가능"`)은 이행이 끝날
  때까지 그대로 둔다.
- 사이드바가 7항목이 되지만 경로 수는 줄지 않는다. 흡수한 화면의 주소를 모두 유지한다.

## ADR-0047: 데스크톱·노트북 전용 지원 폭

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-04 |
| 범위 | `web/frontend`의 레이아웃·CSS 전환점·Playwright viewport |
| 정본 | 이 문서, [`PRD.md`](PRD.md) §5 |

### 문맥

BidOps는 사내망 안의 관리 화면이고 담당자는 데스크톱과 노트북에서만 쓴다. 그런데 현재 화면 CSS는
1180 / 960 / 900 / 640 전환점을 가지고 있고 `playwright.config.ts`는 mobile 390px와 tablet 768px을
포함한 네 폭을 모두 돌린다. 시안 14장은 전부 1440px 한 폭으로 렌더됐다.

좁은 폭 레이아웃은 유지 비용을 두 배로 만든다. 목록·상세 분할이 무너지는 폭에서는 "결정 액션이
첫 화면에서 보인다"는 요구를 다른 방식으로 다시 만족시켜야 하고, 시각 기준선도 폭마다 따로
관리해야 한다. 쓰지 않는 폭 때문이다.

### 결정

1. **지원 기기는 데스크톱과 노트북만이다.** 모바일·태블릿 레이아웃과 터치 전용 조작을 만들지
   않는다.
2. 지원 폭은 **최소 1280px, 설계 기준 1440px, 상한 1920px**이다. 시안의 1440px가 시각 기준선의
   기준 폭이다.
3. **1280px 미만에서는 가로 스크롤을 허용한다.** 별도 레이아웃으로 전환하지 않는다. 목록·상세
   분할은 지원 폭 전체에서 유지된다.
4. 시각·상호작용 검증 viewport를 **laptop 1280×800과 desktop 1440×900** 두 폭으로 고정한다.
   1920px는 가로 스크롤 없음만 확인한다. mobile 390px와 tablet 768px project는 없앤다.
5. 900px·640px 전환점에 의존하던 기존 테스트의 `skip` 조건과 분기는 이행하는 화면에서 함께
   제거한다. 이행하지 않은 화면의 CSS는 그대로 두고, 화면을 이행할 때 그 화면 것만 정리한다.

### 대안

| 대안 | 기각 사유 |
|---|---|
| 네 폭 유지 | 쓰지 않는 두 폭 때문에 시각 기준선과 분기 로직이 두 배가 된다 |
| 좁은 폭에서 상세가 목록을 덮는 전환 유지 | 지원 기기에서 그 폭이 나오지 않는다. 검증할 수 없는 요구는 요구가 아니다 |
| 최소 폭을 1024px로 | 사이드바 248px를 빼면 목록·상세 분할에 776px만 남아 시안의 밀도를 담지 못한다 |

### 결과

- 시각 기준선이 폭당 14장에서 두 폭 28장으로 고정된다. 네 폭이었다면 56장이다.
  (**이후 변경 2026-09-04**: 이 결정과 별개로 화면 검사를 의미·구조·픽셀 세 층으로 갈랐다.
  픽셀 기준선은 대표 화면만 찍고 1440px 한 폭이라 8장이다. 폭 검사는 구조 층이 두 폭에서
  맡으며 기준 이미지를 쓰지 않는다. 이 ADR이 정한 지원 폭은 그대로다.)
- 1280px 미만에서 화면이 깨져 보일 수 있다. 지원 범위 밖이며 그렇게 문서에 적는다.
- 기존 테스트의 폭 분기를 화면 이행과 함께 정리해야 한다. 한 번에 지우지 않는다.

## ADR-0048: 무드보드 기반 색 팔레트와 테마 소유권

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-04 |
| 선행 결정 | [ADR-0039](#adr-0039-astryx-디자인-시스템-채택과-승인-범위) (결정 3을 개정), [ADR-0040](#adr-0040-레이아웃-소유권과-화면-단위-이행) |
| 근거 | [`moodborad.jpg`](moodborad.jpg) (저장소에 있는 파일명 그대로다), `web/frontend/src/themes/neutral/neutralTheme.ts` 토큰 정의, 아래 대비비 실측 |
| 정본 | 이 문서, [`PRD.md`](PRD.md) §4.1, [`PLAN.md`](PLAN.md) 단계 A |
| 팔레트 값 승인 | 2026-09-04, 제품 담당자. 발주계획 목록·상세 팔레트 스터디(승인 시안 마크업에 토큰만 교체)를 보고 §4.1 토큰 표를 그대로 승인함. 기준 이미지 승인은 아니다 |

### 문맥

ADR-0039는 테마를 stock `neutral`로 고정했다. `neutralTheme.ts`가 스스로 밝히듯 이 테마는
"pure grayscale spine"(`#fafafa`·`#f5f5f5`·`#e5e5e5`·`#737373`·`#262626`·`#0a0a0a`)이고
brand·accent 색이 없다. `--color-accent`는 라이트 모드에서 `#262626`, 즉 무채색이다.

그 결과 두 가지가 미해결로 남았다.

- [`PRD.md`](PRD.md) §4는 적합성 등급을 "accent 한 색의 농도 4단"으로 표시하라고 요구하는데,
  현재 accent가 무채색이어서 등급 4단과 `판정 없음`의 무채색이 구분되지 않는다.
- [`PLAN.md`](PLAN.md) §1은 무채색 팔레트를 v1 시각 기준으로 고정하면서, 팔레트를 바꾸려면
  시안을 다시 생성하고 새 기준 버전과 승인 기록을 남기라고 조건을 걸어 두었다.

무드보드는 5색 anchor를 준다. warm greige `#D4CDCB`, cool gray `#8D8F8E`, slate blue `#5B687C`,
deep navy `#161B2F`, near-black ink `#17181F`다. 이 중 slate blue가 accent, deep navy가
사이드바 surface, warm greige가 본문 canvas 계열에 대응한다. 무드보드에는 **의미색(성공·경고·
실패)이 없다.**

Astryx 지침은 brand·accent를 테마에 두고 `:root`에서 `--color-*`를 덮어쓰지 말라고 요구한다.
따라서 팔레트 적용 지점은 CSS가 아니라 theme 정의 파일이다.

### 결정

#### 1. 프로젝트 소유 테마 `bidops`를 만들고 stock `neutral`을 대체한다

ADR-0039 결정 3의 "테마는 `neutral`을 쓴다"를 개정한다.

- `web/frontend/src/themes/bidops/bidopsTheme.ts`를 `defineTheme`으로 정의하고
  `astryx theme build`가 만든 CSS·JS를 저장소에 커밋한다. 런타임 `defineTheme()`은 쓰지
  않는다(ADR-0039 결정 3의 나머지는 그대로 유지한다).
- scope 속성은 `data-astryx-theme="bidops"`다. `neutral`을 그대로 두고 그 위에 색을 덮어쓰지
  않는다. stock `neutral`은 upstream 대조용으로만 남긴다.
- `:root`나 화면 CSS에서 `--color-*`를 **새 색 값으로** 재정의하지 않는다. 골격 CSS는 토큰을
  읽기만 한다(ADR-0040 결정 5).
- **예외는 이행용 token bridge 하나다.** `styles/shell-relaxed.css`의
  `.app-shell[data-astryx-theme="bidops"]` 블록은 legacy 이름(`--surface-app`, `--color-deep`
  등)을 테마 토큰에 잇기만 하고 새 색 값을 만들지 않는다(모든 우변이 `var(--color-*)`다).
  아직 이행하지 않은 화면이 이름을 바꾸지 않고도 새 팔레트를 읽게 하는 장치이며,
  화면 이행이 끝나면 없앤다. 이 bridge 밖에서 `--color-*`를 정의하지 않는다.

#### 2. 무드보드 5색은 anchor이고, 표면 단계는 anchor에서 파생한다

anchor를 그대로 넓은 면에 쓰지 않는다. 파생값은 anchor와 흰색·잉크의 혼합비로 정의하고 그
혼합비를 theme 정의 파일 주석에 남긴다.

| 역할 | 토큰 | 값 | 출처 |
|---|---|---|---|
| 본문 canvas | `--color-background-body` | `#F2F0EF` | greige 30% + white |
| 카드·상세·팝오버 surface | `--color-background-card` · `-surface` · `-popover` | `#FFFFFF` | — |
| 보조 surface | `--color-background-muted` | `#E7E4E2` | greige 55% + white |
| 구분선 | `--color-border` | `#D4CDCB` | anchor |
| 강조 구분선 | `--color-border-emphasized` | `#9F9A9B` | greige 72% + ink |
| 사이드바 surface | `--color-background-inverted` | `#161B2F` | anchor (Astryx core 토큰. neutral 은 재정의하지 않아 core 기본값 `#0A1317` 이 남으므로 `bidops` 가 덮는다) |
| 사이드바 본문 | `--color-nav-text` | `#D4CDCB` | anchor |
| 본문 텍스트 | `--color-text-primary` | `#17181F` | anchor |
| 보조 텍스트 | `--color-text-secondary` | `#3C4452` | slate 55% + ink |
| accent | `--color-accent` · `--color-icon-accent` · `--color-text-accent` | `#5B687C` | anchor |
| accent 위 텍스트 | `--color-on-accent` | `#FFFFFF` | — |

사이드바의 `#161B2F`는 **라이트 모드 안의 어두운 surface**다. 다크 모드가 아니다
([PRD.md](PRD.md) §5, ADR-0039 결정 4). 다크 모드는 이번에도 범위 밖이다.

#### 3. 적합성 등급 4단은 slate 농도 ramp다

[`PRD.md`](PRD.md) §4가 요구한 "accent 한 색의 농도 4단"을 slate anchor에서 만든다. 등급은
심각도가 아니라 순서이므로 의미색을 쓰지 않는다.

| 단계 | 배경 | 라벨 | 대비비 |
|---|---|---|---|
| 1단(최우선) | `#2F3A4C` | `#FFFFFF` | 11.47 |
| 2단 | `#5B687C` | `#FFFFFF` | 5.65 |
| 3단 | `#93A0B0` | `#17181F` | 6.65 |
| 4단 | `#D3D9E1` | `#17181F` | 12.45 |
| `판정 없음` | `#E5E5E5` | `#262626` | 12.01 |

`판정 없음`은 다섯 번째 등급이 아니라 아직 판정하지 않음이므로 ramp 바깥의 무채색이다.
인접 단의 배경 대비는 1.9~2.1이라 **농도만으로는 등급을 구분할 수 없다.** 등급 표시는 항상
텍스트 라벨을 동반한다. 색만으로 등급을 나타내는 표시를 만들지 않는다.

ramp 는 테마 정의가 아니라 `web/frontend/src/themes/bidops/grade-ramp.css` 의 프로젝트 토큰
(`--bo-grade-1`~`4`, `--bo-grade-none` 과 각 `--bo-on-grade-*`)이다. Astryx 의 `TokenName` 이
닫힌 union(`CoreTokenName | DomainTokenName`)이라 커스텀 토큰을 받지 못하기 때문이다 —
`astryx theme build` 는 emit 하지만 `tsc -b` 가 TS2353 으로 거부한다. `--color-*` 가 아닌
접두사를 쓰고 테마 디렉터리에 함께 두어, 색이 한곳에 모이고 화면은 읽기만 한다는 규칙은
유지한다.

#### 4. 무드보드는 의미색을 정하지 않는다

성공·부분 성공·실패·경고·`계산 불가`의 색은 무드보드에서 만들지 않고 테마의 categorical
팔레트에서 계속 가져온다. 무드보드에 맞추려고 실패·미측정 상태의 색을 팔레트 톤으로 낮추지
않는다([PRD.md](PRD.md) §4: 실패를 성공이나 정상으로 보이게 하지 않는다).

등급 ramp가 slate 계열이므로 **상태 표시에 blue 계열 의미색을 쓰지 않는다.** 상태는
green(성공) · yellow·orange(부분 성공·경고) · red(실패) · gray(미측정·`계산 불가`)만 쓴다.

#### 4-1. Astryx 와 이름이 겹치는 legacy 토큰은 제거한다

`styles/theme.css`는 Tailwind 4의 `@theme` 블록을 쓰고, Tailwind는 그 값을 **`:root`에
방출한다.** unlayered `:root`는 `@layer astryx-theme`을 이기므로, 이름이 같은 토큰은 테마가
무엇을 정하든 legacy 값이 앱 안에서 항상 이긴다. 2026-09-04 확인 결과 다섯 개가 겹쳤다.

| 토큰 | legacy(RootLab) | 테마가 정한 값 |
|---|---|---|
| `--color-border` | `#D7E1DB` | `#D4CDCB` |
| `--color-success` | `#276238` | `#007004` |
| `--color-warning` | `#7a3e00` | `#745b00` |
| `--color-error` | `#8f2f1d` | `#a50c25` |
| `--color-accent` | `var(--accent)` (shadcn hover 표면) | `#5B687C` |

앞의 넷은 `@theme`에서 제거해 테마가 소유한다. **미이행 화면을 가드로 감싸 옛 값을 유지하지
않고 전역으로 적용한다**(2026-09-04 결정). 가드를 두면 greige canvas 위에 옛 팔레트의 초록
테두리 카드가 남아 한 앱에 두 팔레트가 공존하고, 화면 이행이 끝날 때까지 그 상태가 지속된다.
대신 아직 이행하지 않은 화면(단계 C~F)의 테두리·의미색이 지금 함께 바뀐다는 것을 받아들인다.
교체 뒤에도 legacy `-bg` 짝과의 대비가 AA를 유지함을 확인했다(아래). `--color-accent`는 의미가 다른 shadcn 토큰이
자리를 차지한 경우이므로 기존 `--color-shadcn-primary` 전례를 따라 `--color-shadcn-accent`로
옮긴다. legacy `-bg`·`-edge` 짝은 그대로 두며, 교체 뒤에도 AA를 유지함을 확인했다
(warning 5.97, success 5.69, error 7.11).

#### 5. 접근성 게이트

anchor는 무드보드가 정하지만 **대비비가 anchor를 이긴다.** 다음을 고정한다.

- 텍스트와 배경은 WCAG AA(4.5:1) 이상이다. 비텍스트 UI 요소는 3:1 이상이다.
- `#8D8F8E`(cool gray)는 **본문 텍스트로 쓸 수 없다.** 흰 배경 3.25, greige body 위 2.87,
  greige anchor 위 2.08로 AA에 미달한다. 용도를 다음으로 제한한다.
  - 흰 surface 위의 비텍스트 요소(아이콘·구분선·disabled 표시): 3.25로 3:1 통과.
  - 사이드바 `#161B2F` 위의 보조 텍스트: 5.24로 AA 통과.
  - greige 계열 면 위: **금지**. 3:1에 미달한다.
- 새 토큰 값이나 배지 조합을 추가할 때 대비 검사를 통과해야 한다. `neutralTheme.ts`의 주석이
  가리키는 `scripts/check-badge-contrast.test.mjs`는 이 저장소에 없었으므로(upstream 산출물),
  같은 역할의 검사를 `web/frontend/scripts/check-contrast.test.mjs`로 새로 만들었다
  (`npm run test:contrast`). 빌드된 `bidops.css`·`grade-ramp.css` 에서 실제 토큰 값을 읽어
  검증하므로 테마를 고치고 다시 빌드하지 않으면 통과하지 않는다. 텍스트 4.5:1, 컴포넌트를
  식별하는 비텍스트 3:1, 등급 라벨 4.5:1, `#8D8F8E` 의 텍스트 토큰 배정 금지, 의미색이 neutral
  값에서 바뀌지 않았는지를 게이트로 둔다. 카드 테두리·구분선·skeleton 은 장식이므로 3:1 대상이
  아니다(upstream neutral 도 그렇게 두지 않는다).
- 위 표의 대비비는 실측값이다. 값을 바꾸면 다시 측정해 이 표를 갱신한다.

#### 6. 팔레트는 시안 재생성 뒤에 적용한다

[`PLAN.md`](PLAN.md) §0의 순서를 어기지 않는다. 시안을 만든 생성기 버전이 아직 저장소에 없어
지금 재생성하면 시각 정본이 옛 화면으로 덮인다. 따라서 순서는 다음과 같다.

1. PLAN §0-3·0-4가 끝나 생성기가 보존본 14장을 다시 만들어 낸다(무채색 기준).
2. 그 다음 `bidops` 테마를 만들고 시안을 팔레트로 다시 렌더해 **v2 기준 이미지**를 만든다.
3. v2 기준 이미지는 v1을 덮어쓰지 않고 변경 사유·영향 화면·승인자와 함께 별도 변경으로 남긴다
   (PLAN §3.2, §6).

0-4를 통과하기 전에는 어떤 화면도 "팔레트 적용 완료"로 기록하지 않는다.

### 대안

| 대안 | 기각 사유 |
|---|---|
| `neutralTheme.ts`의 토큰을 무드보드 값으로 덮어쓰고 slug은 `neutral` 유지 | scope 속성 변경은 없지만 이름이 내용과 어긋난다. stock `neutral`을 다시 빌드하거나 `astryx upgrade --apply`를 돌리면 brand 색이 조용히 사라진다 |
| 화면 CSS나 `:root`에서 `--color-*`를 덮어쓰기 | Astryx 지침 위반이고 `@scope` 격리를 깬다. 화면 단위 이행(ADR-0040)의 되돌리기 단위도 무너진다 |
| 무드보드 5색만으로 의미색까지 구성 | 성공·경고·실패를 구분할 색이 없다. 실패를 정상으로 보이게 하지 않는다는 요구를 만족할 수 없다 |
| `#8D8F8E`를 보조 텍스트로 사용 | 어느 밝은 surface 위에서도 AA에 미달한다. 무드보드 충실도보다 가독성이 우선한다 |
| 팔레트를 지금 적용하고 시안은 나중에 맞추기 | 시각 정본이 구현보다 뒤처진 상태가 되어 PLAN §4의 "기준 이미지 통과 후 다음 단계" 게이트가 무의미해진다 |
| 무드보드를 채택하지 않고 무채색 유지 | 등급 4단을 표현할 accent가 없어 PRD §4의 등급 표시 요구가 계속 미해결로 남는다 |

### 결과

- `--color-accent`가 무채색이 아니게 되어 등급 4단 표시가 가능해진다.
- theme slug이 바뀌므로 `data-astryx-theme` 속성, `design-shell.spec.ts`의 scope 검사,
  시안 생성기의 테마 입력 경로를 함께 고쳐야 한다. 값 한 개의 치환이지만 누락되면 화면이
  테마 없이 렌더된다.
- 14개 아트보드가 모두 색이 바뀌므로 기준 이미지 28장(두 폭)을 v2로 다시 만들어야 한다.
  v1 무채색 기준선은 삭제하지 않고 남긴다.
- stock `neutral`이 저장소에 남아 upstream 변경과의 대조가 가능하다. 다만 테마 파일이 둘이
  되므로 어느 쪽이 앱에 적용되는지 `AppShell`의 scope 속성이 유일한 답이다.
- 다크 모드는 여전히 범위 밖이다. `bidops` 테마의 dark 값은 정의하되 화면에서 활성화하지
  않는다.

## 2026-09-07 사용자 요청에 따른 발주계획 수집 회차 선택

ADR-0046 결정 7의 회차 선택 제한에 발주계획 조회를 예외로 추가한다. 사용자는
2026-09-03~09-07 수집 데이터를 선별 전부터 웹에서 보고 처리하도록 요청했다.
기존 화면은 최근 성공/부분 성공 C-2 실행의 회차만 읽어 새로 적재한 830건을 숨겼다.
기존 `GET /api/runs`와 `GET /api/order-plans?source_run_id=...` 계약을 연결한다.
사업기회 추적 상태는 누적 정본을 유지하며 수집 회차별로 복제하지 않는다.
선별 결과 부재는 `선별 전`으로 드러내고 기존 결과나 품질 승인으로 채우지 않는다.

## ADR-0055: 사전규격 담당자 브리핑 우선 배치

- 상태: 채택(2026-09-12 사용자 실행 승인). 구현·검증 상태는 별도 실행 기록으로 확인한다.
- 범위: 사전규격 목록·상세와 대시보드 진입 링크. 백엔드·수집기·REST 변경 없음.
- 근거: 사전규격 UX 검토의 미표시 정보와 운영자 중심 배치 지적, 프론트 전용 계획 및 개정안.

### 결정

1. 상세의 첫 화면은 사업 개요·과업·규모와 일정·조건·등급 사유·본공고·다음 행동을
   담당자에게 보여 준다. 회차 판정 사유와 사람 정정 사유는 서로 다른 출처로 표시한다.
   등급·참여 준비·추적 선택·최종 Go/No-Go의 경계는 바꾸지 않는다.
2. 목록 행에 색 없는 등급 글자 토큰 하나를 둔다. 기존 개요 상태 보기와 서버 집계는
   유지한다. `auto_preparation_status`는 서버 필터이고 `tracking_decision=pending`은
   신규·추적 미선택/미확인 건을 불러온 페이지에서만 좁힌다. 등급 필터와 같은 고지를 둔다.
3. 문서 준비는 묶음 상태·문서 수·차단 수·자동 준비 상태 요약과 조건부 렌더 토글로
   제공한다. 묶음 없음·draft·processing·needs_review·quarantined·failed가 먼저 열리고,
   ready/superseded도 자동 준비가 blocked·waiting_attachments·bundle_draft·
   deep_review_ready_for_click이면 열린다. 나머지 ready/superseded는 닫는다.
   `processing`의 폴링은 유지하며 조작 폼을 `display:none`으로 감추지 않는다.
4. 범위 확정 폼은 상세 왼쪽 열에 항상 마운트하고 오른쪽 현재 판단에는 알림과 링크만
   둔다. 목록 pane은 범위 확정 폼을 브리핑 아래로 옮기되 확정·재조회 동작을 유지한다.
   검증 진단·모델·해시·회사 핏 실행 정보는 처리 이력으로 옮기며 실패·사람 확인 시 열린다.
5. 수집된 첨부 목록과 API 다운로드 경로를 제공한다. 검증된 절대 HTTP(S) 첨부 URL만
   새 탭으로 열며 이를 공고 원문 URL로 대체하지 않는다. 공식 원문 URL 추정은 비목표다.
6. `lifecycle`·`procurement_class`의 알려진 키는 계약 문서에만 명시한다. opaque JSON을
   타입 가드로 읽고 번호 목록 문자열을 분할하지 않는다. 본공고 미확인은 부재가 아니다.

### 대안과 결과

- 백엔드 동시 확장은 서버 등급 정렬·본공고 보기까지 해결하지만 승인·검증 범위를
  넓혀 제외했다. 최소 상세 수정만으로 끝내면 목록 중복 렌더와 큰 파일이 남아 제외했다.
- Astryx Collapsible로 문서 폼을 감추는 대안은 조작·폴링 경계를 흐려 채택하지 않았다.
- PRD·프론트 작업 규칙·계약·ADR 색인을 함께 갱신한다. 두 지원 폭의 의미·구조 검사가
  게이트이며 의도된 픽셀 변경은 사유·화면·승인자·시각을 기록한 뒤 갱신한다.
- 후속 승인 범위: 공식 원문 URL 수집, 수요기관·연락처·기간 보존, 담당자 메모·
  의견등록 행동 기록, 서버 등급 필터·정렬, 본공고 발생·마감 임박 보기.
