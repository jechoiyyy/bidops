## ADR-0039: Astryx 디자인 시스템 채택과 승인 범위

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-02 |
| 범위 | `web/frontend`의 컴포넌트·테마 |
| 정본 | 이 문서, [`PLAN.md`](PLAN.md) 0단계 |

### 문맥

현재 프론트엔드는 React 19 · Tailwind 4 · radix-ui다. 밀집 표, 상태 배지, 진행률처럼 판정
화면의 핵심 요소를 화면마다 손으로 만들고 있어 같은 의미가 화면마다 다르게 보인다.

`@astryxdesign/core`를 후보로 검토했다. 확인한 사실은 다음과 같다.

- MIT, Meta 공식 npm 계정(`fb <opensource+npm@fb.com>`)이 관리자, `github.com/facebook/astryx` 실재
- 버전 0.5.2, 주간 다운로드 약 10.6만, 컴포넌트 163종
- 테마는 `astryx theme build`가 `@scope([data-astryx-theme="…"])`로 감싼 정적 CSS를 만든다
- 지침이 Tailwind 유틸리티 클래스 사용을 금지한다

네 가지 적용 방식(부분 적용 · 기본 테마 · neutral · stone)을 같은 화면으로 렌더해 비교했고
`neutral`을 선택했다.

`@astryxdesign/core`는 [`CLAUDE.md`](../../CLAUDE.md)가 열거한 승인된 외부 의존성에 없었다.

### 결정

1. `@astryxdesign/core@0.5.2`를 `web/frontend`의 dependency로 추가하고 **승인된 외부
   의존성으로 등록한다.** 버전은 고정하며 자동 갱신하지 않는다.
2. `@astryxdesign/cli`는 devDependency로만 둔다. 테마 빌드와 컴포넌트 조회 도구이며 런타임
   코드가 아니다.
3. 테마는 `neutral`을 쓴다. `astryx theme build` 산출물(CSS·JS)을 저장소에 커밋하고 런타임
   `defineTheme()`은 쓰지 않는다. 런타임 테마는 hydration 이후에 주입되어 첫 페인트와
   결정적 산출을 깨뜨린다.
4. 색 모드는 **라이트 우선**으로 고정한다. 다크 모드는 이번 범위가 아니다.
5. **서체는 현행 Pretendard 자체 호스팅을 유지한다.** neutral이 지정하는 Figtree와 Montserrat에는
   한글 글리프가 없어 한글 본문을 담당할 수 없다. 시안에서는 비교를 위해 웹폰트를 썼으나,
   운영은 내부망이 경계이므로 **런타임에 외부 폰트 호스트를 부르지 않는다.** neutral 테마의
   `--font-family-*` 토큰은 Pretendard를 앞에 둔 스택으로 덮어쓴다.
6. 외부 통신은 **빌드 타임 npm 레지스트리 접근에 한정**한다. 런타임에 Astryx가 외부로 나가는
   경로를 만들지 않는다.
7. `astryx theme add neutral`이 만드는 아이콘 레지스트리(`icons.tsx`)가 `lucide-react`를
   import하므로 `lucide-react@1.39.0`도 dependency로 고정해 함께 승인한다. 0단계에서는
   테마 CSS만 import하므로 번들에 들어가지 않고, 화면 이행이 아이콘을 쓸 때부터 사용된다.

### 대안

| 대안 | 기각 사유 |
|---|---|
| 현행 유지 | 같은 의미가 화면마다 다르게 보이는 문제를 해결하지 못한다 |
| Astryx 전면 재작성 | Tailwind와 공존하지 않아 프론트엔드 재작성이 된다. 회귀 위험이 이번 개선의 이득보다 크다 |
| 다른 디자인 시스템 | 밀집 표·상태 표현·상세 패널을 한 벌로 제공하는 후보를 이번 비교 범위에서 찾지 못했다 |

### 결과

- 화면 단위 이행이 가능해진다(ADR-0040).
- 이행 기간 동안 Tailwind와 Astryx가 저장소에 함께 존재한다.
- 0.x 버전이므로 breaking change를 감수한다. `astryx upgrade --apply`가 있으나 버전 갱신은
  별도 결정으로 다룬다.

## ADR-0040: 레이아웃 소유권과 화면 단위 이행

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-02 |
| 선행 결정 | ADR-0039 |
| 정본 | 이 문서, [`PLAN.md`](PLAN.md) |

### 문맥

Astryx 지침은 레이아웃을 컴포넌트로만 구성하고 `<div>`를 쓰지 말라고 요구한다. 그 규칙을
따르면 현행 화면 골격(사이드바 248px, 상단바 76px, 대시보드 `1.25fr : 0.95fr` /
`1.55fr : minmax(320px,1fr)`, 대기열 목록 pane `min(390px, 34%)`)을 Astryx의 페이지 템플릿으로
갈아엎어야 한다. 시안으로 확인한 결과, 골격을 유지한 채 컴포넌트만 바꿔도 화면은 성립한다.

### 결정

1. **레이아웃은 프로젝트가 소유한다.** 화면 골격과 그리드 비율은 현행 구현을 정본으로 삼고,
   Astryx의 페이지 템플릿으로 대체하지 않는다. Astryx의 "레이아웃도 컴포넌트로만" 규칙은
   이 저장소에 적용하지 않는다.
2. Astryx 페이지 템플릿은 **참조 자료로만** 쓴다. 필요한 상호작용 패턴(토큰 필터, 저장된 뷰,
   크기 조절 상세 패널, 접이식 그룹)만 골라 현행 골격 안으로 가져온다.
3. **화면 단위로 이행한다.** 테마 CSS가 `@scope`로 격리되므로 이행한 화면과 하지 않은 화면이
   한 앱 안에서 충돌 없이 공존한다.
4. Tailwind는 제거하지 않는다. 다만 **한 화면 안에서 두 체계를 섞지 않는다.** 이행을 마친
   화면은 Tailwind 유틸리티 클래스를 쓰지 않고, 색·간격은 Astryx 토큰만 읽는다.
5. 골격 CSS도 값을 새로 정하지 않고 Astryx 토큰(`--color-*`)을 읽는다.

### 결과

- 되돌리기 단위가 화면 하나다. 문제가 생기면 그 화면만 되돌린다.
- 이행 완료 화면과 미이행 화면의 모양이 한동안 다르다. 이는 의도한 상태다.
- 골격 CSS를 직접 유지해야 한다. 시안에서 세 화면 골격이 164줄이었다.

## ADR-0041: 정보구조와 판정 동선

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-02 |
| 선행 결정 | [`../business-rules.md`](../business-rules.md)의 판단 단계 정의 |
| 정본 | 이 문서, [`PRD.md`](PRD.md) |

### 문맥

`route-meta.ts`는 모든 화면을 `dataScope: "run"`(회차 종속, 9개)과 `"cumulative"`(누적, 10개)로
나눈다. 그러나 사이드바는 모니터링·판정·기준·운영으로 묶여 이 축이 드러나지 않고, 상단 회차
선택기가 화면마다 나타났다 사라진다.

사이드바 16항목 중 `/deadlines`와 `/audit`은 리다이렉트, `/reviews`는 미구현 안내,
`/judgments`는 선택 없는 상세 화면이다. 반대로 최종 Go/No-Go(`/opportunities/:id/bid-delta`)와
심층 검토 보고서(`/deep-reviews/:id`)는 사이드바에 항목이 없다.

판정 동선도 화면마다 다르다. 검토 대기열은 목록과 상세를 나란히 놓고 한 화면에서 판정하지만,
발주계획 C-2와 사전규격은 목록에서 상세 페이지로 이동해야만 판정을 저장할 수 있다.

### 결정

1. 사이드바 1차 분류를 **회차 검토 / 누적 추적**으로 바꾼다. 기준·운영은 그 아래 별도 묶음이다.
2. 메뉴 항목을 **16에서 8로** 줄인다. 리다이렉트 항목은 각 화면의 저장된 뷰로 흡수하고,
   기준 4개는 한 화면의 탭으로, 운영 3개와 감사 로그는 한 화면으로 묶는다.
3. **최종 Go/No-Go를 최상위 메뉴로 올린다.** 빈도는 낮아도 되돌릴 수 없는 결정이다.
4. **판정 입력은 목록과 같은 화면에 둔다.** 목록에서 상세 페이지로 이동해야만 판정할 수 있는
   구조를 없앤다. 저장 후 다음 항목으로 이동하는 조작을 모든 판정 화면에 둔다.
5. 다음은 **바꾸지 않는다.**
   - 적합성 등급, 참여 준비 상태, 심층 추적 승인, 최종 Go/No-Go는 각각 별도 조작으로 남긴다.
     화면 수를 줄이려고 한 컨트롤로 합치지 않는다.
   - `unknown`과 `null` 표기를 빈칸으로 바꾸지 않는다. 확인 대기와 값 없음은 다른 상태다.
   - 회차 종속 화면과 누적 화면을 한 목록으로 합치지 않는다.
   - 운영 텔레메트리(`model_digest`, token 수, `duration_ms`)를 삭제하지 않는다. 판정 화면에서
     분리하되 감사 목적으로 접근 가능한 자리에 남긴다.

### 결과

- 메뉴가 업무 축과 일치해 회차 선택기의 등장·소멸이 예측 가능해진다.
- 판정 화면 세 곳의 조작 방식이 하나로 통일된다.
- 리다이렉트로 존재하던 진입점 두 개가 사라지므로, 기존 링크와 북마크는 각 화면의 저장된 뷰로
  연결한다.
