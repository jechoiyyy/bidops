# 사전규격 파싱 비교에 Codex CLI Luna 추가 — 2026-09-07

## 결과

사용자가 지정한 `gpt-5.6-luna`·`xhigh`를 실제 Codex CLI로 실행해 기존 세 방식과 비교했다. 공고 3건의 같은 이미지 16쪽을 사용했다. 고정 확인 항목 22개는 네 방식 모두 보존했다. Luna는 Qwen에서 발견한 두 글자 오독을 정확히 전사했고, 목차/본문 분류가 assistant 참조와 16/16 일치했다. 그러나 개요 범위는 3건 중 1건만 참조 범위와 일치했다.

| 구분 | 현재 방식 | Qwen 이미지 전사 | 직접 추출·시각 검토 | Codex CLI Luna xhigh |
|---|---|---|---|---|
| 고정 문자열·숫자 22개 | 22/22 | 22/22 | v2 22/22 (v1 20/22) | 22/22 |
| 목차/본문 분류 | 해당 출력 없음 | 15/16 | 직접 지정 | 16/16 |
| 개요 본문 범위 | 2건 대기, 1건 목차 선택 | 0/3 일치 | 직접 지정 | 1/3 일치 |
| PDF 요구사항 9분류 수량·합계 24 | 텍스트 보존, 표 구조 없음 | 표로 보존 | 표로 보존 | 표로 보존 |
| 확인된 전사 사례 | 두 원문 표현 보존 | 초기자료→조기자료, 기술적용계획표→기술적응계획표 | 두 원문 표현 보존 | 두 원문 표현 보존 |

22/22는 전체 정확도 100%가 아니다. 사전에 고정한 표현의 존재 검사이며 모든 문장·조건·표를 검사하지 않았다. 두 오독 사례는 Qwen 검토 중 발견했고 Luna에는 알려주지 않았다. 직접 방식은 수동 개입이 있으므로 자동 모델보다 우수하다는 성능 순위에 쓰지 않는다.

## 실행 조건

- 입력: [기존 비교](20260907-prespec-parsing-comparison.md)의 동일 HWP·HWPX·PDF 원문에서 렌더링한 16쪽.
- 공고: pre:R26BD00269025, pre:R26BD00269447, pre:R26BD00269653.
- 문서별 별도 fresh CLI 실행 1회씩, 총 3회 완료. 기존 Qwen·직접 추출·평가 정답은 전달하지 않았다.
- 모델/추론: `gpt-5.6-luna`, `xhigh`.
- CLI: `codex-cli 0.153.4`. 이 설치본은 `--effort`를 인식하지 않아 실제 실행은 아래 동등 설정을 사용했다. `--effort` 구문 확인은 모델 호출 전 인자 오류로 끝났다.

```bash
codex exec --model gpt-5.6-luna   -c 'model_reasoning_effort="xhigh"'   --ignore-user-config --ephemeral --sandbox read-only   --skip-git-repo-check --cd <문서별 실험 디렉터리>   --output-schema <동일 출력 스키마> --json   --image <페이지 이미지> ... --output-last-message <결과 파일> -
```

추론 수준 설정은 [공식 Codex 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference)의 model_reasoning_effort를 따랐다. [공식 Luna 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-luna)는 이미지 입력과 xhigh를 지원한다고 명시한다. 실험 결과는 문서 설명이 아닌 실제 실행에서 확인했다.

공통 작업 지시: 모든 보이는 텍스트와 표 전사, 없는 내용 추정 금지, 목차/본문 구분, 실제 사업 개요 본문 페이지 식별. Codex에는 별도로 도구·파일 탐색·브라우징·위임을 하지 않고 첨부 이미지만 읽도록 했다. CLI item 이벤트에서 세 실행 모두 추가 tool event 0건을 확인했다.

Qwen은 API system/user 메시지, Luna는 Codex CLI의 기본 지시와 사용자 프롬프트를 받는다. 따라서 모델만 교체한 동일 API 조건 실험은 아니다. Qwen thinking off와 Luna xhigh, 이미지 tokenization·런타임 지시가 다르다는 점을 보존한다.

사용자의 이번 명시적 Codex CLI 테스트 지시로 선택 이미지 16쪽을 해당 실행에 사용했다. 운영 C-1·개요·심층 모델 설정을 바꾸거나 자동 fallback으로 연결하지 않았다. CLI stdout/stderr 원응답은 메모리에서 받아 기존 model-response 저장소에 암호화하고 AuditEvent에 hash를 남겼다. 원문 이미지 hash, 요청 설정, 비교용 파싱 산출물은 비공개 실험 디렉터리에 보관한다.

## 문서별 관측

| 문서 | 실제 개요 본문(제공된 페이지 중) | Qwen 선택 | Luna 선택 |
|---|---|---|---|
| HWP: 빅데이터 활용체계 고도화 | 4, 5, 7, 9 | 4, 5, 7, 9, **10** | 4, 5, 7, 9, **10** |
| HWPX: 국세법령정보 등 유지관리 | 4, 5 | 4, 5, **6** | **4, 5** |
| PDF: 국가전문자격 유지보수 | 3 | 3, **4, 6, 7** | 3, **4, 6, 7** |

HWPX 3쪽 하단에는 본문 시작 제목만 있고 목차가 함께 있다. 따라서 페이지 종류는 mixed가 참조값이다. 첫 비교의 제목 포함 집합은 [3,4,5]였으나 본문 범위를 비교할 때 제목만 있는 3쪽의 포함/제외는 오류로 계산하지 않았다. 고정 checks.json을 변경하지 않았으며 four-way-metrics.json은 필수 본문 페이지·선택 가능한 제목 페이지·초과 페이지를 분리해 기록한다. 이 처리는 Qwen과 Luna 모두에 동일하게 적용했다.

두 모델 모두 HWP 10쪽의 '업무 및 정보시스템 현황', PDF 4·6·7쪽의 과업 내용·요구사항 표를 개요로 포함했다. 숫자가 보존돼도 분석 입력의 범위가 넓어질 수 있다는 뜻이다. 공통 지시에는 같은/상위 장 제목에서 종료하는 규칙이 충분히 상세하지 않아, 모델 고유 능력의 한계로 일반화하지 않는다.

Luna의 HWPX 목차에서는 Qwen이 오독한 기술적용계획표를, PDF 표에서는 초기자료를 정확히 전사했다. 이는 확인한 사례의 개선이며 Luna의 나머지 전사 전체가 무오류라는 뜻은 아니다.

## 시간·토큰

| 문서 | Qwen | Luna CLI |
|---|---:|---:|
| HWP | 약 91.1초 | 약 129.3초 |
| HWPX | 약 80.2초 | 약 88.3초 |
| PDF | 약 82.6초 | 약 96.8초 |

Qwen 시간은 요청·응답 저장·후처리 구간, Luna는 CLI subprocess 실행 시간이다. 두 시간 모두 원문 렌더링·직접 검토를 제외하며 측정 경계가 완전히 같지 않다. 한 번씩 실행한 관측값으로 반복 실행 분산을 측정하지 않았다.

Qwen reported usage: 입력 31,729, 출력 6,139. Luna CLI reported usage: 입력 77,671, 출력 15,625, reasoning_output_tokens 7,659. 토큰화·기본 프롬프트·추론 설정이 달라 토큰 수를 문자량이나 직접적인 품질 지표로 해석하지 않는다.

## 판단과 다음 비교

이 표본에서는 Luna가 전사 표현과 목차 분류에서 개선을 보였지만 개요 경계 문제는 남았다. 기존 파싱 결과에도 확인 항목이 있었으므로 파서를 통째로 LLM으로 바꾸는 것보다, 제목 정규화·목차/본문 분리·절 계층·페이지 위치를 먼저 바로잡는 방향이 타당하다.

다음 비교에서는 '개요의 시작과 같은/상위 장에서 종료'를 명시하고 페이지 단위가 아닌 시작/끝 블록 또는 영역을 출력해야 한다. 원문 숫자·문자·표 관계를 결정적으로 대조하고, 사람이 승인한 정답과 더 넓은 문서로 평가한 후 적용 범위를 결정한다.

이 보고서는 3건·16쪽의 `unmeasured_reference` 관측이다. 운영 판정, 최종 사업 결정, 정책 활성화 근거로 사용하지 않는다.
