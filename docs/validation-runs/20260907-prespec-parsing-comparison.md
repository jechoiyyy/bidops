# 사전규격 파싱 3방식 실제 비교 — 2026-09-07

## 결론과 범위

현재 방식은 표본에서 주요 내용을 추출했지만 개요 구간 선택에 실패했다. Qwen 이미지 전사는 표를 읽기 쉽게 복원했으나 일부 글자 오독과 개요 경계 과대 선택이 있었다. 직접 추출·시각 검토는 문서 구조 문제를 찾아 수정하는 데 도움이 됐지만 사람 개입 없는 자동 방식과 동등한 성능 비교가 아니다.

공고 3건, 비교 페이지 16쪽의 탐색 실험이다. 나머지 문서·전체 페이지로 일반화하지 않는다. 고정한 확인 항목 22개는 assistant가 이미지에서 읽은 참조값이며 사람이 승인한 정답이 아니다. 결과는 `unmeasured_reference`로 유지하고 정책 활성화나 운영 품질 승인에 사용하지 않는다.

페이지 번호는 실험 이미지 순번이며 문서에 인쇄된 쪽수와 다르다. HWP/HWPX 이미지는 저장소의 rhwp를 network-none container에서 렌더링했다. PDF는 PyMuPDF로 렌더링했다. 이미지 전송 수는 16이며 다른 페이지나 회사 프로필을 전송하지 않았다.

## 세 방식의 실행

1. 현재 방식: 동일 원문 3개를 실제 ClamAV → ScratchDocumentProcessor → network-none 문서 worker로 재파싱했다. 현재 deterministic_prefix_cut을 적용했다. 기존 실제 실행과 blocks·warnings·cut이 모두 일치했다. 원문 전체 파싱 결과 중 표본의 22개 확인 항목 보존 여부를 검사했다.
2. Qwen: 승인된 사설 Ollama의 qwen3.8:27b, digest `22130167c4c20e20c7b71454612966ca8e8171e9b3cc8ab6ce8aa6cbfec79643`. 기존 ModelClient의 overview 설정·host/revision 검증을 거쳐 이미지 content 배열을 전달했다. 문서당 1회, 총 3회 응답을 받았다. 파일 바이너리를 직접 읽힌 것이 아니라 동일 원문을 렌더링한 페이지 이미지의 전사를 요청했다. 각 이미지의 모든 텍스트·표 전사, 목차/본문 구분, 실제 개요 페이지 식별을 요청했고 기존 파싱 텍스트·직접 검토 결과는 보내지 않았다.
3. 직접 방식: assistant가 별도 추출기를 작성했다. HWP 계열은 렌더링 SVG XML의 문자 좌표를 조합했고 PDF는 PyMuPDF의 텍스트·표를 추출했다. assistant가 이미지와 대조해 페이지 종류와 개요 경계를 직접 정했다. 이는 별도 자동 LLM 호출이나 독립적인 HWP 바이너리 파서가 아니다. rhwp 렌더링 손실은 Qwen과 직접 방식 모두에 영향을 줄 수 있다.

운영 파서·프롬프트·리뷰 상태는 변경하지 않았다. 실험 요청·응답의 식별자와 hash는 AuditEvent에 남겼고 원응답은 model-response에 암호화 저장했다.

### 현재 방식에서 확인한 문제

- HWP: 8,701블록으로 추출됐지만 no_end_heading으로 개요 입력을 만들지 못했다.
- HWPX: 5,684블록을 추출했지만 ordinal [28,38), 목차 10블록을 개요로 선택했다. 기간·예산 본문은 전체 파싱 결과에 존재했다.
- PDF: 84페이지를 84개 문단 블록으로 저장했다. pdf_poppler_fallback·pdf_stdlib_text_fallback 경고 때문에 개요 선택이 중단됐다. 22개 표본 항목 중 이 문서의 7개 항목은 원문 추출 텍스트에 있었다.
- HWP/HWPX의 page 필드는 XML section 열거값을 사용한다. 이 표본은 각각 3·2개 page 항목인 반면 rhwp 렌더링은 256·159쪽이었다. 이것을 실제 화면 쪽수로 해석하면 근거 탐색 위치가 어긋난다. 렌더링 쪽수도 폰트·레이아웃에 영향받으므로 원본 인쇄 쪽수의 정답으로 단정하지 않는다.

### Qwen의 장점과 오류

- 기간·예산 표본 항목을 모두 보존했고, PDF 요구사항 총괄표의 SFR 5, MAR 6, SER 2, MHR 1, QUR 1, DAR 1, COR 3, PMR 4, PSR 1과 합계 24를 보존했다.
- HWP 성과지표 표의 측정산식과 목표치, HWPX 예산 표의 총액과 연차 금액 관계를 Markdown 표로 복원했다.
- 이미지 대조에서 PDF 표의 `초기자료`를 `조기자료`로, HWPX 목차의 `기술적용계획표`를 `기술적응계획표`로 전사한 오류를 확인했다. 이 두 항목은 고정 22개와 별개로 결과 검토 중 발견한 사례다.
- HWPX 3쪽은 목차와 본문 시작 제목이 함께 있는데 toc로 분류했다. 전사문에는 본문 제목이 남았지만 overview_pages에서는 빠졌다.
- 개요 페이지: HWP [4,5,7,9,10]으로 시스템 현황 장의 10쪽을 포함했다. HWPX [4,5,6]으로 다음 사업내용 장의 6쪽을 포함했다. PDF [3,4,6,7]로 과업 내용·요구사항 표까지 포함했다.
- 이번 프롬프트는 actual business/project overview body를 요구했으나, 같은/상위 절 제목에서 종료하는 규칙을 상세히 지정하지 않았다. 이 첫 프롬프트의 결과를 Qwen의 일반적인 경계 추론 능력 한계로 단정하지 않는다. 재실험 시 경계 계약을 먼저 명시해야 한다.

### 직접 방식에서 확인한 문제와 수정

첫 SVG 추출기는 x/y 속성만 읽어 transform=translate/scale로 표현된 각주를 누락했다. 고정 항목 중 HWPX의 일할 계산·국회 심의 조건 2개가 빠졌다. 원문 이미지로 발견한 뒤 해당 좌표 표현을 처리하는 v2를 만들었고 22개 모두 보존됐다. v1을 덮어쓰지 않았다.

PDF는 표의 행·열을 구조로 복원했다. HWP 계열은 좌표·행 텍스트가 남지만 일반적인 표 셀·병합 관계까지 복원하는 구현은 아니다. 개요 경계와 목차 분류에는 assistant가 직접 개입했으므로 자동화 비용과 정확도를 별도로 평가해야 한다.

## 시간과 실행 오류

| 문서 | 현재 방식 재파싱(검사·worker 대기 포함) | Qwen 요청·응답 저장·후처리 구간 |
|---|---:|---:|
| HWP | 3.133초 | 약 91.1초 |
| HWPX | 1.223초 | 약 80.2초 |
| PDF | 9.721초 | 약 82.6초 |

현재 방식은 파일 전체, Qwen은 선택한 이미지 페이지를 처리했다. Qwen 시간에는 원문 렌더링을 포함하지 않는다. 조건이 달라 전체 처리 속도 비율로 일반화하지 않는다. 직접 방식은 수동 검토 시간을 계측하지 않아 속도 순위를 매기지 않는다.

Qwen 사용량은 입력 31,729토큰, 출력 6,139토큰이었다. 3개 응답 모두 finish_reason=stop이며 로컬에서 응답 schema와 입력 페이지 일치 검증을 통과했다. 이는 전사 정확성 검증과 별개다.

실험 스크립트에서 jsonschema 의존성이 없어 응답 암호화 저장 뒤 후처리가 실패했다. 모델은 재호출하지 않고 저장된 객체의 version·hash를 검증한 뒤 응답을 복구해 host에서 schema 검증했다. 현재 방식의 첫 재실행 wrapper는 반환 dict를 속성으로 읽는 오류가 있어, wrapper만 수정해 실제 파싱을 다시 실행했다. 두 오류는 모델·문서 파서 실패로 집계하지 않는다.

## 다음 구현 방향

현재 파서를 우선 고칠 지점은 본문 추출 자체보다 제목 정규화, 표 안 제목, 목차/본문 분리, 절 계층, 실제 페이지와 section의 분리다. PDF는 경고 종류를 구분하고 구조를 보완할 필요가 있다.

Qwen은 표·이미지의 보조 전사나 경계 후보 제안에 활용할 수 있다. 다만 원문 문자·숫자·표 관계와 대조하는 검증이 필요하고, 이번 결과만으로 기존 파서를 전면 대체할 근거는 없다. 직접 방식은 회귀 사례와 검증 기준을 만드는 데 사용하고, 사람 승인 기준을 확보한 후 더 넓은 문서와 페이지로 비교해야 한다.
