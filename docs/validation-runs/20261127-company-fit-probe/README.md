# 2026-11-27 사전규격 회사 핏 측정 — 개요 → 사업 범위 카드 대조

사전규격 개요가 끝난 공고를 회사 사업 범위와 대조해 `matched`를 가려내고, `matched`이면 운영 분석 엔진(업무 근거 지도 엔진)으로 넘기는 흐름을 제품 밖에서 먼저 측정한 기록이다.
**제품 구현이 아니다.** DB 쓰기·화면·스위치는 없고, 결과는 이 폴더의 파일뿐이다. 품질 합격·운영 활성화 근거로 쓰지 않는다.

회사 핏은 회사가 어떤 사업을 하고 하지 않는지가 정해져 있어야 판정할 수 있다. 이번 측정에서 그 기준(사업 범위 카드)을 처음 만들었고, 기준이 확실해질수록 결과가 바뀐다. 그래서 아래는 "이렇게 구현했다"와 "이렇게 개선한다"로 나눠 적는다.

## 구현 방식

### 흐름

```text
사전규격 개요 run (completed, 결정적 검사 passed, auto_processing_predicate)
  → 회사 핏 (로컬 Qwen3.8:27B, 공고 개요 × 사업 범위 카드)
  → 결정적 검증기 (실패 시 1회 재호출, 그래도 실패면 사람 검토)
  → matched / mismatch / unknown
  → (목표) matched면 엔진 분석 제안 → 관찰 후 자동 요청으로 전환
```

| 대상 | 11-26 회차(compose 프로젝트 `bidops-prespec1126`) SW사업대상 38건 중 개요 completed 27건, 그중 개요 결정적 검사 passed 22건 |
| 모델 | LiteLLM `local-agent-main` → Ollama `qwen3.8:27b-ctx32k`(digest `41a558fc…`), 외부 전송 없음 |

### 사업 범위 카드

wiki(`categories/*`, `rules/no-bid.md`, `capabilities/work-*`, portfolio)에서 옮겼다. 독립 검토(차단 6·주의 8 반영)를 거쳤다.

- **scope 10개:** 홈페이지 구축, 고도화, 유지관리·위탁운영, 업무시스템, 모바일 앱, AI, 블록체인, 데이터 플랫폼, 클라우드·SaaS, 실적 있는 물품. 각 scope는 `summary`·`includes`·`boundary`·`keywords`·실적 예시로 이뤄진다.
- **policy 4개**
  - `no-bid`(→ `mismatch`): 하드웨어 정비 주, 감리, 영향평가·컨설팅, 데이터 구매·납품 주
  - `caution`(→ `unknown`): 장비 구매 주, 선거, 단순 인력, 콘텐츠 제작·운영, 대형 SI
  - `onsite`: 대구 밖 상주 필수만 `mismatch`
  - `mixed-scope`: 섞인 사업은 주된 과업으로 판단
- **회사 방향 질문 11개 중 10개에 사용자가 답했다(2026-11-27).** Q8(AI 학습데이터·메타버스)은 미답이다.
- **wiki를 바꾸지 않았다.** 답변은 카드 파일에만 있다.

keywords만으로 거르면 22건 모두 걸린다. 그래서 keywords는 후보 힌트로만 쓴다.

## 개선 방안

1. **회사 방향을 확정해 wiki로 올린다.**
   - Q8과 Q10·Q11(상용SW 단독 유지보수·웹호스팅을 하지 않는지, 확인 대상인지)을 정한다.
   - 확정한 답을 `rootlab.yaml` `policy.no_bid_if`·`rules/no-bid.md`에 확인 수준과 함께 반영한다.
   - 카드는 손으로 고치지 않고 wiki에서 생성해 버전·sha256을 고정한다. 회사 방향이 바뀌면 카드 버전이 바뀌고 같은 gold로 다시 잰다.
2. **새 회차로 다시 잰다.** 카드 v1.2 + 프롬프트 v3.1을 고정하고, 카드를 만들 때 보지 않은 회차(11-27 이후)에서 같은 방식으로 측정한다. 그 회차의 gold는 사람이 건별로 판정한다.
3. **실행마다 흔들리는 판정에 대비한다.** `matched`는 2회 호출이 모두 `matched`일 때만 내는 방식을 비교한다(호출 2배, 건당 약 100초).
4. **남은 오류 유형에 결정적 검사를 붙인다.**
   - `mismatch`가 인용한 policy 항목이 공고의 주된 과업 문구와 맞는지 사람 검토 신호로 남긴다(37·4번 유형).
   - 프롬프트 문구 추가는 효과가 없었다(v3.2).
5. **제품에는 수동 모드부터 넣는다.**
   - 스위치는 `off` / `suggest` / `auto_request` 셋이다. 감사 기록이 남는 DB 행으로 두고, 회사 핏 프롬프트·카드 버전에 묶는다.
   - `suggest`에서는 `matched`를 추천으로만 보여 준다. 사람은 "맞음/아님"과 엔진 분석 요청을 남긴다.
   - 미리 정한 기준을 통과하면 `auto_request`로 전환한다. 기준 예: `matched` 30건 이상, 2주 이상, 정밀도 80% 이상, 중요 누락 1건 이하.
   - 실무자 시뮬레이션(에이전트) 결정은 지표에서 뺀다.
6. **엔진 연결은 ADR-0078을 개정한 뒤에 한다.**
   - 지금 엔진 요청은 사람의 추적 시작에서만 나오고, 전송 승인은 공고 단위다.
   - 엔진 자동 실행(공고별 전송 승인 없이)은 이 범위 밖이다.
   - RL-11 브랜치(`feat/rl11-track-start-entry`, 미병합·mock)의 병합과 live 전송 경로가 먼저 필요하다.
