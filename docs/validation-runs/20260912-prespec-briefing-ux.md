## flake로 확인한 실패

전체 게이트 실행마다 **서로 다른 한 건**이 실패했고 셋 다 단독 실행에서 통과했다.

| 실패 | 단독 재실행 | 판단 |
|---|---|---|
| `pre-specs.spec.ts` ERP 상세 1280 | 통과 | 병렬 부하 flake |
| `screen-semantics.spec.ts:93` 흡수한 마감·감사 경로 | 통과 | 병렬 부하 flake |
| `draft.spec.ts:63` 사업 추적 미저장 입력 | 3/3 통과 | 이번 변경이 건드리지 않은 파일(`git status` 확인) |
| `screen-semantics.spec.ts:93` 흡수한 마감·감사 경로 | 46/46 통과 | 같은 파일 둘 다 `git status` 깨끗함 |
| `common-interactions.spec.ts:344` 흡수한 옇 경로 | 46/46 통과 | 위와 같은 라우트 계열, 병렬 부하에서만 재현 |

`screen-semantics.spec.ts:93`은 여러 회 실행 중 간헐적으로 실패해 단독으로 다시 확인했고
오류 출력 없이 통과했다. 대시보드·라우트 계열이며 이번 변경 경로와 곹치지 않는다.
이 저장소의 기존 부하 민감성으로 보고 남긴다 — 이번 변경의 회귀가 아니며, 고치려면
해당 spec의 fixture·locator를 따로 보는 별도 작업이 필요하다.

`engineering-notes.md`의 "이름만으로 고른 locator" 항에 따라 부하 탓으로 넘기기 전에
각각 단독 실행으로 확인했다. 세 건 모두 이번 변경과 무관하다.

## 검토가 잡은 결함(generation 1 → 2)

`architect` 검토가 내가 놓친 차단 결함 둘을 찾았고 둘 다 실제 결함이었다.

1. **키보드 경계 페이징이 동작하지 않았다.** `updateSearchParams`가 마지막에 `offset`을 무조건
   지워서, 경계에서 방향키로 다음 페이지를 요청하면 1페이지로 돌아갔다. 내 신규 spec은
   한 페이지짜리 fixture만 썼어서 이 경로를 전혀 닿지 못했다. 호출자가 `offset`을 명시적으로
   준 경우에만 유지하도록 고치고, 260건·200/페이지 fixture로 실제 전환을 단정하는 spec을 더했다.
2. **빈 목록 문구가 거짓말을 했다.** 페이지 한정 필터로 0건이 된 경우에도 `누적 수집된 사전규격
   데이터가 아직 없습니다`로 떨어졌다. 불러온 행은 있는데 데이터가 없다고 말하는 것이므로
   `docs/standards.md`의 값 구분 규칙 위반이다. 필터별 문구로 나눠 고쳤다.

함께 반영한 비차단 지적: `표시 범위` 대화상자·목록 바닥에 추적 결정 필터의 페이지 한정 사실
명시(D9), `등급 사유` 위치를 계획 순서(지켜야 할 조건 다음)로 이동하고 PRD를 같은 순서로 맞춤.

generation 3에서 추가로 고친 것: 목록 pane의 `미확인` 구역 제거(개요 구역이 이미 갖는다),
이전 개요 결과의 `claim-{id}` anchor 중복 제거(현재 결과만 anchor를 소유),
`next_action`만 있는 판정에서 빈 구역이 생기던 문제, 그리고 죽은 CSS 선택자 정리.

### 검사가 검사를 못 하던 자리

anchor 중복을 막고 나서 넣은 유일성 단정이 **그 fixture에서는 절대 실패할 수 없는** 상태였다.
같은 run을 current와 history에 둘 다 주었는데 history filter가 그것을 걸러 내 이력이 비었고,
그러면 두 번째 anchor 집합이 아예 생기지 않는다. **고친 자리는 고치기 전으로 되돌렸을 때
실제로 실패하는지 확인했다** — 이제 id가 다른 이전 결과를 fixture에 두고, `anchor={false}`를
되돌리면 이 spec이 실제로 실패한다(확인함). 같은 점검에서 첫 단정은 범위가 너무 넓어
접힌 이력 안의 과거 회차 내용까지 중복로 졌기 때문에, "한 번에 보이는 자리"로 좁혔다.

## 빨간팀 QA

`executor` 빨간팀 lane이 실제 브라우저 자동화로 50개 공격 단정을 실행해 전부 통과했다 — 적대적
`lifecycle`·`procurement_class` JSON(배열·중첩 객체·숫자·문자열 `unknown`), 위험한 첨부 URL
(`javascript:`·`data:`·프로토콜 상대·자격증명 포함), 등급 5값 구분, 토글 규칙표 15행, URL 인자
주입(`<script>`·경로 우회·`%00`), 다음 작업 문장이 추적 컨트롤을 가리지 않는지. 실제 결함 0건.
검증용 scratch spec과 artifact는 저장소에 남기지 않고 삭제했다.

## 구현 중 실제로 발견해 고친 결함

1. **행 키보드 이동이 조용히 동작하지 않았다.** `PreSpecRow`가 `...rowProps`를 구조
   분해만 하고 `DenseListRow`에 내려 주지 않아 `data-row-key`·roving `tabIndex`가 DOM에
   닿지 않았다. 선택은 옮겨지는데 초점만 멈춰 있어 눈으로는 알기 어렵다. 이제 행 요소까지
   내려 주고 신규 spec이 이를 고정한다.
2. **같은 주장이 한 카드 안에서 두 번 보였다.** `OverviewResult`의 결과 머리줄이 첫 주장을
   말하는데 `문서 근거` 목록이 같은 문장을 다시 적었다(이번 변경 이전부터). 근거 목록에서
   첫 주장을 제외했고 근거 건수도 같은 기준으로 센다.
3. **문서 준비 패널이 조작 도중 스스로 닫혔다.** 묶음 확정으로 상태가 `ready`가 되면
   기본값 규칙이 다시 계산돼 방금 한 조작의 결과가 사라졌다. 기본값은 묶음 응답이 도착한
   뒤 한 번만 잠그고, 닫는 것은 사람의 명시적 조작일 때만으로 바꿨다.

## 계획과 다르게 결정한 것

- **`NO_CURRENT_ATTEMPT_NOTICE`**: 개정안은 `회사 핏 판정 없음(자동 판정 비활성)`을
  제안했지만, 이 문구는 `automation_enabled=true`인데 판정만 없는 경우에 **없는 사실을
  단정**한다. `회사 핏 판정 없음 · 불일치 아님`으로 줄이고 비활성 문구는 실제로 비활성일
  때만 덧붙인다. `판정 없음 ≠ 불일치` 의미는 그대로다(CLAUDE.md 강제 게이트).
- **`CompanyFitExecutionInfo` 이동(D4)**: `company-fit.spec.ts`가 목록·상세 **두 경로
  모두**에서 이 정보를 회사 핏 구역 안에서 단정한다. 접힌 `<details>` 안에 있어 이미
  본문 밀도를 차지하지 않으므로 이동하지 않고 제자리에 뒀다.
- **목록 pane의 `PageOverviewSection` wrapper 제거(§6)**: 시도했으나 이 wrapper가
  목록 경로에서 검증된 본문·PDF 페이지 근거·이전 결과·조회 실패 문구까지 소유하고 있어
  `page-overview.spec.ts` 5건이 이를 단정한다. 제거하면 그 계약이 목록 경로에서 사라진다.
  wrapper는 유지하고, 실제 중복이던 **같은 주장 두 번 렌더**만 위 2번으로 해결했다.
