- 70건 이상 두 건은 대조·종합 호출 입력이 27.2만 토큰을 넘어 장문맥 할증(입력 2배, 출력 1.5배)이 붙었다. 문서 길이가 약 20만 자를 넘으면 할증 구간에 들어가 비용이 선형보다 빠르게 는다. 평균은 이런 큰 공고 몇 건에 크게 흔들리므로 **중앙값과 구간별 값을 함께 쓴다.**
- 같은 사례라도 실행마다 앞 단계 결과 길이가 달라 뒤 단계 입력이 달라진다. N3753은 구독 실행에서 입력 61만·장문맥 0회, API 실행에서 82만·장문맥 2회였다. 반복 분산은 재지 않았다.

## 캐시 적중 실험 (같은 날)

API 키로 `codex exec`를 부르면 캐시 적중이 나지 않는 원인을 합성 텍스트(약 3.5만 토큰, 공고·회사 자료 아님)로 6회 시험했다(약 $0.03, `20261126-luna-cache-probe/`).

| 시험 | 캐시 적중 |
|---|---|
| 같은 프롬프트, 같은 작업 폴더 | 0 |
| 같은 프롬프트, 다른 작업 폴더 | 0 |
| 앞부분만 같은 프롬프트 | 0 |
| 같은 스레드 이어서(`codex exec resume`) | 0 (입력이 8.2만으로 늘어남) |

- 작업 폴더 경로(`<environment_context>`의 `<cwd>`)는 호출마다 달라지지만, 같게 해도 적중하지 않았다. `codex exec` 경로에서는 도구가 고칠 수 있는 원인이 없다고 판단했다.
- OpenAI 문서상 GPT-5.6 이후 모델은 기본(implicit) 모드에서 가장 마지막 메시지 끝에 캐시 경계를 하나 두고 그 지점까지 전체를 써서, 앞부분만 같은 다음 요청은 그 캐시와 맞지 않는다. 엔진은 지시문·문서·단계 지시를 메시지 하나로 보내므로 공통인 "지시문 + 문서"에서 경계를 둘 수 없다.
- 대응으로 평가 도구에 Responses API 직접 전송(`--transport responses`)을 추가했다. 지시문(developer)·문서(user, 끝에 명시적 캐시 경계)·단계 지시(user)로 나눠 보내며, 보내는 글자는 Codex 경로와 같다. 테스트 6건(가짜 응답은 공식 문서 형태)이 통과했다. 이 경로는 평가 도구 전용이며 제품과 RL 승인 모델 경로(codex-exec)는 그대로다.

## Responses API 확인 실행 (N4163, 같은 날)

도구 sha256 `d1d78336…`, 엔진 `17e4623a…`, 입력은 api1과 바이트 동일, 승인 `approval-20261126-responses.json`(`"transport": "openai_responses"`), 라벨 `resp1`, 같은 API 키.

| 단계 | Codex 경로 (API 키, api1) | Responses API (resp1) |
|---|---|---|
| extract | 입력 104,526 (전부 쓰기) · $0.0189 | 입력 91,122, 쓰기 84,189 · $0.0169 |
| units | 42,498 (전부 쓰기) · $0.0102 | 29,096, 쓰기 0 · $0.0077 |
| match | 181,321 (전부 쓰기) · $0.0296 | 169,754, **적중 84,189** · $0.0182 |
| synth | 205,329 (전부 쓰기) · $0.0304 | 194,152, **적중 84,189** · $0.0175 |
| 합계 | $0.0892, 280초 | **$0.0604 (−32%)**, 319초 |

- **캐시가 적중했다.** extract가 지시문+문서 84,189토큰을 썼고 match·synth가 그대로 읽었다. units는 경계를 두지 않아 쓰기가 없다.
- 줄어든 이유는 세 가지다: match·synth의 문서 부분을 0.1배 단가로 읽음, 문서 뒤 단계 지시는 쓰기 할증 없이 일반 단가, Codex 기본 지시문(호출당 약 1.3만 토큰)이 빠짐.
- 실제 응답의 `usage`는 `input_tokens_details.cached_tokens`·`cache_write_tokens`(+`cache_write_tokens_details.ttl_30m_tokens`/`ttl_12h_tokens`)·`output_tokens_details.reasoning_tokens`로, 테스트의 가짜 응답과 같은 형태였다. 엔진 `usage.json`·`analysis.json`에도 캐시 읽기 168,378·쓰기 84,189가 기록됐다.
- 결과 비교: 권고는 구독·Codex API·Responses 세 실행 모두 `NO_GO`, 적합 점수 32·29·31이다. Codex API와 Responses의 요구사항 판정은 38건 중 33건이 같고, 다른 5건은 모두 이웃 등급 사이(FULL↔PARTIAL 4건, GAP↔PARTIAL 1건)다. 1건 비교라 전송 경로가 품질에 영향이 없다고 단정하지 않는다.
- 다른 9건은 Responses 경로로 재지 않았다. 같은 구조(extract·match·synth가 문서를 공유)라 비슷한 절감을 예상하지만 측정값이 아니다.

## 후속

**반영함 (같은 변경, `scripts/engine-eval.py`)**

- 라이브 호출은 항상 `--json`으로 이벤트 스트림을 남기고(`calls/NN.trace.jsonl`, 0600), `turn.completed` 토큰을 합산한다. 턴이 끝나지 않은 호출은 0이 아니라 "미측정"(`usage: null`)으로 남긴다.
- 엔진 호출 기록(`CallRecord`, 엔진 `usage.json`)과 `ParseResult.usage`에 캐시 미적중 입력·캐시 입력·출력을 적는다. `cost_usd`는 Luna API 환산 금액(Standard 단가, 27.2만 토큰 초과 요청은 장문맥 단가)이고 `cost_basis=subscription`, `price_model=gpt-6-luna`다. 엔진 `analysis/spend.py`는 `subscription` 기록의 금액을 "API 환산 금액"으로 정의하므로 뜻이 같다.
- 호출 원장(`*.call.json`)에 원래 Codex usage(추론 출력 포함), `api_equivalent_usd`, `long_context`, `price_source`를 더한다.
- 단가는 도구의 `LUNA_USD_PER_MTOK`·`LUNA_PRICE_SOURCE` 한 곳에 둔다. 엔진 패키지의 `pricing.py`는 원본 파일이고 엔진 해시(`17e4623a…`)가 live3·운영과의 비교 기준이라 고치지 않았다. 엔진의 "모르는 모델은 알려진 최대 단가" 규칙은 그대로이며, BidOps에서 Luna를 실제로 부르는 경로는 이 도구뿐이다.
- 2026-11-21 N3235의 $3.36은 BidOps 밖 `bid-deep-agent` 저장소의 일회성 어댑터가 엔진 단가표로 계산한 값이다. 그 어댑터는 이 변경의 범위가 아니다.

**검증**

- `tests/test_engine_eval_usage.py` 7건: 이벤트 합산·미측정 처리·이상값, 표준·장문맥·캐시 쓰기 단가, 가짜 `codex`(실제 trace 형태)로 `CodexLunaTransport.parse`의 `ParseResult`·`CallRecord`·호출 원장·trace 권한. 수정 전 스크립트로 돌리면 실패(오류 6, 실패 1 — 토큰 0 기록)하고 수정 후 7건 통과.
- 이 실측의 실제 trace 43개를 새 함수로 다시 계산하면 합계 $0.8289, 장문맥 3회로 위 집계와 같다.
- `plan` 명령(모델 호출 없음)이 그대로 돈다.
- 엔진 파이프라인이 기록을 합쳐 `analysis.json`의 `usage`를 만드는 경로는 코드로만 확인했다. 수정된 도구로 라이브 실행을 1회 돌리기 전까지 그 합계 값은 "검증됨"이 아니다.

**남은 것: 캐시 적중이 나지 않는 문제**

- 엔진 프롬프트는 extract·match·synth가 **지시문 + 공고 문서 전체**라는 같은 앞부분을 공유한다(공통 접두 N4174 76,195자, N4163 140,450자, N3235 335,022자, 약 5.5만~20만 토큰). units만 다른 문서를 보낸다. 구조상 match·synth는 extract가 남긴 캐시를 읽어야 한다.
- 그런데 적중은 구독 실행에서 호출당 11,648토큰 안팎(Codex 기본 지시문 크기로 보인다), API 실행에서 0이다. 호출마다 새 임시 작업 폴더(`engine-eval-codex-XXXX`)와 새 스레드로 `codex exec`를 띄우므로, 우리 프롬프트 앞에 붙는 Codex 머리말(작업 폴더 경로가 들어가는 환경 정보 등)이 호출마다 달라져 공통 접두가 그 지점에서 끊긴다고 추정한다. 원인은 실제 요청 본문을 보지 못해 확인하지 않았다.
- 공고 문서 부분이 match·synth에서 적중했다면 이번 3건의 청구액은 $0.429에서 약 $0.297로 31% 줄었을 것이다(토큰/글자 비율로 환산한 추정).
- 확인 방법: 같은 공고의 호출들이 같은 작업 폴더를 쓰도록 바꾸고 1건을 다시 돌려 match·synth의 `cached_input_tokens`를 본다. 모델 호출이므로 따로 승인받는다.
- 그 밖에 줄일 지점은 27.2만 토큰 초과 요청(N3235 match·synth)의 분할이다.
