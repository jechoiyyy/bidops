# 2026-11-23 분석 작업 에이전트 위임 시험

분석 엔진이 프롬프트 한 번으로 답을 받는 대신, 공고 문서와 회사 자료가 든 폴더를 에이전트에게 맡겨 스스로 읽고 판정하게 하는 방식을 시험한 기록이다.
시험 기록이며 품질 합격·운영 활성화 근거가 아니다. 정답은 사람이 확인하지 않은 초안(gold v3)이다.

## 목표와 기준

- 목표: 담당자가 "이 공고에 참여할 만한가"를 판단하도록 돕는다(2026-11-22 사용자 결정).
- FULL의 뜻: 같은 종류의 업무를 수행한 기록이 있으면 FULL이다. 세부 조건까지 일치할 필요는 없다(2026-11-22 사용자 결정). 참여 자체를 막는 조건은 요구사항이 아니라 참가자격에서 따로 잡는다.
- 한도: codex exec 실행 7회(사용자 지정). 실행 1회가 시험 1개다.

## 시험 정의와 결과

지시문은 두 가지다.

- **지시문 1 (전체 위임):** 에이전트가 ① 위키 목차·규칙을 읽고 ② 실적 페이지를 전부 읽어 "실적별 업무 종류 색인"을 메모 파일에 만들고 ③ 문서에서 참가자격 조건을 유형 17가지 점검표로 찾고 ④ 요구사항을 10건 안팎씩 나눠 판정하며 묶음마다 메모에 적고 ⑤ 결과 JSON을 쓴 뒤 형식 검사 도구가 통과할 때까지 고친다. FULL은 "같은 종류의 업무 기록이 있으면", PARTIAL은 "일부 범위나 인접 업무 기록만 있으면"이다.
- **지시문 2 (업무 단위 분해 + 검토):** 지시문 1에서 세 가지를 바꿨다. ① 요구사항을 업무 단위로 나눠 모든 단위에 기록이 있으면 FULL, 일부 단위에 기록이 없으면 PARTIAL, 주제만 같은 다른 업무 기록은 근거가 아니다(UNKNOWN). 세부 수준 차이는 FULL을 유지하고 `uncovered`에 적는다. 기록 없는 단위가 회사가 하지 않는 분야이면 `out_of_field`로 표시한다. ② 판정 뒤 FULL·PARTIAL 전체를 한 번 다시 검토한다. ③ 참가자격은 반복 조건을 한 번만 적고 일반 준수 조항을 뺀다.

| 시험 | 공고 | 지시문 | 무엇을 보려 했나 |
|---|---|---|---|
| T1 | 양산 | 1 | 전체 위임이 성립하는지(에이전트가 실제로 자료를 읽고 끝까지 판정하는지) |
| T2 | 소방안전 | 1 | 같은 지시문이 다른 공고에도 통하는지 |
| T3 | 맞춤배움길 | 1 | 같음 |
| T4 | 맞춤배움길 | 2 | T1~T3에서 드러난 후한 판정을 업무 단위 분해로 줄일 수 있는지 |
| T5 | 소방안전 | 2 | 같음 |
| T6 | 양산 | 2 | 지시문 2를 세 공고 모두에서 확인 |
| T7 | 소방안전 | 2 | T5와 같은 입력을 다시 돌려 답이 얼마나 같은지 |

T1 뒤에 T2·T3를 고른 이유: T1이 이전 최고치를 넘었으므로 변형보다 일반화 확인이 먼저였다.
T3 뒤에 지시문을 바꾼 이유: 세 건 모두 낮은 판정은 2~4건인데 후한 판정이 9~20건이었고, 소방안전에서 하드웨어 부품 교체가 섞인 요구사항을 응용 SW 장애 복구 실적만으로 FULL로 판정했다. 참여 판단에는 후한 쪽 오류가 더 위험하다.

### 읽는 법

- **위임 방식 자체:** 세 공고 모두 이전 실험의 범위 이상이다. 양산 66~81%(이전 41~67%), 소방안전 74~81%(이전 47~57%), 맞춤배움길 61~65%(이전 42~65%). 자격 항목은 12/12·13/15·14~15/16을 찾았다(이전 C는 53~69%). 다만 모델·FULL 기준·구조가 함께 바뀌었으므로 어느 요인의 효과인지는 이 시험으로 가를 수 없다.
- **지시문 1 대 2:** 일치율은 소방안전 +7%p, 맞춤배움길 +4%p, 양산 −15%p로 엇갈린다. 양산에서는 업무 단위 분해가 정답 초안보다 엄격해져 FULL 12건을 PARTIAL로 내렸다. 반면 적합 점수는 지시문 2가 정답 초안에 더 가깝다(차이 −3~+4, 지시문 1은 +4~+6로 한쪽으로 치우침). 오류 방향도 지시문 2에서 균형에 가깝다.
- **참여 판단에 쓰이는 정보:** 지시문 2는 회사가 하지 않는 분야의 요구 범위를 따로 내놓는다(소방안전의 하드웨어 정비·부품 수급, 양산의 장비 하자 무상 교환, 맞춤배움길의 추천 모델 재학습). 정답 초안의 메모가 지적한 것과 같은 내용이고, 지시문 1의 결과에는 없던 정보다.
- **자격 판정 일치(53~69%)는 개선되지 않았다.** 어긋난 항목은 대부분 정답 초안 PASS 대 에이전트 RISK·UNKNOWN이다(투입 인력·상주·공동수급). 정답 초안은 총 인원 수 같은 집계 값으로 PASS를 줬고, 에이전트는 개인별 배정·가용 기록이 없다는 이유로 RISK를 줬다. 어느 쪽이 맞는지는 기준의 문제이며 사람이 정해야 한다. 소방안전의 직접생산 항목은 에이전트가 "문서가 10자리라고 적은 번호가 9자리"라는 이유로 UNKNOWN을 줬다.
- 자격 항목 중 `G2B_REGISTERED`·`TAX_DELINQUENCY`(소방안전) 누락은 정답이 입찰공고문에서 인용한 항목일 수 있다(엔진 입력은 사전규격 문서). 채점 도구가 이를 구분하지 못하는 한계는 이전과 같다.

## 판단

**채택 후보: 에이전트 전체 위임 + 지시문 2.** 근거는 다음과 같다.

1. 적합 점수가 정답 초안과 4점 안에 들고(4회), 같은 입력 반복에서 83·86으로 안정적이다. 이전 방식은 같은 입력에서 48↔70, 66↔83으로 흔들렸다. 목표가 "참여할 만한가"이면 개별 요구사항 일치율보다 이 점수와 조건 목록의 안정성이 중요하다.
2. 회사가 하지 않는 분야의 범위를 반복 실행에서도 같은 항목으로 내놓는다.
3. 시간은 이전과 비슷하다.

지시문 1은 양산에서 일치율이 더 높지만 세 건 모두 점수가 후한 쪽으로 치우쳐 채택하지 않는다.

- 3건 모두 루트랩이 수주한 공고다. 참여하면 안 되는 공고를 걸러내는지는 재지 못했다.

- 에이전트는 쓰기 가능한 작업 폴더에서 명령을 실행한다. 제품 경로에 넣으려면 실행 격리, 전송 승인·감사, 승인 모델 변경(RL은 gpt-6-luna/high), 판정 근거의 원문 위치 검증을 다시 설계해야 한다. 이 시험은 그중 어느 것도 다루지 않았다.

## 추가 시험: 참여하기 어려운 공고 (2026-11-23, 실행 7회)

앞 시험의 3건은 모두 수주한 공고라 걸러내는 능력을 재지 못했다. 사용자가 2026-10-20에 모델 출력 전에 직접 작성한 정답 10건(RL-05 `gold.v1.json`, `human_completed`)에서 골라 시험했다. 이 정답은 사람이 쓴 것이지만 당시 카드 판정용으로 쓴 것이라 요구사항별 FULL/PARTIAL은 없다. 그래서 권고와 차단 조건만 대조했다.

### 정의

- **지시문 3:** 지시문 2에 사용자 결정(2026-11-23)을 반영했다. ① 참가자격은 집계 값(총 인원, 등급·직군별 인원, 자격 보유 인원, 지역별 상주 가능 표시)만으로 충족을 판정하고 개인별 배정 기록이 없다는 이유로 RISK·UNKNOWN을 주지 않는다. ② 상주 장소가 프로필에서 상주 불가인 지역이면 FAIL이다. ③ 회사 위키 `rules/`의 제외 조건을 그대로 충족하면 FAIL, 일부만 해당하면 RISK다.
- 회사 자료: 현재 회사 묶음 전체(이 공고들은 2026-10 게시라 제거할 실적이 없다). 위키에 이 공고들의 발주처 이름이 없음을 확인했다.
- 입력: 평가 폴더 `.sdlc/local-runtime/engine-eval-20261123-neg/`(RL-05 문서 구조를 같은 도구로 동결, 엔진 mock 실행으로 문서·요구사항 파싱).
- 한도: 7회(앞 시험과 별도 묶음, 도구가 묶음별로 강제). 모델·실행 조건은 앞 시험과 같다.

- 그러나 "참여할 만한가"의 핵심인 차단과 자격 점검은 엔진 방식이 현재 코드로는 하지 못한다. 엔진 방식을 유지하려면 참가자격 코드에 상주 불가 지역 차단, 참여 제외 조건(`no_bid_if`) 적용, 위키 규칙 반영을 구현해야 한다. 회사 규칙을 글로 추가하면 바로 반영되는 에이전트 방식과 달리 규칙이 늘 때마다 코드 변경이 필요하다.
- 제품 경로 선택은 사용자 결정 대기다.

### 한계

- 각 1회 실행. 엔진 변형과 에이전트는 모델이 다르다(gpt-6-luna/high 대 gpt-6.2-sol/medium).
- 엔진 변형의 대조 프롬프트는 약 50만 자다. 호출당 입력 상한을 두는 기존 RL-11 계획(1만 6천 토큰)과 맞지 않는다.
- 맞춤배움길의 UNKNOWN 18건 원인은 확인하지 않았다.
