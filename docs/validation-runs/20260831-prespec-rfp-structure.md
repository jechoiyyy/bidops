# 제안요청서 소제목·목차 분포 측정 (2026-08-31, T-21)

앞부분을 어디까지 잘라낼지(T-22) 정하려면 실제 문서가 필요했다. 지금까지는
"소제목이 문서마다 다르고 목차가 있는 문서와 없는 문서가 섞여 있다"는 인상만 있었다.

## 방법

2026-08-28 고정 3일 표본의 첨부 URL 1,011개에서 `random.sample(seed=20260831)`으로
**120개**를 내려받았다. 전부 HTTP 200이고 합계 48.9 MiB다.

구조 추출은 제품의 `app.document_mcp.processor.DocumentProcessor`를 그대로 쓴다.
측정이 실제 애플리케이션이 보는 것과 같아야 하고 거부도 같아야 하기 때문이다.

문서 본문 바이트와 추출 텍스트는 저장소에 남기지 않는다. 파일명·크기·sha256·magic과
파생 구조 지표만
[`data/experiments/prespec-rfp-structure/20260831/`](../../data/experiments/prespec-rfp-structure/20260831/)에 둔다.

## 표본 구성

| 확장자 | 건수 | magic |
|---|---:|---|
| `.hwp` | 65 | OLE CFB 64, ZIP 1 |
| `.hwpx` | 34 | ZIP 32, OLE CFB 1, `9b204452`(미상) 1 |
| `.pdf` | 16 | `%PDF` 16 |
| `.zip` | 3 | ZIP |
| `.xlsx` | 1 | ZIP |
| `.docx` | 1 | ZIP |

파일명으로 분류하면 제안요청서·과업지시서 67, 공고문 22, 규격서 7, 기타 24다.

### 정책상 처리되지 않는 비율은 6.7%로 재확인됐다

미지원 확장자 5건(zip·xlsx·docx)과 확장자·내용 불일치 3건을 합쳐 **8/120 = 6.7%**다.
[30건 표본](20260830-prespec-attachment-probe.md)의 6.7%와 같다.

## host에서 PDF가 전부 실패한다 — 문서 문제가 아니다

처음 host에서 추출하니 PDF 16건 중 **15건이 `malformed_pdf`**로 막혔다. 원인은 문서가
아니라 환경이다. `DocumentProcessor`는 표준 PDF 파서가 실패하면 poppler로 fallback하는데
(`processor.py:315`), poppler가 없으면 fallback이 `malformed_pdf`를 던진다
(`processor.py:447-449`). `poppler-utils`는 컨테이너 이미지에 있고(`web/Dockerfile:48`)
host에는 없다.

같은 추출을 `bidops-mock-t7-web` 이미지 안에서(`--network none`) 다시 돌리자
**PDF 16건이 전부 성공**했다.

| 실행 환경 | ok | blocked | 미지원 확장자 |
|---|---:|---:|---:|
| host (poppler 없음) | 99 | 16 | 5 |
| 컨테이너 이미지 | **114** | **1** | 5 |

**문서 파이프라인 측정은 컨테이너에서 해야 한다.** host 결과는 poppler·ClamAV 같은
이미지 의존성이 빠져 있어 문서를 부당하게 거부한다. 아래 수치는 모두 컨테이너 실행이다.

추출 성능은 문제가 없다. 변환 시간 p50 0.31초, p90 0.56초, 최대 0.82초.
block 수는 p50 375, p90 1,694, 최대 7,747이다.

## 측정 결과 (제안요청서·과업지시서 65건)

### 목차가 있는 문서는 3분의 1뿐이다

| | 건수 |
|---|---|
| `목차`·`차례` 표제 보유 | **21/65 (32%)** |
| 없음 | 44/65 (68%) |

점선 leader(`······ 12`)로 목차를 찾는 방법은 쓸 수 없다. 추출 과정에서 점선이 탭으로
치환되어 **65건 전부에서 0줄**로 나온다. `목차` 표제가 유일하게 신뢰할 수 있는 신호다.

목차가 있는 문서는 목차 자체가 절 목록을 준다. 다만 형태가 일정하지 않다 — 절이 한 줄씩
분리된 문서도 있고 목차 전체가 한 block으로 뭉쳐 나오는 문서도 있다.

### 첫 번째 주제 소제목

| 소제목 | 건수 | 비율 |
|---|---:|---:|
| 사업개요 | 38 | 58% |
| 추진목표 | 9 | 14% |
| **찾지 못함** | **9** | **14%** |
| 제안절차 | 3 | 5% |
| 일반사항 | 2 | 3% |
| 사업예산 | 2 | 3% |
| 과업내용 | 1 | 2% |
| 사업기간 | 1 | 2% |

`사업개요`가 과반이지만 **58%뿐이다.** 나머지 42%는 다른 것으로 시작하거나 아예
소제목을 못 찾는다.

### 번호 체계에 지배적인 관행이 없다

| 최빈 번호 체계 | 건수 |
|---|---:|
| 아라비아 숫자 `1.` | 40 |
| 한글 `가.` | 9 |
| 원문자 `○` | 8 |
| 없음 | 7 |
| 로마자 `Ⅰ.` | 1 |

### `과업내용`이 아예 없는 문서가 3분의 1이다

| | 건수 |
|---|---|
| `과업내용`류 소제목 보유 | 43/65 (66%) |
| 없음 | 22/65 (34%) |

위치도 흩어진다. block 기준 최소 5, 중앙값 47, p90 **276**, 최대 **809**.

### 첫 주제 소제목의 위치

최소 2, 중앙값 32, p90 49, 최대 **211** block.

**고정된 "앞 N block을 자른다" 규칙은 성립하지 않는다.** 중앙값에 맞추면 p90 문서는
본문을 잘라먹고, 최대에 맞추면 절반이 표지·목차를 그대로 안고 간다.

### 절 순서에도 지배적인 패턴이 없다

가장 흔한 순서가 `사업개요 → 추진목표 → 사업기간 → 과업내용` 3건이다. 65건에서 3건이
최빈이라는 것은 사실상 공통 순서가 없다는 뜻이다.

## T-22에 넘기는 것

이 측정이 말하는 것은 명확하다. **문서 형식에 의존하는 단일 규칙은 만들 수 없다.**

- 목차 기반 규칙은 32%에만 적용된다.
- `사업개요`로 시작한다는 가정은 58%에만 맞는다.
- `과업내용` 절을 찾는 규칙은 66%에만 적용된다.
- 번호 체계로 절을 찾는 규칙은 최빈이 62%(아라비아)에 그친다.
- **14%는 어떤 주제 소제목도 찾지 못한다.**

이미 정해진 원칙("규칙에 맞지 않는 문서는 추측해서 자르지 않고 `unknown`으로 사람에게
보낸다")을 그대로 적용하면, 어떤 단일 규칙을 고르든 **적어도 3분의 1이 사람에게 간다.**
규칙을 겹쳐 쌓는 사다리(목차 → 주제 소제목 → 번호 체계)를 쓰면 자동 처리 비율은 올라가지만
잘못 자를 위험도 함께 올라간다. 이 절충을 어디에 둘지가 T-22의 결정이다.

## 측정하지 않은 것

- **잘라낸 결과가 판정 품질에 미치는 영향.** 이번 측정은 문서 형태만 셌다. 어디까지
  잘랐을 때 "우리와 맞는 사업인가" 판정이 달라지는지는 재지 않았다.
- 표와 그림 안의 내용. block 텍스트만 봤고 표 구조는 분석하지 않았다.
- `9b204452` magic을 가진 `.hwpx` 1건의 정체. 암호화·DRM 여부는 `unknown`이다.
- 파일명 분류의 정확도. `제안요청`·`과업지시` 등 키워드로 나눴을 뿐 내용을 확인하지 않았다.
- 모집단 1,011건 전체의 분포. 120건 표본이다.
