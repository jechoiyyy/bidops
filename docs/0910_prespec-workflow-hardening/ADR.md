# 사전규격 수집·개요 검토 안정화 결정

작성일: 2026-09-10 · 상태: 설계 채택, 구현 전

이 문서 묶음은 발주계획 수집부터 사전규격 개요를 웹에서 확인하는 구간의 리뷰에서 발견한 네 문제를 수정하기 위한 계획이다. 사용자는 인터뷰의 세 권장안을 모두 선택했다. 코드 수정, 운영 migration, 모델 호출, 정책 활성화는 이 문서 작성으로 실행되지 않는다.

문서 역할: [요구사항](Requirements.md)은 완료 조건, [명세](Spec.md)는 새 계약과 상태 전이, [설계](Design.md)는 구현 경계와 의사코드, [계획](Plan.md)은 작업 순서와 검증을 소유한다. 구현 전까지 현재 동작의 정본은 기존 [구조](../ARCHITECTURE.md)·[계약](../contracts.md)·[업무 규칙](../business-rules.md)이다.

## 배경

| 문제 | 현재 원인 | 수정 방향 |
|---|---|---|
| 기간을 예산의 근거로 허용 | 페이지 안 숫자 집합만 비교하여 `6개월`과 `6억원`의 역할·단위를 구분하지 못함 | 주장마다 정확한 인용·수치 관계를 검증하고 별도 의미 검토 |
| 같은 수집 회차의 원문 덮어쓰기 | 사전규격·입찰 공통 수집기가 기존 경로에 `write_text` | 수집기가 새 회차를 배타적으로 만들고 모든 파일도 배타적으로 생성 |
| vLLM 복구 후에도 개요 큐 정체 | 최초 identity 실패를 runner 수명 동안 캐시 | 성공 binding과 일시 실패의 재확인 시각 분리 |
| v4 중지가 다른 개요 작업까지 차단 | 전역 v4 큐 존재 여부와 OFF 분기가 lease 정리·legacy 분기보다 앞섬 | 중지 대상 취소, 게시 차단, 만료 정리와 다른 문서 처리 분리 |

재현 조건은 [미해결 문제 기록](../tracking/findings.md)의 2026-09-10 개요·수집 관련 네 항목을 따른다. 숫자 오류는 합성 입력에서 검증기의 허점을 재현한 것이며 실제 Qwen 출력의 관측으로 해석하지 않는다.

## 사용자 채택: 결정적 검사와 별도 Qwen 의미 검토

동결한 근거로 구조화 초안을 만든 뒤, 코드로 인용·수치·단위·역할을 검사하고 별도 Qwen 호출 한 번으로 주장과 원문의 의미 관계를 검토한다. 모델은 승인된 사설 vLLM의 `qwen3.8-27B`를 사용한다. `Qwen3.8:27b`라는 사용자 표기에서 served model ID를 추정하거나 변경하지 않는다.

최종 개요는 모든 검사를 통과한 주장 문장을 결정적으로 배치한다. 최종 문장을 다시 자유 생성하면 검증 뒤 새 사실이 생길 수 있으므로 별도의 최종 작성 모델 호출을 두지 않는다. 문장 사실을 바꾸는 편집은 새로운 검증 대상이다.

대안은 결정적 검사만 적용하고 의미 판단을 전부 사람에게 맡기는 방식이었다. 채택안은 한국어 의무·부정·조건·사업 주체의 혼동을 추가로 찾을 수 있지만, 정상 경로의 모델 호출이 두 번으로 늘고 같은 모델의 오류가 반복될 가능성도 남는다. 의미 검토 통과가 결정적 검사 실패를 덮을 수 없고, 두 검사 통과도 사람 정답이나 품질 측정을 대신하지 않는다.

## 사용자 채택: 미검증 주장이 있으면 전체 개요를 사람 검토로

한 주장이라도 불일치·근거 부족·의미 판단 불확실이면 attempt 전체를 `needs_human_review`로 종료한다. 최종 개요 결과는 만들지 않으며, 웹에는 검증 실패 주장과 원문 근거를 구분해 보여 준다. 통과한 부분만 떼어 완료 개요로 게시하는 대안은 채택하지 않는다.

숫자·단위·근거의 불일치를 모델이 자동으로 고쳐 통과시키는 반복은 만들지 않는다. JSON 파싱·형식 문제만 초안 재생성 1회를 허용하고, 사실 검증 실패는 즉시 사람 검토로 보낸다. 이는 [표준](../standards.md)의 “불일치 결과를 자동 보정하지 않고 사람 검토로 보낸다”를 따른다. 현재 v4의 넓은 검증 재시도 규칙은 새 정책에서 축소하며 기존 정책·응답은 보존한다.

사람이 입력이나 범위를 확인한 뒤 실행하는 경우에도 새 attempt를 만든다. 이번 작업은 실패 표시와 명시적 재실행 경로까지 다루며, 웹에서 주장 편집·승인을 저장하는 별도 기능은 만들지 않는다.

## 사용자 채택: v4 중지 시 대기 취소와 실행 중 결과 게시 차단

중지 트랜잭션은 OFF 이벤트와 아직 끝나지 않은 v4 attempt의 취소를 함께 확정한다. 실행 중 요청의 응답이 늦게 도착해도 완료 결과, 현재 개요, 회사 핏 입력으로 게시하지 않는다. 중지 전에 이미 게시된 결과는 이력으로 유지한다.

대안은 신규 작업만 막고 실행 중 결과는 게시하는 방식이었다. 채택안은 운영자가 중지한 시점 이후 새 결과가 나타나는 혼란을 줄인다. 이미 전송한 HTTP 요청의 서버 계산 중단까지 보장하지는 않는다. 재활성화해도 이전 attempt가 살아나지 않도록 activation ID를 고정한다.

## 구현 방침: 수집 회차의 생성 책임은 수집기

발주계획 전용 수집기와 같은 배타적 생성 원칙을 `collect_notices.py`에 적용한다. 입찰공고와 사전규격이 이 파일을 공유하므로 두 입력 모두 적용 대상이다. 출력 폴더가 이미 있으면 비어 있어도 네트워크 호출 전에 거부한다. 파일에도 배타적 생성을 적용한다.

재분류는 `--from-raw <기존 raw 경로>`와 별도의 새 `--output-dir`을 사용한다. 기존 raw를 읽기 전용으로 검증해 복사하고 원본은 변경하지 않는다. 호출부의 폴더 선생성과 raw symlink를 제거한다. 같은 회차 resume·덮어쓰기 옵션은 제공하지 않는다.

수집 JSON의 업무 의미와 날짜 범위는 유지한다. 발주계획의 종료일 제외와 사전규격·입찰 수집의 종료일 포함을 이 작업에서 통일하지 않는다.

## 구현 방침: 모델 복구·작업 배정·호환성

- v4와 기존 개요 runner의 일시적 identity 실패는 문서 payload 없이 backoff 후 재확인한다. 설정·허용 host·revision·served ID 불일치는 계속 차단하며 다른 모델로 전환하지 않는다.
- worker는 이미 만들어진 큐의 실행자다. 날짜별 수집을 예약하는 scheduler와 다르다. scheduler·always-on 기본 비활성, 사람의 실행·추적·최종 입찰 결정 경계는 유지한다.
- 만료 정리는 v4 활성 여부와 무관하게 수행한다. 실행 가능한 v4가 없으면 v4가 예약하지 않은 다른 문서의 기존 개요를 처리한다. 같은 문서를 legacy로 우회하지 않는다.
- 새 주장·검증·페이지 결과·조회 응답·정책은 버전을 구분한다. 기존 권고형 개요를 새 설명형 개요로 교체하지 않고 과거 결과를 새 검증 통과로 소급 승격하지 않는다.
- PostgreSQL의 상태 제약·불변 트리거·역할 권한까지 함께 바꾼다. SQLite 테스트만으로 중지와 게시의 동시성 검증을 완료했다고 하지 않는다.

## 범위와 잔여 조건

발주계획 C-2의 선별 방식·품질 게이트, 변환기 구현, 회사 핏 정책, 심층 검토, 입찰 delta worker, 새 scheduler는 이 작업의 기능 확장 범위가 아니다. 관련 경로는 새 개요를 안전하게 소비하는지와 기존 계약을 유지하는지만 검증한다.

사설 vLLM 연결 복구와 주장 검증을 구현해도 전체 운영 승인 조건이 충족되는 것은 아니다. 실사용 검증은 지정 표본에 대한 참조 실행으로 시작한다. 실행 당시의 정책·전송 승인·endpoint·revision·worker 준비 상태를 별도로 확인하고 `unmeasured_reference`를 유지한다.
