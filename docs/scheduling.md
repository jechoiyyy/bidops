# 정기 실행 설계

정기 실행은 웹 프로세스의 수명주기에 붙어 동작한다. 별도 워커 컨테이너나 호스트 cron을 추가하지 않으며, 수집·정규화·보고는 기존 결정적 스크립트의 파일 계약으로 호출하고 판정만 판정 오케스트레이터가 담당한다. 스케줄러는 입찰 제출, 발주처 연락, 최종 참여 결정을 실행하지 않는다.

이 문서에서 말하는 실행 상태는 스케줄 예약·실행 이력의 상태다. 현재 `Run.status`의 `active`·`superseded`와 파이프라인 내부 객체의 상태를 대체하는 계약이 아니며, 관리 화면에는 아래 여섯 상태만 정기 실행 상태로 표시한다.

## 1. 기동 방식

웹 애플리케이션의 기동 훅에서 스케줄러를 등록하고, 종료 훅에서 다음 예약을 받지 않도록 정리한다. 웹 프로세스가 재기동되면 같은 예약을 다시 만들지 않고 데이터베이스에서 해당 날짜의 예약 이력을 먼저 확인한다. 현재 `web/Dockerfile`은 워커 수를 지정하지 않은 `uvicorn` 실행 명령을 사용하지만, 프로세스가 하나라는 전제는 사용하지 않는다.

스케줄러가 날짜별 실행을 예약할 때 다음 값을 가진 예약·실행 이력을 만든다.

| 열 | 내용 |
|---|---|
| `run_key` | `YYYYMMDD-YYYYMMDD` 형식의 논리 회차 키. 일간 회차에서는 시작일과 종료일이 같은 날짜다. |
| `window_from`, `window_to` | `run_key`에서 해석한 수집 대상 기간. 실제 파이프라인의 기간 입력이다. |
| `status` | 이 문서의 예약·실행 중·성공·부분 성공·실패·건너뜀 가운데 하나다. |
| `execution_id` | 예약을 획득한 실행을 추적하는 식별자. 프로세스 재기동과 회차 식별자를 섞지 않는다. |
| `skip_reason` | 유일 제약 충돌, 자동 실행 중지, 수동 실행 충돌 등 건너뛴 이유. 해당하지 않으면 `null`이다. |

`run_key` 열에 데이터베이스 `UNIQUE` 제약을 건다. 같은 날짜의 `window_from`·`window_to`를 가진 예약이더라도 논리 키가 같으면 하나만 생성되므로, 여러 웹 프로세스가 동시에 기동하거나 같은 시각에 트리거되어도 같은 날 회차를 두 번 시작할 수 없다. 이 제약은 `Run.id`에 추가하는 것이 아니다. 현재 적재기는 회차 산출물의 생성 시각을 포함한 스냅샷 식별자를 만들고, 재분류·재적재 시 같은 수집 기간의 새 스냅샷을 `superseded` 관계로 보존할 수 있으므로 `Run.id`를 일일 예약의 중복 방지 키로 사용하면 기존 불변 스냅샷 경계와 충돌한다.

예약 삽입을 트랜잭션으로 먼저 커밋한다. 유일 제약을 먼저 획득한 쪽만 `Run` 행과 해당 회차 디렉터리를 준비해 파이프라인을 시작하고, 제약에 걸린 쪽의 실행 요청은 `건너뜀`으로 끝낸다. 건너뛴 쪽은 수집·판정·보고서 생성과 새 스냅샷 적재를 시작하지 않으며, 기존 예약의 상태를 바꾸지 않는다. 제약 충돌 자체와 건너뛴 이유는 실행 이력 또는 기존 예약의 경고로 조회 가능해야 한다.

실제 파이프라인을 시작할 때는 예약에 기록된 `window_from`과 `window_to`를 `Run` 행에 고정한다. `web/backend/app/services/pipeline.py`의 `_window`가 회차 행의 기간을 읽어 수집 명령의 `--from-date`, `--to-date`로 전달하는 경계를 유지하며, 스케줄러가 실행 순간의 시스템 날짜를 다시 계산해 덮어쓰지 않는다. 기존 `PipelineService`의 단계 실행 경계와 `PipelineBusyError`를 우회하지 않는다.

스케줄 라이브러리를 새로 도입한다면 백엔드 `requirements.txt`와 `pyproject.toml`에 이름과 허용 버전을 함께 기록하고, `web/Dockerfile`의 설치 단계가 그 의존성을 포함하는지 확인한다. 세 곳 가운데 한 곳만 바꾸거나 컨테이너에서 설치되지 않는 상태로 두지 않는다.

## 2. 작업 정의

### 2.1 일간 작업

일간 작업의 입력과 출력은 회차 키에 귀속한다. 기존 `select_validation_sample.py`와 `bidops.validation-set.v2`는 품질 게이트용 감사 표본을 만드는 입력이며, 정기 판정 대상을 줄이는 선별 수단으로 사용하지 않는다.

| 순서 | 작업 | 입력 | 출력 | 성공 조건 |
|---|---|---|---|---|
| 1 | 수집 | 예약의 `window_from`·`window_to`, `Asia/Seoul` 시간대, 나라장터 API 설정, 사전규격 설정 | `raw/`의 API 페이지, `collected-notices.json`, 수집 경고 | 본공고 API 원문 페이지를 보존하고 `bidops.collected.v2` 계약을 통과한다. API가 돌려준 확인 불가 값은 `unknown` 또는 `unknown_fields`로 남긴다. 사전규격 권한 경고는 9절 규칙을 따른다. |
| 2 | 대상 선별 | `collected-notices.json`, 후보화 규칙의 불변 버전, 회사 실적 제목 자료 | 후보 전량을 표현하는 `bidops.screening-input.v1` 판정 대상 목록과 품질 게이트용 감사 표본 | 규칙 필터를 통과한 후보가 누락 없이 판정 대상에 들어가고 `notice_id`가 회차 안에서 유일하다. 감사 표본은 별도 표본으로 남고 후보를 대체하지 않는다. |
| 3 | 판정 | 판정 대상 목록, 회사 프로필 버전, 정책·프롬프트 불변 버전, 기존 완료 회차의 판정, Ollama 설정 | 신규·재판정 판정, 승계 판정, `screening-failures` 목록, 호출 계측 | 각 대상이 신규 판정·재판정·검증 가능한 승계·실패 목록 중 하나로 설명된다. 실패한 공고는 판정 파일에 넣지 않고 사람 검토 대기로 남긴다. 모델이 만든 값은 원문 위치와 연결하며 자동 보정하지 않는다. |
| 4 | 병합·검증 | 판정 대상 목록, `screening-decisions.json`, 판정 실패 목록, 정규화 공고 원문 | `screening-results.json` | 다섯 관점·근거·반론·확인 항목·등급·준비 상태와 교차 조건을 결정적으로 검사한다. 통과한 판정만 결과에 들어가며, 검증 실패를 빈 값이나 자동 수정값으로 채우지 않는다. |
| 5 | 적재 | 회차의 수집·판정·검증 산출물, 회차 식별자와 정책·모델 역추적 정보 | SQLite의 회차·공고·판정·경고·계측 기록과 파일 경로·해시 | 검증된 회차만 적재하고 같은 회차의 공고 중복을 막는다. 이전 회차의 원문·판정·리뷰를 덮어쓰지 않으며, 적재 경고와 부분 산출물 상태를 관리 화면에서 조회할 수 있다. |
| 6 | 일간 브리핑 | 적재된 당일 회차, `screening-results.json`, 경고·실패 목록, 변별력 점검 결과 | `render_report.py`의 일간 모드로 만든 일간 브리핑과 관리 화면의 실행 결과 | 일간 회차의 변화, 등급·준비 상태, 승계 표시, 실패·경고를 결정적으로 렌더링한다. 보고서 렌더러가 등급이나 근거를 새로 만들거나 보정하지 않는다. |

판정 단계에서 일부 공고만 실패하면 성공한 신규·재판정과 검증된 승계를 병합하고, 실패 목록을 함께 적재한다. 따라서 회차는 `부분 성공`으로 끝나며 실패 한 건 때문에 나머지 공고를 버리지 않는다. 반대로 판정 단계 전체가 입력을 만들지 못하거나 검증 가능한 결과를 하나도 만들지 못하면 회차 전체를 성공으로 표시하지 않는다.

### 2.2 주간 작업

주간 작업은 `Asia/Seoul` 기준 월요일부터 일요일까지의 완료·부분 완료 일간 회차를 입력으로 삼는다. 다음 주 월요일에 전 주 누계를 생성하며, 일간 회차를 다시 수집하거나 재판정하지 않는다.

| 작업 | 입력 | 출력 | 성공 조건 |
|---|---|---|---|
| 주간 누계 보고서 | 전 주의 일간 회차별 `screening-results.json`, 일간 브리핑, 경고·실패 목록, 리뷰·변별력 기록 | `render_report.py`의 주간 모드로 만든 주간 누계 보고서와 포함 회차 목록 | 월요일~일요일의 각 날짜를 포함·제외 사유와 함께 열거하고, 부분 성공 회차와 승계 판정을 구분해 표시한다. 누락된 날짜를 성공한 날로 채우지 않는다. 보고서 생성에 실패하면 일간 회차의 상태는 바꾸지 않고 주간 작업만 실패 또는 부분 성공으로 기록한다. |

## 3. 회차 경계

일간 회차의 논리 식별자는 기존 형식인 `YYYYMMDD-YYYYMMDD`를 유지한다. 일간 회차에서는 시작일과 종료일이 같은 값이다. 예를 들어 2026년 8월 24일의 수집 대상 회차는 `20260824-20260824`로 표현한다. 날짜·실행 시각·API 조회 경계는 모두 `Asia/Seoul`을 기준으로 한다.

기본 실행 시각을 다음 날 02:00으로 두므로, 실행 시각의 전일을 회차의 수집 대상 날짜로 삼는다. 즉 8월 25일 02:00에 `20260824-20260824` 회차를 시작한다. 전일 전체가 공개 API에 반영되었는지와 02:00 실행 창이 판정·보고서 시간 예산을 만족하는지는 운영 전 실측으로 확인하며, 확인 전에는 더 정밀한 완료 시각을 보장하지 않는다.

회차 행을 만들 때 `window_from = window_to = 대상 날짜`를 먼저 기록하고, 수집기는 이 값을 사용한다. `_window`가 이 두 열이 없으면 실행을 거부하는 현재 경계를 유지한다. 회차가 완료된 뒤 수집 기간, 원문 페이지, 정책 버전, 모델·프롬프트 버전은 수정하지 않는다. 값이 달라지는 재실행은 새 스냅샷과 별도 실행 이력으로 다루며 기존 회차를 덮어쓰지 않는다.

## 4. 실행 시각

일간 기본 실행 시각은 다음 날 02:00(`Asia/Seoul`)이다. 전일 API 데이터가 마감된 뒤 실행할 수 있고, 판정 런타임 설계의 약 2시간 안팎 추정과 담당자가 업무를 시작하기 전 일간 브리핑을 준비하는 목적을 함께 고려한 설계 기본값이다. 이 시간은 1차 판정 프롬프트의 실제 응답 시간과 나라장터 API 반영 지연을 측정한 뒤 조정할 수 있으며, 측정되지 않은 처리 시간을 운영 보장값으로 사용하지 않는다.

주간 누계 보고서는 기본적으로 월요일 06:00에 전 주 회차를 대상으로 실행한다. 일요일 회차가 완료되지 않았으면 누락을 숨기지 않고 주간 보고서에 경고를 남기거나 주간 작업을 부분 성공으로 끝낸다.

실행 시각은 설정으로 조정할 수 있다. 시간대를 임의의 서버 로컬 시간으로 해석하지 않으며, 날짜 경계와 회차 식별 규칙은 `Asia/Seoul`에서 고정한다.

## 5. 재판정 규칙

현재 회차의 `lifecycle`과 같은 공고의 가장 최근 완료 회차 `lifecycle`을 안정적인 공고 식별자와 사전규격·본공고 연결로 비교한다. 현재 수집기가 보존하는 API 필드와 정규화 필드는 다음과 같이 대응한다. 같은 값이 반복된 경우에는 재판정하지 않고, 값이 새로 생기거나 달라진 경우에만 재판정한다.

| 감지 대상 API 필드 | `lifecycle` 보존 필드 | 재판정하는 변화 | 재판정 여부 |
|---|---|---|---|
| `chgDt` | `changed_at` | 이전 회차에 없던 정정 시각이 생기거나 현재 값이 이전 값과 다르고, API가 제공한 정정 시각을 현재 공고의 새 이력으로 확인할 수 있는 경우 | 예 |
| `chgNtceRsn` | `change_reason` | 정정 사유가 새로 생기거나 이전 회차와 달라진 경우. 사유 문자열이 같은데 단지 다시 수집된 경우는 재판정하지 않는다. | 예 |
| `reNtceYn` | `re_notice` | API가 재공고 긍정값으로 제공하거나 이전 회차의 값에서 재공고 상태로 바뀐 경우 | 예 |
| `befBidBbancNo` | `previous_failed_notice_no` | 이전 입찰 취소·유찰 공고와 연결되는 번호가 새로 확인되거나 연결 대상이 달라진 경우 | 예 |
| `bfSpecRgstNo` | `pre_spec_no` | 현재 본공고가 이전 사전규격 번호를 가리키고, 동일 사업의 사전규격에서 본공고로 전환된 연결을 확인할 수 있는 경우 | 예 |

필드가 비어 있다는 사실을 변경 없음으로 간주하지 않는다. 이전 회차가 없거나 값의 비교가 불가능하거나 API 값이 해석되지 않으면 자동 승계를 하지 않고 비교 경고와 사람 검토 대기로 남긴다. 확인되지 않은 값을 재판정 사유나 변경 없음으로 추정하지 않는다.

위 변화가 없는 이미 판정된 공고는 모델을 호출하지 않고 이전 판정을 현재 회차 산출물에 승계한다. 승계는 다음 규칙을 따른다.

| 표시 | 기록 내용 |
|---|---|
| `carried_over: true` | 현재 회차에서 이전 판정 내용을 모델 호출 없이 승계했다는 사실 |
| `judged_in_run: false` | 현재 회차에서 새 판정을 만들지 않았다는 사실 |
| 원 판정 메타데이터 | 원래 판정 회차, 모델 이름·모델 버전, 프롬프트 버전, 정책 버전 |
| 현재 회차 메타데이터 | 승계된 판정이 들어간 현재 회차와 현재 산출물의 식별자 |

승계하는 값은 등급·참여 준비 상태·다섯 관점·근거·반론·확인 항목을 포함해 그대로 복사한다. 현재 계약을 만족하지 않는 과거 판정은 승계하지 않고 `carried_over_validation` 실패로 사람 검토에 보낸다. 승계 사실은 결과 JSON과 일간·주간 보고서 및 관리 화면에서 `승계 판정`으로 표시하고 원 회차를 연결한다.

승계는 회차 불변 원칙과 충돌하지 않는다. 이전 회차의 파일·DB 행·리뷰를 수정하는 것이 아니라, 현재 회차의 새 불변 산출물에 이전 판정의 내용과 출처를 복사하는 작업이기 때문이다. 현재 회차의 원문·수집 기간·정책 버전은 현재 회차에 고정되고, 원래 판정의 생성 회차와 기준 버전도 함께 보존된다. 이후 정정·재공고·본공고 전환이 발견되면 그 다음 회차에서 새 판정을 만들며 이전 승계 결과를 덮어쓰지 않는다.

## 6. 중복 방지와 충돌

스케줄러와 담당자의 수동 실행은 같은 `run_key` 예약 경계를 공유한다. 먼저 데이터베이스 예약을 커밋한 요청이 실행권을 얻고, 나중 요청은 새 회차를 만들지 않는다.

| 충돌 시점 | 동작 |
|---|---|
| 스케줄 트리거와 수동 시작이 동시에 예약을 시도 | 트랜잭션의 `run_key` 유일 제약을 먼저 획득한 하나만 진행한다. 나머지 요청은 `건너뜀`으로 끝나고 중복 실행 사유를 남긴다. |
| 예약이 이미 존재하지만 파이프라인이 시작되기 전 | 수동 요청은 기존 예약의 실행 상태를 확인하고 새 수집·판정·보고서를 시작하지 않는다. |
| 같은 웹 프로세스에서 단계가 이미 `예약` 또는 `실행 중` | 기존 `PipelineService.start`의 회차별 메모리 잠금이 `PipelineBusyError`를 발생시킨다. 요청자는 충돌 상태를 받고, 스케줄러는 새 단계를 만들지 않는다. |
| 서로 다른 웹 프로세스에서 같은 회차에 접근 | 프로세스 메모리 잠금에 의존하지 않고 데이터베이스 예약 제약이 먼저 막는다. 어느 프로세스가 하나뿐이라는 Docker 실행 전제를 사용하지 않는다. |

`PipelineBusyError`는 동일 프로세스 안에서 이미 실행 중인 작업을 알리는 기존 메커니즘이고, `run_key` 유일 제약은 프로세스 사이의 일일 회차 시작을 막는 메커니즘이다. 둘을 하나의 잠금으로 합치거나 기존 파이프라인 스크립트를 웹 내부 함수로 복제하지 않는다.

## 7. 실행 상태 모델

정기 실행 상태는 `pending` 하나로 예약·실행·실패를 표현하지 않는다. 현재 파이프라인 실행 객체의 내부 기본값이 `pending`인 경우에도 정기 실행 계약과 관리 화면에는 `예약`으로 매핑한다.

| 상태 | 정의 | 다음 상태와 전이 조건 |
|---|---|---|
| 예약 | 일일 `run_key` 예약이 데이터베이스에 커밋되었지만 아직 파이프라인을 시작하지 않은 상태. 따라잡기 대상이 실행 순서를 기다리는 경우도 포함한다. | 실행 자원을 획득하고 회차의 입력·기간을 고정하면 `실행 중`으로 전이한다. 자동 실행 중지, 중복 예약, 수동 실행 충돌로 실제 작업을 하지 않으면 `건너뜀`으로 전이한다. |
| 실행 중 | 수집·대상 선별·판정·병합·검증·적재·보고서 작업 가운데 하나 이상이 진행 중인 상태. | 모든 필수 결과가 검증되고 보고서까지 생성되면 `성공`, 사용 가능한 결과는 남았으나 일부 공고·소스·보고서가 빠지면 `부분 성공`, 사용 가능한 회차 결과를 만들 수 없는 치명적 오류면 `실패`로 전이한다. |
| 성공 | 일간 작업의 필수 산출물과 적재·일간 브리핑이 모두 완료되고, 판정 대상이 신규 판정·재판정·검증된 승계 중 하나로 정리된 상태. 허용된 비치명 경고가 성공을 가리지 않는 경우에만 사용한다. | 종결 상태다. 결과를 다시 만드는 경우 기존 상태를 바꾸지 않고 별도 명시적 실행·스냅샷의 결과로 추적한다. |
| 부분 성공 | 본공고와 일부 유효 산출물 등 회차를 검토할 수 있는 결과는 남았지만 사전규격 권한 경고, 일부 판정 실패, 일부 적재·보고서 생성 실패 등 누락이 있는 상태. 누락 목록과 수를 반드시 남긴다. | 종결 상태다. 실패한 항목의 복구는 사람 검토 또는 별도 실행으로 시작하며 자동으로 성공으로 승격하지 않는다. |
| 실패 | 치명적 수집 실패, 전역 병합·검증 실패, 적재 실패 등으로 회차를 검토할 수 있는 정본 결과를 만들지 못한 상태. 보존된 원문이나 오류 로그가 있더라도 성공으로 간주하지 않는다. | 종결 상태다. 다음 날짜 회차와 합쳐서 성공으로 만들지 않으며, 복구가 필요하면 원인과 새 실행을 별도로 기록한다. |
| 건너뜀 | 중복 예약, 자동 실행 스위치 중지, 실행 중인 같은 회차와의 충돌 등으로 작업을 시작하지 않은 상태. | 종결 상태다. 건너뛴 이유와 원래 예약·실행 식별자를 남긴다. |

정상 전이는 `예약 → 실행 중 → 성공·부분 성공·실패`이며, 작업을 시작하지 않은 요청은 `예약 → 건너뜀`이다. 종결 상태를 다시 `예약`이나 `실행 중`으로 되돌리지 않는다.

## 8. 실패 처리와 따라잡기

| 실패 지점 | 처리 | 회차 상태 |
|---|---|---|
| 본공고 수집 실패 | API 연결·응답·원문 보존·`collected-notices.json` 생성이 실패하면 해당 회차의 원문과 오류를 보존하고 대상 선별 이후 단계로 진행하지 않는다. 다음 회차에 오류를 숨기거나 빈 수집 결과로 진행하지 않는다. | 사용 가능한 회차 결과가 없으면 `실패` |
| 판정 실패 | 공고 단위 타임아웃·잘린 출력·스키마 위반·근거 누락은 실패 목록으로 분리하고 병합 입력에서 제외한다. 신규 판정과 검증된 승계가 남아 있으면 나머지를 적재한다. OpenAI를 승인 없이 자동 대체 경로로 호출하지 않는다. | 일부 결과가 남으면 `부분 성공`; 전역 판정 실패로 유효 결과가 없으면 `실패` |
| 병합·검증 또는 적재 실패 | 결정적 검증 실패를 자동 보정하지 않는다. 전역 계약 위반이나 DB 트랜잭션 실패는 오류·원인·대상 회차를 남기고 이전 회차를 덮어쓰지 않는다. | 정본 결과를 만들 수 없으면 `실패`; 검증된 일부 산출물만 별도로 확인 가능한 경우 `부분 성공` |
| 일간 브리핑 생성 실패 | 이미 검증·적재된 회차와 판정은 보존한다. 보고서 렌더러 오류, 출력 경로 오류를 관리 화면에 표시하고 보고서만 재생성할 수 있게 한다. | 데이터는 검토 가능하므로 `부분 성공` |

웹 프로세스가 내려가거나 실행 시각을 놓치면, 다음 기동 시 `Asia/Seoul`의 마지막으로 예약된 대상 날짜 다음 날부터 전일까지 누락된 날짜를 조사한다. 각 날짜마다 별도의 `YYYYMMDD-YYYYMMDD` 예약을 오래된 날짜부터 만든다. 여러 날을 하나의 넓은 회차로 합치지 않으며, 각 회차의 시작일·종료일 동일 원칙과 원문·정책·리뷰 보존을 유지한다.

이미 `실패` 또는 `건너뜀`으로 끝난 같은 날짜의 예약을 조용히 다시 성공 처리하지 않는다. 실패 원인을 확인한 담당자가 명시적으로 복구 실행을 요청해야 하며, 복구는 원래 예약 상태를 되돌리거나 새 일간 `run_key` 예약을 만드는 방식이 아니다. 새 실행·스냅샷이 필요하면 기존 결과를 덮어쓰지 않고 원래 `run_key`와의 관계를 기록한다. 따라잡기 중 하나의 회차가 실패해도 이후 날짜의 예약을 임의로 성공 처리하지 않고, 각 날짜를 독립 상태로 남긴다.

## 9. 사전규격 처리

사전규격 수집을 켠 상태에서 사전규격 API가 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`를 반환하면 이를 사전규격 권한 부족으로 분류한다. 본공고 API의 오류와 섞지 않고 다음을 수행한다.

- 사전규격 원문이 없다는 사실과 오류 코드를 회차 경고로 기록한다. API 키 실제 값은 로그·응답·DB에 남기지 않는다.
- 본공고 수집을 중단하지 않고 계속 실행한다. 본공고 원문과 정규화 결과는 정상적으로 회차 산출물에 쓴다.
- 사전규격의 공고·자격·생애주기 값은 `unknown` 또는 값 없음으로 보존하며, 본공고 정보나 회사 역량을 추정해 채우지 않는다.
- 사전규격 결과가 없는 상태에서 본공고 수집과 나머지 단계가 완료되면 회차는 `실패`가 아니라 `부분 성공`으로 표시한다. 경고는 관리 화면의 회차 상세와 일간·주간 보고서에 남긴다.

공공데이터포털 권한이 확보되면 코드나 기존 회차를 수정하지 않고 사전규격 설정만 켠다. 권한 신청 전에는 `BIDOPS_PRESPEC_ENABLED=false`로 두며, 승인 확인 뒤 `true`로 바꿔 다음 회차부터 수집한다. 권한이 없는 상태에서 설정이 켜져 API 오류가 발생하더라도 위의 경고·본공고 계속 규칙을 적용한다. 과거 회차에 없던 사전규격 데이터를 사후에 채워 불변 산출물을 바꾸지 않는다.

## 10. 회차 완료 시의 자동 점검

회차의 검증·적재가 끝나면 모델 호출 여부와 관계없이 변별력을 계산한다. 대상은 해당 회차의 후보 전량이며, 현재 회차에서 새로 만든 판정과 현재 계약 검증을 통과한 승계 판정을 모두 포함한다.

```text
변별력 = grade가 "우선 검토"인 유효 판정 수 ÷ 유효 판정 대상 수 × 100
```

유효 판정 대상 수에는 등급이 있고 결정적 검증을 통과한 판정만 넣는다. 전체 후보 수, 유효 판정 수, 실패 수를 함께 기록해 실패 공고를 분모에서 조용히 제거하지 않는다. 유효 판정 대상 수가 0이거나 10건 미만이면 비율을 `계산 불가(소표본)`로 기록하고 10~25% 임계 이탈 경보를 만들지 않는다. 이 초기 소표본 기준 10건은 통계적 품질 보장이 아니라 작은 회차의 반복 경보를 막는 운영 기준이며, 실제 주말 분포와 담당자 검토 결과를 측정한 뒤 품질 게이트 운영에서 재검토한다.

유효 판정 대상이 10건 이상이면 10% 이상 25% 이하를 정상 구간으로 본다. 구간 밖이면 회차의 변별력 값, 분자·분모, 대상 수, 실패 수, 계산 시각을 회차 경고로 남기고 관리 화면에 알린다. 주말에 후보가 한두 건이고 그중 한 건만 `우선 검토`여도 소표본으로 처리하므로, 그 자체로 임계 이탈 경보를 반복하지 않는다.

변별력 경고는 품질 관찰용이다. 판정의 등급·참여 준비 상태를 자동으로 고치지 않으며, 경고만으로 회차를 `실패`로 바꾸지 않는다. `부분 성공`이나 사전규격 권한 경고가 있는 회차의 변별력도 그 상태와 실패 수를 함께 표시하고, 계산 불가이면 `0%`로 치환하지 않는다.

## 11. 상시 운영 스위치

자동 실행은 다음 설정으로 제어한다. 환경변수 이름은 `BIDOPS_` 접두사를 사용하며, 비밀·API 키를 설정값이나 산출물에 기록하지 않는다.

| 설정 | 기본값 | 역할 |
|---|---|---|
| `BIDOPS_SCHEDULER_ENABLED` | `false` | 웹 프로세스 기동 시 일간·주간 예약을 등록할지 결정한다. |
| `BIDOPS_SCHEDULE_DAILY_TIME` | `02:00` | 다음 날 실행할 전일 회차의 기본 시각. 설정으로 조정할 수 있다. |
| `BIDOPS_SCHEDULE_WEEKLY_TIME` | `06:00` | 월요일에 전 주 누계를 만드는 기본 시각. 설정으로 조정할 수 있다. |
| `BIDOPS_PRESPEC_ENABLED` | `false` | 사전규격 API 호출 여부. 권한 확보 뒤 설정만 `true`로 바꾼다. |

`BIDOPS_SCHEDULER_ENABLED=true`를 적용하기 직전에 `docs/model-quality-gate.md`의 현재 모델·프롬프트·정책 버전에 대한 품질 게이트 결과를 확인한다. 필요한 측정값이 하나라도 `계산 불가`·미측정이거나 임계값을 충족하지 못하면 스위치를 켜지 않고, 활성화 요청을 거부한 사실을 관리 이력에 남긴다. 게이트 통과는 자동 실행을 켜기 위한 조건일 뿐 등급이나 준비 상태를 자동 변경하는 근거가 아니다.

게이트를 통과한 뒤에도 스위치는 담당자가 명시적으로 켠다. 게이트 결과와 활성화 시점의 정책·프롬프트·모델 버전을 함께 기록하며, 이후 새 모델·프롬프트·정책 버전은 별도 품질 측정과 게이트 통과 없이는 상시 운영에 사용하지 않는다. 스위치가 꺼져 있으면 예약 시각의 요청은 `건너뜀`으로 끝나고 수동 실행은 기존 승인·잠금 절차 안에서만 가능하다. 오류·변별력 경고는 메일이나 메신저로 보내지 않고 관리 화면에서만 확인한다.

## 12. 데이터 증가와 보존 검토

현재 사양에서 확인된 기준은 주간 본공고 2,546건, 후보 327건이며, 일간 증분 수집의 후보는 평일 기준 약 60건으로 추정되어 있다. 이는 운영 측정값이 아니라 계획 수립용 기준이다. 현재 수집기는 API 호출마다 `raw/bid-page-NNN.json` 또는 `raw/prespec-page-NNN.json`을 보존하고 기본 `rows` 값은 500이다.

일간 원문 페이지 수는 다음 식으로 운영 기간별 실제 건수에서 계산한다. 사전규격 권한이 없거나 설정이 꺼진 기간에는 해당 소스의 항을 0으로 기록한다.

```text
일간 원문 페이지 수
= max(1, ceil(본공고 일일 건수 ÷ 500))
  + (사전규격이 켜진 경우 max(1, ceil(사전규격 일일 건수 ÷ 500)))
```

주간 본공고 2,546건을 7일에 균등하다고 단순 환산하면 일평균 약 364건이므로 본공고만 놓고는 대체로 하루 한 페이지 수준, 연간 약 365개의 본공고 원문 페이지가 계획 기준이 된다. 실제 일별 분포와 사전규격 건수는 확인되지 않았으므로 연간 총 페이지 수, JSON 용량, 압축률을 확정값으로 쓰지 않는다. 사전규격 원문은 권한 확보 후 실제 페이지 수를 측정해 더한다.

일간 회차 디렉터리는 1년 약 365개, 주간 누계 보고서는 약 52개가 된다. 일간 회차의 핵심 JSON을 `collected-notices.json`, 판정 대상·결정·결과의 세 묶음으로 세면 최소 네 종류의 산출물이므로 연간 최소 약 1,460개 파일이 생기며, 여기에 판정 실패 목록·계측·경고·일간 보고서 파일이 추가된다. 평일 후보 60건이라는 계획 기준을 52주에 적용하면 연간 판정 대상은 약 15,600건이지만, 이는 실제 후보화 결과와 사전규격 권한 상태를 측정하기 전의 추정치다.

보존 기간은 현재 임의로 제한하지 않는다. 상시 운영을 시작하기 전 또는 실제 30일 운영 후에 다음 값을 측정해 첫 보존 정책을 검토한다.

- 회차별 `raw/`, JSON 산출물, 일간·주간 보고서의 실제 바이트 증가량
- SQLite, 첨부 보관소, 보고서 디렉터리의 증가량과 백업 소요 시간
- 회차 원문·산출물·리뷰·정책 버전을 함께 복구하는 데 걸리는 시간
- 사내 저장 용량과 백업·복구 목표가 예상 1년·2년 누계와 맞는지 여부

첫 측정 뒤에는 최소 분기마다, 또는 저장 용량·백업 소요 시간이 사내 운영 한도에 가까워질 때 보존 정책을 다시 확인한다. 정책을 정한 뒤에도 이전 회차 원문이나 기존 리뷰를 먼저 삭제하지 않으며, 삭제·아카이브 기간과 복구 검증을 별도 운영 결정으로 기록한다. 측정되지 않은 페이지 크기나 보존 가능 기간을 문서에서 확정값으로 만들지 않는다.
