# BidOps 독립 UI/UX 리뷰

검토일: 2026-10-16. 제공된 `0073-rootlab-real-company-ax-redefinition.md`, `draft.md`, `hp-contract.md`, `mock/canvas.json`과 HTML 목업 6개를 직접 읽었다. 외부 서비스·외부 자료는 사용하지 않았다. 기존 파일은 변경하지 않았다.

HTML 구조·문구·링크·스타일을 검토했으며 브라우저 렌더링과 실제 사용자 테스트는 하지 않았다. 배치·행동 결과에 대한 예상은 **추정**으로 표시한다. 여섯 HTML 모두 `./support.js`를 참조하지만 해당 파일이 이 디렉터리에 없고 외부 Google Fonts 링크도 있다. 따라서 독립 실행 가능한 ‘자체 포함 HTML’인지 확인되지 않으며, 실제 초점·클릭·스크롤 동작은 검증하지 않았다. 정적 목업의 미구현 자체와 설계상 빠진 동작 정의를 구분했다.

판단 기준은 ADR-0073의 실회사·자동 분석·사람 최종 결정 원칙과 `hp-contract.md` §6~8이다. `draft.md` §9의 최신 인터뷰도 반영했다. 출력 형식은 ADR의 DOCX와 초안 §9의 PDF 우선이 충돌하므로 확정 사항으로 단정하지 않았다. 이 디렉터리에 없는 원문 RFP·회사 증빙의 사실 여부는 검증하지 않았다.

심각도: **차단**은 잘못된 참여 판단·근거 사용 또는 핵심 흐름 단절을 초래하는 설계 문제, **주의**는 이해·복구·협업을 어렵게 하는 문제, **제안**은 효율·가독성을 높이는 개선이다. 구현 비용은 상대적 추정이다.

## 1. 전체 평가

1. **방향은 적합하지만, 현재 목업만으로 ‘직접 서칭 중단’을 지탱할 구조가 완성됐다고 보기는 어렵다.**
2. G1은 `Main.dc.html`의 ‘오늘의 브리핑’과 `Slack.dc.html`의 08:00 메시지로 push 진입점을 확보했다.
3. 그러나 ‘볼게요’·‘추적 시작’·분석 시작의 관계가 혼재해 반응만 하면 된다는 약속이 불명확하다.
4. G2는 `Verdict.dc.html`에 계약의 5블록·부족 우선 정렬·역할 불일치를 갖췄지만, `unknown`을 부족으로 바꾸는 직접적인 계약 위반이 있다.
5. G3는 `Proposal.dc.html`의 대응표·절 초안·빈 자리 표시가 유용하지만, ‘48/48’·‘근거 없는 주장 0’을 확인할 연결이 없다.
6. `Company.dc.html`의 버전·출처·3가지 사실 상태는 좋은 기반이나, 보유 확인과 유효성 확인을 분리해야 한다.
7. `Timeline.dc.html`은 사업기회 단위로 통합했지만 최신 변화·미해결 조건·사람 결정이 여러 위치에 흩어진다.
8. **추정:** 원문 확인, 미확인 보완, 변경 후 재판정 경로가 닫히지 않으면 실무자는 다시 나라장터와 회사 자료를 직접 뒤질 가능성이 높다.
9. 성공은 채택률만으로 판정할 수 없다. `draft.md` §2·§8의 직접 검색 시간·브리핑 누락·초안 작성 시간 지표를 실제 운영에서 확인해야 한다.

| 회사 근거 변경 → 재판정·초안 | Company ‘실행 시점 버전에 결속’은 적절하지만 새 버전이 기존 결과에 미치는 영향이 없다. | 기존 결과는 보존한다. 영향 공고에 ‘새 근거 있음 → 재판정 대기/완료 → 달라진 조건’ 표시를 하고 초안에는 갱신 필요를 알린다. 사람이 수정한 초안의 변경분은 비교 후 반영한다. |
| 공고 정정 → 기존 결과 | Timeline ‘정정공고 없음 · 생기면…알림’만 있고 정정 후 화면이 없다. | 변경 요구·마감·원문 회차와 이전 판정의 최신 여부를 표시한다. 상세 상단과 다음 브리핑/관련 스레드에서 같은 변화 요약을 보여 준다. |
| 상세 → 브리핑 복귀 | 공통 ‘오늘의 브리핑’은 있으나 날짜·읽던 위치·필터·채택 상태 복원은 표현되지 않는다. ‘어제 브리핑’도 Main 자체 링크다. | 진입 날짜와 항목을 보존하고 돌아오면 반응 완료·미반응을 구별한다. Slack에서도 원래 메시지로 돌아갈 링크와 처리 결과를 제공한다. |
| 팀원 간 인계 | Timeline에는 김담당, Slack에는 채택 기록이 있지만 다른 사람의 무시·종료·동시 수정은 없다. | 개인 관심 반응과 팀 결정을 분리한다. 처리자·시각·현재 담당을 공유하고 충돌 시 최신 변경을 보여 준다. |

현재 상태 변화의 발견 장소는 Timeline ‘알림 이력’과 Slack의 ‘완료되면 이 스레드’뿐이다. Main에는 분석 완료·정정·회사 근거 갱신을 다시 모아 주는 영역이 없다. **개선안:** 일일 브리핑에 ‘새 추천’과 ‘추적 중 변경’을 구분하고, 각 상세 상단에 변경 배지와 이전 값 비교를 둔다. 사용자가 모든 타임라인을 다시 순회하지 않도록 해야 한다.

## 5. Slack 메시지 평가

**평일 08:00 한 번의 요약이라는 빈도는 목표에 맞다. 현재 메시지는 길이와 반응 방식이 균일하지 않아, Slack에서 확인을 마칠 수 있다는 약속을 충분히 충족하지 못한다.**

| 항목 | 판단·근거 | 권장안 |
|---|---|---|
| 길이 | `Slack.dc.html`은 6건을 담되 1~4번에 기술·자격 설명을 길게 붙이고 5·6번은 제목만 남긴다. ‘카드 48장 중 31 매핑’은 즉시 반응에 필요한 정보보다 분석 방식 설명에 가깝다. | 각 건을 제목·기관·마감 종류, 추천 이유 한 줄, 핵심 부족/미확인 한 줄로 제한한다. 원문·상세 분석은 제목 링크로 연결한다. |
| 버튼 수 | 추천 영역에는 버튼처럼 보이는 조작이 **10개**다: 1번 3개, 2~4번 각 2개, 5·6번 공용 1개. HTML상 button 4개·스타일된 링크 6개다. | 총개수를 줄이는 것보다 모든 항목의 행동을 예측 가능하게 만드는 것이 우선이다. 각 건에 동일한 채택·무시, 제목에는 상세 링크를 두고 중복 ‘화면에서 열기’를 제거한다. 실제 Slack 구성 한도는 외부 확인하지 않았다. |
| 스레드 | ‘완료되면 이 스레드’라고 하지만 실제 스레드 문맥이 없다. 채택 후 사용자가 다시 ‘눌렀어요’라고 설명한다. | 버튼 반응으로 담당·시간을 기록하고 수동 재보고는 필요 없게 한다. 항목별 처리 결과를 원메시지에 요약하고 상세 대화는 연결된 스레드에 남긴다. |
| 알림 피로 | Timeline은 ‘상태가 바뀔 때만 알림’·‘D-3·D-1’, Slack은 분석 완료 알림을 약속한다. 하루 1회가 본문 발송만 뜻하는지 전체 알림 상한인지 불명확하다. | 새 추천과 일반 변경은 다음 일일 브리핑으로 묶고 동일 변화는 중복 발송하지 않는다. 분석 완료는 관련 스레드에 기록한다. 임박 정정 등 예외 알림은 대상·조건·빈도를 사전에 정의한다. |
| 팀 반응 | ‘어제 반응 3/4’가 공고 기준인지 사람 기준인지 알 수 없다. 한 건에 5명 모두 반응해야 하는지도 없다. | 기본은 팀이 한 번 처리하면 완료된 것으로 집계하고 개인 관심은 별도 보존하는 방안을 제안한다. 이미 담당이 정해진 건을 전원 미반응으로 재촉하지 않는다. |
| 오류·수정 | 무시 취소·권한 없음·기록 실패·기존 메시지의 오래된 판정 표시가 없다. | 저장 성공과 실패를 즉시 알려 주고 취소를 제공한다. 공고 정정 후에는 예전 메시지에서 최신 판정으로 갈 수 있게 한다. |

권장 항목 예시는 다음과 같다. ‘자동 분석 완료’는 **제안하는 상태 예시**이며 실제 완료를 확인한 것이 아니다.

> **외교부 홈페이지 유지관리 · 입찰공고 · 제출 마감 10/25 10:00**  
> 홈페이지 운영 실적과 관련 있음. 서울 상주 조건 부족, 직접생산 품명·유효기간 미확인.  
> **보조 판정: 조건부 진행 · 자동 분석 완료**  
> [볼게요] [무시] · 제목에서 판정 열기  
> 반응 후: 김담당 검토 중 · 취소

**추정:** 이 구성은 세부 분석을 읽기 전에 채택·무시를 정하고, 필요한 건만 판정으로 넘어가게 해 브리핑 확인 시간을 줄인다. 반응 한 번이 추적 승인까지 뜻하는지는 팀 규칙으로 명확히 정해야 하며, 최종 Go/No-Go까지 자동 전이하면 안 된다.

## 6. 구현 전 우선순위 Top 10

효과·비용은 사용성 실험과 개발 산정 전의 **추정**이다. 잘못된 판단을 막는 항목을 먼저 두고, 비슷한 효과에서는 수정 비용이 낮은 항목을 앞세웠다.

| 순위 | 고칠 것·대표 근거 | 기대 효과 | 비용 | 구현 전 완료 기준 |
|---|---|---|---|---|
| 1 | 상태 판정 규칙 수정 — Verdict SER-007 ‘unknown → 부족’, 금액·기간 ‘proposed → 충족’ | 잘못된 탈락·참여 판단 방지. G2 신뢰의 전제 | 낮음~중간 | 미확인·확인된 부족·확인된 충족의 예시가 §7과 일치하고 제안값이 확정 판단 근거로 쓰이지 않는다. |
| 2 | 집계·버전 정합화 — Verdict 54 대 48, Main/Timeline 부족 1 대 3, Company 유효기간 미입력 | 같은 사업기회를 어느 채널에서 봐도 동일하게 이해 | 낮음~중간 | 모든 숫자에 단위·분모가 있고, 동일 버전의 값은 일치하며 이전 결과에는 기준 시점이 표시된다. |
| 3 | 채택·조회·추적·분석 실행 분리 — Slack ‘채택…분석 시작’, Main ‘추적 시작’ | 불필요한 클릭과 중복 결정 제거, push 원칙 복원 | 중간 | 자동 분석 중에도 채택·무시가 가능하고, 조회만으로 사람 결정이 바뀌지 않으며 결과·취소가 보인다. |

| 5 | 원문·회사 근거·문장 연결 — Verdict 자기 페이지 쪽 링크, Proposal 비링크 출처 | 사용자가 나라장터·사내 자료를 다시 찾는 비용 감소 | 중간~높음 | 판정과 문장에서 해당 근거를 열고 복귀한다. 쪽 미확인에는 쪽 점프가 없고 추정 쪽은 구분된다. |
