# UI 레퍼런스 조사와 적용 (2026-10-16)

- 목적: RL 화면(브리핑·Slack·사업기회 타임라인·실무자 판정·제안서 초안·회사 근거)의 참고 서비스를 찾고, 가져올 패턴을 화면별로 고정한다.
- 방법: 리서치 에이전트 2개(국내 입찰정보 서비스 / 해외 입찰 인텔리전스·RFP 대응·트리아지·근거 연결·데이터 신뢰도 도구)가 공식 문서·앱스토어·리뷰·teardown을 읽었다. 로그인 뒤 화면은 보지 못했고 벤더 서술은 "벤더 설명", 유추는 "추정"으로 구분했다. 원문 보고는 세션 기록에만 있고 이 문서는 채택 판단 중심으로 압축했다.
- 결과 반영: 목업 v10(§4), RL spec 항목(§5).

## 4. 피하기로 한 것

- 메뉴 진입마다 검색해야 목록이 뜨는 구조, 업무 흐름과 다른 메뉴 묶음(차세대 나라장터 첫 주 민원).
- 한 행 8열 + 링크 5개(G2B+). 1280px에서 열 6개 이하.
- fit 점수 숫자 하나만 노출. 숫자 대신 요인 칩과 근거 문장(일타비드·GovWin 둘 다 분해를 함께 보여 준다).
- 출처 경로를 popover·사이드바·탭으로 세 갈래 두기(Perplexity 지적). 원문 패널 하나로 통일.
- "Overdue"처럼 비난조 상태 라벨. "검토 대기"로.
- 벤더 자체 후기를 UI 근거로 삼기.

## 5. spec으로 넘긴 것

P5(집계 제외 규칙), P7의 재판정 트리거 조건, P14의 상태 기계와 권한(전원 동일 권한 전제), P16 적중 기록, 키보드 흐름의 정확한 키 배치(기존 `useRowKeyboardNavigation`과 충돌 여부), Slack action_id 규칙과 메시지 갱신 API.

## 7. CRM 계열 앱 구조 적용 (목업 v14~18, 2026-10-16)

사용자 요청: Attio 같은 CRM·ERP의 **제품 UI 구조**(마케팅 사이트가 아니라 앱)를 레퍼런스로. 적용한 문법:

| 구조 | Attio 계열의 원형 | BidOps 대응 |

**결정 필요 (테마).** 현재 제품 테마(ADR-0048, 무드보드 파생 남색 사이드바·연녹 배경)와 달리 CRM 계열은 밝은 회색 사이드바·흰 바탕이다. 목업은 CRM 구조를 따랐으므로 RL 구현 전에 테마 토큰(`bidops`)을 개정할지, 구조만 가져오고 색은 기존 테마를 유지할지 정해야 한다. 화면 CSS에서 `--color-*`를 재정의하지 않는 규칙은 그대로다.

## 8. 정보량 정리와 공통 프레임 (목업 v20~26, 2026-10-16)

- 사용자 지적: 글이 너무 많고 실무자가 볼 필요 없는 운영 정보가 섞여 있으며 한 화면에 너무 많은 것을 담았다.
- 정리 원칙: (1) 모델·정책·실행 시각·변환 수치·집계 분모·인터뷰 번호·영문 상태명은 화면에서 뺀다(운영 화면 몫). (2) 한 화면 = 한 가지 일. 브리핑은 반응하기, 활동은 흐름 보기, 판정은 걸리는 조건 보기, 제안서는 절 검토, 회사 근거는 빈 값 채우기. (3) 설명 문장을 없애고 상태 이름(확인됨·확인 필요·부족·충족·추정값)만 쓴다. (4) 브리핑 표는 6열(공고·단계·판정·마감·반응·담당), 나머지는 피크 패널로.
- 공통 프레임(Attio 데모 영상의 앱 셸 기준): 사이드바 240px = 워크스페이스 전환기 → 검색(⌘K) → 알림·다음 행동·노트·보고서 → 레코드(공고·사업기회·기관·회사 근거) → 리스트(색 점 + 이름 + 건수, 새 리스트) → 하단 팀원 초대·도움말·설정·사용자. 상단바 44px = 왼쪽 오브젝트/리스트 아이콘·이름·건수(레코드 페이지는 breadcrumb), 오른쪽 공유·가져오기·주 버튼. 리스트 페이지는 그 아래 뷰 탭(+ 뷰 추가)과 검색·필터·정렬·보기 설정. 레코드 페이지는 그 아래 아이콘·제목·상태 pill·레코드 액션.
