# RL 화면 구현 명세 (시안 v26 기준)

- 상태: 2026-10-16 사용자 확정 시안 v26을 구현 가능한 수준으로 고정한 명세. 기능 intent·spec·plan(`/sdlc:feature RL-0x`)은 이 문서를 화면 정본으로 인용한다. 시안 HTML 사본은 [`mockups/v26/`](mockups/v26/README.md).
- 적용 범위: 브리핑·사업기회 레코드(활동·판정·제안서 탭)·회사 근거·Slack 메시지. 기존 화면(발주계획·사전규격·사업 추적·Go/No-Go·판정 기준·실행 상태)은 §1.4의 메뉴 재배치 외에는 바꾸지 않는다.
- 지키는 것: 데스크톱 1280~1920 전용(ADR-0047), 테마 토큰만 읽고 화면 CSS에서 `--color-*`를 재정의하지 않음(ADR-0048), Astryx 컴포넌트 우선·레이아웃은 프로젝트 소유(ADR-0040), `unknown`을 부족으로 승격하지 않음(HP 계약 §7), 판정은 보조 의견이고 추적·Go/No-Go는 사람 결정.
- 원칙(§8 ui-references): 운영 정보는 실무 화면에 없다. 한 화면 = 한 가지 일. 상태 이름은 확인됨·확인 필요·부족·충족·추정값·대기·채택·무시·나중에.

### 1.2 사이드바 (`components/shell/Sidebar.tsx` 재작성)

위에서 아래 순서. 항목 높이 30px, 아이콘 15px, 활성은 배경 §2 `sidebar-active` + 글자 600.

1. 워크스페이스: 24px 사각 아이콘(회사 머리글자) + "루트랩" + ▾. 클릭은 설정 메뉴(설정·도움말·로그아웃 자리; 현재 로그인이 없으므로 설정만).
2. 검색: 입력 모양 버튼, 오른쪽 `⌘K`. 커맨드 팔레트는 후속(검색 화면으로 이동해도 됨).
3. 빠른 이동: 알림(건수) · 다음 행동(건수) · 노트 · 보고서. 노트·보고서는 RL 범위 밖이면 비활성(흐림) 상태로 두되 자리를 유지한다.
4. 그룹 "레코드": 공고 · 사업기회 · 기관 · 회사 근거(확인 필요 건수 pill).
5. 그룹 "리스트": 색 점(8px, 라운드 3) + 이름 + 건수. 기본 4개: 오늘의 브리핑(초록, 건수 pill) · 추적 중(청록) · 연차 예고(호박) · 마감 임박(적갈). "새 리스트"는 후속(저장된 필터 = 리스트)이며 v1에서는 비활성.
6. 하단(`margin-top:auto`): 팀원 초대(비활성) · 도움말 · 설정 · 구분선 · 사용자(아바타 22px + 이름 + 역할).

기존 메뉴 대응: 발주계획·사전규격 목록은 "공고" 레코드 뷰의 뷰 탭(발주계획·사전규격·입찰공고)으로, 사업 추적은 리스트 "추적 중", 최종 Go/No-Go는 사업기회 레코드 안 탭(후속), 판정 기준·실행 상태·회차·첨부·감사는 "설정" 아래 운영 메뉴로 옮긴다. DEMO 회사 선택기는 그리지 않는다(회사 1곳).

## 4. 화면별 명세

### 4.1 오늘의 브리핑 (`/briefing`, 시안 `Main.dc.html`)

- 일: 오늘 추천에 반응하기(볼게요·무시·나중에).
- 상단바: 색 점 + "오늘의 브리핑" + "6건 · 10월 16일 (금)" / 어제 · 공고 추가(주).
- 뷰 탭: 반응 대기(기본) · 채택 · 무시 · 나중에. 도구: 검색 · 필터 · 정렬 · 보기 설정.
- 표 6열: 공고(제목 600 + 보조 "기관 · 금액 · 기간"), 단계(pill: 발주계획·사전규격·입찰공고), 판정(pill: 진행 가능·조건부 진행·판단 보류·연차 추적), 마감(D-n 600, warning 색은 7일 이내; 보조 "날짜" 또는 "의견 마감"; 발주계획은 "n월 발주 예정"), 반응(pill: 대기·채택·무시·나중에), 담당(아바타 22px, title로 이름).
- 둘째 묶음 "추적 중인 사업의 변화 n": 같은 표, 정정·마감 변경 행(바탕 warning-subtle, 판정 "재검토 중").
- 피크 패널(선택 행): 머리(단계 pill · D-day pill) · 제목 16px/700 · 보조(기관 · 기간 · 마감 일시) · 버튼 3개(볼게요=선택 시 on 스타일) · 반응 기록 1줄("김담당이 채택 · 08:41") · 판정 블록(판정 이름 600 + 두 문장 이내 사유 + "확인할 것 n · 항목") · 왜 추천(칩 3개 이내: 키워드·비슷한 실적 n건·기관 거래 이력) · 다음 행동(체크 2개 + 담당 아바타) · "자세히 보기"(레코드로).
- 상태: 추천 0건 → 표 자리에 빈 상태("오늘 추천할 공고가 없습니다 · 수집 정상") / 수집 실패 → 경고 블록("오늘 수집이 끝나지 않았습니다") / 판정 진행 중 → 판정 셀 "분석 중". 반응 저장은 즉시 반영 + 되돌리기(5초 토스트, 기존 토스트 컴포넌트).
- 키보드: 행 이동 ↑↓(기존 `useRowKeyboardNavigation` 재사용), 1 볼게요, 2 무시, H 나중에, Enter 레코드 열기, Esc 피크 닫기, Z 되돌리기. 안내는 도움말에.
- 데이터: 브리핑 API(신설, RL-01 spec) — 날짜별 추천 목록(공고 id·단계·판정·사유 2문장·확인 항목·추천 요인·마감·금액·반응·담당)과 반응 PATCH. 공고 상세는 기존 `/api/pre-specs/:id`·`/api/order-plans/:pk`.
- 표시 금지: 깔때기 수치, 모델·정책명, 실행 시각, 카드 매핑 수, 인터뷰 번호, 집계 분모.

### 4.2 Slack 메시지 (`Slack.dc.html`)

- 평일 08:00 1회, 추천 0건이면 발송 안 함. 머리 "오늘의 브리핑 · 날짜 · n건".
- 항목: 제목(레코드 링크) · 기관 · 금액 · 마감(D-n, 7일 이내만 강조) / 한 줄(판정 — 핵심 조건 또는 추천 이유) / 버튼 볼게요(primary)·무시(default). 항목 사이 divider.
- 클릭 뒤 메시지 갱신: 버튼 자리에 "✓ 이름이 볼게요" + 되돌리기. 끝에 "화면에서 보기" 링크 하나.
- 정정·마감 알림은 추적 중 건에만 별도 메시지(같은 형식 1건).

### 4.3 사업기회 레코드 — 활동 (`/opportunities/:id/activity`, `Timeline.dc.html`)

- 일: 이 사업이 지금 어디까지 왔는지 보고 결정·메모하기.
- 레코드 헤더 pill: 단계 · 마감 D-n · 판정 · 추적 상태. 액션: 판정 보기(주) · 제안서 초안 · ⋯(추적 결정 변경·종료).
- 좌측 정보(280px): 속성 8개(발주기관·사업기간·금액·계약·공동수급·입찰 마감·담당·추적) / 다음 행동(체크 2~3) / 제출 서류(진행 막대 + "n / 27" + "남은 서류 보기").
- 탭: 활동 · 판정 · 제안서 · 서류 · 원문 · 비슷한 공고.
- 중앙: 단계 바 → 작성기 → 활동 목록. 활동은 사람 행동(추적 결정·반응·노트)과 사업 사건(발주계획 발견·사전규격 공개·공고 게시·정정·판정 완료·초안 준비)만. 각 항목 한 줄 + 보조(날짜 · 링크). 시스템 처리 세부(변환·호출·정책)는 넣지 않는다.
- 상태: 탭별 빈 상태 문장 1줄. 판정 진행 중이면 헤더 pill "분석 중".
- 데이터: 기존 `/api/opportunities/:id`(링크·추적 상태·마감), 공고 상세, 추적 PATCH `tracking-status`, 활동 피드 API(신설, RL-02 spec).

### 4.4 사업기회 레코드 — 판정 (`/opportunities/:id/verdict`, `Verdict.dc.html`)

- 일: 걸리는 조건과 근거를 보고 다음 행동 정하기.
- 좌측(280px): 판정 이름 20px/700(색: 진행 가능 success, 조건부 warning, 진행 어려움 error, 판단 보류 secondary) + 사유 2문장 / 체크리스트 5행(자격·실적, 상주·인력, 금액·기간, 기술, 운영·SLA — pill) / 다음 행동(체크 + 담당) / 한 줄 고지 "판정은 참고 의견입니다. 추적 여부와 참여 결정은 담당자가 정합니다."
- 헤더 액션: 제안서 초안(주) · 다시 판정 · ⋯(판정 오류 제보).
- 중앙: 제목 "요구사항 n" + 보조 "부족 a · 확인 필요 b · 충족 c" + 도구(상태 select 기본 "부족·확인 필요만", 필수만 토글). 표 4열: 요구사항(정규화 문장 600 + 보조 "유형 · 필수/조건부"), 대조(pill 부족·확인 필요·충족), 회사 근거(한 줄 + 보조 한 줄), 원문(쪽 링크; 쪽 미확인은 "쪽 미확인" 글자). 기본 정렬 부족 → 확인 필요 → 충족. "n건 더 보기"로 페이지.
- 우측(300~380px, 행 선택 시): 원문 패널(§3).
- 규칙: `unknown`은 "확인 필요"로만 표시(부족 아님). 역할 의견 불일치는 좌측 사유 문장에 녹이고 별도 블록 없음. 모델·정책·실행 시각은 ⋯ 메뉴의 "실행 정보"에서만.
- 데이터: HP 계약 §6~8의 unit·대조·역할·종합 결과(RL-03 spec), 원문 쪽 locator(`para_page_map`, 상속 쪽은 링크 뒤 "(추정)").

### 4.5 사업기회 레코드 — 제안서 (`/opportunities/:id/proposal`, `Proposal.dc.html`)

- 일: 절 단위로 초안을 읽고 빈 자리를 채워 검토 완료하기.
- 헤더 액션: PDF로 내보내기(주) · 다시 만들기 · ⋯(HWP 후속·버전 비교).
- 좌측(280px): 단계 4(목차 · 초안 · 검토 완료 · 제출 준비, 세로 stepper) / 숫자 3(확인할 문장 · 비어 있는 자리 · 분량) / 채워야 할 것(담당 아바타 + 항목 + 건수) / 한 줄 범례("주황 표시는 사람이 채우거나 확인할 자리입니다").
- 중앙: 절 탭(제안 개요 · 사업수행 실적 · 수행 전략 · 요구사항 수행방안(확인 건수 pill) · 운영·SLA · 수행조직) → 본문 카드(세리프 14px/1.8, 최대 620px) + 우측 "이 절이 답하는 요구사항" 표(요구사항 600 + 보조 "근거: …", 상태 pill). 본문 안 표식: 출처는 작은 초록 위첨자 "출처", 빈 자리·제안 수치는 warning 바탕 inline. 본문 하단 버튼: 문장 수정 · 이 절 다시 쓰기 · 검토 완료(주).
- 규칙: 가격·투입 인력·전략은 초안에 넣지 않는다. 출처 없는 문장은 생성하지 않는다. 내보낸 PDF에도 표식을 남긴다.
- 데이터: 초안 API(신설, RL-04 spec) — 절·문장·표식·요구사항 연결·단계.

### 4.6 회사 근거 (`/company`, `Company.dc.html`)

- 일: 판정이 막힌 빈 값과 추정값이 무엇인지 보고, 고칠 값을 회사 파일 수정 대상으로 확인하기. **화면은 읽기 전용이다**(2026-10-16 결정, RL-00) — 정본은 회사 파일이고 화면은 등록된 버전을 보여 준다. 시안의 "맞음·수정·입력·저장" 행동은 그리지 않는다.
- 상단바: 아이콘 + "회사 근거" + "㈜루트랩 · 마지막 저장 날짜" / 이전 버전(현재 버전만 표시, 선택은 후속). 저장(주) 버튼은 없다. 본문 상단에 안내 한 줄 "값 수정은 회사 파일을 고쳐 다시 등록합니다(설정 › 도움말)".
- 좌측(240px): 항목 내비(확인이 필요한 것(건수 pill) · 자격 서류 · 실적 · 인력 · 선호·제외 조건 · 제안서 자료) / 숫자 3(확인됨 · 확인 필요 · 곧 만료). 수치는 화면이 `profile` facts로 센다(분모 표시 없음). "곧 만료"는 qualification `valid_until`이 `expiry_warning_days` 이내인 사실이며, 현재 회사 파일에는 유효기간이 없어 0이다(계산 규칙만 구현).
- 그룹 매핑(`?group=`): `attention`="확인이 필요한 것"(추정값 ∪ 확인 필요) · `qualification`=자격 서류 · `performance`=실적(project) · `staff`=인력(staff_group) · `preference`=선호·제외 조건(domain·`pref:`·`excl:` capability) · `proposal-assets`=제안서 자료(**비활성**, 빈 상태 "RL-04에서 채웁니다").
- 중앙: 블록 "확인이 필요한 것 n"(warning 경계; 행 = 항목 + 상태 pill) → 그룹 표(서류·상태 pill·내용). **영향 공고 열은 RL-03(판정 결과)이 생기기 전까지 그리지 않는다**(빈 열 금지). 행마다 **fact_key를 복사하는 ghost 버튼 하나**만 둔다(회사 파일에서 고칠 노드를 찾기 위함).
- 상태 이름: `confirmed`→확인됨(success), `proposed`→추정값(blue), `unknown`→확인 필요(warning), `inferred`→표시 안 함(RL-00 파일에 없음). 확인 필요는 부족이 아니다(error 색 금지).
- 규칙: 확인된 값만 판정·제안서에 쓴다(화면에는 적지 않음). 사본 파일은 저장하지 않고 파일명·발급일·유효기간만. 새 값은 회사 파일을 고쳐 새 버전으로 등록하며 이전 버전은 불변이다. 운영 정보(graph hash·profile version·인터뷰 번호·`unmeasured_reference`)는 DOM에 두지 않는다(§5).
- 데이터: `GET /api/company`(회사 이름·마지막 저장 날짜·만료 기준 일수), `GET /api/companies/{id}/profile`(facts·상태·origin, 화면이 센다), 사이드바 pill은 `GET /api/workload`의 `company_attention`(짝 목록 REST 없음, ADR-0067 예외 — contracts.md).
