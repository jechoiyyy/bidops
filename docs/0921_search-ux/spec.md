# 목록 조회 도구와 검색 UX 통일 — 명세

- 상태: 구현 계약 확정·제품 구현 및 관련 검증 완료(2026-09-21). 운영 배포 전.
- 관련 문서: [의도](intent.md) · [구현 계획](plan.md) · [기존 REST 계약](../contracts.md).
- 범위: 발주계획·사전규격·사업 추적·최종 Go/No-Go의 조회 도구 배치와 목록 검색. API 응답 envelope·DB 스키마·검색 색인은 바꾸지 않는다.

## 1. 화면 배치와 조회 범위

보기 탭을 첫 줄에 두고 조회 도구는 그 **아래 왼쪽부터** 다음 표의 순서로 둔다. 1280×800에서도 기본 도구인 필터 → 검색 → 수집 회차는 **한 줄 배치**를 목표로 하고 기존 검색칸 폭과 테마 토큰 간격을 유지한다. 사전규격의 추가 조회 조건만 공간이 부족하면 다음 줄로 보낸다. 줄을 넘겨도 읽기·탭 순서를 유지한다. 기존 상세 필터의 내용과 열림 상태, 보기 탭, 목록·상세의 레이아웃은 유지한다. 1280×800과 1440×900에서 도구가 겹치거나 잘리지 않아야 한다. 1280px 미만을 위한 별도 레이아웃은 만들지 않는다.

| 화면 | 탭 다음 조회 도구의 순서 | 검색 대상과 실행 위치 | 기존 보조 요소 |
|---|---|---|---|
| 발주계획 `/order-plans` | 상세 필터 토글 → 검색 → 수집 회차 | 이미 불러온 누적 또는 선택 회차의 각 행 `title`, `agency_name`, `order_plan_unty_no`를 클라이언트에서 검색 | 수집 회차는 감사용 범위 선택이며 상세 필터 축·저장된 보기는 유지 |
| 사전규격 `/pre-specs` | 상세 필터 토글 → 검색 → 수집 회차 → 추가 조회 조건 | `GET /api/pre-specs`의 `Notice.title`, `Notice.agency`를 서버에서 검색 | SW 중심 스위치는 보기 탭 옆. 추가 조회 조건은 검토 포함 여부(전체 이력 전용)·마감 구간(검토할 항목 전용, 2026-09-21 [ADR-0064](../tracking/decisions/0064-prespec-actionable-deadline-scope.md))과 관측 날짜. 앞의 둘은 서로 배타적이라 같은 칸을 나눠 쓰며 동시에 보이는 보기는 없다. 기존 나머지 조건은 상세 필터에 유지 |
| 사업 추적 `/opportunities` | 상세 필터 토글 → 검색 | `GET /api/opportunities`에서 해당 사업기회의 **authoritative 소유 링크** 대상인 `OrderPlan.title`, `agency_name`, `Notice.title`, `agency`, `demand_agency`를 서버에서 검색 | 조치 사유 칩은 도구 아래에 유지 |
| 최종 Go/No-Go `/go-no-go` | 검색 | `GET /api/bid-delta/decision-queue?status=all`에서 현재 페이지로 **받은 행만** 클라이언트에서 검색. 행의 실제 `title`, `agency`가 대상 | 범위 안내는 도구 아래에 유지. 받은 범위만 검색한다는 문구와 전체/받은 건수 구분 유지 |

Go/No-Go의 `제목 미확인`·`발주기관 미확인` 같은 표시 대체 문구는 데이터 필드가 아니므로 검색 대상이 아니다. `null` 필드는 그 필드만 건너뛴다. 사업 추적의 후보 대기·거절·검색 미확인 링크 및 다른 사업기회의 필드는 검색하지 않는다. 어느 화면에서도 서로 다른 필드나 링크의 값을 이어 붙여 한 검색어를 맞추지 않는다. 각 필드를 독립적으로 비교한 결과를 OR로 결합한다. 검색은 기존 필터·보기 조건과 AND이며 정렬·대상 모집단을 넓히지 않는다.

## 2. 문자열 비교와 길이

검색용 비교값 `key(s)`는 **query와 각 target 필드에 동일하게** 다음 순서로 만든다. 원문 DB 값, 행 표시, 입력칸 값, 적용된 URL `q`는 이 함수로 덮어쓰지 않는다.

1. 아래 표의 [Unicode `White_Space` 25개 코드포인트](https://www.unicode.org/Public/16.0.0/ucd/PropList.txt)와 BOM `U+FEFF`를 모두 제거한다. 다른 제어문자·문장부호는 제거하지 않는다.
2. ASCII 영문 `A`–`Z`(`U+0041`–`U+005A`)만 각각 `a`–`z`로 바꾼다. 다른 유니코드 문자는 원형을 유지한다. Unicode 전역 casefold, 로캘별 소문자화, NFKC·NFC 변환은 수행하지 않는다.
3. 빈 검색어가 아니면 대상 필드의 `key`에 질의 `key`가 **연속 부분 문자열**로 포함되는지 검사한다. 토큰 AND/OR, 순서 무시, 초성·오타·동의어 검색은 없다.

| 공백 집합 | 정확한 코드포인트 |
|---|---|
| ASCII 제어 공백 | `U+0009` TAB, `U+000A` LF, `U+000B` VT, `U+000C` FF, `U+000D` CR |
| 나머지 Unicode `White_Space` | `U+0020` SPACE, `U+0085` NEL, `U+00A0` NBSP, `U+1680` OGHAM SPACE MARK, `U+2000`–`U+200A`, `U+2028` LINE SEPARATOR, `U+2029` PARAGRAPH SEPARATOR, `U+202F` NARROW NBSP, `U+205F` MEDIUM MATHEMATICAL SPACE, `U+3000` IDEOGRAPHIC SPACE |
| 추가로 지울 문자 | `U+FEFF` BOM |

`%`, `_`, 역슬래시 `\`는 검색 문법이 아닌 **문자 그대로** 비교한다. SQL 검색은 정규화된 query를 매개변수로 바인딩하고 `LIKE`의 `%`·`_`·escape 문자 `\`를 이스케이프한다. SQL `lower()`의 데이터베이스별 비영문 case 동작에 의존하지 않고 위 ASCII 변환과 동일한 연산을 target에 적용한다. PostgreSQL·SQLite에서 같은 공백 목록·비교 결과가 나와야 한다. 프런트엔드도 자바스크립트 기본 `trim()`·`\s` 또는 로캘별 `toLowerCase()`만으로 이 계약을 대신하지 않는다.

사업 추적의 기존 `q` **2~100자 제한**은 유지한다. 길이는 raw query에서 위 공백 집합의 연속 구간을 ASCII SPACE 한 칸으로 바꾸고 양끝을 제거한 **검증용 값**의 Unicode 코드포인트 수로 센다. 이 값은 길이 검사에만 사용한다. 프런트엔드는 `Array.from(...).length`, 서버는 Python `len(...)`처럼 코드포인트 수를 세어 같은 판정을 내린다. 내부 공백의 원래 종류·개수는 입력칸과 URL/API `q`에 그대로 남긴다. raw 길이만으로 먼저 422를 내는 검증은 피한다. 공백만 있는 `q`는 검색 해제, 비어 있지 않으면서 검증용 길이가 1 또는 101 이상이면 invalid다. 나머지 세 화면에는 새 길이 제한을 만들지 않는다.

## 3. 적용, URL, 선택

- 네 화면 모두 입력 중에는 목록·건수·URL·선택을 바꾸지 않는다. Enter로만 draft를 적용한다. `raw draft`(입력칸)와 `applied q`(URL `q`, 실제 검색 조건)를 별도 상태로 둔다. 뒤로 가기·외부 링크·저장된 보기로 적용된 URL이 바뀌면 draft를 그 raw `q`로 동기화한다. 입력 중에는 URL 동기화 효과가 draft를 덮지 않는다.
- 네 입력칸에 공통 안내 `Enter로 검색 · 띄어쓰기 무시`를 보인다. draft가 적용된 raw `q`와 달라지면 `Enter로 적용` 상태를 함께 명확히 표시해 현재 목록이 아직 바뀌지 않았음을 알린다. 오류 문구는 입력칸과 안정적인 ID의 `aria-describedby`로 연결하고 `aria-invalid`를 표시한다. 오류가 생기거나 해제될 때 보조 기술이 상태 변화를 알 수 있게 한다.
- 적용한 유효 query는 띄어쓰기와 대소문자를 포함한 **입력 그대로** URL `q`에 저장한다. `URLSearchParams`로 인코딩하고 읽을 때 원형을 복원한다. `q`가 없거나 공백/BOM만 있으면 `q`를 제거해 검색을 해제한다. 다른 URL 필터는 보존한다. API로 전달하는 `q`도 URL의 raw 값을 사용하고 서버가 비교용 값만 따로 만든다.
- 사업 추적에서 invalid 길이로 Enter를 누르면 적용·URL·서버 요청·페이지·선택은 그대로 유지하고 입력 오류를 표시한다. **기존 검색 결과를 유지**하며 현재 목록을 `검색어 없이 받은 목록`으로 잘못 설명하지 않는다. 오류가 있더라도 마지막으로 적용된 `q`와 실제 결과 범위를 계속 표시한다. 유효한 입력으로 고치거나 지우면 오류를 해제한다. URL 직접 진입의 `q`가 이 길이 규칙에 맞지 않으면 사용자 입력 오류로 표시하고 그 `q`를 URL과 입력칸에 보존한다. 유효한 검색으로 고치거나 지우기 전까지 무검색 요청·결과로 대체하지 않는다. 유지할 이전 결과가 없는 최초 진입에서는 목록을 조회하지 않고 오류 상태를 보인다.
- 입력칸 **지우기 버튼 클릭**은 즉시 draft를 비우고 적용된 `q`만 제거한다. 기존 미저장 입력 guard가 필요한 화면에서는 guard가 승인한 뒤 변경하며 취소하면 draft·`q`·목록·선택을 복구한다. 키보드 Backspace/Delete로 빈칸을 만드는 행위는 draft만 바꾸고 다음 Enter까지 적용하지 않는다. 지우기와 전체 필터 초기화는 별개다.
- 적용된 검색 결과가 0건이면 **현재 적용된 검색어**와 다른 활성 필터가 함께 작용한다는 사실을 빈 상태에 적고 `검색어만 지우기` 버튼을 제공한다. Go/No-Go는 받은 범위의 0건임을 함께 밝힌다. 이 버튼은 입력칸 지우기와 동일한 검색 해제 동작·미저장 입력 guard를 사용하고 다른 필터를 변경하지 않는다. draft가 미적용 상태라면 빈 상태에는 draft 대신 결과를 만든 applied `q`를 보여 준다.
- Enter는 IME 조합 확정 키이면 적용하지 않는다. `keydown`의 `isComposing`, `keyCode===229`, 조합 상태를 함께 확인한다. 현재 Astryx `TextInput.onEnter`는 이벤트를 넘기지 않으므로 공유 `WorkspaceSearch`가 이벤트를 받을 수 있는 `onKeyDown` 경로에서 적용을 중재한다. 이 컴포넌트의 지우기 버튼은 현재 `onChange('', null)`을 호출하므로 이를 지우기 클릭으로 구분하고, 키보드 입력 이벤트의 빈 문자열과 혼동하지 않는다. 컴포넌트 교체 시에도 이 **행동** 계약을 유지한다.
- 선택/page를 바꿀지는 raw `q`가 아니라 `key(applied q)`와 `key(next q)`를 비교해 결정한다. 두 값이 같으면 URL raw 값은 새 입력으로 갱신할 수 있으나 `offset`, 선택 ID, 비교 ID, 사전규격 선택 세대·검토 맥락은 유지하고 불필요한 재조회도 하지 않는다. 달라지면 기존 검색 변경 경로대로 `offset=0`으로 옮기고 유효하지 않은 선택을 정리한다. 사업 추적·사전규격의 미저장 입력 guard는 이 실제 조건 변경에 적용한다.
- 발주계획·사전규격의 기존 선택 fingerprint에는 raw `q` 대신 `key(applied q)`를 넣는다. 다른 축의 fingerprint 규칙은 그대로다. 사업 추적·Go/No-Go도 동등 query에 대한 페이지·선택 초기화를 막는다. 단, 다른 필터 변경이나 새 결과에서 선택 행이 사라지는 기존 정리 규칙은 유지한다.

## 4. API와 건수 의미

`GET /api/pre-specs`와 `GET /api/opportunities`의 `q`는 서버에서 모든 필터와 결합해 **페이지를 자르기 전에** 적용한다. `total`은 적용한 조건 전체 건수이고 `items`만 `limit/offset` 구간이다. 사전규격 `workspace_counts`·`overview_status_counts`는 기존 각 집계의 제외 축 규칙을 지키되 공통 `q`를 반영한다. 사업 추적 `section_counts`는 `section`만 제외하고 `q`를 반영하며, `action_reason_counts`는 `reason`만 제외하고 `q`를 반영한다. 응답 필드와 오류 envelope는 기존 계약을 따른다.

발주계획 화면은 기존대로 불러온 누적/회차 전체에 `q`를 클라이언트에서 적용한 뒤 화면 페이지를 자른다. 보기 탭의 건수는 기존처럼 `q`를 제외한 축의 건수다. 독립 `GET /api/order-plans?q=...` 호출도 같은 세 필드·문자 비교를 적용하고, 그 응답의 `total`은 서버가 `limit/offset` 전에 센 일치 건수다. 화면 검색을 서버의 한 페이지에만 적용하지 않는다.

Go/No-Go는 `q`를 decision-queue API에 추가하지 않는다. 서버 `total`은 계속 추적 중인 전체 queue 건수이며 클라이언트의 보기 탭 건수·검색 결과는 현재 받은 페이지 범위다. `q`는 받은 행을 좁히지만 queue API 요청 인자·서버 `total`을 바꾸지 않는다. `total>받은 건수`이면 검색 결과 0건도 전체 0건으로 말하지 않는다. 선택한 행 하나의 상세 조회 방식은 유지한다.
