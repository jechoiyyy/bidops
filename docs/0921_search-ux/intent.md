# 목록 조회 도구와 검색 UX 통일 — 의도

- 상태: 제품 구현·관련 검증 완료(2026-09-21). 운영 배포 전.
- 정본: [intent.md](intent.md) · [spec.md](spec.md) · [plan.md](plan.md).
- 문서 작성 뒤 사용자의 후속 요청에 따라 제품 구현과 로컬 검증까지 진행했다. 운영 배포·commit·push는 실행하지 않았다.

## 해결할 문제

목록의 보기 탭과 수집 회차는 왼쪽에 있지만 검색칸과 필터 아이콘은 오른쪽 끝에 있어,
같은 목록을 좁히는 조작 사이의 시선·포인터 이동이 크다. 네 목록 화면에서 조작 위치를 통일한다.

검색 규칙도 화면마다 다르다. `사이버수사포털시스템 고도화`는 `사이버수사`로 찾을 수 있지만
`사이버 수사`로는 찾지 못하는 화면이 있다. 사용자가 원문의 띄어쓰기를 기억할 필요 없이
사업명·기관명 등을 검색하도록 한다. 입력 중 목록이 바뀌는 시점도 화면마다 달라 예측하기 어렵다.

## 사용자와 성공 기준

사용자는 데스크톱·노트북에서 발주계획·사전규격을 탐색하고 사업 추적·최종 Go/No-Go를
검토하는 사내 담당자다. 다음 행동이 네 화면에서 일관되게 동작하면 목적을 달성한다.

- 보기 탭 아래 왼쪽에서 필터 → 검색 → 수집 회차 순으로 조작한다. 없는 기능은 추가하지 않는다.
- 원문과 검색어의 공백 차이·영문 대소문자 차이로 검색 결과가 달라지지 않는다.
- 검색어 입력만으로 목록이 바뀌지 않고 Enter로 적용한다. 한글 조합 확정 Enter는 검색하지 않는다.
- 지우기 버튼으로 검색만 해제하며 다른 필터와 미저장 입력 보호는 유지한다.
- 검색 조건이 의미상 같으면 선택과 페이지를 불필요하게 초기화하지 않는다.
- 조회 범위·검색 오류·적용 전 입력을 구분해서 현재 목록의 의미를 알 수 있다.

## 확정한 범위

| 화면 | 조회 도구 순서 | 검색 대상 범위 |
|---|---|---|
| 발주계획 | 필터 → 검색 → 수집 회차 | 기존에 불러온 발주계획의 사업명·기관명·계획번호 |
| 사전규격 | 필터 → 검색 → 수집 회차 → 추가 조회 조건 | 서버 사전규격의 사업명·기관명 |
| 사업 추적 | 필터 → 검색 | 기존 authoritative 연결 대상의 사업명·기관명 |
| 최종 Go/No-Go | 검색 | 기존에 불러온 목록의 표시 사업명·기관명 |

추가 조회 조건은 사전규격의 검토 포함 여부·관측 날짜다. SW 중심 스위치는 보기 탭 옆에 둔다.
사업 추적의 조치 사유와 Go/No-Go의 범위 안내는 조회 도구 아래에 둔다. 검색의 데이터 범위를
넓히지 않으며 Go/No-Go의 받은 범위 내 검색 안내도 유지한다.

공백을 제거한 연속 부분 문자열을 비교한다. `사이버 수사`는 위 예시 사업을 찾지만
`사이버 고도화`나 `고도화 사이버`는 찾지 않는다. 입력과 원문 표시는 보존하며 저장된 원본을 고치지 않는다.

## 하지 않는 일

여러 단어 AND/OR 검색, 순서 무시, 초성·오타·동의어 검색, 모든 문장부호 제거, 검색 순위 재정렬,
Go/No-Go 전체 데이터 서버 검색, 신규 검색 엔진·DB 정규화 열·migration, 모바일 레이아웃은 제외한다.
사업 추적 상태·등급·리뷰·자동 분석 자격과 사전규격 검토 제외 규칙은 변경하지 않는다.

## 구현 운영 원칙

문서 작성과 최종 수정은 관리자가 직접 수행한다. 이후 제품 구현의 사용자 지정 모델은 **Sol high(`gpt-5.6-sol`, high)**와 **Luna max(`gpt-5.6-luna`, max)**다.
관리 에이전트가 계약과 파일 소유 범위를 확정하고 독립 작업을 위임한다. 작업자는 완료 보고를 보내고,
관리자는 완료 통지를 받아 후속 작업·통합·최종 검토를 수행한다. 반복적인 진행 조회나 무한 폴링은 하지 않는다.
질문·차단 문제만 예외적으로 즉시 전달한다. 구체적인 작업 순서와 검증 책임은 [plan.md](plan.md)에 정한다.

문서 단계는 내용·링크·diff만 검사한다. 제품 구현 뒤에는 변경 경로의 관련 검사와 지원 폭
1280×800·1440×900 검증을 수행하고, 통과 뒤 새 변경이나 구체적 실패 없이 같은 검사를 반복하지 않는다.
운영 재배포는 제품 구현·검증 완료 뒤 별도 사용자 요청과 실행 직전 확인에 따른다.
