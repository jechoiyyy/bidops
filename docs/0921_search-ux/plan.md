# 목록 조회 도구와 검색 UX 통일 — 구현 계획

- 상태: 제품 구현·관련 검증 완료(2026-09-21). 운영 배포 전.
- 정본: [의도](intent.md)는 목적·범위, [명세](spec.md)는 동작 계약, 이 문서는 실행 순서·책임·검증을 소유한다.
- 문서는 관리자가 직접 마무리한다. 아래 Sol high·Luna max 위임 방식은 이후 제품 구현에 적용한다.
- 문서 작성 뒤 사용자의 후속 요청에 따라 제품 구현·로컬 검증까지 진행했다. 운영 재배포·commit·push는 실행하지 않았다.

## 1. 구현 기준

네 화면에 명세의 왼쪽 조회 도구 행과 Enter 검색을 적용한다. 구현 중 다음 구분을 유지한다.

- **비교용 값:** query와 target에서 명세의 공백 26개를 제거하고 ASCII A–Z를 소문자로 바꾼다. 필드별 연속 부분 문자열을 OR로 결합한다. 여러 필드·링크를 이어 붙이지 않는다.
- **길이 검증용 값:** 사업 추적에서만 연속 공백을 한 칸으로 줄이고 양끝 공백을 제거한 값의 코드포인트 수가 2~100인지 검사한다. 공백을 모두 제거한 비교용 값의 길이와 혼동하지 않는다. 공백만 있으면 검색 해제다.
- **표시·전달 값:** 입력과 URL/API의 raw `q`는 띄어쓰기와 대소문자를 보존한다. 저장된 제목·기관명·번호를 수정하지 않는다.
- `%`, `_`, 역슬래시는 문자 그대로 비교한다. null 필드·표시 대체 문구는 검색 대상이 아니다.
- 검색 입력과 적용된 조건을 분리한다. Enter·IME·지우기·길이 오류·URL 직접 진입·동등 query의 선택 보존은 [명세 §3](spec.md#3-적용-url-선택)을 따른다.
- 사전규격·사업 추적은 서버에서 페이지 분할 전에 검색한다. 발주계획·Go/No-Go 화면은 기존 클라이언트 검색 범위를 유지한다. 기존 발주계획 API의 `q`도 같은 문자 비교 규칙을 적용한다.

## 2. 담당과 파일 소유권

모델 설정은 사용자 지정대로 고정한다. 관리자는 범위·인계·검증·최종 검토를 맡는다.
공용 입력 컴포넌트와 네 페이지가 겹치므로 아래 두 구현 단계는 **순차 인계**한다.

| 단계 | 담당 | 소유 범위 | 인계 산출물 |
|---|---|---|---|
| 검색 동작·계약 | Sol high (`gpt-5.6-sol`, high) | 서버 검색 helper와 관련 router/service, 프런트 검색 helper, 공용 입력 이벤트, 네 페이지 검색 상태·선택 처리, 관련 단위/API 검사, REST 계약 문서 | 동작 구현·검사 코드, 변경 파일, Luna가 사용할 컴포넌트 props와 이벤트 계약 |
| 배치·안내·화면 검사 | Luna max (`gpt-5.6-luna`, max) | Sol 완료 후 공용 도구 행·네 페이지 JSX, 관련 CSS, 안내와 접근성 표시, Playwright 검사와 mock | 배치·문구·화면 검사 코드, 영향 검사 목록 |
| 통합 검증·최종 검토 | 관리자 | 두 단계의 산출물·diff·관련 검사 실행·완료 기록 | 명세 충족 판정, 실제 실행 결과, 남은 한계 |

구체적인 소유 경계는 다음과 같다.

- Sol: 신규 `web/backend/app/core/search.py`, 신규 `web/frontend/src/lib/search.ts`에 공용 비교 연산을 둔다. 기존 `lifecycle/routers/pre_specs.py`, `lifecycle/services/opportunity_queries.py`, `lifecycle/routers/opportunities.py`와 `screening/routers/order_plans.py`의 검색 경로를 연결한다. 기존 발주계획 API가 위임하는 함수도 함께 수정한다.
- Sol: `WorkspaceFilters.tsx`의 `WorkspaceSearch` 이벤트 계약, `PreSpecsPage.tsx`·`OrderPlansPage.tsx`·`OpportunitiesPage.tsx`·`GoNoGoPage.tsx`의 상태 처리, `listSelection.ts`의 검색 fingerprint를 소유한다. 관련 hook 변경이 필요하면 인계 목록에 포함한다. 배치 CSS는 이 단계에서 수정하지 않는다.
- Luna: 인계받은 공용 컴포넌트와 네 페이지의 위치·표시를 수정한다. Sol의 query·guard·선택 로직을 다시 작성하지 않는다. 공용 및 화면별 CSS와 관련 Playwright 파일을 소유한다.
- Sol이 `docs/contracts.md`의 기존 `q` 의미를 갱신한다. 관리자는 최종 검증 뒤 `docs/tracking/status.md`와 이 계획의 체크리스트를 갱신한다. 기존 설계 문서의 300ms debounce 설명 등 충돌하는 부분은 새 명세를 참조하도록 연결한다.
- 다른 작업자의 미커밋 변경을 보존한다. 공유 파일 편집권은 이전 작업자의 완료 보고를 받은 뒤에만 넘긴다. 공유 파일이 없는 독립 작업만 병렬로 배정한다.

## 3. 구현 순서와 완료 통지

### 검색 동작·계약 — Sol high

1. 명세의 공백 집합·ASCII 변환·literal 비교·길이 검증을 공용 함수와 SQL 식으로 구현한다. Python·SQL·TypeScript가 같은 입력/기대 결과 사례를 소비하도록 검사 데이터를 맞춘다.
2. 서버 검색을 기존 조건·소유 링크·집계·페이지 분할에 연결한다. 사업 추적의 raw `min_length/max_length` 선행 검사가 검증용 값의 길이 계약을 막지 않도록 조정한다. DB 열·인덱스·migration은 추가하지 않는다.
3. `WorkspaceSearch`에서 이벤트를 받는 keydown으로 IME Enter를 제외하고, `onChange('', null)` 지우기와 키보드 삭제를 구분한다. Astryx 패키지를 수정하지 않는다.
4. 네 페이지에서 draft/applied 상태와 URL 동기화, 검색 해제, invalid 입력, 미저장 입력 guard를 연결한다. 동등한 비교용 값이면 선택·페이지와 조회 캐시를 유지한다. 실제 조건 변경일 때만 기존 초기화 경로를 사용한다.
5. 0건 결과의 `검색어만 지우기`를 같은 해제 경로에 연결하고 검사 코드를 작성한다. 제품 검사는 관리자에게 맡기고 완료 보고를 보낸다.

### 배치·안내·화면 검사 — Luna max

1. Sol의 완료 결과와 명세를 읽고, Astryx build/layout/component 안내를 확인한 뒤 기존 컴포넌트로 배치한다. 레이아웃은 프로젝트 소유이고 색·간격·글자는 프로젝트 토큰을 따른다.
2. 기본 도구는 탭 아래 왼쪽에 모으고, 사전규격 추가 조건만 필요하면 다음 줄로 보낸다. 상세 필터·조치 사유·범위 안내 위치와 DOM/키보드 순서는 명세를 따른다.
3. `Enter로 검색 · 띄어쓰기 무시`, `Enter로 적용`, 길이 오류와 0건 안내를 표시하고 입력의 접근성 속성을 연결한다. 화면에 없는 기능은 새로 만들지 않는다.
4. 실제 API 계약을 반영한 mock과 의미·구조 검사를 작성하고 완료 보고를 보낸다. 검사 실행·캡처 검수는 관리자가 맡는다.

### 완료 통지 방식

- 관리자는 Orca Run과 Task를 만들고 지정 모델/effort의 worker에 파일 소유 범위·완료 기준을 전달한다. 같은 worktree에서 작업하며 불필요한 별도 worktree를 만들지 않는다.
- 작업자는 완료 시 주입된 task/dispatch ID로 `worker_done`을 **한 번** 보낸다. 성공/실패를 명시하고 변경 파일·변경 내용·작성한 검사·실행 여부/skip·차단/잔여를 보고한 뒤 종료한다.
- 관리자는 `check --wait --types worker_done,escalation,question`으로 완료 이벤트를 기다린다. 명령은 비동기로 대기시켜 사용자 응답을 막지 않는다. task-list·terminal read·파일 변경 여부를 짧은 주기로 반복 조회하지 않는다.
- timeout은 실패가 아니다. 완료를 기다리며 같은 작업을 중복 실행하지 않는다. 질문·차단 통지가 오거나 실행 장애가 확인된 경우에만 필요한 범위를 확인한다.
- 완료 보고를 받으면 해당 산출물을 검토하고 다음 의존 작업을 배정한다. 같은 검토 회차의 수정 사항은 한 번에 모아 담당자에게 전달한다. 의례적인 추가 승인·상태 보고 단계를 만들지 않는다.
- 완료된 worker는 관리자가 `worker-release`로 정리한다. 즉시 같은 worker에 후속 Task를 맡기면 소유권을 새 Dispatch로 넘긴다. 작업자가 스스로 다른 작업을 시작하거나 터미널을 닫지 않는다.

## 4. 검증 계획과 종료 기준

**검사 코드는 작업자가 작성하고 실행자는 관리자 한 명이다.** 문서 작성 뒤 제품 구현·검증을 진행했다.
제품 구현 뒤 최초 실행 범위를 아래처럼 묶고, 수정 후에는 실패·변경과 직접 연결된 검사만 재실행한다.

| 요구사항 | 대표 입력·기대 결과 | 검사 위치·범위 |
|---|---|---|
| 공통 비교 규칙 | `사이버 수사`는 예시 제목과 일치, `사이버 고도화`는 불일치. 모든 지정 공백·BOM·ASCII case·literal 기호·null·필드 경계 포함 | 공용 helper 검사 및 관련 API 사례; JS도 같은 입력/기대 결과 사용 |
| 길이·오류 | `  A  B  `는 검증 길이 3, 1자·101자는 거부, 공백만 있으면 해제. Unicode 코드포인트 경계 포함 | 사업 추적 API/UI; raw 길이와 비교용 길이를 혼동하는 회귀 검사 |
| 서버 범위·건수 | 현재 페이지 밖 일치 행도 검색 후 total·집계·첫 페이지에 반영, 비소유 후보는 제외 | 사전규격·사업 추적·기존 발주계획 API의 직접 `q` 경로 |
| 적용·선택 | 입력만으로 미적용, Enter 적용, IME Enter 무시, 지우기 즉시 해제, 키보드 삭제는 draft만 변경 | 네 페이지·공용 검색 컴포넌트 Playwright |
| URL·미저장 보호 | raw 공백 보존, 뒤로 가기, invalid URL 안내, 동등 query는 page/선택 유지, 변경 query와 clear의 guard 승인/취소 | 네 페이지와 기존 선택·상세 검토 흐름의 영향 사례 |
| 0건·범위 안내 | 적용된 검색어 기준 0건, 검색어만 지우기, Go/No-Go 받은 범위 제한 표시 | 네 페이지 빈 상태 사례 |
| 배치·접근성 | 기본 도구 순서·왼쪽 정렬·추가 조건 줄바꿈, 필터 펼침과 키보드 이동, 잘림 없음 | 1280×800·1440×900의 관련 구조 검사와 완성 화면 캡처 |

실행 범위:

- Backend: 일회용 `postgres:17.11`과 `BIDOPS_TEST_POSTGRES_URL`로 새 helper 검사, `tests/app/test_api_pre_specs.py`, `test_api_pre_specs_workspaces.py`, `test_api_opportunities.py`의 영향 사례 및 `test_order_plan_screening_api.py`의 목록 `q` 사례를 실행한다. 같은 새 검색 사례는 SQLite 변형도 확인한다. 운영 DB나 모델 호출을 사용하지 않는다.
- Frontend: `web/frontend`에서 `npm run build`를 실행한다. 의미 검사는 `npx playwright test --project=app`에 `order-plans.spec.ts`, `pre-specs.spec.ts`, `opportunities.spec.ts`, `go-no-go.spec.ts`와 공용 검색·선택의 영향 사례를 지정한다.
- 구조 검사는 `--project=layout-laptop --project=layout-desktop`에 `overflow.spec.ts`, `design-shell.spec.ts`의 네 화면 관련 사례만 지정한다. 구현자가 새 검색 전용 사례에는 `[search-ux]` 이름을 붙여 선택 실행할 수 있게 한다. 캡처는 완성 데이터를 기다린 뒤 저장하고 관리자가 직접 확인한다.
- 무관한 전 화면·전체 backend 스위트나 `web/run-web-tests.sh` 전체를 관성적으로 실행하지 않는다. 픽셀 baseline 갱신·전체 이미지 재빌드·동일 빌드 반복은 이 작업의 검증 조건이 아니다.

관련 검사가 통과하고 명세와 결과가 일치하면 검증을 종료한다. 새 코드 변경·실패·구체적인 미해결 위험이 없으면 반복하지 않는다.
실행 명령, pass/fail/skip, 환경 전제와 증거 위치는 기존 `docs/tracking/status.md`에 짧게 남긴다.

운영 재배포는 별도 사용자 요청과 실행 직전 확인을 받은 뒤 기존 백업·배포 절차로 진행한다.
이번 변경에 DB migration은 필요하지 않다. 배포 후에는 health·목록 조회와 대표 검색을 확인하되,
운영 데이터를 임의로 변경하거나 실제 모델 호출을 검증 수단으로 사용하지 않는다.
