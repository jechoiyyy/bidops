## 팔레트 — 흰 바탕·`#75A03B` 포인트·`--bo-*` 프로젝트 토큰

- 결정: 무드보드 파생 팔레트(짙은 남색 사이드바 `#161B2F`, 회색 canvas `#F2F0EF`,
  slate accent `#5B687C`)를 버리고, 옅은 회녹 canvas `#F6F7F4` + 흰 카드 + 회사
  포인트 `#75A03B` 하나로 통일한다. `#75A03B`는 흰 카드 위 3.07:1이라 글자·흰
  글자 채움에는 쓰지 않고, 단추 채움·링크는 한 단계 진한 `#587A2B`
  (`--color-accent`), 강조 글자는 `#3F5A1C`(`--color-text-accent`)를 쓴다.
  `#75A03B`는 Astryx `TokenName`이 닫힌 union이라 테마에 못 넣고 `--bo-brand`
  프로젝트 토큰(`brand.css`)으로 둔다.
- 대안: (a) `#75A03B`를 `--color-accent` 자체로 테마에 넣어 흰 글자 채움에 그대로
  쓴다. (b) 기존 무드보드 팔레트를 유지하고 accent 색상만 초록으로 바꾼다.
- 버린 이유: (a)는 3.07:1로 대비 게이트(글자 4.5:1)에 못 미쳐 단추 글자가
  읽히지 않는다. (b)는 사용자가 요청한 "흰 바탕 기본" 결과를 만들지 못한다.
  근거: `intent.md` §문제·§제안하는 결과, `spec.md` §1.1·§1.2.

## 성공색을 포인트 계열로 옮김

- 결정: `--color-success`/`-muted`를 `#007004`/`#C5E5C0`에서 `#3F5A1C`/`#F1F6E8`로
  옮겨 포인트 초록 계열에 합류시킨다. 경고·실패·정보 의미색은 그대로 둬 포인트와
  경쟁하지 않게 한다. 종전 "의미색은 무드보드가 정하지 않는다" 규칙은 이 팔레트에서
  "성공만 포인트 계열, 나머지는 별도 hue"로 바뀐다.
- 대안: success 색도 독립 hue(기존 `#007004` 유지)로 남겨 팔레트와 분리한다.
- 버린 이유: 포인트가 초록 하나뿐인 팔레트에서 success가 다른 초록을 쓰면 두
  초록이 나란히 나와 등급 ramp·완료 표시와 구분이 어려워진다.
  근거: `intent.md` 결정 1, `spec.md` §1.1(`--color-success` 행).

## 등급 ramp 초록 4단

- 결정: 적합성 등급 1~4단을 짙은 순서의 초록 ramp(`#3F5A1C` → `#587A2B` →
  `#CFDFB5` → `#EEF0EC`)로 통일한다. 2단(검토 권장) 배경이 주 단추 채움
  (`#587A2B`)과 같은 값인 것을 허용한다.
- 대안: 등급마다 서로 다른 hue(예: 신호등 계열)를 써서 단추 색과 절대 겹치지
  않게 한다.
- 버린 이유: 등급은 항상 글자를 동반해 채움색이 겹쳐도 뜻이 섞이지 않는다.
  서로 다른 hue를 쓰면 포인트 팔레트와 별개인 색 체계가 하나 더 생긴다.
  근거: `intent.md` 결정 2, `spec.md` §1.3.

## 사전규격 누적 탐색 (2026-09-16)

## 사전규격 목록 우측 영역 구성

- 결정: 탭 세 개짜리 구조를 없애고 머리 → 사업 설명 → 주요 과업 요약 → 예산·
  일정 4칸 → 일정·규모 → 주의사항 → 바닥 고정(추적 조작 + 상세 진입)
  7단으로 재구성한다. 본문 문장은 말줄임 없이 줄바꿈하고, 1280×800에서
  넘치면 본문만 스크롤하며 머리와 바닥 조작은 고정한다.
- 대안: 기존 탭 구조를 유지하고 탭 전환만 쉽게 만든다(탭 수를 줄이거나 단축키를
  더한다).
- 버린 이유: 탭 구조는 담당자가 추적 여부를 판단하려면 여전히 탭을 오가야 해,
  intent가 지적한 "정보가 탭에 흩어져 위에서 아래로 읽히지 않는다"는 문제를
  해결하지 못한다.
  근거: `intent.md` §문제·§제안하는 결과, `spec.md` §3.1~§3.3.
  참고: `mockups/shots/Main.png`(사이드바가 흰색·좌측 바가 있는 구성)는 옛
  캔버스 판이다 — 구현 정본은 §2.1과 `mockups/artboards/Main.dc.html`이다.

## 상세 세로 보고서형 6단

- 결정: 2열(읽기 열 + 400px 판단 열) 레이아웃을 버리고 단일 열 6단(① 머리 → ②
  추적 결정 → ③ 주요 과업 → ④ 참여 조건·회사 적합성·위험 및 미확인 → ⑤ 근거·

- 버린 이유: 2열은 사업 요약과 추적 결정, 근거와 위험이 좌우로 흩어져 intent가
  지적한 "위에서 아래로 읽히지 않는다"는 문제를 그대로 남긴다.
  근거: `intent.md` §문제·§제안하는 결과, `spec.md` §4.

## 레이아웃 소유권·지원 폭 1280~1920·native compact 밀도 유지

- 결정: 기존 사이드바·상단바의 90% 물리 크기·목록 38% 분할을 native CSS 치수로 유지하고
  전역 `zoom`은 제거한다. 지원 폭 1280~1920px는 이번 재설계에서 바꾸지 않는다.
  레이아웃은 프로젝트가 소유하고
  Astryx 컴포넌트는 그 안에 놓이며, 새 반응형 분기를 만들지 않는다.
- 대안: 시안 프레임(1422×889 = 1280×800 창)에 맞춰 지원 폭을 좁히거나 사이드바
  폭을 조정한다.
- 버린 이유: 데스크톱·노트북 전용이라는 기존 제약과 검증 viewport(1280×800·
  1440×900)를 다시 정의할 이유가 없다. 레이아웃 자체를 바꾸는 것은 이번 재설계
  (팔레트 + 두 화면 재구성)의 범위 밖이다.
  근거: `intent.md` §제약, `plan.md` 시작 전 확인.

## 대화상자 제거 — 인라인 폼과 미저장 보호 경로

- 결정: `추적 선택 변경` 대화상자를 없애고 `TrackingDecisionControl`에
  `presentation="inline"` 변형을 더해 목록 우측 영역 바닥 고정 블록에 인라인
  폼으로 둔다. 미저장 보호는 폼이 `onDirtyChange`로 목록에 알리고, 행 전환·필터
  변경·상세 이동 guard는 기존 `trackingGuard` 경로를 그대로 쓴다.
- 대안: 대화상자를 유지하되 여는 자리만 바닥 고정 블록 쪽으로 옮긴다.
- 버린 이유: intent가 지적한 "추적 조작이 대화상자 뒤에 숨어 있다"는 문제
  자체가 대화상자의 존재에서 나온다. 대화상자를 유지하면 한 화면에서 조작을
  끝낸다는 제안 결과를 만족하지 못한다.
  근거: `intent.md` §문제·§제안하는 결과, `spec.md` §3.3, `plan.md` §위험(대화상자
  제거로 미저장 보호 경로가 바뀌는 것).

- 시안과 달라진 곳: 발주 예정은 `2026.11`이 아니라 기존 `plannedTiming` 출력(`2026년 11월`,
