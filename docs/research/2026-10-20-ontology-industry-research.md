# 현업 온톨로지의 목적·구축·활용 리서치

조사일: 2026-10-20  
관련 문서: [BidOps 구현 비교분석](2026-10-20-bidops-ontology-assessment.md)

읽기용: [도식과 전체 본문을 담은 HTML 보고서](2026-10-20-ontology-report.html)

이 문서는 공개된 운영 서비스, 개발기관의 기술 문서, 구현 당사자의 논문, W3C 표준을 조사한 결과다. 사례의 확인 가능한 사실과 BidOps를 위한 해석·권고를 구분한다. 제품 소개를 독립적인 성능 검증으로 취급하지 않으며, 공개 자료에 없는 구축 비용·ROI·정확도는 추정하지 않는다.

## 1. 핵심 발견

온톨로지가 현업에서 하는 일은 **업무의 대상·관계·용어를 명확하게 정의해 여러 출처의 정보를 같은 의미로 연결하는 것**이다. 실제 제품에서는 그 위에 근거 조회, 검증, 판정 규칙, 사람의 조치가 붙는다. 조사한 사례의 공통점을 종합하면, 성패를 가르는 것은 그래프의 크기보다 다음 세 가지다.

1. 실무자가 반복해서 묻는 질문에 답할 수 있는가.
2. 서로 다른 자료의 동일 대상과 서로 다른 의미를 정확하게 구분하는가.
3. 근거와 적용 조건을 보존하면서 결과를 업무에 연결하는가.

이는 여러 출처를 종합한 분석이다. 모든 조직이 같은 기술이나 구축 순서를 사용한다는 뜻은 아니다.

BidOps와 가장 직접적으로 비교할 사례는 EU의 eProcurement Ontology와 TED다. 업무 실행까지의 연결은 Palantir, 데이터 연결의 점진적 확장은 Siemens, 의미·릴리스 관리는 FIBO, 근거 전파의 제한은 Open Targets가 각각 유용한 참고점이다.

## 2. 혼동하기 쉬운 개념

| 개념 | 담당하는 일 | BidOps식 예 |
|---|---|---|
| 통제 어휘·분류체계 | 표준 명칭, 별칭, 분류 관계 | `상주 운영`, 별칭, 상·하위 분야 |
| 온톨로지 | 대상의 종류와 관계 및 의미를 정의 | 조직이 자격을 보유하고, 요구사항이 특정 자격을 요구함 |
| 지식그래프 | 구체적인 대상과 사실을 연결 | 회사 A가 자격 Q를 특정 기간에 보유 |
| 제약 검증 | 데이터가 정해진 구조·조건을 만족하는지 검사 | 자격 만료일 형식, 관계 양 끝의 타입 |
| 업무 판정 규칙 | 사실을 특정 업무 조건에 대조 | 입찰 기준일에 자격이 유효한지 검사 |
| 검색·RAG | 답변에 필요한 근거를 찾고 전달 | 요구사항과 관련된 수행 실적 원문 검색 |
| 업무 액션 | 결과를 사람의 후속 업무에 연결 | 확인 요청, 추적 결정, 재검토 요청 |

SKOS는 표준 명칭·별칭·개념 간 관계를 다루는 모델이고, OWL은 클래스·속성·개체에 대한 논리적 의미를 표현한다. SHACL은 RDF 데이터에 대한 제약 검증과 검증 결과를 다룬다. 서로 연결할 수 있지만 역할이 같지는 않다. [SKOS Reference](https://www.w3.org/TR/skos-reference/), [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/), [SHACL](https://www.w3.org/TR/shacl/)

또한 온톨로지를 쓰기 위해 반드시 모든 데이터를 그래프 DB로 옮겨야 하는 것은 아니다. OWL 설명서도 데이터베이스가 온톨로지 기반 시스템의 저장 기반이 될 수 있음을 설명한다. 저장 기술과 의미 모델은 별도로 결정해야 한다. [OWL 2 Primer §2](https://www.w3.org/TR/owl2-primer/#What_is_OWL_2.3F)

| EU ePO / TED | 조달 정보의 일관된 해석과 재사용 | 공통 개념, 전문가 합의, 버전별 모델, 공개 지식그래프 질의 | 운영 서비스와 공식 기술 문서 |

### 3.1 EU eProcurement Ontology와 TED: 조달 생애주기의 공통 의미

**확인한 사실.** ePO는 조달 생애주기 각 부분에서 쓰는 개념을 정의한다. 조달 업무를 실행하는 프로세스 엔진 자체는 아니다. 공식 범위는 공고·입찰·낙찰·주문·송장·지급에 걸친다. EU Publications Office는 전문가 Working Group을 통해 분석과 모델에 대한 합의를 만든다. 문서는 개념 모델, 용어집, 변경 이력, 방법론, 사용자 이야기, 버전 규칙을 구분해 제공한다. [ePO 공식 소개](https://docs.ted.europa.eu/epo-home/index.html)

**실제 활용.** TED Open Data Service는 조달 공고를 지식그래프로 제공한다. 이용자는 개별 공고의 그래프를 살펴보고, 질의 라이브러리나 직접 작성한 질의로 자료를 조회·재사용할 수 있다. 따라서 모델 문서만 있는 사례가 아니라 공개 데이터 소비 경로까지 확인할 수 있다. [TED Open Data Service](https://data.ted.europa.eu/)

**BidOps 해석.** 발주계획·사전규격·공고·정정은 같은 사업과 관계를 맺지만 같은 객체는 아니다. 요구사항, 자격, 수행 장소, 발주기관, 공고 버전도 구분해야 한다. 다만 EU 조달 규칙을 한국 조달의 법적 판단 기준으로 그대로 가져올 수는 없다. 재사용 대상은 개념의 분리 방식과 식별·버전 관리 방식이며, 실제 대응 관계는 나라장터 원본과 국내 업무 정의에 맞춰 검토해야 한다.

### 3.2 Palantir: 의미 모델을 업무 조치에 연결

**확인한 사실.** Foundry의 Ontology는 데이터셋·모델을 실제 업무 객체와 연결하는 운영 계층으로 설명된다. 객체·속성·링크 외에 Action types와 Functions를 제공한다. 객체 조회와 분석뿐 아니라 사용자 입력, 의사결정 절차, 기존 시스템과의 연결을 같은 모델 주변에서 다룬다. [Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview)

별도 플랫폼 설명은 의사결정을 데이터·로직·액션으로 나누고, 액션 권한과 결과의 재수집을 설명한다. 이 문서에서 확인되는 것은 제품의 구성 방식이다. 모든 고객이 같은 기능을 사용하거나 같은 효과를 얻었다는 근거는 아니다. [Platform overview](https://www.palantir.com/docs/foundry/platform-overview/overview/index.html)

**BidOps 해석.** 온톨로지의 최종 소비자는 그래프 시각화 화면만이 아니다. “어떤 증빙을 확인하면 판단이 바뀌는가”, “회사 기준이 바뀌었을 때 어떤 공고를 재검토해야 하는가”가 더 직접적인 소비 경로다. 다만 추적 승인과 Go/No-Go는 사람이 결정한다는 현재 경계를 유지해야 한다.

### 3.3 Siemens: 작은 도메인 모델에서 출발해 데이터 간 연결을 확장

**확인한 사실.** Siemens와 metaphacts의 2018년 논문은 단일 데이터 사일로에 도메인 모델을 붙이고, 모델 간 연결을 늘린 뒤 통합 데이터 공간으로 확장하는 접근을 제시한다. 물리적 데이터 통합과 가상화·연합 조회를 모두 구성 요소로 둔다. 건물 디지털 트윈, 이해관계자 위험 관리, 공정 감시, 기계 유지보수를 사례로 설명한다. [Use Cases of the Industrial Knowledge Graph at Siemens](https://ceur-ws.org/Vol-2180/paper-86.pdf)

**적용 한계.** 짧은 당사자 사례 논문이다. 현재 전체 Siemens 시스템의 상태나 비용 절감 수치를 입증하지 않는다.

**BidOps 해석.** 회사 근거와 요구사항 대조를 먼저 완성한 뒤 사업기회·실적·수주 결과로 확장하는 방식이 적절하다. 모든 기존 관계형 테이블을 즉시 그래프로 복제할 이유는 없다. 기존 정본을 유지하고, 질문에 필요한 관계를 검증 가능한 참조나 파생 뷰로 연결할 수 있다.

### 3.4 FIBO: 의미를 소프트웨어처럼 검토·발행

**확인한 사실.** FIBO는 금융 업무의 대상과 관계를 OWL로 정의한다. 개별 데이터베이스·스프레드시트 등에서 쓰는 금융 정보에 공통 의미를 부여하는 것이 목적이다. [FIBO 소개](https://spec.edmcouncil.org/fibo/index.html)

개발 과정에서는 Git 기반 변경 검토, 자동 산출물 생성·시험, Development와 Production 발행 수준을 구분한다. 소스의 성숙도도 별도로 관리하며, 사용자가 받을 산출물을 검사하는 것을 강조한다. 참조가 모두 유효하다는 정도의 검증과 충분한 의미 검토를 통과한 상태를 구분한다. [FIBO Development Process](https://spec.edmcouncil.org/fibo/page/development-process)

**BidOps 해석.** JSON 파싱·해시 검사가 통과한 온톨로지와 실제 차단 조건을 찾을 수 있는 온톨로지를 구분해야 한다. “등록 가능”, “실험 가능”, “업무 적용 가능”의 승격 근거를 분리하고, 개념 변경이 기존 판정에 미치는 영향을 확인해야 한다.

### 3.5 Open Targets: 근거를 연결하되 전파 범위를 통제

**확인한 사실.** Open Targets는 특정 표적과 질병에 직접 연결된 증거와, 질병 온톨로지의 하위 개념에서 가져온 간접 증거를 구분한다. 직접·간접 관계는 API와 다운로드로도 조회할 수 있다. RNA expression 증거는 상위 질병에 약한 관계가 과도하게 쌓이는 것을 피하기 위해 같은 방식으로 전파하지 않는다고 설명한다. [Target–disease associations](https://platform-docs.opentargets.org/associations)

**BidOps 해석.** “같은 분야의 실적”은 후보 근거가 될 수 있지만 곧바로 “해당 필수 요구사항 충족”이 되어서는 안 된다. 수행한 역할·금액·기간·사용 기술·증명 가능성이 요구사항과 맞는지 별도 검사해야 한다. 관계마다 어떤 결론까지 전파할 수 있는지 정의하는 것이 핵심이다.

## 4. 어떻게 구축하는가

아래는 사례와 방법론을 종합해 정리한 권장 절차다. 모든 현업 조직의 공통 표준 절차라고 주장하지 않는다.

### 4.1 답해야 하는 질문을 먼저 고정한다

Ontology Development 101은 범위를 정할 때 지식 기반이 답해야 할 질문인 competency question을 작성하고, 이후 충분한 표현력을 갖췄는지 확인하는 기준으로 쓰도록 설명한다. [Noy·McGuinness, Ontology Development 101, pp. 4–5](https://protege.stanford.edu/publications/ontology_development/ontology101.pdf)

BidOps에서는 다음과 같이 답·근거·답을 유보할 조건까지 쓴 질문이 유용하다.

| 질문 | 필요한 구분 | 답을 유보해야 할 조건 |
|---|---|---|
| 특정 지역의 상주 요구를 수행할 수 있는가? | 수행 장소, 인원, 역할, 기간, 현재 가용성 | 지역의 의미나 투입 가능 기간 미확인 |
| 자격을 제출할 수 있는가? | 보유 여부, 세부 품목, 유효기간, 제출 기준일 | 증명서 세부 또는 기준일 미확인 |
| 유사 실적이 요구조건을 충족하는가? | 사업명과 실제 담당 범위, 계약금액과 인정금액 | 담당 범위·인정 조건 미확인 |
| 회사 제외 정책에 걸리는가? | 요구사항, 회사 정책, 예외 승인 | 단순 언급인지 실제 과업인지 불명확 |
| 기준 변경으로 어떤 판단이 달라지는가? | 과거 입력 버전, 변경 사실, 사용 규칙 | 판정의 의존 사실을 추적할 수 없음 |

### 4.2 어휘·업무 대상·사실·판정을 분리한다

용어 목록은 표현 차이를 줄이고, 업무 대상 모델은 관계의 의미를 정한다. 실제 회사 사실은 개별 근거와 시점을 가진다. 최종 판정은 사실과 규칙을 적용한 별도 산출물이다.

예를 들어 “회사가 보유한 인증”과 “사업 종료 때 받아야 할 산출물 인증”을 같은 `보유 여부`로 대조하면 오류가 생긴다. “하고 싶다”, “해 본 적이 있다”, “지금 수행할 수 있다”, “참가 자격이 있다”도 다른 주장이다. 이는 BidOps를 위한 모델링 권고다.

### 4.3 원천 데이터와의 매핑을 관리한다

개념을 정의한 것만으로 실제 자료가 연결되지는 않는다. 원천의 식별자·열·문장·표 셀이 어느 객체·속성·관계가 되는지 매핑이 필요하다. 기관명 변경, 동일 이름의 다른 기관, 공동수급에서의 역할처럼 동일성 판단이 필요한 경우에는 자동 확정 조건과 사람 확인 조건을 나눈다.

ePO는 사용자 이야기와 자연어 요구, 개념 모델과 기술 산출물을 구분하는 문서 체계를 제공한다. BidOps에서도 원천 표현을 바로 코드 조건으로 묻어두기보다, 그 표현을 어떤 업무 의미로 해석했는지 검토 가능하게 해야 한다. [ePO Methodology](https://docs.ted.europa.eu/epo-home/methodology2024.html)

### 4.4 근거·시점·검토 책임을 붙인다

PROV-O는 Entity·Activity·Agent와 파생·사용·생성 관계로 출처와 처리 과정을 표현하며, 관계에 역할과 시간 같은 부가 맥락을 붙일 수 있다. [PROV-O](https://www.w3.org/TR/prov-o/)

BidOps에 필요한 최소 적용은 다음과 같다. PROV-O 전체를 도입해야 한다는 뜻은 아니다.

- 어떤 원본의 어느 위치에서 얻었는지.
- 사람이 확인한 것인지, 원문 주장인지, 모델이 추론한 것인지.
- 언제 확인했고 언제까지 업무상 유효한지.
- 어떤 정규화·매핑·규칙 버전이 사용됐는지.
- 상충하는 근거가 있을 때 누가 어떤 기준으로 정리했는지.

파일 등록 시각과 자격의 유효기간은 다르다. 사업 실적을 확인한 시각과 그 실적이 발생한 시각도 다르다.

### 4.5 구조 검사와 업무 의미 검사를 함께 둔다

SHACL은 데이터 그래프를 제약에 대조하고 위반 위치와 원인을 담은 결과를 만든다. 이 구조 검증만으로 회사 역량의 실제 진실성이나 사업 참여 가능성이 입증되지는 않는다. [SHACL §3](https://www.w3.org/TR/shacl/#validation)

BidOps용 검사 묶음은 다음처럼 나눌 수 있다.

| 검사 | 예 |
|---|---|
| 구조 | 존재하지 않는 개념·관계, 잘못된 값 타입 |
| 원문 근거 | 인용 위치·내용·파일 해시 일치 |
| 의미 | 선호 조건이 보유 역량으로 쓰이지 않음 |
| 관계 도달성 | 필요한 사실을 검색·대조 경로가 실제로 찾음 |
| 업무 질문 | 상주 장소·기간·역할을 함께 해석함 |
| 회귀 | 새 별칭으로 무관한 요구까지 충족 처리하지 않음 |
| 결과 품질 | 차단 조건 재현율, 잘못된 충족, 기권 원인 |

### 4.6 운영 중 수정하고 새 버전으로 발행한다

ePO는 별도 버전 규칙을 제공하고, FIBO는 검토와 발행 성숙도를 구분한다. 이 두 사례에서 가져올 교훈은 **변경을 허용하되 과거 의미와 산출물을 재현할 수 있게 하는 것**이다. [ePO Versioning](https://docs.ted.europa.eu/epo-home/versioning.html), [FIBO Development Process](https://spec.edmcouncil.org/fibo/page/development-process)

권장 운영 순환은 `미매핑·오판 수집 → 의미 검토 → 원천·규칙 수정 → 영향 평가 → 새 버전 발행 → 기존 판정의 재검토 필요 표시`다. 수정 때마다 모든 공고를 재분석하기보다 영향받은 사실·규칙을 참조한 판정부터 골라야 한다.

## 5. LLM·GraphRAG와의 역할 분담

Microsoft GraphRAG는 텍스트에서 엔티티·관계·주장을 추출하고, 그래프의 커뮤니티 계층과 요약을 만들어 검색·질의에 활용한다. 이는 문서군을 연결해서 설명하는 데 쓰이는 접근이다. [GraphRAG 공식 문서](https://microsoft.github.io/graphrag/)

**분석:** 이 절차에서 생성된 관계는 업무 담당자가 승인한 사실이나 참가 자격 검증을 자동으로 대신하지 않는다. BidOps에는 다음과 같은 분담이 적절하다.

| 역할 | 권장 담당 |
|---|---|
| 원문에서 요구·조건·근거 후보 추출 | LLM + 원문 위치 검증 |
| 별칭·코드·행정구역 등 정규화 | 버전 관리되는 사전·매핑 |
| 새 개념·관계 후보 제안 | LLM 또는 담당자, 승인 전 미확정 |
| 확인된 수량·기간·조건 대조 | 결정적 규칙 |
| 관련 실적·근거 탐색 | 관계 탐색 + 필요할 때 의미 검색 |
| 설명·확인 질문·초안 작성 | 검증된 입력 범위의 LLM |
| 역량 확인·정책 예외·최종 Go/No-Go | 사람 |

LLM을 없애거나 모든 판단을 LLM에 맡기는 선택보다, 각 단계가 무엇을 보증하는지 분리하는 편이 중요하다.

## 6. 기술 선택에 대한 권고

다음은 본 조사와 BidOps의 현재 규모를 바탕으로 한 권고이며 벤치마크 결과는 아니다.

| 선택 | 적합한 상황 | BidOps의 현재 판단 |
|---|---|---|
| PostgreSQL + 명시적 의미 모델 + Python 규칙 | 관리할 데이터와 질의가 제한되고 감사·거래 경계가 중요 | 현재 기반을 유지하는 것이 합리적 |
| SKOS를 참고한 어휘 모델 | 별칭·계층·관련 개념·외부 개념 대응을 관리 | 정의·범위·폐기·대체 정보부터 도입 가치 있음 |
| RDF / OWL / SHACL | 외부 온톨로지 교환, 복합 논리 추론, 표준 검증이 실제 요구 | 필요한 부분의 수출·검증부터 검토 |
| 별도 그래프 DB | 다단계 탐색의 성능·질의 유지보수 비용이 실측 병목 | 병목과 운영 비용을 확인한 뒤 별도 결정 |
| GraphRAG | 많은 문서 간 연결·주제 요약·탐색이 핵심 질문 | 유사 실적 탐색의 후속 후보; 자격 판정 대체 불가 |

모든 것을 하나의 거대한 온톨로지에 넣는 것도 피해야 한다. 조달 개념, 회사 사실, 회사 정책, 요구사항 해석, 판정 기록은 서로 연결하되 변경 주체와 주기가 다르다.

## 7. 구축 성과를 판단할 지표

아래 지표는 BidOps용 제안이며 업계 공통 임계값이 아니다.

- **질문 충족률:** 합의한 업무 질문 중 근거와 함께 답할 수 있는 비율.
- **표현·매핑 범위:** 요구조건 중 개념·술어·회사 사실까지 연결된 비율.
- **판정 가능 범위:** 필요한 사실과 규칙이 있는 조건 중 실제 결론을 낸 비율.
- **차단 조건 재현율과 오차단율:** 놓치는 위험과 불필요하게 버리는 기회를 함께 측정.
- **잘못된 충족:** 미확인·만료·다른 범위의 근거를 충족으로 사용한 건수.
- **기권 원인:** 회사 정보 부족, 원문 모호성, 개념 없음, 규칙 없음, 추출 실패를 분리.
- **근거 최신성:** 유효기간 초과·갱신 필요·상충 상태의 사실 수.
- **업무 효과:** 판단까지 걸리는 시간, 다시 읽는 원문 수, 확인 요청의 해결률.

노드·간선 개수, 파싱 성공률, 모델 실행 완료율만으로 이 지표들을 대신할 수 없다.

## 8. 조사 범위와 남은 한계

공공 조달·기업 운영·제조·금융 표준·생명과학의 서로 다른 목적을 비교했다. 실제 공개 서비스인 TED와 Open Targets, 제품 문서인 Palantir, 당사자 사례 논문인 Siemens, 표준 개발 과정인 FIBO는 증거의 성격이 다르다.

이번 조사는 고객 인터뷰나 유료 제품 실사용 실험을 포함하지 않는다. 한국 조달의 법적 자격 기준을 검증한 문서도 아니다. 외부 사례의 효과 수치를 BidOps에 전이하지 않았으며, 프로젝트에 대한 구체적 평가는 [별도 비교분석](2026-10-20-bidops-ontology-assessment.md)에 코드·데이터·평가 기록 근거와 함께 남겼다.
