# 사업기회 레코드·활동 타임라인·상태 변화 알림 — intent

- 기능 ID: `RL-02-opportunity-timeline`
- 상위 항목: roadmap §RL 표 3행, ADR-0073 결정 4("세 단계 화면을 사업기회 타임라인 하나와 상태 변화 알림으로"), [ui-spec §1.1·§1.3·§3·§4.3](../../../../../1016_rootlab-redefinition/ui-spec.md)
- 크기: L — 레코드 페이지 셸(탭 6개)·활동 피드 REST·노트/다음 행동 테이블·단계 바·마감 D-3/D-1 알림(RL-01 규칙 파일 v2). 모델 호출 없음.
- 작성일: 2026-10-16

## 문제

한 사업이 발주계획→사전규격→입찰공고→정정→마감으로 흘러도 실무자는 발주계획·사전규격·사업 추적 세 화면을 오가며 "지금 어디까지 왔는지"를 머릿속에서 합쳐야 한다. 사람 행동(추적 결정·반응·메모)과 사업 사건(공개·게시·정정·판정)이 한 줄에 없고, 정정·마감 임박은 목록을 열어야 보인다.

## 기대 결과

- `/opportunities/:id/activity`가 사업기회 레코드의 기본 화면이다: 레코드 헤더(단계·마감 D-n·판정·추적 상태 pill, 액션), 좌측 속성 8개 + 다음 행동, 중앙 단계 바(6단계) → 작성기 → 활동 목록. 탭 활동·판정·제안서·서류·원문·비슷한 공고 중 판정·제안서·서류는 RL-03·04 전까지 빈 상태 1줄.
- 활동 피드는 사람 행동(추적 결정·브리핑 반응·노트·다음 행동 완료)과 사업 사건(발주계획 발견·사전규격 공개·공고 게시·정정·마감 변경)을 하나의 시간순 목록으로 보여 준다. 시스템 처리 세부는 넣지 않는다.
- 추적 중(`계속 추적`·`보류`) 사업의 정정과 마감 D-3·D-1은 RL-01 추적 변화 묶음·Slack 메시지로 알린다(상태 변화 때만).

## 유즈케이스

| 유즈케이스 | 실행 방법 | 확인 기준 |
|---|---|---|
| 레코드 열기 | 브리핑 행 Enter 또는 `/opportunities/501` | `/opportunities/501/activity`로 리다이렉트, 헤더 pill 4개(없는 값은 "미공개"), 단계 바에 연결된 단계만 ✓ |
| 활동 피드 | `GET /api/opportunities/501/activity` | 항목이 시간 내림차순, 종류별 enum·사람 이름·링크, 시스템 세부(변환·호출·정책) 없음 |
| 노트·다음 행동 | 작성기에 입력 → "노트" 또는 "다음 행동" | `POST …/notes` 201, 피드 맨 위에 즉시, 다음 행동은 좌측 체크 목록에도; 체크 → `PATCH …/notes/{id}/done` → 피드에 "완료" 항목 |
| 추적 결정 변경 | 헤더 ⋯ → 추적 상태 변경(기존 대화상자) | 기존 `PATCH tracking-status`, 피드에 결정 항목, pill 갱신 |
| 정정 알림 | 추적 중 사업의 공고 마감이 바뀐 관측이 들어온 다음 브리핑 | RL-01 `tracked_change` 1행 + Slack 1건, 피드에 "정정" 사건 |
| 마감 알림 | 추적 중 사업의 마감이 D-3 또는 D-1인 날의 브리핑 | `tracked_change` 묶음에 `deadline_reminder` 행, 같은 날 두 번 보내지 않음 |
| 빈 탭 | 판정·제안서·서류 탭 | 빈 상태 문장 1줄, 운영 정보 없음 |

## 선행·후속 기능

- 선행: `RL-01-daily-briefing`(반응 이벤트가 피드에 들어가고, 알림은 RL-01의 Slack 전송기·추적 변화 묶음을 확장한다).
- 후속: `RL-03-fit-verdict`(판정 탭·헤더 판정 pill·"판정 완료" 사건), `RL-04-proposal-draft`(제안서 탭·"초안 준비" 사건).

## 영향 범위

- 모듈·컴포넌트: lifecycle(`services/opportunity_activity.py`·`opportunity_notes.py`, `routers/opportunities.py` 확장, 모델 `OpportunityNote`), RL-01 규칙 파일 v2(`deadline_reminder_days`)와 `briefing_rules.py`, 프런트 `pages/OpportunityRecordPage.tsx`(기존 `OpportunityDetailPage` 대체), `components/record/{RecordHeader,AttributeList,StageBar,ActivityItem,Composer}.tsx`, `routes.tsx`·`route-meta.ts`.
- 큰 틀 문서의 절: contracts.md "사업기회와 추적"(REST 추가), business-rules.md "입찰공고 전환"(단계 바 의미), ui-spec §4.3, ARCHITECTURE §5.1a.
- 데이터·저장소: 새 테이블 `opportunity_note`(권한 runtime-privileges.sql). 피드는 저장하지 않고 읽기 시점에 기존 이벤트에서 파생한다.
- 외부 서비스·호출: Slack(RL-01 전송기 재사용). 모델 호출 없음.

## 제약

- (공통) feature.json constraints 전부.
- (기능별) 피드에 운영 정보(변환·호출·정책·실행 시각 초 단위) 금지(ui-spec §4.3). 추적 결정은 기존 `set_tracking_status()` 경로만(새 자동 결정 없음). 개찰·계약 단계는 데이터가 없으면 "미확인"으로 두고 추정하지 않는다. 노트 본문은 모델에 전송하지 않는다(RL-03·04 입력 아님).

## 범위 밖

제출 서류 체크리스트(27종)와 "서류" 탭 내용(RL-04 뒤 후속), 판정·제안서 탭 내용(RL-03·04), 원문 탭의 자체 뷰어(기존 사전규격 상세 링크로 대체), 사업 합치기·입찰 delta·Go/No-Go 화면 연결(후속 범위 유지), 알림 채널 추가(DM·메일).
