## 구현 시작점

2026-11-20 기준 기능 ID는 `RL-11-live-prespec-engine`이다. 작업 트리의 main 기준 커밋은 `b839367`, 실행 큐 상태는 `review`(0/5)다. RL-09·10 코드는 main에 있지만 큐의 선행 충족 표시는 둘 다 `x`다. 착수 시 저장소 루트에서 `python3 scripts/feature_status.py queue _ show`와 `git status -sb`로 현재 상태를 확인한다. 이 기록 시점의 RL-11 문서·시안은 미커밋 작업 트리에 있으므로 새 checkout에서는 원본 작업 트리의 문서와 기존 변경을 먼저 확인한다.

**구현 목표**는 사전규격을 독립 발견하고 자동으로 준비한 뒤, 담당자가 승인한 입력만 분석해 원문을 대조하고 추적 결정을 남기는 것이다. 업무 규칙·상태 전이·API·인수 사례는 [최종 명세](spec.md), 회사 입력 기준은 [회사 입력 기준과 위키](company-wiki-mapping.md)(2026-11-22 개정), 화면 행동은 [상세 설계](detail-layout.md)가 정본이다.

| 구현하면서 지킬 결정 | 첫 검증에서 볼 결과 |
|---|---|
| 확정 연결의 C-2는 처리 순서에 반영한다. 계획 없음·모델 미판정도 독립 처리한다. 개요 실패 우회는 추적 중 또는 임박이며 안전한 필수 원문·근거가 완비된 경우에 허용한다. | 담당자는 대시보드에서 준비된 승인 건을 열 수 있고, 연결 후보는 귀속이나 분석에 영향이 있을 때만 보인다. |
| 미확인이 남아도 계속 추적할 수 있다. 회사 증빙·질의처럼 지금 할 일만 업무함에 올린다. | 자료 대기는 상세에 남고 관련 정정·본공고·증빙 도착 때 한 번 재노출된다. 읽음과 추적은 질문을 해결 처리하지 않는다. |
| 공고 답변·기간별 인력 가용성은 해당 조항에 저장한다. 회사 자격·경력은 증빙·범위·유효기간을 검토한 뒤 별도 등록한다. | 같은 인력의 자격 증빙을 두 공고에 재사용해도 두 번째 사업의 가용성은 미확인으로 남는다. |
| Luna에는 원본 회사 자료 묶음의 프로필 렌더링과 그 공고에 고른 위키 발췌를 보낸다(고객명·계약금액 포함, 데모값 사용). 2026-11-22 개정. | 미리보기에서 묶음 digest와 고른 위키 페이지를 확인하고 승인한다. 변경된 입력으로 보내는 호출 0회, 동일 입력 중복 실행 0건. |
| 첫 감독 시운전은 KST 하루 1개 공고, 공고 누적·일일 합계 각각 최대 8회다. | 첫 모델 전송 전에 추출·대조·종합 전체 예산을 계산한다. 성남시 장문 예시는 원본 분할 기준 12회여서 첫 호출 전에 보류한다. |
| 동일 입력으로 기존 RL 카드와 비교하고 사람이 채점한 뒤 운영 기본 표시를 결정한다. | 모의 응답과 로컬 개요 완료는 실행 경로의 증거로만 기록한다. 운영 기본 표시, 실제 모델 전송, 배포는 각각 별도 승인 대상이다. |

**첫 구현 사례.** STEP-001에서 동결한 회사 상주 기준을 STEP-002에서 아래 세 공고 조항에 대조한다. 같은 원문 위치와 회사 근거를 API 응답과 상세에서 따라갈 수 있게 한다. 외부 모델 없이 세 판단을 구분하는 것이 첫 검증이다.

| 원문 예시 | 기대 결과 |
|---|---|
| 수원 사업장 상주가 필수이며 예외가 없음 | 대구만 상주 가능한 확인 근거와 대조해 ‘회사 수행 제한과 충돌’을 표시한다. |
| 발주기관 지정 장소에서 근무 | 장소·상주 의무를 확인할 질문을 남긴다. 담당자가 미확인을 안고 계속 추적할 수 있다. |
| 월 1회 현장 방문 점검 | 방문 인력·비용 검토로 분류한다. 상주 제한에 따른 차단은 0건이다. |

격리 구현 뒤 실전 적용 시점에 확정할 항목은 호출당 토큰/시간 설정, 원응답 보존 기준과 시운전 대상이다(발췌 목록·실적 대응표는 만들지 않는다). 실제 결과를 기본 화면에 게시하는 결정에는 동일 표본 비교와 사람 인수가 필요하다.

## 구현 우선순위

가장 먼저 lifecycle 적재·연결 이벤트와 effective_grade, 업무함 목록/건수에 같은 자격·정렬 술어를 연결한다. 독립 수집, 영향 있는 후보, 준비 실패 복구·개요 우회를 [흐름 인수 시나리오](spec.md#흐름-인수-시나리오)의 앞 다섯 사례로 검증한다. 이 부분은 외부 전송 없이 인수할 수 있다. 이어 아래 순서로 회사·원문 → 승인·검증 게시 → 동일 입력 비교 → 담당자 화면 인수를 진행한다. 화면은 검증용 결과로 먼저 연결할 수 있고, 운영 기본 표시는 비교 인수 뒤에 연다.

## 작업 순서

1. STEP-001 위키 출처·사실·실적 대응 고정 [complex]
   - 같은 단계에서 발견·연결·준비 예외와 승인 후보 projection을 먼저 연결한다. 위 흐름 사례를 대역으로 재생하고 처리 대상·정렬·보류/재개·중복 행을 검사한다.
   - 회사 입력은 원본 회사 자료 묶음과 엔진의 공고별 위키 선택이다(2026-11-22 개정, 입력 v2 구현 완료). G7·G8은 RL 카드·RL-10 쪽 회사 근거 버전에 반영한다.
   - 남은 일: 미리보기에 묶음 digest와 고른 위키 페이지를 싣는다.
   - 검증 T1. 기존 바인딩 불변, 묶음 변경 시 새 입력, 깨진 묶음 거부.
2. STEP-002 원문 정규화·장문·차단 검증 [complex]
   - 문단·표의 분할/재조립, 2자리·다중 요구 ID 회귀, 원문 인용과 결정적 상주·하드웨어 규칙을 구현한다.
   - G8의 독립 필수성 확인과 혼합 업무 보류를 고정한 뒤 새 조건을 활성 회사 근거에 연결한다.
   - 검증 T4·T5. 장문과 표 fixture, 이전에 놓친 차단 7건의 로컬 회귀, 하드웨어 과잉 차단 사례.
3. STEP-003 승인·감사·Luna 연결 [complex]
   - REST·DB 닫힌 계약과 데이터 보존 기간을 확정한 뒤 미리보기/동결/건별 승인/audit 및 런타임 실행을 구현한다.
   - C-2 우선 순위와 공용 슬롯, stage lease·취소 및 동결 입력 재확인을 검증한다.
   - 검증 T2·T3. 합성 전송기로 호출 0과 audit/lease failure, PostgreSQL 역할과 API guard. 실제 전송 전에 별도 승인을 받는다.
4. STEP-004 실제 공고 비교와 표시 경로 결정 [complex]
   - 같은 공고·회사 근거의 RL 카드와 엔진을 정답셋부터 동결하고, 정책별 전송 승인과 소수 실공고 확인 뒤 쌍별 채점을 한다.
   - 검증 T7. 회귀 10건과 새 holdout의 수치·잘못된 차단·필수자격 오충족·인용 오류·범위 누락·운영 시간, 사람 인수 기록.
5. STEP-005 상세 화면 연결·실무자 인수 [complex]
   - 승인 범위 내의 상세 projection과 원문 대조·확인 필요·업무 이력을 연결한다. 운영용 결과와 소스·감사 진단을 구분한다.
   - 검증 T6. production build, 1280×800·1440×900, 현재·부분·실패·정정·복귀, 실제 공고에서 담당자가 원문까지 확인.

## 실행 경계와 검증

- 개발·격리에서는 고정 응답으로 단계·권한·근거를 검증한다. PostgreSQL 17.11 실제 역할, API 거부 경계, 화면 의미·구조 검사를 사용한다. 외부 전송·운영 승인 없이 라우팅을 켜지 않는다.
- 운영 권한/마이그레이션, 개요 플래그, 회사 근거 등록, 모델 정책과 실제 입력 전송, 결과의 운영 표시를 각각 승인 시점에 분리한다. 개요 시운전은 로컬 모델이며 이 기능의 Luna 승인이나 품질 합격이 아니다.
- 실행 중 돌려받은 결과가 부분·실패이거나 오래된 버전이면 원문과 검토할 일을 남긴다. 자동 추적·최종 Go/No-Go 결정을 만들지 않는다.
- 상태 전이·저장 단위·승인 만료·전송 한도·슬롯 예약은 최종 명세를 따른다. 첫 시운전은 KST 하루 1개 공고·하루 및 공고당 최대 8회로 제한한다. 실제 적용 전 동결한 회사 묶음·단계별 호출 계획을 대조하고 건별 승인을 받는다.
