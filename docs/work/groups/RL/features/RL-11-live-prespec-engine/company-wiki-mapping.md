## 독립 CLI에서 로컬 위키 읽기

BidOps 루트에서 `scripts/bid-deep-agent-wiki.sh rootlab lint`를 실행하면 원본 CLI가 루트랩 프로필과 로컬 위키를 대조한다. `scripts/bid-deep-agent-wiki.sh rootlab preview --slug <공고-slug>`로 위키 발췌의 카테고리와 페이지를 모델 호출 없이 확인한다. `analyze --only <공고-slug>`는 같은 회사의 위키를 `--knowledge`로 전달해 매칭·종합 단계에서 읽으며, 외부 모델 호출은 원본 CLI의 확인을 받는다. `--out`의 상대 경로는 독립 체크아웃을 기준으로 한다. 원본 CLI가 다른 위치에 있으면 `BID_DEEP_AGENT_ROOT`로 지정한다. ## Luna에 제공할 회사 자료

2026-11-20 확정. RL-11의 실제 분석에 적용한다. 건별 승인은 아래 범위 안에서 해당 공고에 필요한 자료를 보내는 승인이다.

| 자료 | 전송 허용 | 내부 대조용 |
|---|---|---|
| 자격·인증 | 자격명, 확인된 보유 여부·적용 범위·유효기간 | 증명서 원본, 등록번호 |
| 유사 실적 | 고객을 식별할 수 없는 실적 참조 ID, 사업 유형·수행 기간·확인된 역할과 범위 | 고객 실명, 정확한 계약금액, 계약서 원본·계약번호 |
| 인력 | 확인된 역할·등급·관련 경력 | 이름·연락처·개인별 배정표. 이번 사업의 투입 가능성은 공고별 확인 |
| 회사 수행 기준 | 해당 요구와 직접 관련된, 외부 제공을 허용한 확인 문장 | 위키 전문, 추정·미확인 원값, 무관한 방침 |

회사 실적의 고객·금액 요건은 고정된 공고 조항과 회사 증빙을 BidOps 안에서 대조한다. Luna에는 해당 조항에 대한 충족·미충족·미확인과 기준일만 제공한다. 증빙 부족은 미확인으로 유지한다. 이 경계는 구조화 필드뿐 아니라 발췌 본문·제목·출처 표기와 후속 단계 입력에도 적용한다.

## 등록과 적용

1. 위키 revision·페이지 slug·출처 절과 문장 단위의 대응 회사 사실 ID를 기록한다. 한 페이지 안의 확인·추정·미확인 주장에 같은 상태를 일괄 부여하지 않는다. 위키의 `confirmed`는 출처 검토의 시작점이다. 충돌·증빙 누락·중복은 해결 전 `proposed` 또는 `unknown`으로 둔다.
2. 확인된 구조화 사실은 기존 `import-company-knowledge`와 `activate-company-knowledge`로 새 프로필·그래프 버전에 넣는다. 조회에는 버전과 출처를 연결하고 사라진 사실이나 기존 분석을 덮어쓰지 않는다. 루트랩 원본 파일과 본문은 버전 관리된 승인 보관 위치에 둔다. 비밀·계약번호·연락처·근거 원문 전체를 Git·로그·프런트엔드에 싣지 않는다.
3. 실행 시 승인된 회사 바인딩, 위키 revision, 선택한 발췌의 항목별 ID·출처·내용 digest를 문서 묶음과 함께 고정한다. 공고 유형과 원문 요구사항에 맞는 짧은 승인 발췌만 전송 미리보기에 추가한다. 추정·미확인 값의 원문과 회사 위키 전체는 전송 대상에서 제외한다. 매칭기는 설계·검토를 돕지만 근거 상태와 차단 조건은 서버에서 검증한다.

## 대구 외 상주 불가

G7 확인을 근거로 다음 회사 근거 버전의 `pref:onsite_cap.value.params.onsite_regions`에 완전 목록 `"대구"`를 넣는다. v4의 해시와 기존 평가는 보존한다. 필수 상주의 실제 이행 장소가 확인됐고 이 목록과 교집합이 없을 때만 부족으로 표시한다. `발주기관 지정 장소`처럼 장소가 없거나, 방문·원격 허용·선택 가능한 위치·일시 출장인지 불명확한 경우 확인 항목으로 보낸다. 공고 발주처 주소나 본점 자격에서 상주 장소를 추정하지 않는다. 2026-11-20 사용자가 두 묶음의 업무 후보와 **필수·독립 의무가 원문으로 확인된 경우에만 차단**하는 조건을 승인했다. SW 부수·혼합 과업과 법령·인증 단어는 사람 확인 대상으로 둔다. 현재 RL-10은 등록한 용어를 원문과 비교하므로 필수·독립 판정을 구현·검증한 뒤에 새 버전의 활성 `requirement_terms`에 등록한다.

고정 gold 10건의 저장 블록을 실제 RL-10 비교 함수로 오프라인 재생했다. 납품·공사 후보 4개에서는 일치한 차단 블록이 0개였다. 운용·예비 장비 후보 4개는 기존 하드웨어 차단 조건 2건 중 1건의 블록 2개에서 `gap`을 냈다. 같은 공고의 gold 인용 밖 표 제목에 `전산장비 유지관리`가 있어 추가 `gap` 1개가 나왔으며, 제목은 의무의 충분한 근거로 보지 않는다. 운용 후보의 혼합·부분 일치는 9개였다. 다른 하드웨어 차단 조건은 SW 혼합 과업으로 남았다. 이 탐침은 블록을 제약으로 가정한 진단이며 모델 추출·종단 판정의 성능 측정과 구별한다. 기존 오프라인 비교와 오탐 사례(`docs/validation-runs/20261119-rl10-compare-blockers/README.md`, git 이력)
