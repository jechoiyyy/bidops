## 1. 무엇을 하려는가

**운영시작일부터 매일 전일 1일치를 수집해 그날 바로 처리한다.** 누적해서 한 번에 몰아 처리하지 않고
매일 적은 양을 지속한다. 발주계획은 평일 290~379건, 주말 9~18건이다(게시일 기준 실측, §4).

- 발주계획은 **전일 하루 창**으로 수집한다. 21일 재조회(ADR-0027)는 폐기한다. 기준일을 전일로
  두는 이유는 발주계획 API가 `nticeDt` 구간 조회라 오늘을 기준으로 아침에 돌리면 **그 회차는** 실행 시각
  이후 게시분을 담지 못하기 때문이다(`collect_order_plans.py:143-171`). 같은 이유로 과거 날짜는 나중에도
  날짜를 지정해 수집할 수 있다 — 수집하지 않은 날이 영구히 사라지는 것은 아니다(공백일 따라잡기의 근거).
- 21일 재조회를 버리는 대가는 발주계획 측 `bidNtceNoList`·`changed_at` 갱신을 못 보는 것이다.
  ADR-0027 결과 절이 이미 "입찰공고 측 `orderPlanUntyNo`(76.7%)가 최종 확정 경로"라고 적었으므로
  발주계획→입찰공고 연결은 그 경로 하나로 간다. `docs/tracking/findings.md`의 "ADR-0027의 21일 재조회 근거가
  종단 관측에서 재현되지 않는다"도 같은 방향의 근거다.
- **같은 대가의 사용자 쪽 모습**: 발주계획은 첫 관측 그대로 고정된다. 추적 중인 사업의 예산·발주 시기가 바뀌어도
  화면에 반영되지 않는다(결정 16). 화면에 첫 관측일을 표시하고, "추적 중인 발주계획만 주기적으로 재조회"는 후속
  과제로 둔다(§7).
- 공고(사전규격·입찰공고)는 **기준일 포함 4일 창**으로 수집한다(결정 28이 결정 8을 개정). 입찰공고의
  정정·재공고는 새 공고 id와 그 건의 게시일로 올라와 그날 잡히지만, 사전규격은 조회 기준인 등록일시(`rgstDt`)보다
  공개(접수일시 `rcptDt`)가 최대 3일 늦어 하루 창이면 영구히 빠지는 건이 생긴다(M0 측정: 1일 창 1.55%, SW=Y 2/68,
  4일 창 0건). 겹쳐 다시 관측된 공고는 적재 no-op이고, 개요 run은 중복 방지 규칙으로 다시 돌지 않는다
  ([`spec.md` §9.4](spec.md), [`../validation-runs/20260918-late-indexing.md`](../validation-runs/20260918-late-indexing.md)).
- 발주계획과 공고는 **트랙을 나눠** cron 두 줄로 돌린다(결정 9). 한 트랙의 실패가 다른 트랙을 멈추지 않고,
  공고 트랙(사전규격 개요가 이미 운영 중)과 발주계획 트랙(C-2 활성화 전)을 따로 켜고 끌 수 있다([`spec.md` §8](spec.md)).
- **발주계획 트랙은 C-2 활성화까지 보류한다(결정 10).** 판정 없는 발주계획을 화면에 쌓지 않는다. 트랙은 항상
  수집·적재·C-2·감사 표본 draw를 한 묶음으로 돌고, 활성 policy가 없는 날은 수집도 하지 않는다. 공고 트랙은 먼저
  운영에 올릴 수 있다.
- 발주계획 수집 필터는 **이미** `bsnsDivNm ∈ {일반용역, 기술용역}` allowlist다
  (`collect_order_plans.py:52,658-659`). 바꾸지 않는다. 이 문서의 건수는 전부 그 필터 아래 값이다.
- 운영시작일 이전 데이터는 수집하지 않는다. 첫날이 곧 1일치다. 발주계획 트랙의 운영시작일은 C-2 활성화 이후이며
  사람이 정한다(D-e). 앞선 날짜를 포함하려면 날짜 범위 따라잡기로 하루씩 메운다.

지금은 **수집·적재만 매일 돌 수 있고 판정은 한 건도 자동으로 돌지 않는다.**
`scripts/run-daily-lifecycle.sh`는 나라장터 수집과 선별 적재까지 하지만 모델을 부르지 않는다
(스크립트 자체 계약: `run-daily-lifecycle.sh:33` "No model calls are made").

## 2. 막고 있는 것

### 2.1 C-2는 어떤 값으로도 실행할 수 없다

실행 API는 `policy_status=='active' AND quality_gate_status=='passed'`를 요구한다
(`web/backend/app/screening/services/order_plan_screening.py:256-257`).

- `order_plan_screening_policy` 행을 만드는 코드가 없다. `docs/contracts.md:1086-1088`이 정의한
  REST 3개(`GET …/policies/{version}`, `POST …/policies/candidate`,
  `POST …/policies/{version}/activate`)는 `app/screening/routers/`에 구현이 없다.
- C-2 품질 게이트 결과를 저장할 자리가 없다. policy 테이블에는 `quality_gate_status` 문자열
  한 칸뿐이고, 기존 `quality_gate`·`quality_gate_evaluation`은 C-1 전용이다
  (`purpose = model_comparison|operational_approval`).
- binding의 `external_transport.execution_allowed`가 `false`이고
  `BIDOPS_C2_EXECUTION_ALLOWED` 기본값도 false(`app/core/config.py:231`).

### 2.2 계약이 서로 모순이다

worker와 서비스가 동시에 만족할 수 없는 조합을 요구한다.

| 검사 | 요구값 | 현재 문서 값 |
|---|---|---|
| `workers/order_plan.py:274` | binding `status == "blocked"` | `"blocked"` ✓ |
| `workers/order_plan.py:344` | `external_transport.execution_allowed is True` | `false` ✗ |
| `workers/order_plan.py:265` | policy **파일**의 `policy_status == "active"` | `"draft"` ✗ |
| `workers/order_plan.py:282` | binding `policy.policy_status == policy 파일의 policy_status` | 둘 다 `"draft"` ✓ |
| `services/order_plan_screening.py:262` | policy **파일 payload**가 `policy_status == "active"` | `"draft"` ✗ |

즉 실행하려면 **`status`가 `"blocked"`인 채로 실행이 허용되고, 동시에 policy 파일이 `"active"`로
다시 발행돼야** 한다. 서비스와 worker **둘 다** 파일 `active`를 요구한다. policy 파일을 고치면
sha256이 바뀌고 binding의 `policy.sha256`, DB 행의 `policy_sha256`, validator의 리터럴까지 연쇄로
따라간다. DB 행의 payload·digest는 immutable(`contracts.md:1128`)이라 파일 status를 바꾸는 순간
새 `policy_version`이 필요하다 — 파일을 정본으로 두면 활성화마다 버전이 늘어난다.

### 2.3 21일 창 문제는 1일 창 전환으로 해소한다

처음 초안은 "21일 창을 그대로 판정하면 매일 같은 건을 다시 본다"를 모집단 축소 규칙으로 풀려 했다.
실행 API는 `source_run_id` 하나만 받고 모집단은 회차 파일 전체다
(`services/order_plan_screening.py:364-370`). 21일치면 수천 건이라 BM25 상위 300이 과거 건으로
채워지고, 새 policy 첫 실행에는 21일치 전체가 영구 탈락하는 부트스트랩 문제까지 있었다.

§1의 1일 창 전환으로 **발주계획 하나 = 회차 하나 = 실행 하나**가 되어 이 문제가 구조적으로
사라진다. 모집단 축소 규칙·부트스트랩 floor·제목 변경 재판정은 만들지 않는다.

### 2.4 판정 결과가 실행 하나에 묶여 있다 (UX)

목록 API가 `result.execution_id == 최신 완료 실행 1개`로 조인한다
(`order_plan_screening.py:997`, `:1026`). feedback 조인도 같은 실행에 묶여 있다(`:1017`).
그래서 **매일 실행하면 어제 판정한 건이 오늘 목록에서 "판정 없음"으로 보인다.** 실무자는 회차를
하나씩 되돌려 봐야 한다.

화면이 회차 선택을 강요하는 것(`OrderPlansPage.tsx:433,437`이 항상 `source_run_id`를 보냄)은
그 결과이지 원인이 아니다. API의 `source_run_id`는 이미 선택 인자이고, 생략하면 발주계획
하나당 최신 관측 하나만 남긴다(`:1000-1008`).

대시보드도 이미 어긋나 있다. `검토 후보 N건 · 누적`이라 적어 놓고 같은 단일 실행 목록을 센다
(`app/screening/projection.py:737-748`). 오늘 실행이 없으면 `no_completed_execution`으로 건수가
사라진다.

### 결정 1의 귀결 — 감사 표본은 평일마다 도는 업무다

평일 하루 모집단은 290~379건이라 300 절단은 **0~79건**을 탈락시키고, 실측한 평일 6일 중 5일에 절단이 걸렸다(§4).
탈락 건은 모델을 보지 않으므로 보상 장치는 BM25 탈락 감사 표본뿐이다. 현재 정책의 `audit_sample`은

"실행당 상한 N건, 탈락이 N 이하인 날은 전건"으로 정했고(결정 15) N은 D-c로 남는다.

## 5. GPU 부하 지도 (현재)

| 경로 | 1건당 호출 | 현재 상태 |
|---|---|---|
| C-1 공고 판정 | 공고 1건 = 7단계 직렬, 단계당 최대 2회 → **7~14회** | 워커 상시 기동, 스케줄러 꺼짐 → 큐가 비어 idle |
| C-2 발주계획 선별 | 300건 = 12배치, 배치당 최대 2회 → **12~24회** (모집단과 무관하게 고정). 바뀐 뒤에는 하루 1회, 공백일 따라잡기는 날짜별로 하나씩 | 꺼짐 |
| 사전규격 개요 | run 1개 = **2~3회** (하드 상한 3, 재시도 없음) | 켜짐 — web·분석 워커·첨부 워커 모두 `BIDOPS_PRESPEC_OVERVIEW_ENABLED=true`(2026-09-18 컨테이너 확인). 공고 적재 뒤 문서가 준비되면 이벤트로 돈다 |
| 심층 검토 | 공고 1건 = 3단계 × N조각, 조각당 최대 3회 → **3N~9N회**, N에 상한 없음 | 꺼짐 |

**쉬는 구간이 사실상 없다.** rate limit·semaphore·호출 간 sleep·재시도 backoff가 코드에 없다.
GPU를 지키는 것은 슬롯 1개 설계뿐이다(`config.py:148,215`, `app/workers/analysis.py:36`).

- **C-2는 별도 워커가 아니다.** 분석 워커 루프가 한 poll에 C-2·심층 검토·회사 핏·개요 중 **하나만** 잡는다
  (`app/workers/analysis.py:60-75`, C-2 claim이 우선). 이 넷의 직렬화는 이미 보장돼 있으므로 cron 두 줄의 시각을
  떼는 것은 GPU 충돌 회피의 근거가 되지 않는다. 같은 이유로 휴지를 작업 하나 뒤마다 같은 값으로 걸면 10분짜리
  C-2와 1분 남짓한 개요 run이 똑같이 쉰다 — 결정 13이 연속 가동 시간 기준으로 바꾼 이유다.
- C-1 워커는 web 프로세스 안의 별도 스레드다(`app/screening/runtime.py:177,217`). 분석 워커와는 서로 조율하지
  않는다. C-1을 운영에 쓰지 않는 동안(결정 27)에는 문제가 되지 않는다.

- 분석 워커는 루프 끝에서 매번 `time.sleep(poll)`을 부른다(`analysis.py:113`) — 잡을 처리한
  뒤에도 쉰다. 기본 1초.
- **C-1 워커는 반대로 큐가 비었을 때만 쉰다**(`app/screening/worker.py:294-297`
  `if row is None: self.sleep(delay)`). 공고가 줄지어 있으면 연속 처리다.
- C-2 배치 루프에는 sleep이 없다(`workers/order_plan.py:876-886`, heartbeat + commit만).
- 재시도에도 backoff가 없다(`app/core/model_client.py:1099-1213`). 타임아웃 300초 × 3회 =
  한 조각에서 15분 연속 점유가 가능하다.

## 6. 모델 사용 지점별 품질 장치 지도

| 공고명 1차 판별 | 아직 없다(2026-09-17 논의만) | 없음 | 만든다면 개요 전 자동 필터이므로 C-2와 같은 게이트 필수 |

이 계획은 C-2만 구현한다. 나머지는 "운영에서 켜기 전에 게이트가 있어야 한다"를 선행조건으로 기록하고
([`plan.md` §4·§7](plan.md)) 구현은 각자 별도 계획으로 한다. C-2 게이트의 구조(gold, 임계값, 2 pass,
append-only evaluation)는 회사 핏에 다시 쓸 수 있다.

## 7. 범위 밖

- **scheduler에 C-2를 붙이는 것.** `docs/PLAN.md` Phase 6이 별도 ADR과 별도 변경 계획을 요구한다.
- **활성화 자체.** 이 작업은 켤 수 있는 상태까지만 만든다.
- **발주계획 재관측(21일 창 복원).** 결정 7. 발주계획→입찰공고 연결은 입찰공고 측 경로로만 간다.
- **모델 호출 사이 cooldown.** 결정 3.
- **BM25 절단값 변경.** 결정 1.
- **C-1 자동 판정과 그 선행 S10·S12.** scheduler C-1은 C-1 품질 게이트·policy 활성화·always-on 승인이 필요하고
  이 계획은 다루지 않는다. 자동화 방식(scheduler adopt / 공고 트랙의 REST 호출)과 시각은 그때 정한다([`plan.md` §7](plan.md)).
  그때까지 C-1은 운영에 쓰지 않는다(결정 27).
- **C-2 밖의 품질 게이트·표본 점검.** 회사 핏 게이트, 개요 표본 점검, 심층 검토 근거 점검(§6, 결정 26).
- **추적 중 발주계획의 재조회.** 추적 건만 주기적으로 다시 조회하는 안은 후속 과제다. 나라장터 API가 번호 지정
  조회를 지원하는지부터 확인해야 한다(결정 16).
