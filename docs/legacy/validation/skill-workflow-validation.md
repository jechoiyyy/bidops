# Skill 워크플로 검증 기준 (보관본)

## 확정 범위

- 대상 기간: 2026-08-17 00:00 ~ 2026-08-23 23:59 (Asia/Seoul)
- 대상 데이터: 전국 나라장터 용역 본공고와 용역 사전규격
- 1순위 역량 축: `AI/데이터`, `블록체인·DID`, `공공 SI·통합관리`
- 표본: 분석 대상 30건과 비선정 감사 대상 10건
- 지역 제한: 자동 제외하지 않고 확인 항목으로 표시
- 법적 실적 인정 여부: 확인 자료가 없으므로 모든 수행실적을 `unknown`으로 취급

## 판정 원칙

판정 등급과 참여 준비 상태를 분리한다.

- 판정 등급: `우선 검토`, `검토 권장`, `관찰 대상`, `제외`
- 참여 준비 상태: `확인 완료`, `부분 확인 필요`, `참여 불가 확인`, `해당 없음`
- 기술·도메인 적합성이 높고 확인되지 않은 자격 조건만 남은 공고는 등급을 낮추는 대신 `부분 확인 필요` 항목을 함께 표시한다.
- `제외` 등급에는 `확인 완료`를 부여하지 않는다. 검토하지 않기로 한 공고에 확인 완료를 표시하면 확인을 마쳐 참여할 수 있다는 뜻으로 읽히기 때문이다. `해당 없음` 또는 `참여 불가 확인`을 사용하고, 제외 사유 구분을 함께 기록한다.
- 모든 공고에 다섯 관점(`기술 적합성`, `실적 정합성`, `공공 SI 적합성`, `사업성·자격 제약`, `전략 부합`)의 판단과 근거를 각각 기록하고, 반론을 별도로 작성한다. 어느 하나라도 비어 있으면 병합 스크립트가 산출물 생성을 중단한다.
- 모든 공고에 붙일 수 있는 문장은 반론이 아니다. 동일한 반론 문장이 전체 판정의 40%를 넘게 반복되면 오류로 처리한다.
- 회사소개서 수행실적은 기술·도메인·수행 역할의 근거로만 쓴다. 입찰 실적 요건 충족이나 법적 참여 자격의 확정 근거로 쓰지 않는다.
- 1차 후보군은 정규화된 한영 전략 개념 또는 회사소개서 41–46페이지 수행실적 사업명 유사 신호 중 하나가 있으면 포함한다.
- 개념 일치 신호가 조달 분류명에서만 나온 경우에는 공고 제목에서 나온 신호와 같은 무게로 취급하지 않는다.
- 수행실적 제목 유사도는 탐색 신호이며, 일반 시설·행사·공사처럼 디지털 납품 문맥이 없는 공고는 제목의 일부 단어가 같다는 이유만으로 포함하지 않는다.
- 공고 제목이나 API 요약에 없는 사실은 추정하지 않는다. 다만 지역 제한, 조달 분류, 실적제한경쟁, 정정·재공고 이력처럼 API가 이미 제공한 값은 확인 항목으로 올리지 않고 근거로 사용한다.

## 통과 기준

"워크플로가 동작했다"는 사실만으로는 이식 여부를 판단할 수 없다. 다음 다섯 항목은 측정 방법과 임계값을 착수 전에 확정한다.

| 항목 | 측정 방법 | 사전 확정 임계값 |
|---|---|---|
| 재현성 | 동일한 표본을 다른 시점에 같은 프롬프트로 재판정하고 등급 일치율을 계산한다 | 등급 일치율 80% 이상, 불일치가 한 관점에 절반 넘게 몰리지 않을 것 |
| 변별력 | 분석 표본에서 `우선 검토`가 차지하는 비율 | 10~25%. 이 구간을 벗어나면 기준을 재조정한다 |
| 근거 타당성 | 담당자가 `review-feedback.yaml`에 기록한 `system_judgment_review` 분포 | `동의` 70% 이상, `근거 부족` 10% 이하 |
| 정보 충분성 | 확인 항목 가운데 첨부 문서 없이는 해소되지 않는 항목의 비율 | 비율을 정량화하여 다음 단계의 우선순위를 정한다 |
| 관점 분할의 타당성 | 다섯 관점의 `assessment`가 한 공고 안에서 서로 갈리는 비율 | 표본의 40% 이상에서 관점 간 판정이 갈릴 것. 항상 같은 값만 나오는 관점은 통합하거나 질문을 재정의한다 |

변별력의 상한을 두는 이유는 다음과 같다. 우선 검토가 표본의 절반에 가까우면 담당자가 줄여야 할 검토 대상이 그대로 남으므로, 시스템이 시간을 절약해 주지 못한다.

검증에는 정답셋이 필요하다. 과거에 실제로 참여한 공고와, 검토했으나 참여하지 않은 공고를 함께 확보해야 한다. 참여한 공고만으로 구성하면 부적합 판정의 정확도를 측정할 수 없기 때문이다.

## 감사 표본의 역할

감사 표본은 1차 필터가 놓친 공고를 찾기 위한 표본이다. 감사 풀 2,200여 건에서 10건을 무작위로 뽑으면, 누락률이 5%라 하더라도 한 건도 발견하지 못할 확률이 약 60%이므로 어떤 결과가 나와도 정보량이 거의 없다. 따라서 다음 세 층으로 나누어 표적 추출한다.

1. `분류 근접`: 조달 분류가 디지털 사업군인데 후보에 들지 못한 공고
2. `실적 유사 근접`: 수행실적 유사도가 채택 임계값 바로 아래인 공고
3. `무작위`: 나머지

감사 표본 가운데 의미 판정에서 제외되지 않은 건수가 1차 필터의 누락 건수이며, 주간 보고서의 지표로 표시한다.

## 사람 피드백

각 공고에 다음 항목을 기록한다.

- 최종 처리: `심층 검토 진행`, `관찰`, `제외`
- 시스템 판정 평가: `동의`, `등급 수정`, `근거 부족`
- 수정된 등급과 수정된 참여 준비 상태
- 근거가 가장 부족했던 관점
- 수정 또는 제외 사유
- 확인 항목 답변(확인할 수 있는 경우)

피드백은 `review-feedback.yaml`에 구조화하여 보관한다. 근거가 가장 부족했던 관점을 함께 받는 이유는, 어떤 관점의 질문을 다시 써야 하는지를 판단하기 위해서이다.

## 결과물

Skill 검증 단계에서는 정적 HTML 두 종류를 생성한다.

1. 주간 모니터링 보고서: 우선순위, 마감, 사전규격, 확인 요청, 감사 누락 건수 중심
2. 공고별 분석 문서: 관점별 판단, 근거 실적, 반론, 확인 항목, 1차 검색 신호, 다음 행동 중심

누적 추적 대시보드는 판정·변경 이력이 쌓인 뒤 애플리케이션 단계에서 구현한다.
