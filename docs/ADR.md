## ADR-001 · skill 스크립트를 수정하지 않고 산출물을 적재한다

**맥락**
1국면에서 `skills/` 아래 네 개의 스크립트와 세 개의 SKILL.md가 검증을 마쳤고, 2026-08-17~23 회차의 판정 결과가 모델 이식의 기준선으로 보관되어 있다. 웹 애플리케이션을 만들면서 이 코드를 웹 서비스 형태로 다시 쓰고 싶은 유혹이 있다.

**결정**
기존 스크립트를 변경하지 않는다. 웹 계층은 스크립트가 만든 JSON·YAML 파일을 읽어 데이터베이스에 적재하고, 파이프라인 실행이 필요하면 같은 스크립트를 서브프로세스로 호출한다.

**근거**
프로젝트 개요 9.4절은 1국면 판정 결과를 모델 이식의 품질 기준선으로 사용한다고 규정한다. 스크립트를 웹 서비스로 재작성하면 판정 결과가 달라졌을 때 원인이 규칙 변경인지 이식 과정의 버그인지 구분할 수 없게 된다. 또한 스크립트는 표준 라이브러리만 사용하도록 작성되어 있어 실행 환경 의존성이 없다는 장점이 있는데, 웹 프레임워크에 흡수시키면 이 성질을 잃는다.

**결과**
- 적재기가 산출물 계약을 다시 검증해야 한다. 스크립트가 이미 검증했더라도 파일이 손으로 수정되었을 가능성이 있기 때문이다.
- 파이프라인 실행이 프로세스 경계를 넘으므로 진행 상황을 실시간으로 알기 어렵다. 로그를 줄 단위로 수집하는 방식으로 보완한다.
- 판정 로직 개선은 여전히 SKILL.md 수정으로 이루어진다. 이는 프로젝트 개요 9.1절이 skill을 선택한 이유와 일치한다.

**대안**
스크립트 로직을 백엔드 모듈로 흡수하는 방안을 검토했으나, 기준선 보존이 이 프로젝트의 핵심 자산이므로 기각했다.

## ADR-002 · 저장소로 SQLite를 사용한다

**맥락**
한 회차의 수집량은 2,546건이고 후보 풀은 327건이다. 회차가 주 단위로 쌓이면 연간 13만 건 규모가 된다. 사용자는 담당자 한 명이다.

**결정**
SQLite를 WAL 모드로 사용하고, 파일은 `web/data/bidops.db`에 둔다.

**근거**
데이터 규모가 SQLite의 실용 한계에 한참 못 미치고, 동시 쓰기가 사실상 발생하지 않는다. 별도 데이터베이스 서버를 요구하면 담당자 PC에서 실행하는 시나리오가 무너진다. PostgreSQL로 옮겨야 할 시점이 오더라도 SQLAlchemy를 쓰므로 전환 비용이 크지 않다.

**결과**
- 전문 검색은 SQLite FTS5를 쓰거나 `LIKE`로 처리한다. 공고 제목 검색 수준에서는 충분하다.
- 데이터베이스 파일은 저장소에 커밋하지 않는다. 산출물 파일에서 언제든 재생성할 수 있다는 점이 이 결정의 전제이다.

## ADR-003 · 스키마 계약 위반을 오류가 아닌 경고로 적재한다

**맥락**
`skills/references/workflow-contract.md`는 "계약을 어긴 파일은 다음 단계의 스크립트가 오류로 중단시킨다"고 규정한다. 그런데 산출물이 계약을 부분적으로만 충족하는 상황은 실제로 발생한다. 현재 회차(`20260817-20260823`)의 `screening-results.json`은 `bidops.screening.v2`이고 관점을 다섯 개 모두 갖추고 있으나, 판정 40건 가운데 18건에는 확인 항목이 하나도 기록되어 있지 않다. 이런 파일을 계약대로 통째로 거부하면 이미 축적된 판정을 화면에 전혀 띄울 수 없다. 과거 회차의 `bidops.decisions.v1` 산출물처럼 관점이 하나뿐인 경우도 같은 문제를 일으킨다.

**결정**
적재 단계는 위반 유형을 두 층으로 나눈다. 식별자·등급·준비 상태처럼 데이터의 의미를 규정하는 필드가 없으면 해당 판정을 적재하지 않는다. 관점 수 부족, 반론 누락, 확인 항목 누락은 있는 만큼 적재하고 경고를 기록한다. 어느 경우에도 누락된 값을 만들어내지 않는다.

**근거**
계약이 오류 중단을 규정한 이유는 "판정에 필요한 내용이 없으면 산출물이 만들어지지 않는 것이 정상"이기 때문이다. 이 원칙은 산출물을 **생성**하는 단계에 적용되어야 하며, 이미 생성된 산출물을 **표시**하는 단계에 그대로 적용하면 데이터를 볼 수 없게 만드는 것 말고는 얻는 것이 없다. 대신 경고를 화면에 그대로 노출하여, 계약 미달 상태가 조용히 넘어가지 않도록 한다.

**결과**
- 수집 실행 관리 화면에 산출물별 스키마 버전과 검증 결과가 표시된다.
- 관점 분할 지표는 관점이 하나뿐일 때 0%가 아니라 **계산 불가**로 표시된다. 값이 없는 것과 값이 나쁜 것을 구분한다.
- v2 판정이 생성되면 같은 적재기가 별도 수정 없이 다섯 관점을 적재한다.

## ADR-004 · design.md에서 팔레트만 차용하고 밀도는 재설계한다

**맥락**
`design.md`는 Ease Health의 스타일 참조 문서로, 마케팅 랜딩페이지를 전제한다. 디스플레이 74px, 카드 패딩 28~42px, 21px 미만 패딩 금지, 그림자 금지, 새 액센트 색 금지를 규정한다.

**결정**
색 팔레트와 그림자 없는 원칙만 가져온다. 타이포와 간격은 관리자 화면 밀도에 맞게 새로 정의한다. 팔레트에 없는 색은 마감·차단 표시용 테라코타 `#9a4a2f` 하나만 추가한다.

**근거**
40건의 공고를 한 화면에서 훑고 다섯 관점의 근거를 읽는 작업에 42px 패딩과 74px 헤드라인을 적용하면 한 공고가 화면을 가득 채운다. 반면 팔레트는 밀도와 무관하게 성립하며, 등급 4단계를 색상 대비가 아니라 표면 농도(Forest Ink → Sage Mist → Keylime Wash → 테두리만)로 구분하는 방식은 오히려 데이터 밀집 화면에 잘 맞는다.

테라코타 한 색을 추가한 이유는 팔레트에 경고를 표현할 색이 없기 때문이다. 마감 임박과 참여를 막는 확인 항목은 다른 정보와 같은 무게로 읽히면 안 된다. 다른 용도로 확장하지 않는다.

**결과**
- 등급과 상태는 색만으로 구분하지 않고 항상 문자 라벨을 함께 표시한다. 표면 농도 구분은 색각 특성에 따라 판별이 어려울 수 있다.
- `design.md`를 그대로 따르는 다른 화면이 생기면 두 밀도 체계가 공존하게 된다. 이 애플리케이션은 관리자 밀도 하나만 사용한다.

## ADR-005 · 첨부 확보를 자동 연계와 수동 등록의 혼합으로 구성한다

**맥락**
2026-08-17~23 회차에서 수집한 2,546건 중 275건이 첨부 정보를 갖지 않는다. 후보 풀 327건으로 좁혀도 34건(10.4%)이 첨부 없이 수집된다. 이들 공고는 나라장터에 목록만 게시되고 상세 공고와 첨부는 발주기관의 자체 조달시스템에 있다. 첨부가 없으면 제안요청서를 확인할 수 없으므로 심층 검토를 시작할 수 없다.

**결정**
기관별 조달시스템을 `agency_portal` 테이블로 등록하고, 공고의 발주기관 문자열에 부분 일치하면 검색 주소를 자동 생성한다. MVP 대상은 한국수자원공사, 한국도로공사, 한국토지주택공사 세 곳이다. 파일 자체는 담당자가 내려받아 수동으로 등록하며, 등록한 파일은 `origin=manual`로 기록하여 나라장터 제공분과 구분한다.

**근거**
기관마다 조달시스템의 구조와 인증 방식이 다르므로 자동 수집을 일괄 구현할 수 없다. 반면 "어느 시스템에서 무엇으로 검색하는가"는 기관 단위로 고정되므로 데이터로 관리할 수 있다. 이 절반만 자동화해도 담당자가 매번 기관 홈페이지를 찾아 들어가는 시간이 사라진다.

세 기관을 MVP 대상으로 삼는 이유는 담당자가 지목한 우선순위이기 때문이다. 표본 기간에는 이 세 기관의 첨부 미제공 사례가 나타나지 않았으므로, 초기 데이터의 검색 주소 템플릿은 실사용에서 검증이 필요하다.

**결과**
- 애플리케이션이 외부 시스템에 직접 요청하지 않는다. 링크 생성까지만 담당하므로 상대 시스템의 정책 위반 위험이 없다.
- 첨부 확보 여부가 검토 대기열의 필터와 대시보드 지표로 노출된다.
- 파일 원문은 `web/data/attachments/`에 저장하고 저장소에 커밋하지 않는다.

## ADR-006 · 판정 단계는 애플리케이션에서 실행하지 않는다

**맥락**
파이프라인 네 단계 가운데 수집·표본·보고는 결정적 스크립트이지만, 판정은 에이전트가 `screening-decisions.json`을 직접 작성하는 단계이다. 워크플로 계약은 이 파일을 "이 워크플로에서 LLM이 직접 작성하는 유일한 파일"로 규정한다.

**결정**
애플리케이션은 수집·표본·보고 세 단계만 실행한다. 판정 단계는 화면에 대기 상태로 표시하고, 담당자가 Claude Code에서 skill을 실행한 뒤 파일이 갱신되면 적재기가 인식한다.

**근거**
판정을 애플리케이션에서 실행하려면 LLM 호출을 애플리케이션에 넣어야 하는데, 이는 프로젝트 개요 9.4절의 2국면 모델 이식에 해당하는 별도 과제이다. 그 단계에서는 관점마다 다른 모델을 배치하는 설계가 필요하며, 지금 임시로 구현하면 이식 설계를 앞당겨 잘못 고정하게 된다.

**결과**
- 한 회차를 완성하려면 화면과 Claude Code를 오가야 한다. 이 불편은 2국면 이식으로 해소한다.
- 판정 단계의 상태 표시가 "파일이 있는지"로만 판단되므로, 판정이 진행 중인지 아직 시작하지 않았는지 구분되지 않는다.

## ADR-007 · 리뷰의 정본을 데이터베이스로 옮기되 YAML 내보내기를 유지한다

**맥락**
현재 담당자 리뷰는 `reports/<run>/review-feedback.yaml`에 기록하도록 되어 있으나, 40건 전부가 빈 상태로 남아 있다. 손으로 YAML을 채우는 방식이 실제로 수행되지 않는다는 사실이 확인된 셈이다.

**결정**
리뷰의 정본을 데이터베이스로 옮긴다. 애플리케이션 화면에서 입력하고, 기존 형식이 필요할 때는 `/api/reviews/export`로 같은 구조의 YAML을 생성한다. 적재 시점에 기존 YAML에 값이 채워져 있으면 초기 데이터로 가져온다.

**근거**
리뷰가 쌓이지 않으면 통과 기준의 근거 타당성 지표를 영원히 측정할 수 없고, 프로젝트 개요 2.2절이 정의한 기준 개선 순환도 성립하지 않는다. 반면 YAML 형식 자체는 skill 워크플로와 문서에서 계속 참조되므로 폐기하지 않는다.

**결과**
- 같은 공고에 대한 리뷰가 회차별로 보관되어, 판정이 바뀌었을 때 담당자의 평가가 어떻게 달라졌는지 대조할 수 있다.
- YAML과 데이터베이스가 어긋날 수 있다. 데이터베이스가 정본임을 문서와 화면에 명시한다.

## ADR-008 · 인증을 구현하지 않고 로컬 실행을 전제한다

**맥락**
사용자는 기획부 담당자 한 명이며, 데이터에는 공개 입찰 정보와 회사 프로필이 포함된다. 고객 정보나 내부 영업 정보는 다루지 않는다.

**결정**
인증과 권한 분리를 구현하지 않는다. 애플리케이션은 로컬호스트에서 실행하며, 리뷰 작성자는 설정값으로 기록한다.

**근거**
사용자가 한 명인 상태에서 인증을 구현하면 검증해야 할 표면만 늘어난다. 프로젝트 개요 6.3절이 내부 영업 정보와 고객 정보를 범위에서 제외했으므로 보호해야 할 민감 정보의 등급도 높지 않다.

**결과**
- 사내망 공유가 필요해지면 이 결정을 다시 기록해야 한다. 그 시점에는 리뷰 작성자 식별도 함께 필요해진다.
- API 키는 여전히 `.env`에 두고 응답과 로그에 노출하지 않는다. 인증 부재와 비밀 관리는 별개의 문제이다.

## ADR-009 · 회차를 불변 스냅샷으로 취급하고 재분류는 새 회차로 만든다

**맥락**
2026-08-24에 검색 규칙을 보완하여 같은 기간의 원문을 `--from-raw`로 재분류했고, 후보 풀이 328건에서 327건으로, 분석 표본이 5건 교체되었다. 디렉토리는 같은 이름을 그대로 사용했으므로 이전 결과는 파일 시스템에서 사라졌다.

**결정**
데이터베이스에서는 재분류 실행을 새로운 `run` 행으로 만들고, 이전 행에 `superseded_by`를 기록하여 대체됨으로 표시한다. 두 회차의 판정을 모두 보관한다.

**근거**
재현성 지표는 "같은 공고를 다른 시점에 판정했을 때 등급이 일치하는가"로 정의되므로, 이전 판정을 지우면 이 지표를 계산할 수 없다. 규칙 변경의 효과를 측정하는 것도 마찬가지이다. 어떤 규칙 변경이 무엇을 회수하고 무엇을 놓쳤는지는 두 스냅샷을 비교해야만 알 수 있다.

**결과**
- 회차 선택기에 대체된 회차가 함께 나타난다. 기본 선택은 최신 유효 회차이다.
- 디렉토리 이름이 같은 두 실행을 구분해야 하므로, `run.id`는 디렉토리명이 아니라 디렉토리명과 `generated_at`의 조합으로 만든다.
- 저장 용량이 회차 수만큼 늘어나지만, 회차당 수천 건 규모이므로 문제가 되지 않는다.
