# 업무 규칙

## 사전규격 C-1 기본 대상

### 누적 목록의 업무 보기 (2026-09-16)

사전규격 기본 화면은 누적 공고 중 검토할 항목을 보여준다. 개요 상태가
`needs_human_review`이거나 자동 준비 상태가 `deep_review_ready_for_click`이거나,
개요가 `completed`이면서 발견 경로가 `신규`이고 추적 상태가 null/미선택인 공고의
합집합이다. 이는 읽기 전용 탐색 조건이며 추적 승인·분석 실행·최종 판단을 바꾸지 않는다.
의견 마감이 지나도 업무 대상에서 제외하지 않으며 소멸시키지도 않는다. 다만 검토할 항목의
기본 시야는 마감 전과 마감 미확인 구간이고, 마감 경과 구간은 건수와 함께 항상 보이며
1클릭으로 전환한다(2026-09-21 개정). 마감 미확인은 항상 기본 구간에 남으며 마감 경과로
접지 않는다. 구간은 검토할 항목에만 적용하고 최근 수집·추적 중·전체 이력은 영향받지 않는다.
다음 행동 안내는 사람 확인,
심층 검토 열기, 추적 결정 순으로 우선한다.

2026-09-22 개정(시안 M7 승인): 위 합집합에 **추적 상태가 null 또는 `미선택`**이라는 조건을
바깥에서 AND로 건다. 사람이 추적 결정을 내린 공고는 개요·자동 준비 상태와 무관하게 검토할
항목에서 빠지고 추적 중(계속 추적·보류)·전체 이력에서 보인다. `계속 추적`·`보류`·`종료`는
이유가 달라도 모두 사람이 내린 결정이므로 구분하지 않는다 — 옛 규칙에서는 `보류`를 고른
공고가 개요 `needs_human_review`라는 이유로 검토할 항목에 남았다. 추적 상태를 `미선택`으로
되돌리면 다시 들어온다. 대시보드 `02 사전규격` 타일의 `pre_spec_deep_review_ready` 건수도
같은 추적 조건을 쓴다. 검토 제외는 종전대로 업무 집계를 바꾸지 않는다.

최근 수집은 관측 기간, 추적 중은 계속 추적·보류, 전체 이력은 누적 전체를 조회한다.
회차는 관측 소속만 제한하며 해당 공고의 현재 상태를 표시한다. 개요 실행이 없는
미시작과 실제 실행 대기는 구분한다. 화면의 발견 경로는 `발주계획 연계`·`독립 발견`으로
읽으며 기존 계약의 `추적`·`신규` 의미와 값은 유지한다.

### 사전규격 검토 제외·복원 (PoC)

`notice.review_exclusion_status`는 팀 공통 검토 목록의 포함(`included`)·제외(`excluded`) 상태다.
기존 건은 포함이며 변경 담당자·사유·시각은 null이다. 단건·선택 묶음 제외와 전체 이력의
단건 복원을 제공한다. 제외 건은 사람 확인·심층 검토 클릭 대기·추적 예외에 해당해도
검토할 항목과 최근 수집에서 숨긴다. 추적 중·전체 이력·별도 상세에는 검토 제외 표식을 붙인다.
사업기회 추적, 등급, 리뷰, 자동 문서 준비·분석 자격과 대시보드 업무 집계는 바꾸지 않는다.
재관측·분석 상태 변화로 자동 복원하지 않으며 복원 뒤에도 기존 조회 조건을 만족해야 보인다.

변경은 공고 ID 순서로 잠근 뒤 상태와 감사 이벤트를 한 트랜잭션에 저장한다. 이미 목표 상태면
변경 담당자·사유·시각과 감사를 덮어쓰지 않는다. 담당자 이름은 인증이 아닌 감사 표식이다.
한 요청은 1~200건이고 잘못된 대상이 섞이면 전체 거부한다. 화면은 200건 초과 선택의 실행을
막으며 자동 분할·자동 재시도를 하지 않는다. 실패 시 입력·선택을 유지하고 명시적으로 재시도한다.
성공 시 처리한 선택을 해제하며 활성 행이 사라지면 다음 행, 없으면 이전 행으로 이동한다.
마지막 페이지가 비면 이전 유효 페이지로 이동한다. 미저장 추적 입력은 기존 이탈 확인으로 보호한다.

2026-09-07 사용자 지정 기준으로 새 C-1 정책은 `SW사업대상=Y`를 기본 대상으로 한다.
키워드 후보군 밖의 Y도 포함하며, N·미확인은 일괄 실행에서 제외한다.
N은 사용자가 공고를 지정한 단건 요청으로 실행할 수 있다.
기존 정책과 고정 품질 표본은 소급 변경하지 않는다. 새 규칙은 별도 불변 정책의
`sw-business-selection.v1`로 묶고 품질 승인 없이 운영 활성화하지 않는다.

## 용어와 판단 단계

- `사업기회`는 발주계획, 사전규격, 입찰공고가 같은 조달 목적을 가리킨다고 확인된 내부 추적 단위다. 공식 통합번호가 없는 유사 관계는 사람 확인 전까지 같은 사업기회로 확정하지 않는다.
- `발주계획 후보`는 조기 탐색 결과다. 후보 편입 또는 탈락은 회사 적합성, 자격 충족, 참여 결정을 뜻하지 않는다.
- `등급`은 회사와 사업의 전략·기술 적합성을 나타내는 `우선 검토`, `검토 권장`, `관찰 대상`, `제외` 중 하나다.
- `참여 준비 상태`는 입찰 자격 확인 정도를 나타내는 `확인 완료`, `부분 확인 필요`, `참여 불가 확인`, `해당 없음` 중 하나다.
- `심층 추적 승인`은 사전규격을 계속 분석하고 입찰공고까지 감시하라는 사람의 결정이다. 최종 입찰 참여 승인이 아니다.
- `사전규격 개요 검토`는 제안요청서 앞부분을 근거로 **이 사업이 회사가 수행할 만한 내용인지**만 확인하는 저비용 단계다. 앞부분만 읽으므로 참가자격·배점·제출물·실적요건을 보지 못한다. 그 결과로 `참여 준비 상태`를 정하거나 `등급`의 자격 축을 채우지 않는다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)). 대화에서 쓰는 `1차 검토`는 이 단계의 별칭이다.
- `예비 적합성 등급`은 개요 범위의 실제 주요 과업과 세 관심 축(AI/데이터·블록체인/DID·공공 SI/통합관리)의 관계를 나타내는 화면용 우선순위다. 기존 선별 등급, 참여 준비 상태, 심층 추적 승인, 최종 Go/No-Go를 바꾸지 않는다([ADR-0065](tracking/decisions/0065-prespec-overview-preliminary-assessment.md)).
- `심층 검토`는 첨부 원문을 근거로 자격·요구사항·평가·수행 위험·경제성을 구조화하는 단계다.
- `정책 버전`은 후보 선정 조건, 관점·가중치, 모델·프롬프트, 검증 기준의 고정 묶음이다. 실행은 시작 시점의 버전을 끝까지 사용한다.

## 발주계획 탐색

발주계획의 관측 규모는 3일 약 1,200건, 1주 약 2,000건이다. 일반용역과 기술용역을 매일 수집하며 계획 단계에서는 `SW사업대상`이 없거나 비대상이라는 이유로 자동 제거하지 않는다. 제목·기관·예산·예정 시기·발주 방식은 탐색 신호이며 제안요청서에 근거한 참여 판단으로 승격하지 않는다.

운영 선별 방식은 구현 전에 고정 3일치 자료로 비교한다.

| 후보 방식 | 비교 입력 | 결과에 반드시 남길 값 |
|---|---|---|
| 키워드 규칙 | 같은 정규화 제목·기관·공개 메타데이터 | 일치 규칙, 일치 위치, 점수와 순위 |
| ColBERT | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·색인 버전, 입력 해시, 유사도와 순위 |
| Qwen | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·프롬프트 버전, 구조화 선택·이유·근거 |
| Luna | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·프롬프트 버전, 구조화 선택·이유·근거 |

네 방식은 한 번 저장한 동일 원문을 사용한다. 방식마다 API를 다시 호출하거나 입력 구간을 바꾸면 비교 결과로 인정하지 않는다. Sol의 평가는 합집합을 검토하기 위한 참고 판정이며 정답이 아니다. 사람은 네 방식의 합집합과 각 방식이 탈락시킨 감사 표본을 가림 검토해 최종 라벨을 확정한다.

선택 방식은 전체 적합 건 회수율, 상위 후보 적중률, 중요한 누락 건수, 사람이 검토할 건수, 처리시간, 비용을 함께 비교해 정한다. 한 지표만 가장 높다는 이유로 활성화하지 않는다. 실험 결과와 사람 라벨이 확정되기 전에는 키워드·ColBERT·Qwen·Luna 중 어느 것도 운영 정본으로 간주하지 않는다.

선택된 후보만 저장해서는 안 된다. 각 발주계획의 외부 식별자, 공개 메타데이터, 원문 해시, 최초·최근 확인 시각, 네 방식의 점수·순위·이유·버전, 사람 판정·이유·작성자·시각을 보존한다. 탈락 기록을 삭제하면 누락률과 정책 변경 효과를 측정할 수 없으므로 금지한다.

발주계획은 매일 수집하지만 사람의 누적 후보 검토는 월요일과 목요일에 진행한다. 수집 주기와 사람 검토 주기를 같은 값으로 묶지 않는다.

## 사전규격 수집과 심층 추적

### 개요 기준 예비 적합성 판단 (2026-09-21)

새 개요 계약은 사실 요약과 예비 판단을 함께 생성하되 따로 검증한다. 모델은 등급을 쓰지 않고 실제 주요 과업, 수행 역할, 세 관심 축의 `direct|partial|indirect|unrelated|unknown` 관계와 근거 ID를 낸다. 서버는 가장 강한 유효 관계를 `우선 검토|검토 권장|관찰 대상`으로 계산한다. 세 축이 모두 무관한 경우에는 개요 전체와 판단에 대한 선택 의미검증까지 통과해야 `제외`가 된다.

핵심 과업, 역할, 원문 근거, 사용한 회사 근거가 부족하거나 손상되면 `판단 보류`로 표시한다. 이는 다섯 번째 등급이 아니며 저장 등급은 `null`이다. 미확인을 무관으로 바꾸거나 자격·실적 미확인만으로 낮은 등급을 만들지 않는다. 사람 정정이 있으면 화면에서 가장 먼저 쓰고, 그다음 현재 문서의 새 판정/보류, 기존 선별 등급, 판정 없음 순으로 대표값을 고른다. 새 판정의 기술 실패·재실행 대기는 이전 유효 결과를 덮지 않고 최신 실행 상태로 따로 보인다.

정상 생성은 1회다. 제외 후보, 수치 관계 모호성, 역할 불명확, 모델이 표시한 불확실성, 검증 인용과 생성 문장의 부정·조건 표식 차이는 의미검증 1회를 추가한다. 형식 오류 재시도 1회를 포함한 실행 상한은 3회다. 의미검증 미실행은 통과가 아니며, 실패해도 결정적으로 검증된 개요는 보존하고 등급만 보류한다.

자동 준비·회사 핏·자동 심층 시작은 계속 기존 effective grade와 종전 개요 검증 수준을 사용한다. 새 화면 등급이 `우선 검토`라는 이유로 자동 실행 자격을 열지 않는다. 같은 문서에 종결 결과가 있으면 정책·프로필 변경이나 재관측만으로 자동 재평가하지 않으며, 사람이 요청한 재실행은 새 이력으로 실제 평가한다. 기본 정책은 v7이고 v8은 품질 비교와 운영 확인 전까지 활성 정책이 아니다.

사전규격은 매일 독립 수집한다. 수집 대상은 일반용역과 기술용역 전체이며 `SW사업대상`으로 걸러 내지 않는다. 발주기관이 매긴 이 값은 저장해 두고 화면 표시와 선택 필터로만 쓴다([ADR-0024](tracking/decisions/0024-prespec-collect-all-flag-sw.md)). 화면은 `<일반용역 + SW사업대상>`과 `<기술용역 + SW사업대상>`을 **기본으로 켠 채** 보여 주고 담당자가 끌 수 있게 한다. 다만 **추적 중인 발주계획에 연결된 사전규격은 `SW사업대상=N`이어도 목록에 남긴다.** 발주기관이 매긴 라벨 때문에 담당자가 직접 고른 추적 대상을 숨기지 않는다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)). 선택된 발주계획에 연결된 항목만 수집해서는 안 되며, 발주계획이 없는 사전규격도 새 사업기회 후보로 등록한다.

외부 통합번호가 정확히 일치하면 발주계획과 사전규격을 확정 연결한다. 통합번호가 없고 기관·사업명·예산·시기가 유사하면 후보 연결만 만든다. 후보 연결의 점수나 모델 설명만으로 이전 사람 선택을 승계하지 않으며 담당자가 관계를 확인해야 한다.

발주계획에서 사전규격으로 가는 공식 키는 없으므로 후보는 사업명 부분일치 검색으로 만든다. 검색어는 원문, 검색을 깨뜨리는 문자에서 쪼갠 조각, 정규화한 이름, 앞 12자를 정밀한 순서대로 시도하고 후보마다 어느 방식으로 걸렸는지 남긴다. 검색을 깨뜨리는 문자는 `·`(U+00B7), `&`, `‘`, `’`, `•` 다섯이며 괄호·쉼표·하이픈·마침표·낫표·겹낫표·물결·빗금·밑줄과 `・`·`‧`·`․`는 무해하다. 무해한 문자에서 쪼개면 질의가 짧아져 사람이 확인할 후보만 늘어난다.

사전규격 연결 상태는 `확정`, `후보 확인 대기`, `사람 확인 완료`, `검색 미확인`, `사람 확인 병합` 중 하나다(2026-09-17, `사람 확인 병합` 추가). `검색 미확인`은 사전규격이 없다는 뜻이 아니라 확인되지 않았다는 뜻이며 화면·API·집계 어디에서도 부재로 바꾸지 않는다. 검색 시점에는 미공개와 이름 불일치를 가를 근거가 없으므로 두 상태로 쪼개지 않는다. 이 상태에는 마지막 검색 시각과 시도한 방식을 남기고 재검색과 수동 검색 경로를 제공한다([ADR-0025](tracking/decisions/0025-prespec-link-search-unconfirmed-state.md)). `사람 확인 병합`은 후보 수락이 병합으로 끝난 link이며(아래 병합 규칙), 소유권은 옮겨진 공식 link가 갖는다.

사업기회 소유권을 정하는 authoritative 연결은 `official + 확정` 또는 `candidate + 사람 확인 완료 + accepted`뿐이다. 후보 확인 대기, rejected, 검색 미확인, 사람 확인 병합은 소유권이나 다음 자동 병합에 사용하지 않고 이력으로 남긴다.

**병합 규칙(2026-09-17, 후보 수락과 공식 키 자동 병합에 공통 적용).** 병합 대상 사업기회 집합에서
`사람 상태 보유` = `tracking_status ≠ 미선택` 또는 `recheck_signal_at IS NOT NULL`인 것을 H라 하면,

| \|H\| | 동작 |
|---|---|
| 0 | 가장 오래된 사업기회를 유지하고 나머지를 병합한다(기존 규칙) |
| 1 | H의 사업기회를 유지하고 나머지를 병합한다. 유지 쪽의 추적 상태·사유·선택자·시각은 바꾸지 않는다 |
| 2 이상 · H의 추적 상태가 전부 같고 H 어디에도 재검토 신호가 없음 | **2026-09-22 개정**: 병합한다. H 중 가장 오래된 사업기회(`created_at`, 동률이면 `id`)를 유지하고 그 추적 상태·사유·선택자·시각은 바꾸지 않는다. 병합된 H의 결정(상태·사유·선택자·시각)은 사라지지 않고 그 행에 그대로 남으며, 사람 수락 병합의 감사 이벤트 `details.merged_human_states[]`에도 함께 적는다([ADR-0068](tracking/decisions/0068-same-state-merge-and-tracking-reset.md)) |
| 2 이상 · 그 밖(상태가 하나라도 다르거나 재검토 신호가 있음) | 병합하지 않는다. 도착 레코드는 자기 사업기회(없으면 새로 생성)에 두고, H의 각 사업기회에 도착 레코드를 대상으로 하는 `병합 확인` 후보(`후보 확인 대기`, `search_strategy=merge_confirmation`)를 만든다 |

재검토 신호는 그 행에 남은 미해결 질문이므로 상태가 같아도 조용히 병합하지 않는다. 상태가 달라
병합이 막힌 건은 사람이 한쪽을 `미선택`으로 되돌린 뒤(추적 상태 변경과 같은 PATCH, 사유·담당자·감사
기록 필수) 다시 수락한다. 되돌리기는 자동으로 수락을 재시도하지 않는다 — 두 번째 결정도 사람이 한다.

병합은 이전처럼 secondary row를 삭제하지 않고 `merged_into_*` 이력으로 보존하며 링크를 유지 쪽으로 옮긴다. 유지 쪽의 `first_registered_stage`는 병합된 것 중 가장 이른 단계(`order_plan` < `pre_spec` < `bid_notice`)로 둔다. 자동 병합으로 새 공식 확정 링크가 들어오고 유지 쪽이 `계속 추적`·`보류`·`종료`면 재검토 신호를 켠다. 도착한 공고가 공식 키를 가졌는데 병합이 |H|≥2로 막히면(옛 규칙은 이 경우 고아로 되돌렸다) 고아로 남기지 않고 위 병합 확인 후보로 대신한다.

### 후보 대조와 찾아보기

위 이름 사다리(`full → breaking_split → normalized → longest_fragment → prefix12`)는 SW=Y 자동
대조와 사람이 요청하는 찾아보기가 공유하는 같은 판정 함수다.

**SW=Y 사전규격 자동 후보(2026-09-17).** SW사업대상=Y 사전규격이 적재되는 시점(같은 트랜잭션, 실패는 적재를 막지 않고 경고만 남김)에 **기관이 일치**(발주계획 기관명과 사전규격 발주·수요기관의 공백 정규화 값이 같음)하고 이름 사다리가 일치하며, 그 발주계획의 소유 사업기회에 아직 authoritative 사전규격 링크가 없으면 자동으로 `후보 확인 대기` 링크를 만든다. 이름만 일치하고 기관이 다르면 자동 후보를 만들지 않는다 — 담당자가 찾아보기로 확인한다. 정렬은 전략 정밀도 → 발주계획 최신 순, 사전규격당 최대 5건이며 이미 기각된 owner+target 쌍은 다시 만들지 않는다.

**찾아보기.** SW=Y 자동 대조 밖의 연결은 담당자가 `사전규격 찾아보기`·`입찰공고 찾아보기`로 요청한다. 이 조회는 모델이나 원격 API를 호출하지 않고 보관된 회차의 수집 색인(선별 여부와 무관하게 모든 수집 레코드를 담은 검색 전용 투영)을 이름 사다리로 검색한다. 기관 일치 후보를 우선하되 기관 불일치 후보도 `agency_match=false`로 함께 보여 준다. 0건이어도 `검색 미확인`으로 남기며 "레코드가 없다"로 바꾸지 않는다. 찾은 레코드가 아직 적재되지 않았으면 그 회차 파일에서 적재한 뒤 후보 링크를 만든다.

### 전량 수집과 선별 적재(2026-09-17)

발주계획·사전규격·입찰공고는 매일 **전량 수집해 회차 파일로 보관**한다(원본 불변). 그중
**추적·SW 관련 레코드만 사업기회로 적재**하고, 나머지는 가벼운 수집 색인에만 남아 나중에 추적을
시작하거나 찾아보기를 할 때 쓰인다. 실측(3일 창, 2026-09-17)으로는 입찰공고 전체 1,818건 중
1468(소프트웨어사업자) 업종 표시는 138건이며, SW 사전규격 계보를 잇는 입찰공고 84건 중 24건
(29%)이 1468 밖이었다 — 업종제한이 없는 SW 공고는 1468 조회에 잡히지 않으므로 **1468은 수집
필터가 아니라 표시로만 쓴다**([`../validation-runs/20260917-bid-collection-probe.md`](../validation-runs/20260917-bid-collection-probe.md),
[ADR-0059](tracking/decisions/0059-full-collection-selective-ingest-and-index-search.md)).

입찰공고는 다음 중 하나에 해당하면 적재한다. ① 공식 키(발주계획 통합번호·사전규격 등록번호·
같은 공고번호의 다른 차수)가 `계속 추적`·`보류`·`종료` 사업기회를 가리킴, ② `bfSpecRgstNo`가
SW=Y 사전규격(DB 또는 색인)을 가리킴, ③ 1468 표시가 있고 계약방법이 있으며 `수의`가 아닌
경쟁입찰. 사전규격은 SW=Y만 적재하되 추적 사업이나 적재된 입찰공고가 가리키는 사전규격도
적재한다. 발주계획은 기준일(전일) 하루 창으로 수집한 회차를 전량 적재하며 재조회하지
않는다([ADR-0061](tracking/decisions/0061-daily-collection-window.md)). 조건에 쓰는
값이 `null`이면 그 조건은 불일치로 보고 적재하지 않으며(수집 색인에는 남는다) 추정 적재하지
않는다.

선별 적재의 통계(원천별 수집 건수, 사유별 선별·제외 건수)는 그 회차 적재 시점의 결과
snapshot이다. 나중에 추적 보충이나 찾아보기로 적재된 레코드는 회차 통계를 다시 쓰지 않고
색인 행에만 반영한다. 상세 계약은 [contracts.md](contracts.md#적재-cli와-수집-색인-spec-2)가
정본이다.

### 조치 필요·신규 입찰공고 구역과 보류 재검토(2026-09-17)

`조치 필요`는 추적 대상(`계속 추적`·`보류`·`종료`)의 할 일만 담는다 — 새 공고 연결(`new_link`),
후보 확인 대기(`candidate_pending`), 병합 확인 대기(`merge_confirmation`), 미답변 차단 항목
(`blocking_item`), 보류 기한 지남(`hold_overdue`) 중 하나 이상이면 이 구역에 들어간다. 사유는
행마다 여러 개일 수 있으며 구역과는 다른 축이다. 입찰공고로 **처음** 등록된 미선택 사업(
`first_registered_stage=bid_notice`이고 `미선택`)은 `조치 필요`에 섞지 않고 **`신규 입찰공고`**
구역으로 분리한다 — 이전에는 입찰공고를 매일 적재하면 이런 건이 `조치 필요`를 채웠다.

`보류`는 저장 시각(`tracking_selected_at`)으로부터 **14일**이 재검토 기한이다. 대시보드는 기한
지남·임박(3일 이내) 건을 보여 주고, 기한이 지난 건은 사유 `보류 기한 지남`으로 `조치 필요`에
올라온다. 보류를 다시 저장하면 `tracking_selected_at`이 갱신되어 기한이 새로 시작한다.

**재검토 신호(2026-09-17, ADR-0030 확장).** `raise_recheck_signal`은 대상 사업기회가
`계속 추적`·`보류`·`종료` 중 하나이고 근거가 공식 확정 링크일 때 켠다 — 이전에는 `종료`에서만
켰다. `미선택`과 사람이 수락한 병합은 신호를 켜지 않는다. 같은 링크 재관측은 no-op, 다른
링크면 근거를 교체하고 감사를 남긴다. `POST /api/opportunities/{id}/recheck-acknowledgements`는
담당자가 근거 링크를 확인했다는 사실만 기록해 신호를 해제한다 — **추적 상태는 바꾸지 않는다.**
근거 링크가 이미 바뀌었으면 409로 거부하고 최신 상태를 다시 읽게 한다. 추적 상태를 다시
저장하면 그 저장이 신호를 해제하는 기존 동작도 그대로 유지한다.

### 발주계획 일괄 추적과 단건 추적

발주계획 화면의 일괄 추적은 선택한 plan ID를 서버에서 중복 제거한 뒤 authoritative
active owner만 처리한다. 미리보기는 읽기 전용이며, 저장 시 owner ID 오름차순으로 잠그고
최신 상태를 다시 확인한다. **현재 `미선택`인 owner만 `계속 추적`으로 전환**하고, 이미
`계속 추적`·`보류`·`종료`인 owner는 상태별 제외로 반환한다. 제외된 사람의 actor·reason·
시각·recheck와 기존 감사는 바꾸지 않는다. authoritative owner가 없거나 경합으로 확인할
수 없으면 실패 항목으로 남기며 임의 사업기회를 만들지 않는다.

같은 owner에 여러 plan이 연결되어도 사람 결정·감사는 owner당 한 번만 기록하고 결과를 plan
항목에 fan-out한다. 항목별 성공·제외·실패는 다른 항목을 되돌리지 않지만, 사람 감사와
최종 receipt는 하나의 transaction으로 함께 commit되어야 한다. 기존 `IdempotencyRecord`의
요청 fence로 commit 뒤 유실된 응답은 같은 request ID와 동일 payload/actor를 exact replay한다. 결과 미확인
상태에서 새 key를 자동 생성하지 않으며, 완결 receipt를 사람이 확인한 뒤 실패 plan만 새
request ID로 재시도한다. 별도 batch/job table, outbox, hook exactly-once 전달을 이 규칙이
제공한다고 보지 않는다.

이는 기존 단건 `PATCH /api/opportunities/{opportunity_id}/tracking-status`와 별도 경로다.
단건은 네 상태를 모두 받으며 `미선택` reset과 같은 상태 재선택도 기존 감사·검증 규칙대로
기록한다. 일괄 처리를 단건 PATCH 반복 호출로 대체하지 않으며 일괄 성공이 활성 행을 자동
순회하거나 단건 입력 초안을 지우지 않는다.

일괄 추적 종료는 같은 규칙으로 **현재 `미선택`인 owner만 `종료`로 전환**한다([ADR-0063](tracking/decisions/0063-order-plan-bulk-tracking-end.md)).
미리보기·공통 actor·공통 사유·확인 단계·owner당 감사 1건·request ID receipt·상태별 제외·실패 항목 규칙이 일괄 추적
시작과 같고, 한 요청은 200건까지다(PoC 값). 같은 request ID를 시작과 종료에 보내도 receipt는 작업별로 갈라진다.
`종료`한 건은 발주계획 기본 보기에서 빠지지만 삭제가 아니며 추적 필터 `종료`와 사업 추적의 `추적 종료` 구역에서 조회한다.
일괄 되돌리기는 없고 되돌림은 단건 PATCH로 한다. 일괄 보류(hold)는 제공하지 않는다.
단건 PATCH가 먼저 잠겨 비-미선택 상태로 commit되면 일괄 요청은 이를 제외하고 감사하지
않는다. 일괄 commit이 먼저 끝나면 대기 중인 단건 PATCH는 기존 규칙대로 후속 결정을
기록할 수 있으며, 이는 일괄 receipt를 다시 쓰는 동작이 아니다.

### 목록 선택과 사전규격 상세 순회

활성 행은 지금 키보드·상세 진입의 위치이고, 체크 묶음은 일괄 작업·선택 검토의 대상이다.
둘을 합치지 않는다. 두 목록의 선택은 화면별 `sessionStorage`에만 두고 같은 탭의 페이지
이동·refresh·상세 왕복에서 복원한다. 적용된 의미 필터가 바뀌면 선택과 세대를 초기화하며,
offset·정렬 변경·재조회는 선택을 유지한다. 검색어를 입력하는 중간 값은 필터 변경으로
보지 않고 실제 적용된 값만 비교한다.

사전규격 선택 순회는 진입 시점에 현재 탭이 마지막으로 관측한 목록 정렬 metadata를
`published_at` 또는 `deadline_at`과 PK로 고정한다. timezone offset과 microsecond를
보존하며 서버 전체의 새 snapshot을 주장하지 않는다. 순회 위치·건수와 양끝 경계를
표시하고, 상세가 loading·404·5xx·source/projection 오류여도 같은 항목의 오류·재시도·
이전/다음·목록 복귀를 제공한다. 오류 항목을 자동으로 건너뛰거나 체크에서 삭제하지 않는다.
상세 token이 없거나 손상되면 저장된 선택을 추정하지 않고 단건 상세로 연다.

`sessionStorage` 읽기·쓰기가 막히면 복원 가능한 일괄 작업·선택 순회를 시작하지 않고
사유와 단건 경로를 안내한다. 이 상태에서 기존 단건 상세와 단건 추적 PATCH는 계속 사용할
수 있다. 이 기능은 검색 결과 전체 선택, 현재 페이지 전체 선택, Shift 범위 선택, 일괄
보류, 모바일/태블릿, 탭·계정 동기화를 제공하지 않는다. 발주계획의 일괄 종료는 위 "발주계획 일괄
추적과 단건 추적"의 규칙으로만 제공한다.

검토는 `1차 분류`(발주계획 공고명) → `사전규격 개요 검토`(제안요청서 앞부분) → `심층 검토`(첨부 원문 전체) 순으로 좁혀 간다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)).

사전규격에 도달한 건은 개요 검토를 자동으로 수행한다. 발주계획에서 추적하기로 고른 건이 사전규격에 올라오면 바로 검토하고, 발주계획에 없던 건은 **`신규`로 명시하고** 역시 바로 검토한다. 개요 검토는 앞부분만 읽는 저비용 단계이므로 아래 금지의 대상이 아니다.

개요 검토의 입력 문서는 첨부 문서의 파일명에 `제안요청서`가 포함된 문서를 우선 자동 선택하고, 그런 문서가 없으면 `과업지시서`가 포함된 문서를 선택한다(2026-09-07 사용자 결정, 2026-09-17 갱신). 공백·Unicode 표기 차이는 정규화한다. 같은 종류(제안요청서 또는 과업지시서) 후보가 하나면 role이나 업로드 순서와 무관하게 선택하고, 후보가 없거나 같은 종류 후보가 여러 개면 `needs_human_review`로 담당자 확인에 넘긴다. 영문 `RFP`, role 지정만으로 대체하지 않는다. 아직 취득된 문서가 없으면 기존 `awaiting_document`를 유지하며, 선택한 문서의 안전성·구조 검증은 별도로 수행한다.

개요 검토의 앞부분은 [ADR-0032](tracking/decisions/0032-prespec-overview-cutting-rule.md)에 따라 정한다. 목차 항목이 본문 소제목과 대응하면 목차를 사용하고, 그렇지 않으면 의미 있는 주제 소제목을 사용한다. 번호 형식만으로 절단하지 않는다. 시작 또는 종료 위치가 모호하면 추측해 자르지 않고 `unknown`으로 남겨 사람 검토로 보낸다. 자동 추출 입력에는 사용 전략(`strategy`), `start_locator`, `end_locator`, `source_sha256`를 보존하며, 고정 block 수나 전체 문서를 개요 검토에 자동 투입하지 않는다.

범위를 정하지 못한 개요 입력은 **사람이 확정한다**([ADR-RDP-004](0910_rhwp-document-pipeline/ADR.md)). rhwp의 안전한 PDF·페이지 텍스트가 핵심 산출물이며 절 후보(`bidops.section-candidates.v1/v2`)는 참고다. 후보가 있어도 담당자는 쪽 범위를 직접 지정할 수 있고, 일부만 반환된 후보는 전체 목록처럼 사용하지 않는다. 확정은 `POST /api/pre-specs/{notice_id}/overview/range-confirmations`로 **개요 run의 범위를 정하는 것일 뿐 실행 승인이 아니다** — 담당자 이름은 감사 표식이다. 유효 본문과 함께 있는 공백 쪽은 보존하되 근거로 인정하지 않으며, 선택 범위 전체가 공백이면 `manifest_invalid`로 닫고 모델을 호출하지 않는다.

개요 검토의 상태 의미, 자동 심층 검토 진입 조건, 실행 흐름은 아래
"사전규격 개요 검토 상태 (MVP)" 절이 정본이다. v3 권고형 개요, legacy v4 단일 호출, v5
주장 검증 스택(activation v2·call ledger·verification, [ADR-0033](tracking/decisions/0033-prespec-overview-review-runtime-contract.md)·[ADR-0035](tracking/decisions/0035-prespec-overview-attempt-result-lifecycle.md)가 설계했던 attempt/snapshot 분리와 attempt별 `quality_status`)는
2026-09-11 [ADR-0054](tracking/decisions/0054-prespec-overview-mvp-rewrite.md)로 폐기했다.
새 `prespec_overview_run`에는 권고(`추진 검토|조건부 추진 검토|보류|검토 종료`)와
`quality_status` 필드가 없다.

사전규격 메타데이터는 전량 보존하지만 첨부 바이트는 조건을 만족할 때만 취득한다. 다음 중 하나이면 대상이다.

- `notice.qualification_flags_json.sw_business_status = 'Y'`인 사전규격
- 사전규격을 가리키는 `opportunity_link`가 `stage='notice'`이고 상태가 `확정`·`사람 확인 완료`·`후보 확인 대기`이며, 그 opportunity의 `tracking_status`가 `계속 추적` 또는 `보류`이고, 같은 opportunity에 `stage='order_plan'`이면서 `order_plan_id`가 있는 링크가 존재하는 경우

`검색 미확인` 링크와 `미선택`·`종료` opportunity, order-plan 링크가 없는 opportunity는 첨부 취득 자격을 만들지 않는다. 사람이 추적 상태를 나중에 선택할 수 있으므로 이 자격은 배치 한 번으로 고정하지 않고 재평가 큐에서 갱신한다. 이 조건은 수집 필터가 아니며 `SW사업대상` 표시 값의 의미도 바꾸지 않는다.

### 회사 핏 판정 (2026-09-08)

검증된 개요와 승인된 불변 회사 프로필을 대조하여 `matched`(업무 부합), `mismatch`(확인된 업무 범위와 과업의 차이), `unknown`(판단 보류)을 기록한다. 사유마다 공고 과업과 회사 구조화 항목을 연결하며, 역량·자격·실적의 미기재나 inferred/unknown 항목만으로 불일치를 만들 수 없다. 개요의 모델 의견은 회사 사실로 재사용하지 않는다. 실제 계약의 과업과 감리 대상 사업의 과업도 구분한다.

회사 핏은 자동 분석의 추가 조건이다. 기존 등급·참여 준비·추적 선택·최종 Go/No-Go를 변경하지 않는다. 개요 결과, 문서 버전, 활성 회사 프로필/심층 정책, 핏 정책·모델 배포 버전이 바뀌면 이전 핏은 현재 자동 시작에 사용할 수 없다. 새 입력은 새 attempt이고 같은 입력은 중복 호출하지 않는다. 실패/만료된 입력을 자동 재시도하지 않는다.

- 응답이 결정적 검증에 실패하면 같은 입력으로 seed를 바꾼 1회 재시도를 보내고, 보정 지시에는 실패한 검사 코드만 담는다. 두 응답을 모두 암호화 보존하고 감사에 `validation_retry`로 남긴다. 이는 한 attempt 안의 호출 재시도이며 종결된 attempt를 다시 실행하는 것이 아니다. 재시도도 실패하면 `needs_human_review`로 남기고 자동 보정하지 않는다.

기본 비활성이며 현재 품질 측정 정책이 없어 명시적인 참조 실행 모드에서만 실행한다. `matched`이더라도 mock 결과나 운영 모드에서는 자동 심층 시작을 허용하지 않는다. 참조 실행의 부합·불일치 결과와 실제 심층 검토 생성 여부는 별도로 표시한다. 근거 ID·숫자 검증 통과는 의미 정확도나 회사 적합성 품질 통과를 뜻하지 않는다.

### 자동 문서 준비와 자동 심층 시작

effective grade(사람 정정 등급이 있으면 그것, 없으면 판정 등급)가 `우선 검토`인 사전규격은 문서 준비를 자동으로 진행한다([ADR-0049](tracking/decisions/0049-prespec-auto-preparation-and-auto-deep-review.md)). 안전 검사를 통과한 현재 문서로 묶음 초안을 만들고, **자기가 만든 초안만** 확정한다. 사람이 만든 초안은 사람이 확정한다. 등급이 나중에 내려가도 이미 만든 묶음을 되돌리지 않는다. 그 밖의 등급과 등급 없음은 자동 준비 대상이 아니며 사유는 `grade_not_priority`다 — "등급 없음"을 특정 등급으로 접지 않는다. 다만 MVP 기간에 `BIDOPS_PRESPEC_OVERVIEW_ENABLED`가 켜져 있으면 자격이 "`우선 검토` 또는 `SW사업대상=Y`"로 넓어진다(2026-09-11 실사용 검증 결정). 플래그가 꺼져 있으면 완화는 없고 위 등급 규칙 그대로다. 완화는 자격만 넓히며 등급 값 자체를 만들거나 바꾸지 않는다. 같은 완화가 사람이 누르는 경로의 등급 자격 검사에도 적용된다 — 문서 묶음 생성(`POST /api/notices/{notice_id}/document-bundles`)과 심층 검토 생성(`POST /api/notices/{notice_id}/deep-reviews`)의 403 `effective_grade_ineligible`은 플래그가 켜져 있는 동안 "`우선 검토` 또는 `SW사업대상=Y`"를 기준으로 판정하며, 기록되는 등급(`effective_grade_at_start`)은 실제 값 그대로이고 등급 없음은 등급 없음으로 남는다.

촉발 지점은 셋이다. 회차 적재, 사람 정정으로 effective grade가 바뀐 시점, 첨부 취득이 한 공고에서 종결된 시점이다. **수동 업로드로 구조가 저장된 시점은 촉발하지 않는다.** 그 경우는 사람이 확정한다.

자동 준비 상태는 여덟이다. `not_applicable`(자동 준비 대상 아님), `waiting_attachments`(첨부 취득 대기), `bundle_draft`(묶음 초안), `bundle_ready`(묶음 확정), `overview_running`(개요 검토 실행 중), `deep_review_started`(심층 검토 자동 시작됨), `deep_review_ready_for_click`(심층 검토 클릭 대기), `blocked`(자동 준비 중단, 사유 `attachments_failed` — 취득 행이 모두 `차단`·`실패`로 끝나 준비된 문서가 없는 경우). `not_applicable`은 "대상이 아님"이며 "알 수 없음"이 아니다.

다음이 모두 성립하면 심층 검토를 시스템이 자동으로 만든다. 사전규격이고 `SW사업대상=Y`, 자동 준비가 확정한 `ready` 묶음이 있고, 그 묶음의 최신 개요 run이 `completed`이며, 같은 불변 입력의 심층 검토가 아직 없고, 현재 등급이 우선 검토이며 검증을 통과한 현재 회사 핏이 `matched`여야 한다. 회사 핏은 활성 설정과 참조 실행 경계도 충족해야 한다. 하나라도 어긋나면 각각의 사유 코드(`not_sw_business`, `bundle_not_auto_ready`, `overview_not_completed`, `service_unavailable`, `deep_review_exists`, `processing_failed`, `company_fit_*`)로 남기고 사람 클릭으로 넘긴다. 평가 순서는 이 목록 순서이며 첫 일치가 이긴다 — 앞의 넷은 쓰기·읽기가 같은 함수로 판정하고, `deep_review_exists`와 `processing_failed`는 실제로 만들어 보는 쓰기 경로에서만 나온다. **읽기 경로는 `deep_review_exists`를 내지 않는다.** 이미 심층 검토가 있으면 사유가 아니라 상태 `deep_review_started`로 답한다.

자동 시작은 추적 상태를 바꾸지 않는다. 사업기회는 `미선택` 그대로이고, 자동 시작이 적합성 등급·참여 준비 상태·추적 선택·최종 입찰 Go/No-Go를 대신하지 않는다. **자동으로 여는 것은 분석의 시작뿐이다.**

자동으로 열리지 않은 건은 개요 검토 결과를 읽은 사람이 심층검토 실행 여부를 선택한다. 어느 경로든 승인된 문서 묶음만 구조화·분석하고, 실패한 변환이나 검증을 성공 결과로 보정하지 않는다.

심층검토 결과에서 사람은 다음 상태 중 하나를 선택한다.

| 선택 | 의미 | 금지되는 해석 |
|---|---|---|
| `계속 추적` | 새 문서·입찰공고·정정공고를 감시하고 변경 시 다시 검토 | 최종 입찰 참여 승인 |
| `보류` | 정보나 선행 조건이 부족해 현재 결정을 미룸 | 자동 제외 또는 승인 |
| `종료` | 현재 사업기회에 대한 능동 추적을 끝냄 | 관련 신규 공고의 영구 삭제 |

`종료` 사업기회에 공식 번호로 연결되는 새 레코드가 도착하면 새 사업기회를 만들지 않고 같은 사업기회에 붙이며, 사람이 고른 `종료`를 바꾸지 않고 재검토 신호를 올린다([ADR-0030](tracking/decisions/0030-opportunity-tracking-state.md); 2026-09-17부터 `계속 추적`·`보류`도 같은 신호를 올린다 — 아래 "조치 필요·신규 입찰공고 구역과 보류 재검토" 참조). 공식 번호가 없는 비슷한 공고는 원문을 버리지 않으며 사람 확인 후보로만 제시할 수 있다.

## 입찰공고 전환

`계속 추적`인 사업기회에 입찰공고가 연결되면 사전규격 문서와 입찰공고 문서의 금액, 계약기간, 참가자격, 공동수급, 평가방식, 배점, 제출물, 제출기한, 요구사항 변경을 비교한다. 비교할 문서 버전이나 연결이 불확실하면 `변경 없음`으로 추정하지 않고 사람 확인으로 보낸다.

중요한 변경이 있으면 새 문서 묶음과 새 분석 시점을 가진 리포트를 만든다. 사전규격 리포트의 문장·근거·사람 의견을 수정하지 않는다. 변경이 없으면 비교한 양쪽 버전과 확인 범위를 남긴다. 시스템은 이 결과를 자동 제출이나 발주기관 연락으로 연결하지 않으며 최종 Go/No-Go는 사람이 결정한다.

R-07의 상세 계약은 [ADR-0034](tracking/decisions/0034-bid-delta-final-decision.md)로 채택했다.
아직 backend·DB·production UI는 구현되지 않았으며 다음 안전 경계를 R-08이 그대로 구현한다.

- 비교는 ready bundle에 고정된 기준·비교 document version, structure, source/payload hash를
  저장한다. live 첨부나 mutable current pointer로 과거 비교를 다시 해석하지 않는다.
- 동일 사업기회에 사전규격·입찰공고·정정이 여러 개면 exact pair를 명시한다. 서버가
  `latest`를 추정하지 않고 새 문서는 새 비교 후보로 보존한다.
- 계산 상태 `pending|running|completed|failed`와 결과 상태
  `changed|unchanged|unknown|failed`를 분리한다. 아직 계산하지 않음, 계산 실패, 판단 불가를
  변경 없음으로 바꾸지 않는다.
- `changed`와 `unchanged`에는 기준·비교 양쪽 원문 locator가 필요하다. 한쪽 근거를 검증할
  수 없으면 `unknown` 또는 `failed`다.
- 최종 입찰 결정은 actor, reason, request ID, 비교 version·result digest·양쪽 document
  version fence를 가진 append-only 사람 기록이다. 새 결정은 과거 결정을 수정하지 않는다.

**결정 근거 분리(2026-09-17, [ADR-0058](tracking/decisions/0058-final-decision-basis-separated-from-comparison.md)).**
비교를 실제로 계산하는 worker는 여전히 없으므로, 최종 결정은 완료된 문서 비교가 **없어도**
기록할 수 있다. 근거는 `comparison`(위 비교 fence) 또는 `notice_conditions`(입찰공고 조건)
둘 중 하나이며 한 행은 한 근거만 갖는다. 공고 조건 근거는 수집기가 이미 정규화한 결정적 값
(금액·마감·개찰·자격·지역 제한·정정 사유 등)을 모델 호출 없이 차수 순으로 비교하고, 담당자가
확인한 정확한 공고·관측에 fence를 건다(다른 차수나 바뀐 관측으로는 저장되지 않는다). 두 근거는
같은 actor·사유·idempotency·supersession 규칙을 공유하고 결정 큐·현재성도 근거와 무관하게
같은 규칙으로 계산한다. 비교 근거 결정에 관한 위 규칙(계산 상태 분리, `changed`/`unchanged`의
양쪽 locator 요구, 원문 role allowlist)은 바뀌지 않는다.

최종 결정은 `go|no_go`다. material 범주는 금액·경제성, 계약기간·일정, 참가자격,
공동수급·하도급, 과업·요구사항, 평가, 제출의 7개다. v1은 근거 없는 수치 임계값을 두지
않고 공식 값·조건의 실질 변경을 `material`, 양쪽 근거로 의미가 같은 표기·서식 차이만
`non_material`로 둔다. 불확실·검증 실패는 `unknown|failed`로 보존한다.

새 authoritative 입찰공고·정정 또는 새 ready 비교 문서가 생기면 기존 최종 결정 row는
그대로 두고 strict currentness projection을 즉시 `stale`로 만든다. 순서·효력이 불확실하면
`unknown`이다. 비교 모델은 회사 내부망의 allowlist된 사설 vLLM만 사용하고 exact
snapshot의 비교 생성 요청을 건별 처리 승인으로 감사한다. 외부·hosted fallback은 없으며
감사 metadata에는 안전한 ID·code·count·hash·binding digest만 남긴다.

## 후보 선정과 현재 1차 판정

세 우선 축 `AI/데이터`, `블록체인·DID`, `공공 SI·통합관리`는 동등하다. 예산, 지역, 업종, 실적 요건이 확인되지 않았다는 사실만으로 자동 제외하지 않는다. 제목·조달 분류·수행실적 유사도는 후보 편입 신호이지 적합성의 확정 근거가 아니다.

후보에 들지 않은 공고는 부적합 정답이 아니다. 조달 분류 근접, 수행실적 유사도 임계값 근접, 무작위 층에서 감사 표본을 뽑는다. 감사 표본에서 `제외`가 아닌 판정이 나오면 누락으로 집계하고 정책 변경 제안의 근거로 쓰되 한 사례만으로 기준을 자동 변경하지 않는다.

1차 판정은 `기술 적합성`, `실적 정합성`, `공공 SI 적합성`, `사업성·자격 제약`, `전략 부합`을 정확히 한 번씩 가져야 한다. 각 관점에는 관점 고유의 이유와 최소 하나의 근거가 있어야 하며 근거 상태는 `confirmed`, `inferred`, `unknown` 중 하나다. 회사 프로필의 `unknown`을 모델 추론이나 외부 상식으로 `confirmed`로 올리지 않는다.

등급과 참여 준비 상태는 독립적으로 계산한다. 적합성이 높고 자격이 미확인이면 `우선 검토`와 `부분 확인 필요`가 함께 올 수 있다. 미확인 자격만으로 등급을 내리거나 높은 등급만으로 준비 상태를 `확인 완료`로 올리지 않는다.

| 조건 | 허용 결과 | 금지 결과 |
|---|---|---|
| 등급이 `제외` | 준비 상태 `해당 없음` 또는 `참여 불가 확인`, 제외 사유 필수 | `확인 완료`, 제외 사유 누락 |
| 등급이 `제외`가 아님 | 제외 사유 `null` | 제외 사유 문자열 유지 |
| 준비 상태 `부분 확인 필요` | 미확인 항목 최소 1개 | 확인 항목 없는 부분 확인 |
| 준비 상태 `확인 완료` | 차단성 미확인 항목 0개 | 차단 항목을 남긴 확인 완료 |
| 준비 상태 `참여 불가 확인` | 확인된 차단 항목 최소 1개 | 막는 근거 없는 참여 불가 |

`사업성·자격 제약`이 `확인 불가`인데 종합 등급이 `관찰 대상` 또는 `제외`이면 `two_axis_mixing_flag=true`, `two_axis_mixing_label=확인 요망`을 남긴다. 이 표시는 판정 실패가 아니며 등급·준비 상태를 자동 수정하거나 모델을 재호출하지 않는다.

수행실적 유사 신호가 있으면 연결된 실적마다 대응 이유와 설명되지 않는 차이를 기록한다. 법적 실적 인정 여부가 확인되지 않았으면 `unknown`을 유지한다.

## 불변 회차와 재판정

회차는 수집 구간, 원문, 정책, 프롬프트, 모델, 프로필, 생성 설정을 고정한 스냅샷이다. 같은 기간을 새 규칙으로 다시 처리하면 새 실행 식별자를 만들고 이전 회차를 수정하지 않는다. 새 회차에 필요한 판정이 없으면 완성된 이전 회차를 최신 유효 회차에서 밀어내지 않는다.

사용자가 선정 기준·가중치·프롬프트를 바꾸면 새 정책 버전을 만든다. 변경은 이후 시작하는 실행에만 적용한다. 과거 결과를 새 기준으로 비교하려면 새 회차를 명시적으로 실행한다.

정정, 재공고, 사전규격에서 본공고로의 전환처럼 확인된 생애주기 변화가 있으면 재판정한다. 동일 값이 다시 수집된 것만으로 재판정하지 않는다. 이전 값이 없거나 비교할 수 없으면 변경 없음으로 추정하지 않고 사람 검토로 보낸다.

변화가 없으면 검증된 기존 판정을 모델 호출 없이 현재 회차로 승계할 수 있다. 승계는 최초 판정 회차와 원래 모델·프롬프트·정책·프로필 식별자를 보존하고 현재 기록 회차를 별도 필드에 남긴다. 과거 판정이 현재 결정적 검증을 통과하지 못하면 승계하지 않고 사람 검토 대기로 보낸다.

## 심층검토 입력과 판단

HWP 원본은 그대로 보존하고 HWP 분석에는 검증된 HWPX 변환 결과를 사용한다. 변환 실패 또는 구조 손실 검증 실패 시 원본 HWP를 모델에 직접 넣지 않고 `변환 확인 필요`로 보낸다. 이미 HWPX인 문서는 변환 없이 정본이 되며 PDF는 추출 결과와 원본 위치의 대응을 검증한다.

문서 묶음은 파일명, 해시, 획득 출처, 객체 버전, 변환기 버전, 변환 시각을 가진다. 같은 파일명이더라도 해시가 다르면 새 문서 버전이며 기존 분석을 덮어쓰지 않는다. **원본의 정체는 해시와 크기이지 이름이 아니다.** 첨부 목록의 이름(나라장터 메타데이터에서는 흔히 `첨부 1` 같은 자리표시자다)과 취득 응답 header가 준 실제 파일명이 다른 것은 정상적인 관측이므로 비차단 경고 `source_name_differs`(severity 보통)로만 남긴다. 원문 크기·해시·provider source snapshot이 어긋나는 경우는 그대로 차단(`source_changed`·`source_hash_mismatch`)이다.

| 평가 영역 | 필수 확인 | 근거가 부족할 때 |
|---|---|---|
| 입찰 자격과 참여 구조 | 업종·면허, 기업 규모, 지역, 실적, 공동수급, 하도급, 보안·인력 증빙, 마감 | `충족`으로 쓰지 않고 차단 여부·확인 주체·기한을 남김 |
| 과업과 요구사항 | 구축·운영 범위, 제외 범위, 산출물, 검수, 요구사항 ID | 누락·중복·모순을 원문 위치와 함께 표시 |
| 평가 전략 | 기술·가격 배점, 정량·정성, 발표·시연, 감점·실격 | 배점 합계와 제출물을 코드로 다시 계산 |
| 수행 가능성 | 기간, 인력, 선행 의존성, 이관, 교육, 안정화, 유지보수 | 입력 없는 인월·일정을 생성하지 않음 |
| 기술·보안·법무 위험 | 연계, 데이터, 비기능, 개인정보, 망분리, 권리, 위약 | 문서상 의무·미확인·전문 검토 필요를 구분 |
| 사업성 | 예산, 원가, 지급·검수, 보증, 제안 비용, 파트너 | 회사 마진이나 비용을 임의 생성하지 않음 |
| 경쟁·제안 전략 | 발주 배경, 차별점, 예상 평가 초점, 레퍼런스 | 원문 사실과 전략 추론을 분리하고 반대 근거를 포함 |

문서 구조를 저장할 때 결정적 segment manifest와 요구사항 inventory를 함께 만든다([ADR-0051](tracking/decisions/0051-deep-review-v2-deterministic-subset.md)). segment는 네 taxonomy label(`business_eligibility_evaluation`, `technical_functional`, `quality_security_constraints`, `partnership_governance`)로 분류하며 **분류 출처는 `deterministic` 고정, `confidence`는 언제나 `null`**이다. 결정적 규칙에는 확률이 없으므로 경계를 정하지 못한 자리는 확률을 지어내지 않고 `needs_human_review` 상태로 남긴다.

심층 검토 검증에 결정적 check 두 종을 더한다. `requirement_inventory`는 문서가 준 요구사항 ID 집합과 claim이 적은 ID 집합을 대조해 누락·예상 밖 ID를 실패(중대), 중복을 warning, ID 체계가 없는 문서를 warning "inventory 없음"으로 남긴다. `segment_coverage`는 간극·중첩을 warning(보통)으로 표시하되 차단하지 않는다. **문서에 ID 체계가 있는데 claim이 ID를 적지 않으면 `requirement_inventory`가 실패한다.** 요구사항 전수성은 형식 완결성으로 대신할 수 없다.

심층 검토 실행에도 품질 표식 `quality_status`가 붙는다. `measured`는 측정값이 활성화 게이트를 통과했다는 뜻이고, `unmeasured_reference`·`mock_reference`는 참조 실행이며, 표식이 없던 시절의 실행은 `null`(표식 없음)이다. **없음을 미측정이나 측정으로 승격시키지 않는다.**

요구사항 대응 상태는 `대응 가능`, `추가 확인`, `갭`, `해당 없음` 중 하나다. 위험은 `차단`, `중대`, `보통`, `낮음`으로 표시하고 근거, 영향, 확인·완화 행동, 담당 역할, 기한, 잔여 위험을 가진다. 정보가 없으면 항목을 삭제하지 않고 `산정 불가`와 필요한 자료를 남긴다.

사전규격 개요 검토는 권고를 만들지 않는다(2026-09-11 MVP 재작성, 위 "사전규격 개요 검토 상태 (MVP)" 절 참조). `completed` 개요 run의 구조화 결과(business_overview·main_tasks·budget_and_period)가 심층 검토 입력의 참고 자료이며, 이 결과와 사람이 고른 `계속 추적`은 최종 입찰 참여 승인이 아니다.

## 근거와 검증

모든 수치, 자격 조건, 요구사항, 배점, 일정, 위험 근거는 문서 파일과 페이지·절·표·요구사항 ID 중 가능한 가장 구체적인 위치를 가진다. 인용 위치에서 내용을 찾을 수 없으면 `미검증`이며 확정 사실에 포함하지 않는다.

결정적 검증은 요구사항 ID 유일 개수·중복, 금액·기간·배점 산술, 필수 분석 영역, 자격 판정 모순, 원문에 없는 수치, 인용 위치 존재를 확인한다. 실패 결과는 자동 승인하거나 문장을 고쳐 통과시키지 않고 실패 항목과 함께 사람 검토로 보낸다.

모델·프롬프트·정책의 품질 게이트는 고정 40건을 A/B로 독립 실행한다. 최종 등급 재현성은 80% 이상, 한 관점의 불일치 집중은 50% 이하, `우선 검토` 비율은 유효 10건 이상에서 10~25%, 사람 근거 동의는 70% 이상, 근거 부족은 10% 이하, 관점 분할은 40% 이상이어야 한다. 계산 불가·미측정·불완전 표본은 통과가 아니다. 비교 목적의 역사 프로필과 운영 승인 목적의 현재 프로필을 섞지 않으며 통과만으로 정책이나 상시 실행을 자동 활성화하지 않는다.

## 리뷰와 개선

리뷰 작성자의 이름은 감사 귀속용이며 신원 인증이 아니다. 이름이 같다는 이유로 권한이나 실제 신원을 보장하지 않는다.

피드백은 `1차 판정 품질`, `심층 리포트 품질`, `실제 사업 결과`, `사용자 경험·처리 흐름`으로 구분한다. 등급 수정과 근거 부족은 공고·회차·정책 버전에 연결하고 실제 결과는 참여 여부·제안 결과·실패 원인처럼 사후 확인 가능한 사실을 기록한다.

피드백과 발주계획 선별 실험은 변경 제안을 만들 수 있지만 선정 기준, 회사 프로필, 프롬프트, 모델 설정을 자동 변경하지 않는다. 담당자가 제안을 검토하고 승인하면 새 불변 정책 버전으로 이후 실행에만 적용한다.

## 발주계획 C-2 선별 상태 규칙

C-2는 기존 공고의 적합성·참여 준비 판정과 별도의 relevance 흐름이다. Phase 0의 고정
정의와 machine-readable schema는 [`docs/contracts.md`의 C-2 계약](contracts.md#c-2-phase-0-fixed-contract)과
`skills/bidops-screen/contracts/`를 따른다.

- 전체 `bidops.collected-order-plans.v1` 회차를 먼저 검증한다. `metadata.collection.complete=false`,
  warning, count 불일치, raw record hash 불일치는 실행 거부다. 원본 JSON·raw page·정규화
  projection은 기존 회차 디렉터리에서 덮어쓰지 않는다.
- 현재 정책은 전체 제목을 NFKC·casefold·공백 축약 후 BM25로 계산하고 score 내림차순,
  `order_plan_unty_no` 오름차순으로 tie-break한다. Top 300은 `selected`, 나머지는
  `filtered_out`이며 탈락을 `not_relevant`라고 기록하지 않는다. 300건 이하 규칙은
  select-all까지 문서화했지만 탈락 감사 표본은 사람 승인 전까지 비활성이다.
- Qwen은 Top 300만 25건의 rank-contiguous batch로 순차 전송한다. 승인된 private vLLM,
  정확한 model/prompt/profile/BM25 digest와 허용 payload를 모두 일치시켜야 하며 hosted
  fallback은 없다. retryable failure만 최대 2회 재시도하고, binding·model·payload·policy
  거부는 재시도하지 않는다.

상태의 의미는 다음과 같다. 하나의 상태가 다른 축의 결론을 대신하지 않는다.

| 상태 | 의미 | 보존 규칙 |
|---|---|---|
| `filtered_out` | deterministic Top 300 밖 | relevance 음성이나 적합성 제외로 바꾸지 않음 |
| `relevant` / `not_relevant` | Qwen 또는 사람의 relevance label | 등급·준비·추적·Go/No-Go로 승격하지 않음 |
| `uncertain` | relevance 확인 보류 | 기본 사람 검토 목록에 남김 |
| `unknown` | 정보 부족·결과 결정 불가 | 성공·비관련으로 보정하지 않음 |
| `null` | 해당 field가 미시도 또는 비적용 | unknown·failed의 동의어가 아님 |
| `failed` | 실행된 단계의 timeout·transport·schema 등 실패 | failure type/code와 사람 검토 필요를 남김 |
| `rejected` | preflight·binding·payload·policy 검증 거부 | 모델 결과나 `not_relevant`를 만들지 않음 |

실행 상태는 `대기 → 실행 중 → 성공|부분 성공|실패`, `실행 중 → 중지 요청 → 중단됨`,
`대기 → 중단됨`만 허용한다. terminal 상태는 종료 시각을 갖고, active slot은 1이다. stale
또는 process interruption은 자동 재개하지 않고 성공 subset·failure artifact를 보존한 뒤
사람이 새 execution으로 재시작한다. 사람 feedback은 execution·plan별 append-only revision
이며 `relevance=관련|비관련|판단보류`에 대응하는 machine 값과 `priority=높음|보통|낮음|null`,
메모를 기록한다. 이 feedback은 `grade`, `readiness`, `tracking_status`, final `go_no_go`를
변경하지 않는다.

현재 policy와 binding은 `blocked`, validator는 `valid_but_blocked`를 반환한다. C-1 gold
manifest는 `partially_human_adjudicated`이며 사람 22건, draft 603건, 잔여 확인 87건이다.
잔여 gold를 사람 완료로 추정하거나 품질 gate를 통과로 표시하지 않는다. 감사 표본 크기·
주기, 승인 gold 기반 quality threshold, execution별 private vLLM 전송 승인이 채워지기
전에는 policy를 active로 바꾸지 않는다. `계속 추적|보류|종료`와 사람 최종 Go/No-Go는
여전히 별도 생애주기·입찰 결정 이벤트다.

## 사전규격 개요 검토 상태 (MVP)

2026-09-11 [ADR-0054](tracking/decisions/0054-prespec-overview-mvp-rewrite.md)로 v3
권고형 개요, legacy v4 단일 호출, v5 주장 검증 스택(activation v2·call ledger·
verification)을 폐기하고 `prespec_overview_run` 단일 테이블로 다시 썼다. 첨부 취득·묶음·
자동 준비·문서 변환·PDF/쪽 텍스트 스냅숏과 주장 결정적 검증 함수는 그대로 유지한다. 상세
wire·DB 계약은 [contracts.md](contracts.md#사전규격-개요-검토-mvp-2026-09-11)가 정본이다.

### 상태 의미

| status | 뜻 | 자동 심층 검토 |
|---|---|---|
| `queued` / `running` | 대기·실행 중 | 대기 |
| `completed` | 모든 결정적 검사·의미 검토 통과, 결과 있음 | 진행 가능 |
| `needs_human_review` | 인용 불일치·주장 0개(`claims_empty`)·의미 검토 미확정 | `overview_not_completed` |
| `failed` | 기술 실패(변환·형식·용량·timeout 등) | `overview_not_completed` |
| `cancelled` | `BIDOPS_PRESPEC_OVERVIEW_ENABLED`가 꺼져 닫힘 | `overview_not_completed` |

공고의 "현재 개요"는 생성 시각이 가장 최신인 run이다. 이력은 그 공고의 모든 run이며 새
run이 이전 run의 결과를 덮어쓰지 않는다.

개요 run의 자동 enqueue 자격은 자동 준비와 **같은 판정**이다. `BIDOPS_PRESPEC_OVERVIEW_ENABLED`
가 켜져 있으면 effective grade `우선 검토` 외에 `SW사업대상=Y` 사전규격도 자격을 갖는다
(2026-09-11 MVP 완화). 이미 적재된 공고를 이 규칙으로 한 번에 태우는 것은
`python -m app.deep_review.cli prepare-overviews --all-eligible`이며, 그 명령도 묶음 준비까지만
하고 모델은 부르지 않는다.

### 자동 심층 검토 사유 판정 순서

`not_sw_business → bundle_not_auto_ready → overview_not_completed → service_unavailable →
회사 핏 사유` 순으로 평가하며 첫 일치가 이긴다. `overview_recommendation_closed`·
`overview_bundle_mismatch`는 새 개요 run에 권고 필드 자체가 없으므로 삭제했다.

### 개요가 만드는 것 (2026-09-16)

개요 검토는 공고 **앞부분의 목적·내용·기간·금액만** 읽어 요약한다. 결과는 세 절
`business_overview`·`main_tasks`·`budget_and_period`뿐이며 참여 조건, 검토 의견, 미확인 판정은
개요가 내리지 않고 심층 검토가 소유한다([ADR-0057](tracking/decisions/0057-overview-scope-and-company-fit-in-deep-review.md) 결정 1).
`important_conditions`·`reviewer_analysis`·`unknowns`는 결과에서 **key 자체가 빠졌다** — 빈
배열로 남기면 "검토했는데 없었다"로 읽히기 때문이다. 선택 범위에 예산·기간이 없어 절이 비면
run의 `warnings`에 `section_empty:<section>`을 남긴다.

### 검증 규칙: 경고와 사람 검토를 구분한다

주장별 정확한 인용 대조(원문 한 곳에 유일하게 대응하는지)는 실패하면 **사람 검토로
보낸다**(`needs_human_review`). 2단(두 열) 편집 쪽처럼 원문에서 인용이 연속하지 않으면 줄·
리스트 표식·생략 기호(`…`·`...`) 조각으로 나눠 각 조각이 한 곳에 순서대로 대응할 때만
통과시키고 경고 `evidence_fragment_match`를 남긴다. 한 주장의 인용이 둘이고 **하나만**
대조에 실패하면 그 인용만 빼고 주장은 통과하며 경고 `evidence_dropped`를 남긴다 — 인용이
모두 실패하면 종전대로 그 주장이 빠진다. 섹션 배정(business_overview·main_tasks·
budget_and_period)의 쏠림은 2026-09-11부터 경고 `required_fact_missing`이며
차단하지 않는다. 수치·단위·역할·VAT·기산점·날짜·라틴 표기·requirement_id 대조의 불일치도
**경고**(`warnings`)로만 남긴다. 주장이 한 개도 없으면(`claims_empty`) attempt 전체가
`needs_human_review`로 끝나며 결과는 없다. 검증 실패를 자동 보정하지 않는다.

의미 검토 입력에는 기대 주장 ID 목록과 개수를 명시하고 응답 schema의 `checks` 길이를 그 run의
실제 주장 수로 못박는다. 응답에 기대 ID가 **모두 정확히 한 번씩** 있으면 그 밖의 항목은 무시하고
경고 `semantic_extra_ids`를 남긴다. 누락(`semantic_missing_ids`)·중복(`semantic_duplicate_ids`)·
schema 위반(`semantic_schema_invalid`)은 계속 `failed`이며 그 사유 코드가 run에 남는다.

### 부분 완료 규칙 (2026-09-11, 2026-09-16 갱신)

결정적 검사에 **실패한 주장은 결과에서 빼고 나머지로 계속 간다.** 통과한 주장이 1개 이상이고
전체 주장의 절반(`ceil(n/2)`) 이상이면 의미 검토·구성을 거쳐 `completed`가 되고, 그 미만이면
예전처럼 `needs_human_review`(`deterministic_check_failed`)로 끝난다. 12개 중 1~2개만 인용이
어긋난 run을 통째로 사람 검토로 보내지 않기 위한 규칙이다. 빠진 주장은 `failed_claims`로 계속
노출하고 run의 `warnings`에 `claims_dropped`가 남는다.

주장의 `contradicted`·`insufficient`는 그대로 attempt 전체를 `needs_human_review`
(`semantic_review_failed`)로 보낸다.

미검증 문장은 여전히 게시되지 않는다. 빠진 주장과 빠진 인용은 `result_json`에 들어가지 않으며,
결과에 남는 문장은 모두 인용 대조와 의미 검토를 통과한 것이다.

### fallback 범위 규칙

자동 선택은 목차를 먼저 본다(ADR-0057 결정 2). 앞 5쪽에서 "제목 … 쪽번호" 항목이 4개 이상인
쪽을 목차로 읽고, 첫 level-1 항목의 제목을 본문에서 찾아 인쇄 쪽과 물리 쪽의 차이를 구한다.
두 장 이상이 같은 차이를 낼 때만 정렬을 확정하며, 확정하면 개요 키워드가 있는 첫 장(없으면 첫
장)부터 다음 장 직전까지가 범위다(`strategy=toc_scope`). 정렬을 확정하지 못하면 추측하지 않고
본문 heading 선택기로 내려간다. 그 사유(`toc_missing`·`toc_alignment_failed`·
`toc_target_missing`)는 본문 선택이 성공하면 남기지 않고, 최종적으로 fallback이나 사람 검토로
갈 때만 본문 사유 뒤에 덧붙인다. 본문 선택기는 로마숫자 표식과 다음 줄 제목이 갈라진 조판을
한 장으로 읽고, `제안서 작성 안내`류 헤딩 뒤의 장은 발주처 사업 범위가 아니므로 시작 후보에서
뺀다.
목차로 확정한 범위에는 아래 최소 크기 규칙을 적용하지 않는다.

결정적 heading 선택기가 범위를 정하지 못하면 실패가 아니라 1쪽부터
`min(60쪽, 100,000자)`까지를 `range_fallback_head` 사유로 자동 선택한다(`range_source=fallback`).
본문 선택기(`strategy=heading_scope`)의 자동 선택이 2쪽 미만이거나 1,500자 미만이면 목차·표제만
고른 것으로 보고 `range_too_small`을 남기고 같은 fallback을 탄다. 반대로 자동 선택이 60쪽·100,000자를 넘으면 버리지 않고 시작
쪽부터 상한까지 잘라 쓰며 `range_clipped_to_limit`를 남긴다(`range_source=auto` 유지).
선택 범위 전체가 공백이면 모델을 호출하지 않고 `failed/manifest_invalid`로 닫는다. 사람이
`POST /api/pre-specs/{notice_id}/overview/range-confirmations`로 직접 쪽 범위를 확정하면
`range_source=human`이 되고, 확정은 개요 run의 범위를 정하는 것일 뿐 실행 승인이 아니다.

### 설명형 심층검토 v2의 해석 (2026-09-22)

새 정책의 보고서에서도 시스템 권고, 사람의 심층검토 의견, 추적 선택, 최종 입찰 Go/No-Go는 별도다. `not_analyzed`와 근거의 `unknown/unsupported/conflicting`을 사업 위험 없음·회사 역량 미달·확정적 불가로 변환하지 않는다. 재분석 중/실패에 이전 보고서를 조회할 수 있지만 그것이 새 실행의 완료를 뜻하지 않으며, 현재 실행 완료 전 수정·의견 저장 gate는 유지한다. 품질 표식은 기존 규칙을 그대로 따른다. 상세는 [v2 계약](contracts.md#심층검토-설명형-보고서-v2-2026-09-22-선택형-poc).

표기 차이만으로 분석 전체를 중단하지 않는다. 공백·따옴표 등의 인용 표기는 원문으로
연결하고 동일한 원화 금액은 단위 환산을 인정한다. 축약 연도의 세기 해석은 보고서를

현재성은 활성 binding(graph/profile)+문서 집합/bundle/개요+정책/model/generation 전체 일치로 판정하고, 옛 결과는 `is_current=false`로 보존하며 다른 회사 결과로 채우지 않는다. 승인된 실행은 이후 버전 변경에 영향받지 않고, 승인 후 bundle이 교체되면 worker가 호출 전에 `bundle_not_ready`로 실패하며 재시도는 새 preview·승인이다. 실패 결과는 사람 검토로 남기고 자동 보정·자동 재호출하지 않는다. 모든 회사 결과는 `unmeasured_reference`다.

## 회사 근거 사실 상태 (RL-00, 2026-10-16)

루트랩 실회사의 근거는 회사 파일을 정본으로 등록한 불변 버전이다(계약은 [DEMO 계약 RL 개정](work/demo-contract.md#rl-개정-2026-10-16-rl-00-adr-0073)). 실회사는 DB 전체에서 1곳이고 가상회사는 `BIDOPS_DEMO_ENABLED=true`에서만 등록한다.

- **사실 상태는 네 값이다.** 화면 이름과 대응은 다음과 같다.

  | status | 화면 이름 | 뜻 | pill |
  |---|---|---|---|
  | `confirmed` | 확인됨 | 출처가 있고 사람이 확인한 사실(회사소개서·홈페이지·인터뷰·사용자 확인 선호) | success |
  | `proposed` | 추정값 | 에이전트가 제안한 값, 사람이 아직 확인하지 않음 | blue(ADR-0048 개정: 이 pill만 blue) |
  | `unknown` | 확인 필요 | 문서에 없거나 미입력. 값 null·근거 0개 | warning |
  | `inferred` | (표시 안 함) | 모델 추론 전용. 등록 파일에는 없다 | — |

- `proposed`(에이전트 제안)와 `inferred`(모델 추론)를 한 값에 섞지 않는다. `proposed`는 origin `agent_proposal`에서만 나오며 사람이 확인하면 새 버전에서 `confirmed`로 바뀐다.
- **`proposed`는 차단 조건도 판정 근거도 아니다.** 추정값은 "확인 필요"와 같이 근거로 쓰지 않고(충족 근거 금지), 그렇다고 `부족`으로 승격하거나 그것만으로 공고를 막지도 않는다(HP 계약 §7의 `unknown` 규칙과 같다). `proposed`의 evidence는 확인 근거가 아니다. 판정·전송 쪽 고정은 RL-03 spec이 하며, 현재 `company_knowledge_retrieval.py`·`company_fit_policy.py`는 `proposed`를 모른다 — 실회사 binding이 활성화돼도 회사 핏·심층 경로는 demo off에서 닫혀 있다.
- **보유와 세부는 상태를 분리한다.** "자격 있음, 세부 미입력"은 `confirmed` 노드(`{held:true,detail:null}`)와 별도 `unknown` 세부 노드로 둔다. 세부 미입력을 부족이나 미보유로, 보유 확인을 세부 확인으로 읽지 않는다. 명시되지 않은 값은 0이나 "해당 없음"으로 채우지 않는다.
- "곧 만료"는 qualification `valid_until`이 있고 오늘부터 `BIDOPS_COMPANY_EXPIRY_WARNING_DAYS`(기본 60일) 안이거나 이미 지난 사실이다(지난 것은 행에 "만료됨"으로 표시하며 수치에서 빼지 않는다). 유효기간이 없는 사실은 만료 후보가 아니다.
- **회사 근거 화면은 읽기 전용이다.** 값 수정·확정은 화면 행동이 아니라 회사 파일을 고쳐 다시 등록(새 버전, 이전 버전 불변)하는 절차다([operations.md](operations.md) "회사 근거 갱신"). 등록은 자동 활성화하지 않고 활성화는 명시적 CLI다.

## 브리핑 추천·반응 (RL-01, 2026-10-17)

평일 아침 한 번, 담당자가 먼저 볼 후보를 결정적 규칙으로 고른다. LLM을 부르지 않는다(Luna 정책 발행은 RL-03). 계약은 [contracts.md "브리핑"](contracts.md), 기능 명세는 `docs/work/groups/RL/features/RL-01-daily-briefing/spec.md`다.

- **모집단과 창.** 브리핑 1건은 `briefing_date`(KST 평일) 하루 1건이며 재생성·삭제가 없다(수정은 다음 날 브리핑). 후보 창은 (직전 브리핑 `generated_at`, 지금]이고 직전 브리핑이 없으면 D-1 00:00 KST부터다. 창 안에서 **처음 관측된** 레코드만 후보이며(`min(NoticeObservation.observed_at)`·`OrderPlan.first_discovered_at`) 이미 어느 브리핑의 항목인 공고·발주계획은 다시 추천하지 않는다. 후보 stage는 셋이다 — 사전규격(SW사업대상 `Y`, 검토 제외 아님), 입찰공고(마감이 지금 이후, 검토 제외 아님), 발주계획. 소유 사업기회가 없는 후보는 항목을 만들지 않고 경고 `orphan_candidate`로 센다.
- **발주계획은 "반복 발주처 ∧ 유사 실적"일 때만 든다.** C-2 최신 결과가 `relevant`인 발주계획 중 `repeat_agency`와 `similar_project`가 **둘 다** 참인 것만 후보다. relevant 전부를 넣지 않는다(연차 사업 예고 전용, ADR-0073 결정 3). 하나만 참이면 후보가 아니다.
- **회사 사실은 `confirmed`만 읽는다.** 규칙은 RL-00 활성 그래프의 `status=confirmed` 사실(분야 tier·키워드, 제외 조건, 금액 하한·범위, 단독 상한, 선호 기관, 과거 사업)만 쓴다. `proposed`·`unknown`·`inferred`는 점수에도 제외에도 쓰지 않고 — 키워드가 `proposed`뿐인 분야는 점수 0이다 — `unknown`을 차단 근거로 승격하지 않는다(ADR-0073 결정 6). 확정 사실을 받지 못하면 브리핑을 만들지 않고 `company_not_registered`로 끝낸다. 0건 브리핑으로 접지 않는다.
- **제외가 먼저고 한 사유로만 센다.** 제목·기관·수요기관을 이은 정규화 텍스트(NFKC·구분자·공백 제거·casefold)에 제외 키워드(`hardware`·`election`·`design_only`·`staffing_only`)가 있으면 제외한다. 지역 제한(`region`) 제외는 **보류한다**(2026-10-17 사용자 결정). 수집한 `region_limit_json.basis`는 "본사소재지" 같은 소재지 판단 기준이고 공동도급 지역은 의무 지역이라, 참가 가능 지역 이름을 알 수 없다. 모르는 값으로 공고를 빼지 않으므로 `excluded.region`은 항상 0이다. 루트랩 v2의 허용 지역(`excl:region.keywords` = **대구·세종**, [RL-00 증거 README v2](validation-runs/2026-10-16-rl/RL-00/README.md))은 참가 가능 지역 수집이 생기면 쓸 값으로 남긴다([findings](tracking/findings.md) 2026-10-17). 금액 하한(`amount_floor`)은 `estimated_price`(없으면 `budget`)가 있고 `pref:amount_floor`보다 작을 때이며 금액이 둘 다 없으면 제외하지 않는다. 한 후보에 사유가 여럿이면 `hardware → election → design_only → staffing_only → region → amount_floor` 중 앞선 하나로만 세어 `excluded` 합이 제외 후보 수와 같다. 발주계획은 지역 정보가 없어 `region`을 적용하지 않는다.
- **점수와 정렬.** 점수 = 분야 tier 최고 1개 가중치(30/20/10) + `repeat_agency`(기관 필드가 선호 기관명과 정규화 동일) 25 + `similar_project`(과거 사업명의 길이 6 이상 조각이 후보 텍스트에 부분문자열로 있음) 25 + `sw_target`(사전규격 `Y`) 10 + `amount_in_range`(금액이 선호 범위 안) 10이다. 가중치와 상위 N(10)은 immutable 규칙 파일에 있다. 동점은 마감 오름차순(마감 없음은 뒤), 다음 `first_observed_at` 오름차순이다. **점수 0은 항목에 넣지 않고** 상위 N만 `recommendation`이 된다. 같은 입력은 같은 결과다.
- **이유와 차단 조건은 규칙이 만든다.** 이유 칩(최대 3)은 첫 hit 키워드·유사 사업 수·반복 발주처 순서다. 차단 조건(최대 2)은 금액이 `min(단독 상한, 20억)` 이상이면 "컨소시엄 검토", 마감이 7일 이내면 "마감 n일"뿐이다. 지역·HW 등은 제외 조건이라 차단 조건에 나오지 않는다. 판정 표시(`verdict_display`)는 지금 사전규격·입찰공고 `분석 대기`, 발주계획 `연차 추적`, 추적 변화 `재검토 중`, 마감 알림 사유만 있는 추적 변화 `마감 임박`(RL-02, 아래)만 만든다.
- **추적 중 사업 변화는 공고당 한 행이다.** 추적 상태 `계속 추적`·`보류`인 사업기회의 권위 연결 공고에 창 안의 관측이 `deadline_at`·`title`·`budget`·`estimated_price`(규칙 파일 v2부터 `method` 포함) 중 하나라도 바꿨으면 `tracked_change` 행 1건을 낸다(바뀐 필드의 합집합, 반응 없음, 추천 상한과 별개). 추적하지 않는 사업의 변화는 행이 없다. 같은 공고가 추천에도 해당하면 추천 행만 만들고 변화 필드를 그 행에 적는다.
- **반응은 개인 기록이며 업무 상태를 바꾸지 않는다.** `대기|채택|무시|나중에`는 "마지막 담당 기록"일 뿐이다. 반응(화면·Slack 버튼)이 사업기회의 추적 상태, 회사별 추적, 최종 Go/No-Go를 바꾸거나 승인을 대신하지 않는다 — 추적 승인과 최종 Go/No-Go는 사람이 기존 화면에서 따로 결정한다. 채택은 "볼게요"이지 "계속 추적"이 아니다(ux-review 결정 3). 두 사람이 다르게 누르면 나중 요청이 `version_conflict`를 받고 다시 조회해 누르며 모든 변화는 append-only 이벤트로 남는다.
- **수집이 불완전해도 브리핑은 만든다.** D-1 notices 회차가 없거나 둘 이상이거나 적재 경고가 있으면 `status=collection_incomplete`이고 화면이 이를 드러낸다. 추천이 0건이고 수집이 완전하면 `empty`("오늘 추천할 공고가 없습니다 · 수집 정상")다.
- **0건이면 Slack으로 보내지 않는다.** `status=empty`는 보내지 않으며, 추천이 0건이면 추적 변화 행만 있어도 `empty`라서 보내지 않는다(현재 코드의 문자 그대로의 동작이며 화면에는 보인다). 보냈는지는 `slack_sent_at`, 실패는 `slack_send_failed` 경고로 구분하고 재전송은 `--send` 재실행이다.

## 사업기회 레코드 단계 바·활동 피드 (RL-02, 2026-10-17)

사업기회 하나가 지금 어디까지 왔는지(단계 바), 누가 무엇을 했는지(활동 피드), 곧 마감인 추적 중 사업을 알리는 규칙(마감 알림)이다. 계약은 [contracts.md "레코드 활동 피드·노트"](contracts.md#레코드-활동-피드노트-rl-02-2026-10-17)·[브리핑](contracts.md#브리핑-rl-01-2026-10-17), 기능 명세는 `docs/work/groups/RL/features/RL-02-opportunity-timeline/spec.md`다. LLM을 부르지 않는다. "run 결정 기록 #N"은 `docs/work/_runs/rla-20261016/decisions.md`의 번호다.

- **권위 연결의 정의를 그대로 쓴다.** 단계 바·레코드 제목·피드의 "발견·공개·게시" 사건·마감 알림은 모두 contracts "마감 임박 창"의 권위 연결(`official`·`확정` 또는 `candidate`·`사람 확인 완료`·`accepted`)만 읽는다. 확인 대기·거절 후보와 `검색 미확인` 연결은 어느 단계도 만들지 않는다. Python 쪽 판정은 `is_authoritative_link` 하나이고 SQL 쪽은 `authoritative_link_predicate`이며, 이 규칙을 화면이나 다른 service가 다시 만들지 않는다. 단계 구분은 발주계획 = `stage=order_plan`, 사전규격 = `stage=notice` ∧ `Notice.source_type`이 사전규격 종류(`PRE_SPEC_SOURCE_TYPES`), 입찰공고 = `stage=notice` ∧ `source_type='bid_notice'`이고 그 밖의 공고 종류는 단계를 정하지 않는다. 한 단계에 권위 연결이 여럿이면 연결 시각이 가장 늦은 것(같으면 연결 id가 큰 것)이 그 단계를 대표한다.
- **단계 바는 6단계 고정 순서다**: 발주계획 → 사전규격 → 입찰공고 → 마감 → 개찰 → 계약. 앞 세 단계는 권위 연결이 있으면 `done`이고 **가장 뒤 단계**는 `current`다(단, 입찰공고가 가장 뒤 단계이고 마감이 이미 지났으면 입찰공고도 `done`이다). 마감은 입찰공고 `deadline_at`이 지났으면 `done`, 아직이면 `upcoming_deadline`이며 입찰공고가 없거나 `deadline_at`이 `null`이면 `unknown`이다 — **사전규격 의견 마감은 마감 단계가 아니다**. 개찰은 입찰공고 `lifecycle_json.opening_at`(시간대가 있는 ISO)이 있고 지났으면 `done`, 미래면 `upcoming_deadline`이며 키가 없거나 `null`이거나 시간대가 없으면 `unknown`이다. **계약은 읽을 데이터가 없으므로 언제나 `unknown`이다.** 어느 칸에도 맞지 않는 단계는 뒤 단계가 이미 `done|current`면 `unknown`(건너뛴 단계는 있었는지 추정하지 않는다), 아니면 `pending`이다. 예: 발주계획만 있으면 사전규격·입찰공고 `pending`, 마감·개찰 `unknown`; 사전규격 없이 입찰공고가 있으면 사전규격 `unknown`. 개찰·계약 시각을 마감 날짜로 추정하지 않는다(`unknown`은 "미확인"이며 미실시나 부족이 아니다).
- **레코드 제목은 가장 뒤 단계 대표 연결의 제목**(입찰공고 > 사전규격 > 발주계획)이다. 권위 연결이 없거나 제목이 비면 `#<id>`이며 추정하지 않는다.
- **활동 피드는 저장하지 않는 파생 뷰다.** 이미 append-only인 원본(연결·공고 관측·추적 감사·반응·노트)에서 요청마다 계산하고 이벤트 테이블을 두지 않는다. 항목은 사람 행동(추적 결정·후보 판정·신호 확인·반응·노트·다음 행동·완료)과 사업 사건(발주계획 발견·사전규격 공개·입찰공고 게시·정정·판정 완료·초안 준비)뿐이다. **시스템 처리 이벤트(수집 회차·변환·모델 호출·정책)는 어떤 항목도 만들지 않는다**(kind 열거 밖의 감사 action과 회차·경고 테이블은 읽지 않는다). 정정은 공고의 **첫 관측을 제외한** 관측에서 마감·제목·예산·추정가격·계약방법이 바뀐 것만 센다. 판정 완료(RL-03)·초안 준비(RL-04)는 해당 모듈이 확장점으로 제공하기 전에는 0건이다. 병합된 사업기회도 읽을 수 있고 화면이 병합 대상으로 옮겨 간다(쓰기만 `opportunity_merged`로 막는다).
- **노트·다음 행동은 사람의 메모이며 업무 상태를 바꾸지 않는다.** 본문은 append-only(수정·삭제 없음)이고 다음 행동의 완료만 한 번 기록한다. 노트·다음 행동은 추적 상태·Go/No-Go·판정을 바꾸거나 대신하지 않는다. 작성자 이름은 인증이 아닌 감사 표식이다. **노트 본문은 어떤 모델 입력에도 넣지 않는다** — 사람 메모는 외부 전송 승인 범위 밖이며 RL-03·RL-04도 이 규칙을 상속한다.
- **마감 알림은 추적 중인 입찰공고에만, 브리핑이 있는 평일에만 계산한다.** 대상은 추적 상태 `계속 추적`·`보류`인 사업기회의 권위 연결 **입찰공고**(`source_type='bid_notice'`)이며, 공고 `deadline_at`의 KST 날짜 − 브리핑 날짜가 규칙 파일의 `deadline_reminder_days`(기본 3·1, 곧 D-3·D-1)에 들면 알린다. 미선택·종료 사업, 사전규격 의견 마감, `deadline_at`이 없는 공고, 이미 지난 마감은 알리지 않는다. 알림은 새 메시지나 새 행 종류가 아니라 RL-01 `tracked_change` 행의 사유 `deadline_reminder`다 — **(브리핑, 공고)당 한 행**이라 같은 날 정정이 있으면 그 행 `change_fields`에 사유를 합치고(표시 "재검토 중") 마감 사유만 있으면 표시 "마감 임박"이며, 같은 공고가 그날 추천에도 해당하면 추천 행의 `change_fields`에 합치고 표시는 `분석 대기`를 유지한다(run 결정 기록 #12). 브리핑 날짜가 하루 1건이라 알림도 하루 1회다. Slack에서는 추적 변화 메시지의 같은 형식 한 줄이며 마감 사유는 "바뀐 항목"이 아니라 "마감 임박" 표식으로 쓴다. 공고 정정의 필드 집합은 규칙 파일 v2에서 `method`를 더해 피드의 `notice_corrected`와 같다.
- **알려진 한계 두 가지(spec 문자 그대로의 동작, backlog).** (1) 추천이 0건이라 브리핑이 `empty`인 날은 RL-01 규칙상 Slack을 보내지 않으므로 그날의 D-3·D-1 알림도 **Slack으로 가지 않는다** — 화면에는 보인다(run 결정 기록 #9). 바꾸려면 RL-01 spec 결정이 필요하다. (2) 알림은 브리핑이 있는 평일의 날짜 기준으로만 계산하므로 D-3·D-1이 **주말·브리핑이 없는 날**이면 그 알림은 없고 자동 따라잡기도 없다(run 결정 기록 #10).
