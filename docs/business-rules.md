# 업무 규칙

## 사전규격 C-1 기본 대상

2026-09-07 사용자 지정 기준으로 새 C-1 정책은 `SW사업대상=Y`를 기본 대상으로 한다.
키워드 후보군 밖의 Y도 포함하며, N·미확인은 일괄 실행에서 제외한다.
N은 사용자가 공고를 지정한 단건 요청으로 실행할 수 있다.
기존 정책과 고정 품질 표본은 소급 변경하지 않는다. 새 규칙은 별도 불변 정책의
`sw-business-selection.v1`로 묶고 품질 승인 없이 운영 활성화하지 않는다.

## 용어와 판단 단계

- `사업기회`는 발주계획, 사전규격, 입찰공고가 같은 조달 목적을 가리킨다고 확인된 내부 추적 단위다. 공식 통합번호가 없는 유사 관계는 사람 확인 전까지 같은 사업기회로 확정하지 않는다.
- `발주계획 후보`는 조기 탐색 결과다. 후보 편입 또는 탈락은 회사 적합성, 자격 충족, 참여 결정을 뜻하지 않는다.
- `등급`은 회사와 사업의 전략·기술 적합성을 나타내는 `우선 검토`, `검토 권장`, `관찰 대상`, `제외` 중 하나다.
- `참여 준비 상태`는 입찰 자격 확인 정도를 나타내는 `확인 완료`, `부분 확인 필요`, `참여 불가 확인`, `해당 없음` 중 하나다.
- `심층 추적 승인`은 사전규격을 계속 분석하고 입찰공고까지 감시하라는 사람의 결정이다. 최종 입찰 참여 승인이 아니다.
- `사전규격 개요 검토`는 제안요청서 앞부분을 근거로 **이 사업이 회사가 수행할 만한 내용인지**만 확인하는 저비용 단계다. 앞부분만 읽으므로 참가자격·배점·제출물·실적요건을 보지 못한다. 그 결과로 `참여 준비 상태`를 정하거나 `등급`의 자격 축을 채우지 않는다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)). 대화에서 쓰는 `1차 검토`는 이 단계의 별칭이다.
- `심층 검토`는 첨부 원문을 근거로 자격·요구사항·평가·수행 위험·경제성을 구조화하는 단계다.
- `정책 버전`은 후보 선정 조건, 관점·가중치, 모델·프롬프트, 검증 기준의 고정 묶음이다. 실행은 시작 시점의 버전을 끝까지 사용한다.

## 발주계획 탐색

발주계획의 관측 규모는 3일 약 1,200건, 1주 약 2,000건이다. 일반용역과 기술용역을 매일 수집하며 계획 단계에서는 `SW사업대상`이 없거나 비대상이라는 이유로 자동 제거하지 않는다. 제목·기관·예산·예정 시기·발주 방식은 탐색 신호이며 제안요청서에 근거한 참여 판단으로 승격하지 않는다.

운영 선별 방식은 구현 전에 고정 3일치 자료로 비교한다.

| 후보 방식 | 비교 입력 | 결과에 반드시 남길 값 |
|---|---|---|
| 키워드 규칙 | 같은 정규화 제목·기관·공개 메타데이터 | 일치 규칙, 일치 위치, 점수와 순위 |
| ColBERT | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·색인 버전, 입력 해시, 유사도와 순위 |
| Qwen | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·프롬프트 버전, 구조화 선택·이유·근거 |
| Luna | 같은 공개 메타데이터와 승인된 회사 역량 요약 | 모델·프롬프트 버전, 구조화 선택·이유·근거 |

네 방식은 한 번 저장한 동일 원문을 사용한다. 방식마다 API를 다시 호출하거나 입력 구간을 바꾸면 비교 결과로 인정하지 않는다. Sol의 평가는 합집합을 검토하기 위한 참고 판정이며 정답이 아니다. 사람은 네 방식의 합집합과 각 방식이 탈락시킨 감사 표본을 가림 검토해 최종 라벨을 확정한다.

선택 방식은 전체 적합 건 회수율, 상위 후보 적중률, 중요한 누락 건수, 사람이 검토할 건수, 처리시간, 비용을 함께 비교해 정한다. 한 지표만 가장 높다는 이유로 활성화하지 않는다. 실험 결과와 사람 라벨이 확정되기 전에는 키워드·ColBERT·Qwen·Luna 중 어느 것도 운영 정본으로 간주하지 않는다.

선택된 후보만 저장해서는 안 된다. 각 발주계획의 외부 식별자, 공개 메타데이터, 원문 해시, 최초·최근 확인 시각, 네 방식의 점수·순위·이유·버전, 사람 판정·이유·작성자·시각을 보존한다. 탈락 기록을 삭제하면 누락률과 정책 변경 효과를 측정할 수 없으므로 금지한다.

발주계획은 매일 수집하지만 사람의 누적 후보 검토는 월요일과 목요일에 진행한다. 수집 주기와 사람 검토 주기를 같은 값으로 묶지 않는다.

## 사전규격 수집과 심층 추적

사전규격은 매일 독립 수집한다. 수집 대상은 일반용역과 기술용역 전체이며 `SW사업대상`으로 걸러 내지 않는다. 발주기관이 매긴 이 값은 저장해 두고 화면 표시와 선택 필터로만 쓴다([ADR-0024](tracking/decisions/0024-prespec-collect-all-flag-sw.md)). 화면은 `<일반용역 + SW사업대상>`과 `<기술용역 + SW사업대상>`을 **기본으로 켠 채** 보여 주고 담당자가 끌 수 있게 한다. 다만 **추적 중인 발주계획에 연결된 사전규격은 `SW사업대상=N`이어도 목록에 남긴다.** 발주기관이 매긴 라벨 때문에 담당자가 직접 고른 추적 대상을 숨기지 않는다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)). 선택된 발주계획에 연결된 항목만 수집해서는 안 되며, 발주계획이 없는 사전규격도 새 사업기회 후보로 등록한다.

외부 통합번호가 정확히 일치하면 발주계획과 사전규격을 확정 연결한다. 통합번호가 없고 기관·사업명·예산·시기가 유사하면 후보 연결만 만든다. 후보 연결의 점수나 모델 설명만으로 이전 사람 선택을 승계하지 않으며 담당자가 관계를 확인해야 한다.

발주계획에서 사전규격으로 가는 공식 키는 없으므로 후보는 사업명 부분일치 검색으로 만든다. 검색어는 원문, 검색을 깨뜨리는 문자에서 쪼갠 조각, 정규화한 이름, 앞 12자를 정밀한 순서대로 시도하고 후보마다 어느 방식으로 걸렸는지 남긴다. 검색을 깨뜨리는 문자는 `·`(U+00B7), `&`, `‘`, `’`, `•` 다섯이며 괄호·쉼표·하이픈·마침표·낫표·겹낫표·물결·빗금·밑줄과 `・`·`‧`·`․`는 무해하다. 무해한 문자에서 쪼개면 질의가 짧아져 사람이 확인할 후보만 늘어난다.

사전규격 연결 상태는 `확정`, `후보 확인 대기`, `사람 확인 완료`, `검색 미확인` 중 하나다. `검색 미확인`은 사전규격이 없다는 뜻이 아니라 확인되지 않았다는 뜻이며 화면·API·집계 어디에서도 부재로 바꾸지 않는다. 검색 시점에는 미공개와 이름 불일치를 가를 근거가 없으므로 두 상태로 쪼개지 않는다. 이 상태에는 마지막 검색 시각과 시도한 방식을 남기고 재검색과 수동 검색 경로를 제공한다([ADR-0025](tracking/decisions/0025-prespec-link-search-unconfirmed-state.md)).

사업기회 소유권을 정하는 authoritative 연결은 `official + 확정` 또는 `candidate + 사람 확인 완료 + accepted`뿐이다. 후보 확인 대기, rejected, 검색 미확인은 소유권이나 자동 병합에 사용하지 않고 이력으로 남긴다. 공식 관계가 뒤늦게 여러 사업기회를 연결하더라도 모든 관련 사업기회가 `미선택`이고 recheck state가 없을 때만 자동 병합한다. 병합은 secondary row를 삭제하지 않고 retained opportunity를 가리키는 이력으로 보존하며, 사람 선택이나 recheck가 하나라도 있으면 자동 병합하지 않고 사람 확인으로 보낸다.

검토는 `1차 분류`(발주계획 공고명) → `사전규격 개요 검토`(제안요청서 앞부분) → `심층 검토`(첨부 원문 전체) 순으로 좁혀 간다([ADR-0031](tracking/decisions/0031-prespec-overview-review-stage.md)).

사전규격에 도달한 건은 개요 검토를 자동으로 수행한다. 발주계획에서 추적하기로 고른 건이 사전규격에 올라오면 바로 검토하고, 발주계획에 없던 건은 **`신규`로 명시하고** 역시 바로 검토한다. 개요 검토는 앞부분만 읽는 저비용 단계이므로 아래 금지의 대상이 아니다.

개요 검토의 입력 문서는 현재 첨부 문서의 파일명에 `제안요청서`가 포함된 경우에만 자동 선택한다(2026-09-07 사용자 결정). 공백·Unicode 표기 차이는 정규화한다. 후보가 하나면 role이나 업로드 순서와 무관하게 선택하고, 없거나 여러 개면 `needs_human_review`로 담당자 확인에 넘긴다. `과업지시서`, 영문 `RFP`, role 지정만으로 대체하지 않는다. 아직 취득된 문서가 없으면 기존 `awaiting_document`를 유지하며, 선택한 문서의 안전성·구조 검증은 별도로 수행한다.

개요 검토의 앞부분은 [ADR-0032](tracking/decisions/0032-prespec-overview-cutting-rule.md)에 따라 정한다. 목차 항목이 본문 소제목과 대응하면 목차를 사용하고, 그렇지 않으면 의미 있는 주제 소제목을 사용한다. 번호 형식만으로 절단하지 않는다. 시작 또는 종료 위치가 모호하면 추측해 자르지 않고 `unknown`으로 남겨 사람 검토로 보낸다. 자동 추출 입력에는 사용 전략(`strategy`), `start_locator`, `end_locator`, `source_sha256`를 보존하며, 고정 block 수나 전체 문서를 개요 검토에 자동 투입하지 않는다.

범위를 정하지 못한 개요 입력은 **사람이 확정한다**(2026-09-10, [ADR-RDP-004](0910_rhwp-document-pipeline/ADR.md)). 결정적 선택기가 경계를 못 정하면 준비는 실패 attempt를 만들지 않고 절 후보 목록을 가리키는 `needs_human_review` target을 남긴다. 담당자가 절 후보의 시작·끝이나 쪽 범위를 고르면 같은 snapshot·관측에 `human_confirmed` `ready` target이 새로 생기고 이전 target은 그대로 보존된다. 확정은 **개요 검토 입력을 준비하는 것일 뿐 실행이 아니다** — attempt는 만들어지지 않고 응답의 `attempt_enqueued`는 언제나 `false`이며, 실행·추적 승인·최종 Go/No-Go는 기존 경로의 사람 결정이다. 모델 보조 선택은 명시 CLI 액션에서만 돌고 결과는 제안(감사 행)일 뿐이어서 target·등급·참여 준비 상태를 바꾸지 않는다. 담당자 이름은 감사 표식이다.

2026-09-11 MVP에서는 rhwp의 안전한 PDF·페이지 텍스트가 핵심 산출물이며 절 후보는 참고다.
후보가 있어도 쪽 범위를 직접 지정할 수 있고, 일부만 반환된 후보는 전체 목록처럼 사용하지
않는다. 자동 ready도 실행 대기가 없으면 PDF 확인 후 새 범위로 확정할 수 있다. 대기/실행
중 확정과 새 범위 뒤 옛 target의 재실행은 차단한다. 같은 줄 복수 장 제목과 `제안개요`
작성 양식의 오선택은 자동 범위로 확정하지 않고 경고한다. 유효 본문과 함께 있는 공백 쪽은 보존하되 근거로 인정하지 않는다. 변환 완료·
범위 확정·내용 검증 통과를 서로 대신하지 않으며 모델 미실행/실패여도 안전한 PDF는 열람한다.

개요 검토의 결정적 절단 snapshot과 모델 attempt는 분리한다([ADR-0033](tracking/decisions/0033-prespec-overview-review-runtime-contract.md)). 승인된 사설 vLLM binding이 없으면 절단까지만 만들고 `awaiting_model`로 두며 결과와 완료 시각은 `null`로 보존한다. 경계가 모호한 절단은 `needs_human_review`로 보내고 모델을 호출하지 않는다. 결정적 mock은 `reference_only`, `deployable=false`이며 운영 완료로 집계하지 않는다. `completed`는 승인된 binding의 응답이 strict schema, evidence locator, source hash 검증을 모두 통과한 경우에만 허용하고 hosted OpenAI·Codex로 자동 fallback하지 않는다.

모든 개요 attempt는 품질 표식 `quality_status`를 갖는다. `reference_only`인 attempt는 `mock_reference`, 그 밖은 `unmeasured_reference`다. **완료한 개요 attempt는 언제나 `unmeasured_reference`다** — `reference_only`인 attempt는 완료할 수 없으므로(위 문단) `mock_reference`는 완료하지 못한 attempt에만 붙는다. 저장소만으로 개요를 완주시키려면 mock을 provider가 아니라 transport 층에 두어야 하고, 그때 표식은 `unmeasured_reference`다. 심층 검토의 `mock_reference`는 provider에서 나오므로 이 제약과 무관하다([ADR-0050](tracking/decisions/0050-unified-openai-compatible-model-client.md)). `deployable=false`인 `completed`의 뜻은 "완료 불가"가 아니라 **"운영 완료로 집계하지 않음"**이다. 참조 실행 결과를 사업 판단, 품질 근거, 정책 활성화 근거로 쓰지 않는다.

검증에 실패한 응답(schema 위반, snapshot 밖 evidence)은 재호출하지 않고 바로 `failed`다. 같은 seed와 같은 고정 프롬프트가 같은 결과를 내므로 재호출이 결과를 바꾸지 않기 때문이다. 재시도는 transport 계열 실패(timeout·잘림 등)에만 1+2회 적용한다.

실제 모델 attempt의 입력 snapshot·sequence·입력 hash·binding은 생성 뒤 바꾸지 않는다
([ADR-0035](tracking/decisions/0035-prespec-overview-attempt-result-lifecycle.md)). 상태·허용 시각·
검증 결과 참조만 열 단위로 전이하고 모든 전이를 별도 append-only event로 남긴다. 검증된
결과는 attempt와 분리한 immutable row에 한 번만 기록한다. 재실행은 기존 attempt나 결과를
초기화하지 않고 새 sequence를 만든다. `조건부 추진 검토`는 조건과 확인 기한이 모두 있어야
하고, 현재 snapshot 밖의 evidence locator나 검증되지 않은 source hash는 완료 결과로
승격하지 않는다.

개요 결과는 `추진 검토`, `조건부 추진 검토`, `보류`, `검토 종료` 중 하나다. `조건부 추진 검토`에는 조건과 확인 기한이 필요하다. 이 결과는 적합성 등급, 참여 준비 상태, 심층 검토 추적 선택, 최종 입찰 Go/No-Go를 채우거나 대신하지 않는다.

사전규격 메타데이터는 전량 보존하지만 첨부 바이트는 조건을 만족할 때만 취득한다. 다음 중 하나이면 대상이다.

- `notice.qualification_flags_json.sw_business_status = 'Y'`인 사전규격
- 사전규격을 가리키는 `opportunity_link`가 `stage='notice'`이고 상태가 `확정`·`사람 확인 완료`·`후보 확인 대기`이며, 그 opportunity의 `tracking_status`가 `계속 추적` 또는 `보류`이고, 같은 opportunity에 `stage='order_plan'`이면서 `order_plan_id`가 있는 링크가 존재하는 경우

`검색 미확인` 링크와 `미선택`·`종료` opportunity, order-plan 링크가 없는 opportunity는 첨부 취득 자격을 만들지 않는다. 사람이 추적 상태를 나중에 선택할 수 있으므로 이 자격은 배치 한 번으로 고정하지 않고 재평가 큐에서 갱신한다. 이 조건은 수집 필터가 아니며 `SW사업대상` 표시 값의 의미도 바꾸지 않는다.

### 회사 핏 판정 (2026-09-08)

검증된 개요와 승인된 불변 회사 프로필을 대조하여 `matched`(업무 부합), `mismatch`(확인된 업무 범위와 과업의 차이), `unknown`(판단 보류)을 기록한다. 사유마다 공고 과업과 회사 구조화 항목을 연결하며, 역량·자격·실적의 미기재나 inferred/unknown 항목만으로 불일치를 만들 수 없다. 개요의 모델 의견은 회사 사실로 재사용하지 않는다. 실제 계약의 과업과 감리 대상 사업의 과업도 구분한다.

회사 핏은 자동 분석의 추가 조건이다. 기존 등급·참여 준비·추적 선택·최종 Go/No-Go를 변경하지 않는다. 개요 결과, 문서 버전, 활성 회사 프로필/심층 정책, 핏 정책·모델 배포 버전이 바뀌면 이전 핏은 현재 자동 시작에 사용할 수 없다. 새 입력은 새 attempt이고 같은 입력은 중복 호출하지 않는다. 실패/만료된 입력을 자동 재시도하지 않는다.

- 응답이 결정적 검증에 실패하면 같은 입력으로 seed를 바꾼 1회 재시도를 보내고, 보정 지시에는 실패한 검사 코드만 담는다. 두 응답을 모두 암호화 보존하고 감사에 `validation_retry`로 남긴다. 이는 한 attempt 안의 호출 재시도이며 종결된 attempt를 다시 실행하는 것이 아니다. 재시도도 실패하면 `needs_human_review`로 남기고 자동 보정하지 않는다.

기본 비활성이며 현재 품질 측정 정책이 없어 명시적인 참조 실행 모드에서만 실행한다. `matched`이더라도 mock 결과나 운영 모드에서는 자동 심층 시작을 허용하지 않는다. 참조 실행의 부합·불일치 결과와 실제 심층 검토 생성 여부는 별도로 표시한다. 근거 ID·숫자 검증 통과는 의미 정확도나 회사 적합성 품질 통과를 뜻하지 않는다.

### 자동 문서 준비와 자동 심층 시작

effective grade(사람 정정 등급이 있으면 그것, 없으면 판정 등급)가 `우선 검토`인 사전규격은 문서 준비를 자동으로 진행한다([ADR-0049](tracking/decisions/0049-prespec-auto-preparation-and-auto-deep-review.md)). 안전 검사를 통과한 현재 문서로 묶음 초안을 만들고, **자기가 만든 초안만** 확정한다. 사람이 만든 초안은 사람이 확정한다. 등급이 나중에 내려가도 이미 만든 묶음을 되돌리지 않는다. 그 밖의 등급과 등급 없음은 자동 준비 대상이 아니며 사유는 `grade_not_priority`다 — "등급 없음"을 특정 등급으로 접지 않는다.

촉발 지점은 셋이다. 회차 적재, 사람 정정으로 effective grade가 바뀐 시점, 첨부 취득이 한 공고에서 종결된 시점이다. **수동 업로드로 구조가 저장된 시점은 촉발하지 않는다.** 그 경우는 사람이 확정한다.

자동 준비 상태는 여덟이다. `not_applicable`(자동 준비 대상 아님), `waiting_attachments`(첨부 취득 대기), `bundle_draft`(묶음 초안), `bundle_ready`(묶음 확정), `overview_running`(개요 검토 실행 중), `deep_review_started`(심층 검토 자동 시작됨), `deep_review_ready_for_click`(심층 검토 클릭 대기), `blocked`(자동 준비 중단). `not_applicable`은 "대상이 아님"이며 "알 수 없음"이 아니다.

다음이 모두 성립하면 심층 검토를 시스템이 자동으로 만든다. 사전규격이고 `SW사업대상=Y`, 자동 준비가 확정한 `ready` 묶음이 있고, 그 묶음의 개요 검토가 `completed`이며, 권고가 `검토 종료`가 아니고, 개요가 본 묶음과 지금 묶음이 같으며, 같은 불변 입력의 심층 검토가 아직 없고, 현재 등급이 우선 검토이며 검증을 통과한 현재 회사 핏이 `matched`여야 한다. 회사 핏은 활성 설정과 참조 실행 경계도 충족해야 한다. 검증 통과한 페이지 기반 개요가 있으면 이를 우선 사용하고, 없으면 기존 검증된 추출형 개요를 사용한다. 최신 페이지 개요 검증 실패 뒤 기존 결과로 자동 우회하지 않는다. 하나라도 어긋나면 각각의 사유 코드(`not_sw_business`, `bundle_not_auto_ready`, `overview_not_completed`, `overview_recommendation_closed`, `overview_bundle_mismatch`, `service_unavailable`, `deep_review_exists`, `processing_failed`, `company_fit_*`)로 남기고 사람 클릭으로 넘긴다. 평가 순서는 이 목록 순서이며 첫 일치가 이긴다 — 앞의 여섯은 쓰기·읽기가 같은 함수로 판정하고, `deep_review_exists`와 `processing_failed`는 실제로 만들어 보는 쓰기 경로에서만 나온다. **읽기 경로는 `deep_review_exists`를 내지 않는다.** 이미 심층 검토가 있으면 사유가 아니라 상태 `deep_review_started`로 답한다.

자동 시작은 추적 상태를 바꾸지 않는다. 사업기회는 `미선택` 그대로이고, 자동 시작이 적합성 등급·참여 준비 상태·추적 선택·최종 입찰 Go/No-Go를 대신하지 않는다. **자동으로 여는 것은 분석의 시작뿐이다.**

자동으로 열리지 않은 건은 개요 검토 결과를 읽은 사람이 심층검토 실행 여부를 선택한다. 어느 경로든 승인된 문서 묶음만 구조화·분석하고, 실패한 변환이나 검증을 성공 결과로 보정하지 않는다.

심층검토 결과에서 사람은 다음 상태 중 하나를 선택한다.

| 선택 | 의미 | 금지되는 해석 |
|---|---|---|
| `계속 추적` | 새 문서·입찰공고·정정공고를 감시하고 변경 시 다시 검토 | 최종 입찰 참여 승인 |
| `보류` | 정보나 선행 조건이 부족해 현재 결정을 미룸 | 자동 제외 또는 승인 |
| `종료` | 현재 사업기회에 대한 능동 추적을 끝냄 | 관련 신규 공고의 영구 삭제 |

`종료` 사업과 비슷한 신규 공고가 발견되어도 원문을 버리지 않는다. 새 외부 식별자와 변경 근거가 있으면 별도 후보로 다시 제시할 수 있다.

## 입찰공고 전환

`계속 추적`인 사업기회에 입찰공고가 연결되면 사전규격 문서와 입찰공고 문서의 금액, 계약기간, 참가자격, 공동수급, 평가방식, 배점, 제출물, 제출기한, 요구사항 변경을 비교한다. 비교할 문서 버전이나 연결이 불확실하면 `변경 없음`으로 추정하지 않고 사람 확인으로 보낸다.

중요한 변경이 있으면 새 문서 묶음과 새 분석 시점을 가진 리포트를 만든다. 사전규격 리포트의 문장·근거·사람 의견을 수정하지 않는다. 변경이 없으면 비교한 양쪽 버전과 확인 범위를 남긴다. 시스템은 이 결과를 자동 제출이나 발주기관 연락으로 연결하지 않으며 최종 Go/No-Go는 사람이 결정한다.

R-07의 상세 계약은 [ADR-0034](tracking/decisions/0034-bid-delta-final-decision.md)로 채택했다.
아직 backend·DB·production UI는 구현되지 않았으며 다음 안전 경계를 R-08이 그대로 구현한다.

- 비교는 ready bundle에 고정된 기준·비교 document version, structure, source/payload hash를
  저장한다. live 첨부나 mutable current pointer로 과거 비교를 다시 해석하지 않는다.
- 동일 사업기회에 사전규격·입찰공고·정정이 여러 개면 exact pair를 명시한다. 서버가
  `latest`를 추정하지 않고 새 문서는 새 비교 후보로 보존한다.
- 계산 상태 `pending|running|completed|failed`와 결과 상태
  `changed|unchanged|unknown|failed`를 분리한다. 아직 계산하지 않음, 계산 실패, 판단 불가를
  변경 없음으로 바꾸지 않는다.
- `changed`와 `unchanged`에는 기준·비교 양쪽 원문 locator가 필요하다. 한쪽 근거를 검증할
  수 없으면 `unknown` 또는 `failed`다.
- 최종 입찰 결정은 actor, reason, request ID, 비교 version·result digest·양쪽 document
  version fence를 가진 append-only 사람 기록이다. 새 결정은 과거 결정을 수정하지 않는다.

최종 결정은 `go|no_go`다. material 범주는 금액·경제성, 계약기간·일정, 참가자격,
공동수급·하도급, 과업·요구사항, 평가, 제출의 7개다. v1은 근거 없는 수치 임계값을 두지
않고 공식 값·조건의 실질 변경을 `material`, 양쪽 근거로 의미가 같은 표기·서식 차이만
`non_material`로 둔다. 불확실·검증 실패는 `unknown|failed`로 보존한다.

새 authoritative 입찰공고·정정 또는 새 ready 비교 문서가 생기면 기존 최종 결정 row는
그대로 두고 strict currentness projection을 즉시 `stale`로 만든다. 순서·효력이 불확실하면
`unknown`이다. 비교 모델은 회사 내부망의 allowlist된 사설 vLLM만 사용하고 exact
snapshot의 비교 생성 요청을 건별 처리 승인으로 감사한다. 외부·hosted fallback은 없으며
감사 metadata에는 안전한 ID·code·count·hash·binding digest만 남긴다.

## 후보 선정과 현재 1차 판정

세 우선 축 `AI/데이터`, `블록체인·DID`, `공공 SI·통합관리`는 동등하다. 예산, 지역, 업종, 실적 요건이 확인되지 않았다는 사실만으로 자동 제외하지 않는다. 제목·조달 분류·수행실적 유사도는 후보 편입 신호이지 적합성의 확정 근거가 아니다.

후보에 들지 않은 공고는 부적합 정답이 아니다. 조달 분류 근접, 수행실적 유사도 임계값 근접, 무작위 층에서 감사 표본을 뽑는다. 감사 표본에서 `제외`가 아닌 판정이 나오면 누락으로 집계하고 정책 변경 제안의 근거로 쓰되 한 사례만으로 기준을 자동 변경하지 않는다.

1차 판정은 `기술 적합성`, `실적 정합성`, `공공 SI 적합성`, `사업성·자격 제약`, `전략 부합`을 정확히 한 번씩 가져야 한다. 각 관점에는 관점 고유의 이유와 최소 하나의 근거가 있어야 하며 근거 상태는 `confirmed`, `inferred`, `unknown` 중 하나다. 회사 프로필의 `unknown`을 모델 추론이나 외부 상식으로 `confirmed`로 올리지 않는다.

등급과 참여 준비 상태는 독립적으로 계산한다. 적합성이 높고 자격이 미확인이면 `우선 검토`와 `부분 확인 필요`가 함께 올 수 있다. 미확인 자격만으로 등급을 내리거나 높은 등급만으로 준비 상태를 `확인 완료`로 올리지 않는다.

| 조건 | 허용 결과 | 금지 결과 |
|---|---|---|
| 등급이 `제외` | 준비 상태 `해당 없음` 또는 `참여 불가 확인`, 제외 사유 필수 | `확인 완료`, 제외 사유 누락 |
| 등급이 `제외`가 아님 | 제외 사유 `null` | 제외 사유 문자열 유지 |
| 준비 상태 `부분 확인 필요` | 미확인 항목 최소 1개 | 확인 항목 없는 부분 확인 |
| 준비 상태 `확인 완료` | 차단성 미확인 항목 0개 | 차단 항목을 남긴 확인 완료 |
| 준비 상태 `참여 불가 확인` | 확인된 차단 항목 최소 1개 | 막는 근거 없는 참여 불가 |

`사업성·자격 제약`이 `확인 불가`인데 종합 등급이 `관찰 대상` 또는 `제외`이면 `two_axis_mixing_flag=true`, `two_axis_mixing_label=확인 요망`을 남긴다. 이 표시는 판정 실패가 아니며 등급·준비 상태를 자동 수정하거나 모델을 재호출하지 않는다.

수행실적 유사 신호가 있으면 연결된 실적마다 대응 이유와 설명되지 않는 차이를 기록한다. 법적 실적 인정 여부가 확인되지 않았으면 `unknown`을 유지한다.

## 불변 회차와 재판정

회차는 수집 구간, 원문, 정책, 프롬프트, 모델, 프로필, 생성 설정을 고정한 스냅샷이다. 같은 기간을 새 규칙으로 다시 처리하면 새 실행 식별자를 만들고 이전 회차를 수정하지 않는다. 새 회차에 필요한 판정이 없으면 완성된 이전 회차를 최신 유효 회차에서 밀어내지 않는다.

사용자가 선정 기준·가중치·프롬프트를 바꾸면 새 정책 버전을 만든다. 변경은 이후 시작하는 실행에만 적용한다. 과거 결과를 새 기준으로 비교하려면 새 회차를 명시적으로 실행한다.

정정, 재공고, 사전규격에서 본공고로의 전환처럼 확인된 생애주기 변화가 있으면 재판정한다. 동일 값이 다시 수집된 것만으로 재판정하지 않는다. 이전 값이 없거나 비교할 수 없으면 변경 없음으로 추정하지 않고 사람 검토로 보낸다.

변화가 없으면 검증된 기존 판정을 모델 호출 없이 현재 회차로 승계할 수 있다. 승계는 최초 판정 회차와 원래 모델·프롬프트·정책·프로필 식별자를 보존하고 현재 기록 회차를 별도 필드에 남긴다. 과거 판정이 현재 결정적 검증을 통과하지 못하면 승계하지 않고 사람 검토 대기로 보낸다.

## 심층검토 입력과 판단

HWP 원본은 그대로 보존하고 HWP 분석에는 검증된 HWPX 변환 결과를 사용한다. 변환 실패 또는 구조 손실 검증 실패 시 원본 HWP를 모델에 직접 넣지 않고 `변환 확인 필요`로 보낸다. 이미 HWPX인 문서는 변환 없이 정본이 되며 PDF는 추출 결과와 원본 위치의 대응을 검증한다.

문서 묶음은 파일명, 해시, 획득 출처, 객체 버전, 변환기 버전, 변환 시각을 가진다. 같은 파일명이더라도 해시가 다르면 새 문서 버전이며 기존 분석을 덮어쓰지 않는다.

| 평가 영역 | 필수 확인 | 근거가 부족할 때 |
|---|---|---|
| 입찰 자격과 참여 구조 | 업종·면허, 기업 규모, 지역, 실적, 공동수급, 하도급, 보안·인력 증빙, 마감 | `충족`으로 쓰지 않고 차단 여부·확인 주체·기한을 남김 |
| 과업과 요구사항 | 구축·운영 범위, 제외 범위, 산출물, 검수, 요구사항 ID | 누락·중복·모순을 원문 위치와 함께 표시 |
| 평가 전략 | 기술·가격 배점, 정량·정성, 발표·시연, 감점·실격 | 배점 합계와 제출물을 코드로 다시 계산 |
| 수행 가능성 | 기간, 인력, 선행 의존성, 이관, 교육, 안정화, 유지보수 | 입력 없는 인월·일정을 생성하지 않음 |
| 기술·보안·법무 위험 | 연계, 데이터, 비기능, 개인정보, 망분리, 권리, 위약 | 문서상 의무·미확인·전문 검토 필요를 구분 |
| 사업성 | 예산, 원가, 지급·검수, 보증, 제안 비용, 파트너 | 회사 마진이나 비용을 임의 생성하지 않음 |
| 경쟁·제안 전략 | 발주 배경, 차별점, 예상 평가 초점, 레퍼런스 | 원문 사실과 전략 추론을 분리하고 반대 근거를 포함 |

문서 구조를 저장할 때 결정적 segment manifest와 요구사항 inventory를 함께 만든다([ADR-0051](tracking/decisions/0051-deep-review-v2-deterministic-subset.md)). segment는 네 taxonomy label(`business_eligibility_evaluation`, `technical_functional`, `quality_security_constraints`, `partnership_governance`)로 분류하며 **분류 출처는 `deterministic` 고정, `confidence`는 언제나 `null`**이다. 결정적 규칙에는 확률이 없으므로 경계를 정하지 못한 자리는 확률을 지어내지 않고 `needs_human_review` 상태로 남긴다.

심층 검토 검증에 결정적 check 두 종을 더한다. `requirement_inventory`는 문서가 준 요구사항 ID 집합과 claim이 적은 ID 집합을 대조해 누락·예상 밖 ID를 실패(중대), 중복을 warning, ID 체계가 없는 문서를 warning "inventory 없음"으로 남긴다. `segment_coverage`는 간극·중첩을 warning(보통)으로 표시하되 차단하지 않는다. **문서에 ID 체계가 있는데 claim이 ID를 적지 않으면 `requirement_inventory`가 실패한다.** 요구사항 전수성은 형식 완결성으로 대신할 수 없다.

심층 검토 실행에도 품질 표식 `quality_status`가 붙는다. `measured`는 측정값이 활성화 게이트를 통과했다는 뜻이고, `unmeasured_reference`·`mock_reference`는 참조 실행이며, 표식이 없던 시절의 실행은 `null`(표식 없음)이다. **없음을 미측정이나 측정으로 승격시키지 않는다.**

요구사항 대응 상태는 `대응 가능`, `추가 확인`, `갭`, `해당 없음` 중 하나다. 위험은 `차단`, `중대`, `보통`, `낮음`으로 표시하고 근거, 영향, 확인·완화 행동, 담당 역할, 기한, 잔여 위험을 가진다. 정보가 없으면 항목을 삭제하지 않고 `산정 불가`와 필요한 자료를 남긴다.

사전규격 초기 권고는 `추진 검토`, `조건부 추진 검토`, `보류`, `검토 종료` 중 하나다. `조건부 추진 검토`에는 해소 조건과 결정 기한이 필요하다. 이 권고와 사람이 고른 `계속 추적`은 최종 입찰 참여 승인이 아니다.

## 근거와 검증

모든 수치, 자격 조건, 요구사항, 배점, 일정, 위험 근거는 문서 파일과 페이지·절·표·요구사항 ID 중 가능한 가장 구체적인 위치를 가진다. 인용 위치에서 내용을 찾을 수 없으면 `미검증`이며 확정 사실에 포함하지 않는다.

결정적 검증은 요구사항 ID 유일 개수·중복, 금액·기간·배점 산술, 필수 분석 영역, 자격 판정 모순, 원문에 없는 수치, 인용 위치 존재를 확인한다. 실패 결과는 자동 승인하거나 문장을 고쳐 통과시키지 않고 실패 항목과 함께 사람 검토로 보낸다.

모델·프롬프트·정책의 품질 게이트는 고정 40건을 A/B로 독립 실행한다. 최종 등급 재현성은 80% 이상, 한 관점의 불일치 집중은 50% 이하, `우선 검토` 비율은 유효 10건 이상에서 10~25%, 사람 근거 동의는 70% 이상, 근거 부족은 10% 이하, 관점 분할은 40% 이상이어야 한다. 계산 불가·미측정·불완전 표본은 통과가 아니다. 비교 목적의 역사 프로필과 운영 승인 목적의 현재 프로필을 섞지 않으며 통과만으로 정책이나 상시 실행을 자동 활성화하지 않는다.

## 리뷰와 개선

리뷰 작성자의 이름은 감사 귀속용이며 신원 인증이 아니다. 이름이 같다는 이유로 권한이나 실제 신원을 보장하지 않는다.

피드백은 `1차 판정 품질`, `심층 리포트 품질`, `실제 사업 결과`, `사용자 경험·처리 흐름`으로 구분한다. 등급 수정과 근거 부족은 공고·회차·정책 버전에 연결하고 실제 결과는 참여 여부·제안 결과·실패 원인처럼 사후 확인 가능한 사실을 기록한다.

피드백과 발주계획 선별 실험은 변경 제안을 만들 수 있지만 선정 기준, 회사 프로필, 프롬프트, 모델 설정을 자동 변경하지 않는다. 담당자가 제안을 검토하고 승인하면 새 불변 정책 버전으로 이후 실행에만 적용한다.

## 발주계획 C-2 선별 상태 규칙

C-2는 기존 공고의 적합성·참여 준비 판정과 별도의 relevance 흐름이다. Phase 0의 고정
정의와 machine-readable schema는 [`docs/contracts.md`의 C-2 계약](contracts.md#c-2-phase-0-fixed-contract)과
`skills/bidops-screen/contracts/`를 따른다.

- 전체 `bidops.collected-order-plans.v1` 회차를 먼저 검증한다. `metadata.collection.complete=false`,
  warning, count 불일치, raw record hash 불일치는 실행 거부다. 원본 JSON·raw page·정규화
  projection은 기존 회차 디렉터리에서 덮어쓰지 않는다.
- 현재 정책은 전체 제목을 NFKC·casefold·공백 축약 후 BM25로 계산하고 score 내림차순,
  `order_plan_unty_no` 오름차순으로 tie-break한다. Top 300은 `selected`, 나머지는
  `filtered_out`이며 탈락을 `not_relevant`라고 기록하지 않는다. 300건 이하 규칙은
  select-all까지 문서화했지만 탈락 감사 표본은 사람 승인 전까지 비활성이다.
- Qwen은 Top 300만 25건의 rank-contiguous batch로 순차 전송한다. 승인된 private vLLM,
  정확한 model/prompt/profile/BM25 digest와 허용 payload를 모두 일치시켜야 하며 hosted
  fallback은 없다. retryable failure만 최대 2회 재시도하고, binding·model·payload·policy
  거부는 재시도하지 않는다.

상태의 의미는 다음과 같다. 하나의 상태가 다른 축의 결론을 대신하지 않는다.

| 상태 | 의미 | 보존 규칙 |
|---|---|---|
| `filtered_out` | deterministic Top 300 밖 | relevance 음성이나 적합성 제외로 바꾸지 않음 |
| `relevant` / `not_relevant` | Qwen 또는 사람의 relevance label | 등급·준비·추적·Go/No-Go로 승격하지 않음 |
| `uncertain` | relevance 확인 보류 | 기본 사람 검토 목록에 남김 |
| `unknown` | 정보 부족·결과 결정 불가 | 성공·비관련으로 보정하지 않음 |
| `null` | 해당 field가 미시도 또는 비적용 | unknown·failed의 동의어가 아님 |
| `failed` | 실행된 단계의 timeout·transport·schema 등 실패 | failure type/code와 사람 검토 필요를 남김 |
| `rejected` | preflight·binding·payload·policy 검증 거부 | 모델 결과나 `not_relevant`를 만들지 않음 |

실행 상태는 `대기 → 실행 중 → 성공|부분 성공|실패`, `실행 중 → 중지 요청 → 중단됨`,
`대기 → 중단됨`만 허용한다. terminal 상태는 종료 시각을 갖고, active slot은 1이다. stale
또는 process interruption은 자동 재개하지 않고 성공 subset·failure artifact를 보존한 뒤
사람이 새 execution으로 재시작한다. 사람 feedback은 execution·plan별 append-only revision
이며 `relevance=관련|비관련|판단보류`에 대응하는 machine 값과 `priority=높음|보통|낮음|null`,
메모를 기록한다. 이 feedback은 `grade`, `readiness`, `tracking_status`, final `go_no_go`를
변경하지 않는다.

현재 policy와 binding은 `blocked`, validator는 `valid_but_blocked`를 반환한다. C-1 gold
manifest는 `partially_human_adjudicated`이며 사람 22건, draft 603건, 잔여 확인 87건이다.
잔여 gold를 사람 완료로 추정하거나 품질 gate를 통과로 표시하지 않는다. 감사 표본 크기·
주기, 승인 gold 기반 quality threshold, execution별 private vLLM 전송 승인이 채워지기
전에는 policy를 active로 바꾸지 않는다. `계속 추적|보류|종료`와 사람 최종 Go/No-Go는
여전히 별도 생애주기·입찰 결정 이벤트다.

## 설명형 PDF 개요와 기존 권고의 구분

`prespec_page_overview`의 새 설명형 결과는 사업 이해를 위한 참조 요약이다. 근거 검사
통과와 원실행 검증 상태를 별도로 보존하며, 원실행 실패는 재적재로 통과시키지 않는다.
이 결과에는 권고가 없으므로 `prespec_overview_review.status/result`, 자동 준비 집계,
심층 검토 자동 시작, 사람의 추적 결정과 최종 Go/No-Go를 변경하지 않는다.
기존 권고 결과가 있으면 화면은 설명형 요약 아래에서 기존 기록임을 구분해 표시한다.

- 과거 policy v4의 스키마·페이지 근거 검증이 실패하면 같은 입력으로 seed를 바꾼 1회 재시도를 보내고,
  보정 지시에는 실패한 검사 코드만 담는다. 두 응답을 모두 암호화 보존하고 감사에
  `validation_retry`로 남긴다. 재시도도 실패하면 실패로 남기고 자동 보정하지 않는다.
- 검증기 v3의 경고(`pdf_inline_locator_normalized`)는 실패가 아니며 재시도 사유도 아니다.
  완료된 attempt의 `validation_warnings`에 목록으로 남고 감사에도 같은 목록을 적는다.
  경고가 없으면 빈 목록이며, `0023` migration 이전 행은 `null`(미기록)이고 이를 경고 없음으로
  승격시키지 않는다.

2026-09-10 신규 policy v5·page-review v4는 주장별 결정적 검사와 별도 Qwen 의미 검토를
함께 적용한다. 기간과 금액·사업 주체·역할·VAT·조건/부정이 다른 주장을 자동 수정하거나
재호출해 통과시키지 않는다. 하나라도 미검증이면 전체 `needs_human_review`(화면 “근거 확인
필요”)이며 최종 개요는 없다. 초안의 기술적 형식 오류만 1회 재생성 가능하고, 정상은 초안+
의미 2회, 최대 3회다. 의미 응답 형식 실패는 `failed`이며 의미 재호출은 없다.
최종 사실·분석은 검증된 text를 그대로 구성하고 unknown·입력 한계는 서버가 실제 검토 범위로
표시한다. 모호한 수치 관계는 추정하지 않고 사람 확인으로 보낸다.

선택 원문이 5,000자를 넘었다는 이유만으로 개요를 거절하지 않는다. 두 단계의 실제 요청·
모델 context·출력 예약·payload 예산 안에서는 전체를 검토하고 자동 절단·사전 요약은 하지
않는다. 용량 초과 또는 안전 예산 확인 불가의 `failed/input_capacity_exceeded`는 “입력
용량 초과로 미실행”으로 표시하며 내용 검증 실패나 품질 판정이 아니다. 해당 단계는 미전송이고
이미 받은 초안은 호출 이력으로만 보존한다. 범위 변경/추가 호출이 필요하면 새 승인을 받는다.

입력 범위 미확정 target과 주장 검증 대기 attempt는 별개다. 중지하면 queued/running은
`cancelled`가 되고, OFF→ON 뒤에도 이전 activation 응답은 게시하지 않는다. 만료 정리와
v4에 예약되지 않은 다른 문서의 기존 개요는 계속 진행한다. 과거 성공·사람 리뷰·참조 표식은
보존하되 현재 실패/검증 대기/취소/stale을 대체하지 않는다. v3는 이전 검증 기준으로 읽고
v4 완료도 `unmeasured_reference`를 운영 품질 승인으로 승격하지 않는다. 추적·Go/No-Go와
회사 핏·심층 자동 실행의 기존 승인 조건은 바꾸지 않는다.
